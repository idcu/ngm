### 1.2 牙齿验证没有红 → 判据漏了一整类写法 ✅（本版最重要的一步）

改掉 `observability.md` 里的 `pathsTruncated`，网**仍然绿**。查下去发现两件事：

1. 判据只认**纯**标识符（`` `pathsTruncated` ``），而散文里更常见的是
   **带取值的形态**（`` `pathsTruncated: true` ``）——那一类**从未被扫到**；
2. 同一个名字在 `cli.md` 里还有**第二处**（纯标识符形态），改一处不足以让它消失。

把判据放宽到"允许 `: 取值` 后缀"，并在**两处同时**改名之后，网才红：

```
the living docs name the json field "pathsTruncatedX" (in cli.md, observability.md),
but no such json tag exists in the implementation
```

**"牙齿没红"是一次测量，不是一次失败**——它测出的是判据的覆盖范围。

`ProjectFile` 与 `Dependency` 的每个字段都被点名过（含只在正文里提到的 `schemaVersion`）。

## 5. 过程洞察

### 5.1 "牙齿没红"是一次测量，不是一次失败

本版的牙齿验证本意是"证明这张网会红"，结果它**没红**。
第一反应容易是"网坏了"或"改错了地方"——但它真正的价值是**测出了判据的边界**：
那一整类"键 + 取值"的写法从未进入扫描范围。

**验证牙齿时，没红要当成一条读数来查，而不是当成一次意外。**

### 5.2 越散的文档，越需要"锚点型判据"

表格式的清单可以逐行核对；散文不行。所以散文的判据必须**绑到一个锚点**上——
这里用的是"**这一行提到 `--json`**"。

锚点选对了，误报从 27 降到 0；锚点选错了（比如"整份文档"），
网就会被误报淹掉，然后被人放宽判据直到它什么都抓不到。

### 5.3 "明确不做"也是交付的一部分

`vendor` 与全局配置的反向判据没做——不是因为没时间，而是因为**做法不对**：
用散文描述的字段没有机械可比对的对象。把它写进"不做"，比做一半再让它误报更有价值。
