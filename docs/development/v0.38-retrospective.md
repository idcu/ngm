## 5. 过程洞察

### 5.1 退 0 是这张网**唯一**的口子

四条通道的契约全都建立在"**退出非零**"这个前提上。于是退 0 的格子：

- 没有建议可给（错误文本那条不适用）；
- 没有报告可查（行动行那条不适用）；
- 不是用法文本、也不是静默。

**它什么都不违反——因为它什么都不说**。而这一版把形状从 3 扩到 8 时，退 0 从 8 格涨到 **22** 格：
如果不登记，这种增长会以"覆盖率上升"的面目出现。

处置沿用本项目的老办法（v0.15 负例名单、v0.22 缺口名单、v0.26 豁免清单）：
**写下来 + 双向对账**。第三、四次的复用说明这条办法已经成了这个项目的肌肉：
**一张名单只要能被对账，它就不会腐烂。**

### 5.2 同一个形状下，命令们**合法地**行为不同

扩形状后我盯着 `add` 与 `update` 那两格：它们与 `verify` / `install` 不同——
后者在锁损坏时正确地退 **3**（`delete ngm.lock and re-run ngm install to regenerate it`），
而前者退 **0**。看着像不一致，于是逐条取证：

| 命令 | 锁损坏时 | 合法吗 |
|------|---------|-------|
| `verify` · `install` | 退 3，给出精确建议 | ✅ 它们**必须**读锁 |
| `add` | 照常追加清单，打印 `next: run ngm install to resolve and lock` | ✅ 它**不读锁**（解析交给 install） |
| `update --all` | 全量重解析并**写出新锁**（400 字节，含依赖） | ✅ 它**的职责就是写锁** |

**三处行为都合法**，但它们的共同前提值得写下来：
**"该不该在第 N 层失败"取决于那个命令是否需要第 N 层的信息**——
判据不能假设"所有命令都该在锁这一层失败"。

这也是为什么登记表里写的是**理由**而不是**豁免**：理由要经得起别人重读。

### 5.3 形状的"廉价性"定义了枚举的边界

`ngm.lock` 损坏这一形状只花**一个文件**，所以它进了矩阵；而 `ngm.vendor` 损坏
需要先 `install`（起 git、种 mirror），我把它**排除**了——不是因为不重要，
而是因为它把矩阵从"零夹具、1 秒"变成"要夹具、几十秒"。

**枚举完整到什么程度，是成本问题，不是原则问题。** 说清楚边界在哪、为什么，
比假装已经枚举完了更诚实。

### 5.4 又一次"先取证再断言"

那两格退 0 完全可以两种处理：直接记成"合法"（省事），或者去查清楚。
这一版花了两次探针去量——**结果与我的第一直觉相反**（我原以为 `add` 会悄悄重建锁、
丢掉其他依赖的钉住版本；实测它**根本没碰锁**）。

这与 v0.31（"删掉 vendor 后 verify 退 0"其实是我删了个不存在的路径）是同一条经验，
只是这次结论朝**相反**方向：**直觉说"有问题"，实测说"没问题"**。
两个方向都只有取证能分开。
