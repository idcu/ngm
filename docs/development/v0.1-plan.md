# v0.1 实施计划 — Git 依赖可证明性闭环

> 范围与退出标准以 [internals/roadmap.md](../internals/roadmap.md) 为唯一事实源；本计划将其拆为 8 个可独立验收的阶段。
> 每个阶段的"验收"必须是可执行验证；规范细节一律引用链接，不在此重复。
>
> **状态：本计划已全部完成（M0–M7）**，实测结论、未达标项与 v0.2 范围见 [v0.1 复盘](./v0.1-retrospective.md)。
> 正文里的任务复选框**保留写作时的初始形态**（未勾选），不再逐项维护——完成情况以本状态行与复盘为准。

## 阶段总览

| 阶段 | 目标 | 规模建议 |
|------|------|---------|
| M0 | 可构建、可测试、可运行的 CLI 骨架 | 1 个迭代 |

## M0 — 工程骨架与配置层

**目标**：一个可构建、可测试、可运行的 CLI 骨架；错误模型与配置系统就位。

**任务**

- [ ] 初始化代码仓与 Go module；目录骨架按 [p0-core 模块结构](../modules/p0-core.md) 建立
- [ ] CLI 骨架：标准库 `flag` 子命令分发；`--version`（含 git 短哈希与构建时间）、`--help`（命令表与 [installation 的 help 输出](../guides/installation.md) 一致）
- [ ] 错误模型：`NgmError{Code, Message, Cause, Hint}`；全局退出码 0–5，对齐 [observability · 退出码约定](../architecture/observability.md)
- [ ] 配置系统：`ngm.json` schema 校验 + 三级合并（内置 / `~/.ngm/config.json` / 项目），对齐 [configuration](../guides/configuration.md)
- [ ] `ngm config validate|show`（show 输出合并后的生效配置）
- [ ] `ngm init <name> --runtime=node|deno`：生成 ngm.json 模板
- [ ] 测试基建：`testutils`（fixture 仓库生成器雏形 + golden 比对助手）
- [ ] CI 骨架（三平台 matrix）：build / vet / test；文档链接检查任务

**验收**

- `ngm --help` 与文档命令表逐项一致（快照测试）
- 非法 ngm.json → exit 3，Hint 给出可操作建议；配置合并优先级表驱动用例全绿
- `ngm config show` 能展示三级合并结果

**风险**：标准库 `flag` 的子命令树可维护性——命令集膨胀时走 ADR 修订评估 `cobra`，不私自引入依赖。

## M1 — Git 层

**目标**：把"Git URL + refType"解析为确定的 commit，并建立可复用的本地 mirror。

**任务**

- [ ] URL 归一化：4 种协议 → canonical（用例表 = [dependency-resolution §1](../architecture/dependency-resolution.md) 的表格；含 gitee / gitlab shorthand 与私有 GitLab 多级路径）
- [ ] refType 解析：`tag` / `branch` / `commit` → commit（`git ls-remote`；有 mirror 时优先本地）
  - ⚠️ **annotated tag 必须解引用**（`refs/tags/x` 指向 tag object 时需 `^{}` 得到 commit），否则 lock 的 commit 语义错误
- [ ] mirror：`git clone --mirror` / `git fetch` 增量；布局 `~/.ngm/mirror/<host>/<org>/<repo>.git`
- [ ] 认证：ssh-agent、git credential helper、token 环境变量**透传**（ngm 不落盘、不写入 lock / 日志）
- [ ] fixture 增强：annotated tag、force push 模拟、LFS 指针、gitlink、monorepo 子路径
- [ ] `ngm add <url>@<ref> --ref-type <type>`：refType 必填；交互推断仅作辅助（[推断规则](../guides/configuration.md)）；写 ngm.json（含 `path` 子路径字段）
- [ ] `ngm update` 的解析骨架（重新解析 refType → 新 commit）

**验收**

- 全部 git 测试在离线 fixture 上运行通过；网络类失败 → exit 4
- annotated tag、branch、commit 三类解析用例正确；归一化表驱动全绿
- 认证用例：token 不出现于任何输出与本地文件（测试断言）

**风险**：Git 协议差异（ssh / https 认证、浅路径）——错误 Hint 必须指向具体凭证配置方式（[安全模型](../architecture/security-model.md)）。

## M2 — 内容清单与 archiveDigest（规范关键路径）

**目标**：实现 [ADR-008](../adr/adr-008-archive-digest.md) 的完整定义，冻结测试向量。

**任务**

- [ ] `BuildManifest(commit)`：从 mirror 读取 commit tree 递归展开，生成 `ngm-archive-digest/v1` 清单字节流（排序、mode、blob-sha256、NUL 记录、头部）
  - 实现建议（非规范）：`git ls-tree -r -z <commit>` 遍历 + `git cat-file --batch` 取 blob 原始字节；symlink 哈希的是链接目标字符串
- [ ] 异常路径：LFS 指针检测 → 报错；gitlink（`160000`）→ 报错（均不得静默哈希）
- [ ] content store：`~/.ngm/content/sha256/<hex>/{tree/,meta.json}`（内容树为解包结果，`meta.json` 记录 repo / commit / digest 规范版本）
- [ ] **冻结测试向量**（写入 `testdata/vectors/`）：普通文件 / 可执行 / symlink / 空文件 / 嵌套目录 / Unicode 与空格路径 / 含 CRLF 文件 / 大文件 → 期望 digest golden
- [ ] 三平台一致性测试（CI 内断言同一 fixture 输出同一 digest）

**验收**

- 同一 fixture 仓库的同一 commit，在三平台输出相同 digest；重复执行幂等
- **CRLF 不做转换**（golden 中含 CRLF 文件，证明字节原样参与哈希）
- 规则任何变更必须同时更新向量与规范版本——PR 模板中设为必答项

**风险**：路径排序必须用字节序（不得使用依赖本地化的排序）；Go `map` 不得参与序列化。这是全项目确定性要求最高的一环，建议本阶段代码评审加上 ADR-008 逐条核对。

## M3 — 依赖图 / 冲突 / 确定性 lock

**目标**：`ngm install` 产出可复现的 ngm.lock。

**任务**

- [ ] 广度优先遍历：每个节点 refType → commit；并行控制（默认 4 并发，参考 [p0-core 并发模型](../modules/p0-core.md)）
- [ ] 传递依赖：读取依赖根 `ngm.json`（[规则](../architecture/dependency-resolution.md)：唯一来源、不递归 package.json 但输出提示、refType 缺失报错、循环去重）
- [ ] 冲突策略：同 refType 同 ref 合并；**根声明优先（root wins）**；仅传递间冲突报错 exit 3
- [ ] lock 序列化：字段顺序固定、2 空格缩进、LF、末尾换行；`resolvedAt` 为唯一非确定性字段（[可复现定义](../architecture/locking.md)）
- [ ] `ngm install`：无 lock → 解析并生成；有 lock → 尊重 lock，不更新 ref
- [ ] `ngm update [<dep>|--all]`、`ngm remove <dep>`

**验收**

- golden lock 用例：同一 fixture 项目连续两次 install，除 `resolvedAt` 外字节级一致（CI 常态化检查）
- 冲突三场景测试：合并 / root wins / 传递冲突 exit 3（Hint 提示"在根 ngm.json 显式声明以覆盖"）
- 传递依赖进入 lock：多层依赖链（A→B→C）全部出现在 lock 中

**风险**：field 顺序与转义规则一旦发布即为格式契约；建议本阶段末期做一次"格式冻结"评审并记录在 lockfileVersion 说明中。

## M4 — vendor 4 层与 mappings

**目标**：依赖落地为可审计的 vendor 树，并生成外部构建工具可消费的 mappings。

**任务**

- [ ] link tree：逐文件 hardlink（目录结构真实创建；symlink 条目重建为 symlink）；`linkMode`：`auto`（hardlink → 失败降级 copy）/ `hardlink` / `copy` / `symlink`
- [ ] cache 层：`~/.ngm/cache/{metadata,osv,tmp}`；`ngm cache clean`
- [ ] mappings 生成：入口推断三层规则（ngm.json → package.json exports → index 约定，见 [configuration](../guides/configuration.md)）；缺失入口时输出警告
- [ ] `ngm mappings validate`：`from` 在 lock 中、`to` 存在、`main` / `types` 存在
- [ ] vendor 与 content 一致性校验工具函数（供 verify 复用）

**验收**

- vendor 文件与 content 逐文件哈希一致（全量校验，非抽样）；copy 模式与 symlink 模式各有测试
- Windows 上 hardlink 失败自动降级 copy（CI Windows job 覆盖）
- `mappings validate` 能检出缺失入口 / 不存在的 `to` 路径

**风险**：Windows 路径与链接语义差异；所有链接失败路径必须可观测（输出使用的 linkMode）。

## M5 — verify

**目标**：`ngm verify` 实现三级检查、漂移分类与退出码契约。

**任务**

- [ ] 检查一：ref → commit 对比（重新解析 refType；`--offline` 用本地 mirror 快照并在输出标记 stale）
- [ ] 检查二：digest 重放（从 mirror 同一 commit 重建清单、重算 digest，与 lock 对比；完全本地）
- [ ] 检查三：落地完整性（vendor 与 content store 的存在性与链接校验）；`--deep` 追加逐文件内容哈希
- [ ] 输出：human 文本 + `--json`（含 `driftKind: expected|unexpected|critical`）
- [ ] 开关与退出码：`--strict`（预期更新升级为 1）、`--allow-drift`（非预期降级为 0）、退出码 0/1/2/3/4 与 [退出码总表](../architecture/observability.md) 一致
- [ ] fixture 场景：tag 重打、branch 前进、commit 改写、content 被篡改、离线 mirror 缺失

**验收**

- 退出码矩阵全绿（5 类场景 × 开关组合的代表性子集）
- 预期更新默认不阻断（exit 0 + `driftKind: expected`）；篡改 content → exit 2
- [README 四问](../README.md) #2 实测记录：branch 前进与 tag 重打可区分

**范围细化（需同步文档）**：verify 的 `--offline` / `--deep` 在 v0.1 交付；**install** 的 `--frozen-lockfile` / `--offline` 属 v0.2（roadmap 的 CI 行指 install 侧）。若需调整该拆分，先提 roadmap PR。

## M6 — adapter 与构建命令

**目标**：通过 adapter 调用外部引擎完成构建 / 类型检查 / CSS。

**任务**

- [ ] adapter 框架：接口与 `EngineKind` 5 类（[engine-adapter](../architecture/engine-adapter.md)）、注册表、EngineManager（primary → fallbacks）、subprocess 协议（[P4](../modules/p4-ecosystem.md)）
- [ ] esbuild adapter：bundle + transform（v0.1 只需 esbuild，见 [roadmap](../internals/roadmap.md)）
- [ ] `self` stub：仅 `--dry-run` 使用；非 dry-run 调用 → 报错（**禁止静默降级**）
- [ ] 命令：`ngm build` / `ngm typecheck` / `ngm css`（`--engine` 指定；默认取 ngm.json 配置）、`ngm engines list|info|validate`
- [ ] 引擎缺失 → exit 5，Hint 指向安装方式与配置

**验收**

- 样例 TS 项目通过 `ngm build --engine=esbuild` 产出可运行 bundle；引擎缺失场景 exit 5
- 简写与完整写法配置等价（`{"transform":"esbuild"}` ≡ `{primary, fallbacks: []}`）
- 三平台 CI 上 esbuild 调用一致

**风险**：subprocess 启动开销与 stderr 解析的健壮性——错误映射保留原始 stderr 片段。

## M7 — 端到端验收与发布

**目标**：v0.1 退出标准全量达成，可发布。

**任务**

- [ ] 真实 Node 项目跑通 [quickstart](../guides/quickstart.md) 全流程（init → add → install → verify → build）
- [ ] 三平台 CI 全绿；lock 字节可复现回归常态化
- [ ] 文档验收：命令表 / 退出码 / 输出示例与 [guides](../guides/) 逐项比对，偏差先改文档
- [ ] 发布产物：交叉编译（installation 的下载路径命名）、`--version` 元信息、校验文件（sha256）
- [ ] v0.1 复盘：性能 baseline 记录、已知限制清单核对（LFS / submodule / shallow）、进入 v0.2 的范围确认

**验收（= v0.1 总退出标准）**

1. 能在真实项目上跑通 `ngm install`
2. lock 跨平台字节级一致（排除 `resolvedAt`）
3. verify 能检测出 tag 重打与 branch 前进
4. digest 重放不匹配能阻断构建（exit 2）

## 全局注意事项

- 提交前自查：新增行为是否有对应测试；golden 变更是否在 PR 说明
- 输出设计：human 与 `--json` 分离，禁止让 CI 解析人类文本
- 全部锁文件与清单统一 LF；Windows 换行不得影响 digest 与 lock 字节
- 并发：默认 4 并发拉取，失败重试策略需可配置（v0.1 固定值即可，但接口留位）
- 每个阶段结束做一次"文档-实现对照"抽查，防止文档漂移
