# v0.69 复盘 — **打开唯一愿意付钱的市场：SBOM 导出**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：新增 `ngm sbom`（CycloneDX 1.5 / SPDX 2.3，只读 lock）——
> 八年（68 版）攒下的 "commit + digest + 来源链" 第一次有了**别人能读**的形态。
> 同时它是"新命令会被既有契约网自动接管"的一次完整演示：四张网全部亮过。

## 1. 逐组验收

### 1.1 `ngm sbom` 本身

| 决定 | 落处 |
|------|------|
| 输入只有 lock | `runSbom` 读 `ngm.json`（项目名）+ `ngm.lock`；不触网、不重解析、不写项目 |
| 两种格式 | `internal/sbom`（`cyclonedx.go` / `spdx.go`，各自具名结构体；字段顺序即序列化顺序） |
| 哈希在场 | 每个组件带 `archiveDigest` 的裸 hex；CycloneDX 的 `properties` 与 SPDX 的 `comment` 都写明**它是规范化清单哈希，不是 tarball 哈希** |
| 确定性 | 排序在**导出器内部**做（不信任调用方）；SPDX 的 `documentNamespace` 由内容哈希派生（不是随机 UUID）；时间戳是唯一非确定字段 |
| 不猜 | 许可证/版权 `NOASSERTION`、`filesAnalyzed: false` |
| 出口 | `--out=<file>`；`--out=`（空值）与"没给"等价（v0.42 的不变量：不允许"都成功而结果不同"） |

**读数**（`internal/sbom` 与 `cmd/ngm` 的断言）：

```
同输入两次导出          → 逐字节相同
输入顺序打乱            → 逐字节相同（排序由导出器做）
只改 Now                → 除时间戳外逐字节相同
空依赖集合              → 仍是合法文档（"没有依赖"是一份有信息的 SBOM）
未知 --format           → exit 3 + hint 给出支持列表
无 lock                 → exit 3 + hint 点名 `ngm install`
stdout 永远写失败        → exit 6（与其它报告命令同一条路径）
```

### 1.2 既有契约网对新命令的"接管"（四张，全部要过）

这是本版最有信息量的部分——**加一个命令，四张为别的目的建的网依次亮起**：

| 网 | 它问了什么 | 处置 |
|----|-----------|------|
| **V37**（22 命令 × 8 配置错误形状） | 参数表 21 项 ≠ 命令 22 个 ⇒ 直接 Fatal：**"一个命令不在矩阵里，正是这张网要防的"** | `matrixArgs` 加 `"sbom": {}` |
| **V22**（退出码声明对账） | `ngm sbom` 声明 0/3/6 却"没实测、没登记" | 0 与 3 进 `exitCodeMeasured`；6 进 `exitCodeElsewhere`（指针指向新增的子测试 `TestV22StdoutWriteFailureIsMeasured/sbom`） |
| **V57**（码来源登记） | `runSbom` 有一个新的 `return errs.CodeInternal.ExitCode()` 站点 | 登记为 `catInternal`：`` `write report: %v`——SBOM 文档写不出去（v0.69 新增的出口） `` |
| **V19 / V15**（用法文本与文档） | 每个命令的用法文本必须写自己的 EXIT CODES；`cli.md` 的命令表要有一行 | 两者都在交付里 |

> **这不是"四张网各挡一次"，而是同一件事被四个角度问了一遍**：
> 它在矩阵里吗 · 它的码有实测吗 · 它的出口登记了吗 · 用户看得到它吗。
> 一个命令要"完整地存在"，这四问一个都不能少——而它们中没有一条是为此新写的。

### 1.3 覆盖面

`internal/sbom` 的 6 组断言（确定性 / 排序 / 时间戳唯一性 / 两种格式的必需字段 / 空集合 / 格式解析）
+ `cmd/ngm` 的 5 条端到端（导出 / `--out` / 未知格式 / 无 lock / 跨运行确定性）。

## 2. 未达成项

| # | 项 | 状态 |
|---|----|------|
| 1 | **SLSA attestation 谓词**（评估第 3 层第二条） | 未做，**待立 ADR**：它要给 manifest 接一层 provenance 谓词（而不是自造签名），牵涉"谁来签、签什么、验证方是谁"三个问题——那是一份 ADR 的体量，不是一版顺手能带的 |
| 2 | `verify --json` 报告升级为"策略引擎可直接消费的证据"（第 3 层第三条） | 未做：现有报告已经带 `driftKind` / `exitCode` / `remediation`，缺的是"证据"定义（给谁用、什么消费器）——在没有具体消费方之前设计它是猜 |
| 3 | SBOM 的**传递依赖**标记（哪个组件是谁引入的） | 未做：CycloneDX 有 `dependencies` 段、SPDX 有 `DEPENDS_ON` 关系，而 ngm 的 lock **不含来源链**（`why` 从上游重新展开）。要导出它得先把图信息带进 lock 或在此命令里重建图——后者要网络。如实记：当前 SBOM 是**扁平清单**，与 lock 的信息面一致 |
| 4 | SPDX / CycloneDX 的**官方校验器**验证 | 未做（离线环境）；字段集按两份规范的公开 schema 手写，断言覆盖了必需字段与形态，但"某个校验器会不会挑刺"没有证据 |

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么 |
|---|---------|---------|-------|
| 1 | 计划未写"`--json`" | `sbom` 没有 `--json`，输出**本身就是** JSON | 再包一层 `--json` 只会让脚本多解一层 |
| 2 | 没想好 purl 的子路径怎么表达 | 用 purl-spec 的 **subpath 段**（`#packages/core`） | 与 lock 的口径一致（子路径是同一个包的不同切片）；另写一种 custom 字段会让下游解析器多学一套 |
| 3 | 最初想在 `documentNamespace` 里放随机 UUID | 改为**内容哈希派生** | SPDX 只要求"一次导出内唯一"，而随机 UUID 会让两份文档无法被工具比对——对以"可复现"为卖点的项目是错误方向 |
| 4 | 没有计划让 `Put`/`ArchiveMaterial` 参与 | SBOM 不碰 store，只读 lock | 合规清单要对**声明**负责（lock），而不是对本地恰好装了什么负责 |

## 5. 过程洞察

### 5.1 第 3 层的三条里，只有第一条能"顺手做掉"

评估把三条并列在一起（SBOM / attestation / verify 证据化），但它们的**性质不同**：
SBOM 是"把已有数据翻译成标准格式"（一天）；attestation 要先回答
"签什么、谁签、谁验"（一份 ADR）；"报告升级为证据"要先有**消费方**（一个真实场景）。
把后两条硬塞进本版，产物会是"看起来有、没人能用的字段"——
而 SBOM 恰好相反：标准是别人定的，字段由规范要求，**做完就能被下游吃**。

> **一句话：能翻译的先翻译，要设计的先设计。**

### 5.2 四张网接管新命令，成本是四处登记、收益是"完整存在"

给 `ngm sbom` 接线的实际工时里，**命令本身与四张网的登记大约各占一半**。
一开始会觉得这是"流程税"，但逐条看下去：
矩阵那条抓的是"新命令没被任何形状测过"、退出码那条抓的是"声明的码没有证据"、
来源登记那条抓的是"新出口没进账本"、文档那条抓的是"用户不知道它存在"——
**四条都是"命令半吊子存在"的四种形态**。没有它们，`sbom` 会以
"能跑但没人真的用"的状态悄悄进仓。

### 5.3 与 v0.67 的呼应：这一次，"打牌"有了牌面

v0.67 把 PackageGate 写进 README 时说"合规是唯一愿意付钱的市场"——
那是**判断**。这一版给出了那个市场要的第一件东西：一份能被
`grype` / `dependency-track` / 采购流程直接读的清单。
两者合起来才是完整的动作：**说清为什么（v0.67）· 交出能验收的形态（v0.69）**。
