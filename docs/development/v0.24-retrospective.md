> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。

> 开工第一次跑就抓到 `observability.md` 里**另一处**漏写（码 1 没提 audit 钩子）。

## 1. 逐组验收

### 1.1 A 组 — 四方对账 ✅

| 对账 | 内容 |
|------|------|
| ①↔③ | 规格的 `iota + 1` 推出的**名字→数值**必须与实现逐一相同 |
| ② | `observability.md` 列全 0…5，每行有非空的语义与来源 |
| ④ | `cli.md` 的一行汇总同样列全 0…5 |

读数：**6 impl codes · 5 spec codes · 6 table rows · 6 summary entries** ✓
（规格 5 个是因为它不含 `OK`——0 不是错误码。）

**最想钉的一条是 `iota` 顺序**：规格是给人抄的，而 `iota` 的值取决于行序——
重排一行，所有退出码**静默平移**。牙齿验证时故意把 `ErrConfigInvalid` 与
`ErrDigestMismatch` 换位，网点名报出：

```
docs/modules/p0-core.md implies ErrDigestMismatch = 3 (from iota ordering), the implementation says 2
```

### 1.2 B 组 — 码 1 的来源必须写全 ✅（先修了一处文档）

码 1 是**唯一**被四种情形共用的数字。判据是一份会自己过期**的关键词表**：
`漂移` / `引擎` / `漏洞` / `钩子`。

**开工第一次跑就红**：`observability.md` 写着"verify 非预期漂移；adapter 引擎运行失败；audit 存在超阈值漏洞"——
**没提 audit 钩子**（而那确实是码 1 的来源，见 `audit_hook.go`）。已补上。

这正是这一版存在的理由：**上一版的漏写是人眼抓的，这一版的漏写是网抓的。**

### 1.3 C 组 — 补上 v0.23 遗留的"改了但没网" ✅

v0.23 给 audit 钩子的两条失败分支改了显示名，却在复盘里如实记了"**改了但没有网看着**"
（走到那两条分支要真的用 Deno 跑脚本，而本环境没有 Deno）。

处置：抽出纯函数 `auditHookVerdict(*security.Result)`，用合成结果测三件事——
**是谁否决的**（`AuditHook` 而非 `RefDrift`）、**数值仍是 1**、
**两种失败说的话必须不同**（"它说自己不过关" ≠ "它没能给出结论"）。

## 5. 过程洞察

### 5.1 人眼抓到的漏写，必须变成网抓到

v0.23 的 D1 是"人眼在写文档时顺手发现"。**顺手发现的东西，下次不一定顺手**——
那一处的价值不在于修好了，而在于**它是否从此有人看着**。
这一版把"看着"这件事做成了可执行的判据，而它第一次跑就抓到第二处同类漏写。

### 5.2 判据要能区分"列全了"与"写全了"

"四方对账"只能保证**每个码都被提到**；它保证不了**每个码的来源被写全**。
这两件事需要两条判据——前者是集合比对，后者是关键词表（而且那张表**自己会过期**，
理由与 v0.15 的负例名单、v0.21 的缺口名单相同）。

### 5.3 探针的复原也要被网看着

D2 是我在复原牙齿探针时漏了一行。它没有变成事故，唯一的原因是：**我把复原后的文件放在同一张网下面跑了一遍**。
"改回来"与"改对了"是两件事——**凡是动过的东西，复原后都要重新过一次判据**。
