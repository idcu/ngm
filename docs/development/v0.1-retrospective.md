> 属于 v0.2 的优化项而非设计缺陷——**但不能据此宣称 v0.1 达到性能目标**。

## 3. 性能 baseline

### 3.1 实测值

方法：`NGM_BENCH=1 go test -count=1 -run TestBaseline -v ./cmd/ngm`。
全部使用本地 fixture（无网络），每个依赖一个独立上游仓库；100 MiB 依赖用固定种子的
不可压缩伪随机字节（否则 git 的 zlib 会把它压到几 MB，测的是压缩率而不是 digest 计算）。

| 操作 | 实测 | 口径 |
|------|------|------|
| cold install (10 deps, mirror 已就绪) | 1.91s | 解析 + digest + content store + vendor 落地 + lock |
| **warm install (10 deps, 无变更)** | **11ms** | 有 lock → 尊重 lock；content store 命中 |
| verify (10 deps, 在线 ref 对比) | 1.91s | 三级检查 + 远端 ref 对比 |
| verify --offline (10 deps) | 1.08s | 三级检查 + 本地 mirror 快照 |
| verify --deep (10 deps) | 1.29s | 追加：从落地内容树重放 digest（全量哈希） |
| cold install (100 deps) | 17.88s | 同上 |
| **warm install (100 deps, 无变更)** | **107ms** | 同上 |
| verify (100 deps, 在线) | 18.77s | 同上 |
| verify --offline (100 deps) | 11.12s | 同上 |
| verify --deep (100 deps) | 12.75s | 同上 |
| cold install (1 dep, 100 MiB) | 1.17s | 含 content store 解包（全量写盘） |
| verify --offline (1 dep, 100 MiB) | 452ms | digest 重放：从 mirror 重建清单并逐 blob 计算 sha256 |

### 3.2 与设计目标对照

来源：[健康度指标](../internals/metrics.md) §性能目标（那些是设计值，本节是首次实测）。

| 目标 | 设计值 | 实测 | 结论 |
|------|--------|------|------|
| cold install（10 依赖） | < 5s | 1.91s | ✅ 达标 |
| warm install（无变更） | < 500ms | 11ms（10 依赖）/ 107ms（100 依赖） | ✅ 达标 |
| verify（100 依赖） | < 3s | 18.77s | ❌ **超 6.3×** |
| offline verify（100 依赖） | < 5s | 11.12s | ❌ **超 2.2×** |
| archiveDigest（100MB） | < 1s | 452ms | ✅ 达标 |

> **不宣称达标**：5 条中 2 条未达标，且未达标项恰好是 CI 里跑得最频繁的那条（`verify`）。

### 3.3 未达标项的根因（已测量，非推测）

`verify` 的成本**几乎全在 git 子进程启动**，不在哈希或 I/O：

| 测量 | 结果 |
|------|------|
| `git --version`（最小 spawn） | 26.6 ms/次 |
| `git ls-remote <本地裸仓库>` | 65.3 ms/次 |
| 每个依赖的 spawn 次数 | ~4：`ls-remote`（检查一）+ `cat-file -e` + `ls-tree -r` + `cat-file --batch`（检查二） |
| 推算 100 依赖 | ~400 次 spawn ≈ 11s — 与实测 11.12s 吻合 |

即：`verify --offline` 的 11s 中约 10s 是**进程启动开销**（Windows 上尤其贵），
哈希 100 个依赖的内容几乎不花时间（同机器 100 MiB 的单次 digest 重放只要 452ms）。

### 3.4 v0.2 行动项（按性价比排序）

1. **按仓库合并 git 调用**：每个仓库一次 `for-each-ref` + 一次 `cat-file --batch`，
   并让检查一与检查二**共用**同一份 `ls-tree` 输出 → 4 次 spawn/dep 降到 1–2 次。
2. **`refType=commit` 跳过 `ls-remote`**：字面量没有"重新解析"可言，可省掉最贵的 65ms/dep。
3. **跨依赖并发**：默认 4 并发（[P0 并发模型](../modules/p0-core.md) 已规定，`resolve` 已实现，`verify` 尚未用上）。
4. **`--deep` 的落地重放并行哈希**：当前串行读文件。

预计 1+2+3 可把 100 依赖的 verify 拉进 3s 目标区间，但**未做验证前不写进承诺**。

### 3.5 M7 期间修掉的一处承诺性问题（顺带大幅改善 warm install）

初测 warm install 是 **1025ms（10 依赖）/ 9470ms（100 依赖）**，根因是：即使 lock 被尊重、
content store 已命中，`install` 仍对每个依赖执行一次 `git fetch`。

这不只是慢——[锁定机制](../architecture/locking.md) 明确承诺"配合 content store 或 vendor，
**环境无网络也能安装与构建**"，而那种实现下无网络的 CI 会在**什么都没变**时失败。
改为"content store 命中即跳过 mirror"，并输出命中来源：

```
installed 10 dependencies from ngm.lock (lock respected; all 10 served from the content store (no git access)); wrote ngm.mappings.json
```

修复后 11ms / 107ms（约 90×）。该行为由 `TestM7InstallDoesNotNeedGitWhenTheStoreIsWarm`
固定：删掉整个 mirror 后仍能完成安装。

## 4. 已知限制核对

逐条核对**实际行为**（而非复述文档），每条给出验证方式。

| 限制 | v0.1 实际行为 | 验证 |
|------|---------------|------|
| **Git LFS** | 指针被**拒绝**（exit 3），绝不对指针求哈希 | `TestBuildArchive_RejectsLFSPointer`、`TestContentStore_RejectsLFSEntry`；检测阈值 1024 字节，见 `TestDetectLFSPointer_SizeGuard` |
| **submodule / gitlink** | mode `160000` 被**拒绝**（exit 3），不静默跳过 | `TestBuildArchive_RejectsGitlink` |
| **非标准 mode** | 只接受 `100644` / `100755` / `120000`，其余报错（目录 `40000` 是合法输入，由调用方跳过、不进清单） | `validateTreeEntry` 的 switch（`git update-index --cacheinfo` 会把非标准 mode 规范化，因此只能靠单元测试覆盖） |
| **shallow / partial clone** | **不支持**：mirror 保留完整历史（无任何 `--depth` 代码路径） | 全仓 grep 无 `--depth`；大仓库成本列入 v0.3 探索 |
| **hardlink 的跨卷限制** | `auto` 模式 hardlink 失败时整树降级为 copy，并**报告实际使用的模式** | `TestLinkTree_AutoUsesHardlink`、`TestLinkTree_CopyModeProducesIndependentFiles`；M4 验收断言 hardlink/copy/symlink 三种落地 |
| **hardlink 与 content store 共享 inode** | 就地编辑 vendor 文件会**同时改写层 2**，后续 install 不会察觉 | 已在 [vendor 4 层 §诚实说明](../architecture/vendor-layers.md) 与 `ngm verify --deep` 说明；`TestM5Acceptance/same-size_content_tampering_requires_--deep` 固定检测能力 |
| **无 registry（Git 直连）** | 每个依赖一次远端访问；host API 不被使用（outdated/audit 属 v0.2+） | 设计如此，见 [ADR-002：Git 直连](../adr/adr-002-git-direct.md) |
| **`verify` 的网络依赖** | 默认需访问远端做 ref 对比；`--offline` 用本地快照并标记 `[stale]` | `TestM5Acceptance/offline_uses_the_local_snapshot_and_marks_it_stale` |
| **引擎适配范围** | 只适配 esbuild（bundle + transform）；`tsc` / `deno` / `postcss` 声明后明确 exit 5，**不静默降级** | `TestM6Acceptance/missing_engine_exits_5`、`.../esbuild_is_refused_as_a_type_checker` |
| **性能** | 见 §3：2 条设计目标未达标 | 同上 |

## 7. v0.2 范围确认

以 [roadmap](../internals/roadmap.md) §v0.2 为准，并纳入本次实测新增项：

**路线图原有**

- OSV：OSV.dev 查询 + 缓存 + 报告
- 策略：`minimumReleaseAge`、白名单、`postInstallPolicy`
- `ngm audit` 命令 + 报告格式化
- 可观测性：`why` / `tree` / `outdated`
- adapter：`tsc` / `deno` / `postcss`
- CI：`install --frozen-lockfile` / `install --offline`

**本次实测新增**

- `verify` 的 git 调用合并 + 跨依赖并发（§3.4）
- `install --offline` 落地时，把"warm install 不碰 git"的规则同样施加到 `resolve` 阶段

**建议先做的事**：v0.1 的 lock schema 与 adapter 协议已稳定（关键路径），v0.2 可以并行铺开
OSV 与 verify 优化两条线。

仓库提交已于 2026-09-29 建立（`a47b0ad`，113 文件；Gitee 主仓 → GitHub 镜像 → CI 三平台全绿），
**剩下的是打 tag 触发首发**——发布与可追溯性都从那一刻算起。
