# v0.68 计划 — **把重复的那 4 个 spawn 拿掉**

> 范围来源：[assessment-2026-10-09.md](../internals/assessment-2026-10-09.md) 第 2 层
> （"这两条是量级改进（2–3×），而且已经有现成的仪器可以证明它"）。
>
> 一句话目标：**install 的每依赖成本回到它应有的样子**——digest 不该算两遍。

---

## 0. 起点：两条被量出来的结构性浪费

| # | 位置 | 问题 |
|---|------|------|
| P1#4 | `install.go` + `vendor/content.go` | 每依赖 **6 次 git spawn**：`BuildArchiveDigest` 2 次（自己一遍、`Put` 内部一遍）+ `Put` 内部再 `ListTree` + `CatFileBatch`。**其中 4 个是重复劳动**——同一份 (mirror, commit) 的树与内容被读了两遍 |
| P1#3 | `resolve/graph.go` | **先解析、后判重**：跨层菱形（A→C 且 A→B→C）里 C 被完整重新解析一次（含一次真实 `fetch`）。复杂度从 O(节点) 退化成 O(边) |

## 1. 处置

1. `internal/git`：新增 `ArchiveMaterial`（条目 + 内容 + 清单记录 + digest，
   一次算出）与 `BuildArchiveMaterial`；`BuildArchive` 变成它的薄包装——
   **两条路径的字节级行为由同一段代码保证**。
2. `vendor.Put`：`Meta` 接受可选的 `Material`（`json:"-"`，进程内传递）。
   传了就不重算（0 spawn），但**仍核对 Commit / Digest 两个身份字段**；
   不传（installFromLock 的校验路径）时内部构造一次（4 → 2）。
   "lock 的声明值 vs 实际内容"那条校验**保留原样**——它就是那个路径的目的。
3. `resolve.ResolveGraph`：**先与 `seen` 对账、再解析**；来源合并（RequiredBy / Depth）
   与冲突检测仍在原处发生（且比从前更早）。
4. `install` / `update` 改走 Material；`installFromLock` 刻意**不**改（见 §3 偏离 1）。

## 2. 验收

判据用**现成的仪器**（`git.SpawnCount`，理由见 `git/spawn.go`）——不掐表：

```bash
go test -count=1 -run 'TestV68' -v ./internal/vendor ./internal/resolve ./cmd/ngm
go test -count=1 ./...          # 整套
```

**读数**（计划时的预期，实测以复盘为准）：
- `Put(material)` → **0** spawn；`Put(无 material)` → **2**（was 4）
- `install(fresh, 1 依赖)` → **6**（was 10）
- 跨层菱形里 leaf 的解析次数 → **1**（was 2）

**牙齿**：`Put` 的身份核对（commit / digest 各一条）——把 Material 拼错必须被拒绝。
