# v0.31 计划 — 错误面：按**失败路径**看，而不是按**声明**看

> 范围来源：[v0.30 复盘](./v0.30-retrospective.md) §7 候选 2（"报告式失败也纳入契约"）。
>
> 一句话目标：v0.30 的运行时普查按**声明覆盖**组织（每对 `(命令, 退出码)` 一条），
> 于是**配置类错误的 21 条用例全都是同一个场景**（未知 flag）。
> 覆盖率看起来很高，错误面其实很窄。这一版按**失败路径**组织，把用户真会撞到的入口逐条走一遍。

---

## 0. 为什么有这一版

v0.30 的读数很好看：64 个用例、15 处错误文本全部带建议。但把它拆开看：

| 声明 | 用例数 | 场景数 |
|------|-------|-------|
| 3（配置 / 策略 / lock 错误） | **21** | **1**（每条命令给一个未知 flag） |
| 1 / 2 / 4 / 5 | 43 | 约 20 |

也就是说"15 处错误文本"里，绝大多数来自**同一个场景**。

## 1. 判据：按失败路径组织的表

每条路径 = 一个 `setup`（造出那个状态）+ 一条命令。用户真会撞到的入口：

- **配置类**：`ngm.json` 是坏 JSON / 缺 `name` / `runtime` 不认识 / 根本没有清单 / `config validate` 撞坏 JSON
- **锁与落地**：lock 没了 / 依赖的 vendor 树没了 / 依赖树里多了一个文件 / **`ngm.vendor/` 根**多了一个文件
- **依赖图**：`add` 一个畸形地址 / `why` 一个没声明的依赖 / `remove` 一个没声明的依赖
- **集成与映射**：`integrations add` 一个不存在的集成 / `mappings` 撞坏 JSON
- **取数**：`tree --osv --offline` 而没有缓存结果
- **对照组**：健康的项目 `verify` **应当**通过

## 2. 三条断言

1. **错误文本必须带 `hint:`**（与 v0.30 同一条契约）；
2. **非零不许静默**；
3. **可达性守卫**：钉住失败用例条数（防缩水）+ 身份不少于 2 种 + 必须有报告式失败。

## 3. 一条特别的用例：**把边界也写进网**

实测发现一个位置差异：

- 依赖**树内**多一个文件 ⇒ `verify` 退 **2**（"critical"）
- `ngm.vendor/` **根**多一个文件 ⇒ `verify` 退 **0**

后者不是缺陷——`verify` 按**每个依赖自己的树**核对，落在根、不属于任何依赖的文件不在它的判据里。
但这件事值得钉住：所以它作为 `expectZero` 用例进表，**并把原因写在用例上**——
行为哪天变了，这一条会红，逼着人重新读一遍那句说明。

这与"负例名单"（v0.15）、"缺口名单"（v0.22）是同一族：**名单自己要有牙齿**。
