## 1. 逐组验收

### 1.1 A — 在线 verify 的成本与方差

**验收原话**：100 依赖在线 verify 的**最大值 < 3s**（≥5 次采样）；达不到则写下"同等具体"的未达标结论
（根因 + 这条目标是否定错了），**不允许再出现"单次读数达标"**。

#### 开工前的读码把计划的前提改了两次

计划 A1 写的是"`refType=commit` 的依赖，commit 对象已在 mirror 时**跳过 `ls-remote`**"。
读码后发现两个事实都与它不同：

| 计划假设 | 实际 |
|---------|------|
| commit 型依赖会发 `ls-remote` | ❌ 它对 commit 是**纯字符串处理**（`normalizeCommitRef`），根本不发 |
| 所以"跳过"能省一次 spawn | ❌ 它发的是"读 mirror 的 `remote.origin.url`"那次子进程，而那个地址**对 commit 分支根本用不到** |

于是 A1 的决策从"跳过 `ls-remote`"改成 **"commit 型不做 ref 解析，零子进程"**（[ADR-015](../adr/adr-015-commit-ref-resolution.md)），
A4 则成了"把那次用不到的地址查询本身去掉"（[ADR-016](../adr/adr-016-mirror-url-local-read.md)）。
**这一步没有写一行实现代码，却决定了后面三次改动的方向**——先读、后测、再改的顺序在这里兑现了。

#### 仪器先于改动（A2）

`git.SpawnCount()`（`internal/git/spawn.go`，三个启动点都记账）。第一次测量给出的清单：

| 形态 | 改动前 | 改动后 | 构成 |
|------|--------|--------|------|
| commit 型 | 3.00 次/依赖 | **2.00** | `ls-tree` + `cat-file --batch`（digest 重放，与 refType 无关） |
| tag / branch 型 | 4.00 次/依赖 | **3.00** | 上面 2 次 + `ls-remote`（+ 曾经的 `config --get`） |

> **4.00 这个数字与 v0.1 复盘写下的"每个依赖约 4 次 git spawn"完全吻合**——
> 一条跨三个版本的旧结论被新仪器复现。它也因此把 A 组的收益**变成了可断言的东西**：
> `TestV05RefResolutionSpawns` 断言 commit 型 **0** 次、tag 型**恰好 1** 次（互为对照）。

#### 受控 A/B（A3）

v0.5 复核的三次采样是 2.201 / 3.068 / 2.556s。本轮先做了 5 次采样（中位 1.969s / 最大 2.078s），
但**跨轮比较不成立**——机器状态可能不同。因此又做了一次**同一天、同一台机器、临时关掉快路径**的对照：

| | 5 次采样 | 中位 | 最大 |
|---|---------|------|------|
| 对照组（= 未优化） | 2.355 / 2.364 / 2.416 / 2.427 / 2.433s | 2.416s | 2.433s |
| 实验组 | 1.752 / 1.910 / 1.969 / 2.065 / 2.078s | **1.969s** | **2.078s** |
| | | **−18%** | **−15%** |

**验收结论：满足（最大值 2.078s < 3s，5 次采样）。但必须同时读下一句**：

> ⚠️ **对照组也过线**（最大 2.433s）。也就是说复核里那次 3.068s **不是取数策略造成的**，
> 它在今天的机器状态下复现不出来。**跨机器状态的方差大于本次优化的收益**。
> 因此本文不允许写成"A4 让它达标了"——正确的写法是：
> **这条目标在今天的机器上，不依赖本轮的改动也已经满足**。

单次成本实测（同机、裸仓库）：`config --get` **30.6ms** / `ls-remote`（本地）**77.8ms** /
`ls-tree` **36.4ms**。按 tag 型 4 次计约 183ms/依赖，100 依赖 ÷ 8 并发 ≈ 2.2s——
与复核时中位 2.56s 吻合，因此**这条模型能用来预测收益**，不只是事后解释。

### 1.2 B — 可复现性：把翻案条件判掉

**验收原话**：ADR-013 里"翻案条件"一节给出**成立或不成立**的结论 + 可复现的命令与结果；
不得再以"在收敛"结束。

**结论：`REPRODUCIBLE ACROSS MACHINES`** —— Linux x86_64 / Windows x86_64 / **macOS arm64**
三个平台 × **7 个形态**产物字节一致（`treeA=7412c584ca107988`，esbuild 0.28.2 / tsc 5.6.3），
且各自 `treeA == treeB`（路径无关）。**但拿到这个结论花了四次迭代，而前三次红的是探针自己**：

| 轮次 | 结果 | 从中学到什么 |
|------|------|-------------|
| 1 | Linux = Windows ✓，**macOS 上 treeA ≠ treeB**（同一台机器、两个目录） | 差异不在"跨平台"而在"同机可复现"——比跨平台更难解释 |
| 2 | 加**逐形态哈希**后点名：`esbuild-plugin` | 整棵树的哈希只能说"某处不同"；形态级哈希让结果自己说出是哪一处 |
| 3 | 再拆成两个文件：`plugin.metapaths` 差异、**`plugin.appjs` 一致** | 差异在 metafile 的**路径内容**，不在产物 |
| 4 | metafile 移出产物树、降级为**观察项**（`obs.` 前缀，打印但不判定） | 门禁只看产物；**诊断文件不是产物** |

**根因（三个，都属于"只有实测才会知道"）**：

1. **原始 metafile 的字节不稳定**：本机专项 20 轮——`app.js` **1** 个取值、
   `JSON.stringify(metafile)` **20** 个取值；递归按键排序后仍是 20 个（变的是
   `inputs[*].imports` 这类**数组元素顺序**）。拿它的字节当门禁，测的是 esbuild 内部的调度顺序。
2. **路径字符串**：插件（与真实插件一样）用 `path.resolve` 把裸导入解析成**绝对路径**交给 esbuild，
   metafile 再相对化；macOS 的 `/var` 是指向 `/private/var` 的符号链接，相对化在一侧成功、
   另一侧失败 → 同机两目录的 metafile 不同。**产物不受影响**。
3. **`node` 版本一直被打印却没被判定**：第一次跑就显示 macOS v22.23.2 / Linux v22.23.3，
   而四层判定里没有一层看它。已纳入"引擎版本一致"这一层（B3）。

**判定（B2）**：翻案条件第 1 条的**技术前提已具备实测支撑**（"先实测某个真实引擎能做到"那半句）；
**ADR-013 仍决定不发布**，但**理由的构成变了**——剩下的是产品问题（用户是否愿意为一次远端构建
而在本地抽样构建一遍）与"合成夹具 vs 真实项目"的差距。
**发布与否是另一个决策，必须另立 ADR 修订 ADR-013**（该 ADR 自己的纪律），已登记为本轮收尾项。

> 顺带产出一条对用户的提醒（写进了 ADR-013）：**把 esbuild 的 metafile 放进产物目录的项目，
> 在 macOS 上会得到依赖机器的字节**——它是诊断文件，别拿它做可复现性判定。

### 1.3 C — 权限施加点的机械核对

**验收原话**：权限面上没有"声明了、不生效"的项；每项有一条"改了配置 → 行为变了"的端到端断言；
`read:` / `write:` 的裁决已写进文档，且被检查要求不得留白。

做的第一件事不是读文档而是**数出口**，于是两处缺口当场现形：

| # | 缺口 | 实测证据 | 处置 |
|---|------|---------|------|
| ① | 文档写着 `run:git` 的施加点是"`git.Run`（**所有** git 子进程的出口）"，而包里 `RunAllowFailure`（`cat-file -e` / `merge-base`）与 `CatFileBatch`（digest 重放）**各自直接 exec** | `deny: ["run:git"]` 下：前者执行**成功**（`err == nil`）、后者**启动了 1 个进程** | 三个出口收进唯一构造点 `newGitCommand`；`TestSpawn_GateOnEveryExit` 逐出口断言"拒绝 + **计数器为 0**" |
| ② | **`ngm audit` 的 OSV 查询没有 `net:` 门禁**（`internal/supplychain` 里零个 `CheckNet` 调用） | 同一份配置文件：`ngm install` 会 `exit 3`，而 `ngm audit` 照样连上 `api.osv.dev` | 判定放进 `queryRemote`（**只有它知道最终主机**），发请求前执行；`TestV05AuditNeedsNetPermission`：不授权 → `exit 3` 且替身**零命中**，授权 → 通过 |

**C2 的产出是三张网（都验证过会红）**：

- `TestEnforcementPointsAreRegistered`：每个命名空间必须登记"施加点在哪"与"哪条测试证明改了配置行为就变"，
  且该测试必须**真的存在**（扫源码，不靠名字形状猜）；文档的施加点表必须提到该命名空间。
- `TestHTTPEgressIsRegistered`：非测试源码里每个 `net/http` 出口都必须登记——**缺口②正是这样漏掉的**。
- `TestSpawn_OnlyOneFileBuildsProcesses`：`internal/git` 里只有 `spawn.go` 能构造进程（带空跑保护）。

**C4 裁决**：`read:` / `write:` **不在 ngm 自身路径上施加**（"读项目、写 vendor 与 lock"本就是它的职能），
仅在沙箱内（`read:` 按依赖子树授予、`write:` 恒不授予）。这条裁决写进安全模型的表，
并由检查要求"不许留白"——**裁决与遗漏的区别，是前者被写下来并被检查。**

> 顺带发现：**三条既有 audit 验收此前正是靠"没有门禁"才一直能连本地替身**。
> 修完缺口后它们需要显式授权 `net:127.0.0.1`——于是它们顺便成了这道门禁的活证据。

### 1.4 D — 交付：v0.2 ~ v0.4 补发布

**验收原话**：三版在 GitHub 与 Gitee 上各有 7 个附件，`SHA256SUMS` 一致；抽查记录写进发布清单或复盘。

| tag | 落点 | GitHub release | 附件 |
|-----|------|---------------|------|
| `v0.2.0` | `51e5e29`（加 v0.2 复盘那次提交） | 14:19:34Z，7 个 | 6 平台二进制 + `SHA256SUMS`（合计 66.73 MB） |
| `v0.3.0` | `f78d0c0` | 14:19:56Z，7 个 | 同上（合计 88.89 MB） |
| `v0.4.0` | `03e6426` | 14:20:00Z，7 个 | 同上（合计 89.09 MB） |

落点选在**各版"加复盘"那次提交**（与 `v0.1.0` 的惯例一致）：tag 的树里同时含有该版代码与它自己的复盘。
推送前核对了三项前提：流水线与发布脚本在三个落点上与当前**完全一致**、
`GO_VERSION=1.27` 满足各落点的 `go 1.22.0`、三个落点当时的 CI 都是绿的。
三次运行 `completed / success`（每次先跑全量测试，再交叉编译六平台）。

**Gitee 侧未完成**（见 §2.1）：仍是 3 × 7 = 21 个文件要人工上传。

**顺带被实测推翻的一处估算**：发布清单里原本按 v0.1.0 的 25.05 MB/版写着"约可容纳 40 个版本"。
实测各版合计 **66.73 / 88.89 / 89.09 MB**（单文件 10.1–14.9 MB），四版合计约 **270 MB**，
1GB 大约还够 **8 个版本**。原因也清楚了：v0.1 的网络操作全走 git 子进程、**没有 `net/http`**，
v0.2 的 OSV 引入了它、v0.3 又加上 wazero。

### 1.5 E — 挂账项里**可验**的部分

**E1 已完成，并且它当场暴露了一对缺陷。** 目标是"`deno bundle` 的实验性提示必须真的到达用户"。
做的时候发现它**此前到不了**：

| 路径 | 引擎的 stderr | ngm 的说明（Notes） |
|------|--------------|-------------------|
| bundle | ✅ 转发 | ❌ **丢失**——`deno bundle` 的"实验特性"提示写好了没人读 |
| css | ❌ **丢失**——postcss 的警告到不了用户 | ✅ 转发 |

根因是两种结果类型里**同名的 `Warnings` 字段含义不同**。处置：字段分家
（`Warnings` = 引擎原话、`Notes` = ngm 的话，subprocess 与 wasm 的四个方法一并统一），
CLI 两端都打印（ngm 的话带 `note: ` 前缀）。验收 `TestV05EngineChannelsAcceptance`（4 条，
**回退修复验证过正好那两条红**）。顺带固定了此前**零测试**的 `deno bundle` 版本闸门（< 2.4 → `exit 5` 且指向 esbuild）。

第一项尤其要紧：那句提示是"我们没说过它稳定"的**全部依据**。

**E2（store / mirror 的 GC）按计划不做**：缺的是**实测的磁盘增长数据**。理由写在计划里，
本版没有为了"迟早要做"而把它塞进来。

## 2. 未能完全达成的项

### 2.1 Gitee 附件仍未上传（D3/D4 未完）

**缺什么**：21 个文件的人工上传（Gitee 无 API token），随后才能做 D4 的两源 `sha256` 抽查。
**影响是具体的**：[安装指南](../guides/installation.md)把 Gitee 列为国内推荐源，
而 v0.2 ~ v0.4 走推荐路径会 404——**这三版对国内用户仍然取不到**。
待传清单与直链模板已在[发布清单](./README.md)里。

### 2.2 "合成夹具"这顶帽子只摘了一半（B）

插件链 / loader 链 / 压缩链都有了，但插件仍是**我们自己写的最小插件**（一个 `onResolve`），
不是真实项目的插件生态（Vite 插件、`postcss` 插件队列、资产指纹、代码分割）。

### 2.3 online verify 的目标线在噪声里**不可判别**（A）

这是本版最重要的一条方法论结论，单列在 §5.1。**目标 3s 在今天的机器上既拦不住真正的退化，
也无法证明某次优化有效**——因为跨状态的方差（0.3s 以上）大于本轮收益（0.45s）。
本版没有重定目标（那需要更长的采样与更可控的环境），只把"怎么判"写清楚。

### 2.4 `read:` / `write:` 在 ngm 自身路径上不施加

**这是裁决，不是遗漏**（§1.3 C4）。它的边界很清楚：ngm 读自己的项目、写 vendor 与 lock 时没有门禁；
一旦将来出现"需要拦下 ngm 自身读写"的场景，这条裁决要重新过一遍。

### 2.5 `deno bundle` 仍等上游（E1 的另一半）

条件写死为"上游把 bundle 标为稳定"；截至 2026-10-01 仍标 "experimental and subject to changes"。

### 2.6 跨机器一致性是**一次**运行的结果

它证明"这三个 runner 上一致"，不证明"任意机器都一致"。这条边界写进了 ADR-013。

## 3. 设计偏离登记

| # | 计划原话 | 实际做法 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | A1：`refType=commit` 跳过 `ls-remote` | 改成"commit 型**不做 ref 解析**"，另立 A4 去掉那次地址查询 | 读码发现 commit **本来就不发** `ls-remote`；真正的浪费是那次用不到的 address 查询。**照做会优化一个不存在的成本** |
| 2 | A3：复测 ≥5 次采样 | 额外做了**受控 A/B**（同机临时关掉快路径） | 5 次采样与复核的 3 次采样**跨机器状态**，不足以支撑"改变了多少"。受控对照让收益从"看起来快了"变成 −18%/−15% |
| 3 | A 组只提"跳过 `ls-remote`" | 新增 **A4**（读 config 文件代替子进程，带保守回退） | 第 4 次 spawn 是唯一还能砍的一次（约 17%）；但它需要一份"形状不符就回退"的解析规则，属于**新决策**，因此单独立 ADR-016 |
| 4 | B1：跑一次探针、看 compare 判定 | 迭代 **4 轮**，其中 3 轮修的是探针自己 | 第一版探针把 esbuild 的 metafile 当成产物哈希。**"跨机器比对红了"不等于"产物不可复现"**——先分清红在哪一层 |
| 5 | B3：把"引擎版本一致"写进 ADR | 同时把 **`node` 纳入**这一层 | 它一直**被打印却没被判定**；印出来不等于被检查 |
| 6 | C1：枚举 `read:` / `net:` / `run:` / `env:` 的施加点 | 增加一项裁决：`read:` / `write:` **不在 ngm 自身路径施加** | 按"生效 = 改变行为"的判据，没有需要拦下的场景就是没有；**不许留白**，因此写成裁决 |
| 7 | E2：store / mirror GC | 不做 | 缺实测的磁盘增长数据；没有数据就不排期（与"迟早要做"区分开） |
| 8 | D：补发布 | 三版全补 | 三版在仓库里都已交付、发行源上却取不到——**"只存在于源码里"等于没有交付** |

## 4. 本轮发现并修复的缺陷

**安全（两处都是"声明了、不生效"）**

1. **`run:git` 只挡住三个 spawn 出口中的一个**：`RunAllowFailure` 与 `CatFileBatch` 无门禁。
   实测下 `deny: ["run:git"]` 仍会执行 git。→ 收进唯一构造点 + 结构不变量。
2. **`ngm audit` 的 OSV 查询没有 `net:` 门禁**：同一份配置下 `install` 拒、`audit` 不拒。→ 判定放进 `queryRemote`。

**协议（两条消息通道各丢一半）**

3. bundle 丢 ngm 的说明（`deno bundle` 的实验性提示无人读）、css 丢引擎的 stderr。

## 5. 过程洞察

### 5.1 次数优先于秒数

同一份代码在同一天的两次采样相差 0.3s，而本轮优化的收益是 0.45s——**在秒数上，它们几乎不可分辨**。
`git.SpawnCount()` 给出的 4.00 → 3.00 则与机器状态无关。

> 因此本版把它写成纪律：**比较性能时次数优先于秒数**；秒数只回答"用户等多久"，
> 不用来判断"改动有没有用"。另见 §2.3：3s 这条目标线在今天的机器上**既拦不住退化、
> 也证明不了优化**——下一次定目标时应当同时写下**对照**怎么取。

### 5.2 印出来不等于被检查

`node` 版本从一开始就印在结果里（macOS v22.23.2 / Linux v22.23.3），而四层判定里没有一层看它。
**"信息已经打出来了"很容易被当成"这件事已经盯住了"**——它不是。

### 5.3 规则写在第二个地方，就一定会有一处不一致

本版四处缺陷是同一个形态：`run:git` 的门禁（三个出口）、两条消息通道（两种结果类型）、
`genericInvocation` 的参数转发（两处分支）、CLI 复刻 adapter 的 loader 规则（两个地方）。
**处置方式也一致**：把规则收回**唯一**的地方，再让机械检查守住"没有第二个地方"。

### 5.4 仪器要先于改动

A 组先装 `SpawnCount()` 再动手，于是"改了 4 个出口中的 1 个"这件事**从第一天就是可断言的**；
B 组先加逐形态哈希，于是第三轮的红**自己说出了** `esbuild-plugin`。
反过来，第一版探针没有形态级数字，第一轮只能报"整棵树不同"——**那一轮的定位成本全落在人身上**。

### 5.5 "本机跑通"与"三台真机器跑通"是两件事

探针在本机（Windows）两次运行同值，看起来通过了；CI 一跑就红。
**本机的一致性是运气**（20 个取值里抽中同一个两次）。这一条与 v0.4 复盘 §3.2 的
"机器检查的有效性与边界"是同一条，第三次确认。

### 5.6 我这一版犯的两处错

- **覆盖文件**（§4.5）：教训是"新建文件前先确认名字"——这在有 200+ 文件的仓库里不是小事。
- **探针模型错**（§4.6）：把诊断文件当产物。教训是"**先定义清楚被测对象是什么**，
  再决定拿什么哈希它"；否则门禁会一直在测一件无关的事，而且**它会红得很有道理**。

## 7. v0.6 候选（按证据强度排序，非路线图承诺）

| # | 候选 | 证据 / 前置 |
|---|------|-----------|
| 1 | **发布 `remote` adapter 与否** | ADR-013 的技术前提已成立；这是**决策**不是实现，须先立 ADR 修订 ADR-013。要回答的是产品问题（用户是否愿意抽样构建一遍） |
| 2 | **Gitee 附件补传 + 两源 `sha256` 抽查** | D3/D4 的唯一残项；21 个文件，纯人工 |
| 3 | **可复现性再进一步：真实项目形态** | 摘掉"合成夹具"帽子——真实 Vite 插件链、代码分割、资产指纹 |
| 4 | **目标线的重新定义** | 3s 在噪声里不可判别（§2.3）；要么定"次数预算"，要么把采样与环境写进目标 |
| 5 | **store / mirror 的 GC** | 缺磁盘增长数据；先测再排 |
| 6 | `read:` / `write:` 在 ngm 自身路径上的施加 | 仅在出现真实拦停需求时（当前是裁决，不是遗漏） |

**对下一版的建议**（与上表不同：这些是方法，不是功能）：

1. **定目标时同时定"对照怎么取"**——否则达标与未达标都不可判别（§5.1、§2.3）。
2. **新增任何"出口/分支/通道"时，同时加一张机械检查的网**——C 组的三张网是模板。
3. **交付纪律已进发布清单第 0 步**：版本交付即打 tag，不等"下次一起发"（D5）。
4. **探针与夹具也要写清"被测对象是什么"**——B 组的四轮都花在这句话没说清上。
