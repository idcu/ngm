# v0.31 复盘 — 错误面：按**失败路径**看，而不是按**声明**看

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：v0.30 那张网按**声明覆盖**组织，配置类错误的 21 条用例**全是同一个场景**。
> 这一版按**失败路径**组织，逐条走 14 个用户真会撞到的入口：
> **12 处错误文本全部带建议、2 条走报告、0 处静默**。**产品代码 0 行改动**，
> 但过程里有一条判断被测量**当众否掉**（见 §5.3）。

| 位置 | 结果 | 为什么 |

## 5. 过程洞察

### 5.1 覆盖率是按什么算的，比覆盖率的数字更重要

v0.30 报的是"64 个用例、15 处错误文本全部带建议"——听起来很宽。
但按**声明**组织的表，配置类错误那 21 条**全是同一个场景**（未知 flag）。

**同一组数字，换一种组织方式，含义完全不同。**
这一版把表按**失败路径**重排，读数从"15 处"变成"14 条路径 / 12 处错误文本"——
数字变小了，但**它现在说的是"用户会撞到的入口"**。

### 5.2 判据不该要求世界符合我的预期

我给这张网写的守卫原本是"错误身份至少 **4** 种"。第一次跑就红了：

```
only 2 distinct error identit(y/ies) were reached (map[ConfigInvalid:11 GitFetch:1])
```

红的不是产品，是**我的预期**。实测的真相是：

- **"你做错了什么"** → 走错误文本（`ConfigInvalid`，11 条都在这）
- **"这份树为什么不可信"** → 走**报告**（`verify` 给出逐条 landing/digest 细节）

这是**设计**，不是缺陷：报告能给出逐条细节，错误文本只能说一句话。
处置是把守卫改成如实的两条，并把这段推理写进测试注释——
否则下一个读到那条断言的人会以为"4 种"是某个真实的要求。

### 5.3 第三次栽在同一族：**夹具指错路径**

测量中我一度以为抓到了缺陷：**"删掉整个 `vendor/` 后 `verify` 退 0"**。

真相是：这个项目里**没有 `vendor/` 目录**，而有 **`ngm.vendor/`**——我删的是一个
**不存在的路径**（`os.RemoveAll` 对不存在的路径静默成功）。改用真实路径重量：

```
verify 删掉 ngm.vendor 后: code=2
  ✗ github:x/dep@v1 (tag) → 2bb5272 — integrity failure
      landing: vendor path is missing: …\ngm.vendor\github.com\x\dep
    → driftKind: critical; do NOT build from this tree; investigate how the bytes
      changed, then re-run `ngm install` to restore provable content
```

**产品没有缺陷，我的假设有。** 而这是同一族陷阱的**第三次**：

| 版本 | 形态 |
|------|------|
| v0.16 | 篡改掩盖了漂移——读数说谎 |
| v0.21 | 夹具被前面的命令改掉——状态耦合 |
| **v0.31** | **夹具指错了路径**——删了个不存在的东西 |

三次的共同点：**我以为我在改 X**。
所以这张网现在有一条断言专门管这件事（§1.3 第二条）：
一条"失败用例"如果退 0，报的错是
*"either the path changed or the fixture no longer builds the state it names"*——
**把"我以为"变成一条会被测出来的东西**。
