# v0.21 复盘 — 一张网真正的敌人，是"判据自己先错了"

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：把"声明 ↔ 实测"钉成了一张网（**70 对声明，44 条已实测**），
> 网本身成立；但本版真正的收获是**两次先修判据**——
> 一次是解析器把段里的续行当成了段落结束，**21 个命令只解出 6 个**；
> 一次是环境在用例之间泄漏。以及它当场抓出的一处**产品缺陷**：
> `ngm tree --offline` 不穿 `--offline`，退了 3 而不是自己承诺的 4。

---

## 1. 逐组验收

### 1.1 A 组 — 段必须格式正确 ✅

21 个命令的用法文本**都有** `EXIT CODES` 段，码 ∈ 0..5、不重复、每条带说明。

**这里踩了一个坑，值得单独说**：第一版解析器用"缩进 ≥ 6"当续行判据，
于是带跨行说明的段在第一行续行处就被当成结束——`verify` 只解出 `0 1 2`，
`install`/`update` 只解出 `0 1 2 3`。**21 个命令里只有 6 个被正确解析。**

表面看网是绿的（它确实在核对那 6 组），**但它在对着一份残缺的声明对账**。
这类失败比"网没抓到东西"更危险：**它假装已经对过账。**

修法是改用"顶格且不是 `<数字> 说明`"作为段落结束的判据，续行只看缩进。

### 1.2 B 组 — 声明 ↔ 实测 对账 ✅

| 结果 | 数量 |
|------|------|
| 声明的（命令, 码）对 | **70** |
| 已实测（离线触发并断言一致） | **44** |
| 记录的已知缺口 | **26** |

已实测的覆盖：
- **3**（配置 / 策略 / lock 错误，含用法错误）：**21 个命令全部**——给每个命令一个它不认识的 flag，必须退 3；
- **0**（成功态）：15 个命令；
- **4**（Git 或网络失败，`--offline` 且资源不在本地）：`install` / `update` / `audit`；
- **5**（引擎不可用：目录里声明了但命令不存在）：`typecheck` / `typedecl` / `build` / `transform` / `css` / `engines`。

顺带量清了一个**容易混淆的边界**：引擎名字**不在目录里** ⇒ 3（配置错误）；
名字在目录里但**命令没装** ⇒ 5（引擎不可用）。两者是不同的码。

### 1.3 C 组 — 缺口名单会自己过期 ✅

`exitCodeGaps` 里每条都断言"该命令确实还声明着这个码"。
牙齿验证时故意把 `engines` 的期望码从 5 改成 4——网立刻红，
并且**精确指出**"`engines` 声明的 5 现在既没实测也没缺口"。

## 4. 缺陷清单

| # | 缺陷 | 性质 | 状态 |
|---|------|------|------|
| D1 | **`ngm tree --offline` 不把 `--offline` 穿进图解析**：`tree.go` 用 `env.GraphOptions()`，而它不带 offline；解析于是发起取数意图，被权限层判成"权限被拒" ⇒ **exit 3**，而该命令自己声明的是 **4**（"Git or network failure，含 `--offline` 且冷 mirror"）。对比 `install` / `update`：它们用 `offlineEnsureMirror(env)` 显式穿上，同样冷 mirror 正确地退 4 | **产品缺陷**（分类不一致） | ✅ **已修**（`tree.go` 同款穿上，注释写明实测证据） |
| D2 | 第一版 `declaredExitCodes` 把续行当段结束，21 个命令只解出 6 个 | 网的判据错误（最危险的一类） | ✅ 已修 |
| D3 | 用例之间泄漏环境（OSV 替身的 `t.Setenv` 残留 ⇒ `audit` 的 4 被读成 0） | 夹具状态耦合 | ✅ 已修（每个用例重新隔离） |

## 5. 过程洞察

### 5.0 上一版"以为交付了"：v0.20 的文档写了、却没提交也没打 tag

本版开工前查了一遍 tag 与 release：**本地 tag 停在 `v0.19.0`，GitHub 仍是 15 个 release**，
而 v0.20 的计划与复盘**还躺在工作区里没被提交**（`git status` 里是未跟踪文件）。

也就是说 v0.20 只完成了"写"，没完成"交付"——而**没有任何东西会因此报错**：
`release status` 门禁只在 CI 里跑，而这次根本没有推送。

处置：v0.20.0 与 v0.21.0 的 tag 随本次推送一起补上。
教训是**"交付"这个词必须绑定动作**（commit → tag → push），
而不是绑定"我把文档写完了"这种感觉。这也正是 v0.12 那句
"凡是能复读的数字都该绑一条命令"的另一种形态：**凡是声称已交付的版本，都该有一个 tag 能验证它。**

### 5.1 一张网真正的敌人，是判据自己先错了

D2 那一次：网在跑、在绿，但它核对的对象是**残缺**的。
**"绿"只能证明判据跑通了，不能证明判据是对的。**
所以本版把判据本身也当成一个待验证物——用 `tree` 的 4 当探针，
看它能不能被判据看到（它能，于是缺陷浮出来）。

### 5.2 状态耦合是这版的慢性病，连踩三次

| 次 | 现象 | 处置 |
|---|------|------|
| 1 | 探针把 `add` 跑在共享目录上，后面的 `remove` 于是**合法地**退 0 | 每个命令独立目录 |
| 2 | 配置错误探针里 `init` 报"已存在"（`newProject` 预建了清单） | 引入 `setupEmpty` |
| 3 | OSV 替身的 `t.Setenv` 在用例间残留，`audit:4` 被读成 0 | 每个用例重新隔离环境 |

**一个"合法"的读数，可能是因为夹具被前面的人改过了。**
读数不对，先怀疑夹具，再怀疑被测物。

### 5.3 "已知的洞"也要被看住

`exitCodeGaps` 是一张"我知道这里还没人盯着"的名单。
它极易变成永久住户。**给它加一条"条目必须仍对应真实声明"的断言**，
它就只能在"声明还在"的前提下存在——声明一改，条目必须一起走。
