# v0.27 计划 — 散在句子里的字段名，也是机器接口

> 范围来源：[v0.26 复盘](./v0.26-retrospective.md) §7 候选 1 与 2。
>
> 一句话目标：把"文档 ↔ 实现"的对账推进到**最散的那一份**——
> 既不在表里、也不属于任何"形状"、而是**散在散文句子里**的字段名；
> 并给 `configuration.md` 补上**反向**判据。

---

## 0. 为什么有这一版

到目前为止，对账覆盖了三份**结构化**的清单：`--json` 形状表、配置字段表、退出码。
剩下的两类是：

| 类别 | 例子 |
|------|------|
| **散文里点名的字段** | `observability.md`："`--json` 里对应 `pathsTruncated: true` 与 `pathsLimit: 64`" |
| **配置文档的反向** | `configuration.md` 的字段表只挡"写了不存在的键"，不挡"加了字段没写" |

散文那一类最容易被改名遗漏：它**既没有表可对，也不属于任何形状**。

## 1. A 组 — 散文里的字段名（判据先量）

按 v0.25 的教训，先量两条判据：

| 判据 | 结果 |
|------|------|
| "活文档里所有反引号驼峰标识符" | 误报 **27/62**（Go API、配置键、Git 配置键、占位符全卷进来） |
| "**提到 `--json` 的那些行**里的驼峰标识符" | **21 个 token，误报 0** |

采用后者：**提到 `--json` 的行**正是文档在讲机器接口的地方。

**牙齿验证时发现判据漏了一整类写法**：第一版只认纯标识符（`` `pathsTruncated` ``），
而散文里更常见的是带取值的形态（`` `pathsTruncated: true` ``）——改掉后者，网**没红**。
判据放宽到"允许 `: 取值` 后缀"之后，两处同时改才会红。

## 2. B 组 — `configuration.md` 的反向

`ProjectFile` 与 `Dependency` 的每个 json 字段，都必须在 `configuration.md` 里被点名过。

判据比形状表那张松一档：**允许字段在文件别处被点名**（正文、散文、小标题都算）——
配置文档本来就是"表 + 说明"混排的写法。它仍然挡得住"加了一个谁都没写的字段"。

## 3. 明确不做

| 不做的 | 理由 |
|--------|------|
| `vendor` / 全局配置的反向判据 | 它们用**散文 + 小标题**描述（`### linkMode（落地方式）`），没有字段表——机械判据在那里只会误报。**明确不做，而不是做一半** |
