# v0.3 复盘

> 结论：**计划 A–E 五组的交付项全部结项，逐条验收有可执行证据，三平台 CI 全绿**。
> 其中 `remote` adapter **以"决定不发布"结项**——[ADR-013](../adr/adr-013-remote-adapter.md)
> 论证了它的核心问题（产物无法被用户本地证明）不是工程问题而是立场问题，因此它不是待办。
> v0.2 遗留的两项（在线 verify 性能、tsc / postcss 真引擎覆盖）已在开工时闭环。
>
> 本轮立/定 **4 份 ADR**（010 收尾、011、012、013），发现并修掉 **8 处缺陷**，
> 其中 **2 处在已发布代码里**：`ngm build` 的别名键会静默解析到错误代码、
> `permissions` 被解析但从未施加。
>
> **仍有一项未结项**：沙箱自述文件签名检查（需先定签名格式与密钥管理，属独立设计），见 §2.3。

- 复查日期：2026-10-01
- 范围：[v0.3 实施计划](./v0.3-plan.md) 的 A–E 五组
- 基线环境：Windows 10 / 8 核 / `go1.27.1 windows/amd64` / git 2.56.0 / Deno 1.45.2
- 提交范围：`e7c785a` … `8daaa67`（16 个提交；其中 `e7c785a`、`73a3a3e` 是 v0.2 遗留项收尾）

## 2. 未能完全达成的项

### 2.1 `remote` adapter 不发布（这是结论，不是延期）

计划开工前的复核就写下："**若这三个问题答不上来，不发布比发一个说不清的更强**"。
本轮把三个问题逐个答了：**第 1 问**（发给谁）答不上来，**第 2 问**（如何证明对方没替换字节）
是结构性的答不上来，**第 3 问**（失败如何不静默降级）答得上但不足以翻案。

第 2 问的论证值得单独记一句，因为它会被再次用到：**签名证明的是"谁发的"，不是"发了什么"**
——一台诚实、密钥保管良好的服务照样能签出一个被植入后门的产物，攻击发生在签名**之前**。
唯一成立的思路是"本地复现后比对"，而那要求**可复现构建**，在 JS 生态里不是既有能力；
把它写进依赖项等于把一个尚未解决的行业问题塞进 ngm 的正确性前提。

ADR 里留了**可证伪的翻案条件**（产物可复现且用户能抽样本地复现），使将来的改变必须与论证较劲。

### 2.2 Vite / Webpack / Deno 的集成配置没有真工具验证

CI 的 `engine-integration` job 只装了 esbuild / typescript / postcss。
因此 Vite / Webpack / Deno 的生成物**只有内容断言**：它证明 ngm 按各家语义生成了正确的键与目标，
**没有证明**这三个工具真的会那样解释这些配置。

这是刻意的取舍（CI 不装一堆构建器），但必须写清它证明了什么、没证明什么——
[v0.3 计划 §B](./v0.3-plan.md) 与 [P5](../modules/p5-integrations.md) 都已写明。

> **同类的教训在 v0.2 出现过一次**（当时是 tsc / deno / postcss 只有假引擎），
> 而那次"补上真工具"立刻抓到一个假引擎永远抓不到的缺陷（tsc 把诊断写在 stdout）。
> 本轮的真 esbuild 也抓到了一个：生成的 esbuild 脚本是 `.mjs` 时，
> 只有全局安装 esbuild 的项目会 `ERR_MODULE_NOT_FOUND`（ESM 不认 `NODE_PATH`）。

### 2.3 沙箱自述文件签名检查未做

它是 C 组唯一未打勾的项，而计划里已写明原因：不只需要沙箱，还要**先定签名格式与密钥管理**。
在没有那两样之前实现它，只会做出一个"看起来验过了"的检查——比不做更糟。

## 3. 设计偏离登记（每条都写明"为什么不是照做"）

| # | 计划原文 | 实际做法 | 理由 |
|---|---------|---------|------|
| 1 | mappings "v2 校验" | `version` **保持 1**，只新增可选 `path` | 按 schema 版本策略"同一大版本内只新增可选字段"。计划的"v2"指协议扩展，不是版本号 |
| 2 | tsconfig 与工具配置"一并生成" | 拆成 `ngm.tsconfig.json`（ngm 拥有、可重生成）+ 新项目的 `tsconfig.json` 用 `extends` 指向它 | `tsconfig.json` 属于用户且常带注释，直接改写是破坏性的 |
| 3 | esbuild 集成产物 | **`ngm.esbuild.cjs`（CommonJS）**，不是 `.mjs` | 实测 ESM 的模块解析不认 `NODE_PATH` → 全局安装 esbuild 的项目会失败 |
| 4 | 已存在的 `tsconfig.json` / `deno.json` | 报 **skipped + 一行提示**（exit 0），不是冲突 | 文件本身没有错，只是需要用户加一行。报成冲突会让人以为出了问题 |
| 5 | 沙箱按权限词表映射（含 `run:`） | **从不映射 `run:`**，并把"可执行的程序"从授权结构里删掉 | 实测：`--allow-run` 允许的进程**不受 Deno 权限约束**（能读到被禁止读取的文件） |
| 6 | `postInstallPolicy: prompt` 交互确认 | 语义改为"**不自动执行**并说明如何开启" | ngm 是非交互工具；真去读 stdin 会让 CI 挂住。"询问"没有真实形态时，诚实的做法是说明，而不是假装问过 |
| 7 | 权限默认档位 | `env:` **默认允许透传**，其余默认"需配置" | ngm 不读 token，只把它交给 git；默认拦下会让认证在无人配置时直接坏掉。`env:` 的用途是**收窄** |
| 8 | wasm 运行时取最新 | 钉 **v1.9.0** | 实测 `go get` 会把 `go` 指令从 1.22 改写成 1.25，而那是**对外契约**、必须单独决定。v1.9.0 恰好要求 1.22 |
| 9 | wasm 的 `typeDecl` 能力 | **明确拒绝**并指向 subprocess | 多文件输出需要写权限，沙箱不给。静默返回空列表会被当成"没有声明要生成" |
| 10 | wasm 的 `--outfile` | 由 **ngm 代写**（模块只产 stdout） | 模块没有写权限，而用户给了 outfile 就期待文件出现。ngm 代写让两件事同时成立 |
| 11 | `remote` adapter 进引擎清单 | 枚举保留该值，但报"按决定排除" | 删掉它会让"为什么没有 remote"无处可查；保留 + 指向 ADR 是把决定放在用户会遇到它的地方 |

## 4. 本轮发现并修复的缺陷

| # | 缺陷 | 由什么发现 | 影响 |
|---|------|-----------|------|
| 1 | `permissions`（`read:`/`write:`/`net:`/`run:`/`env:`）**结构齐全、从未施加** | 复核时"去验证而不是假设" | 文档写明的门禁**一条都没在跑**；用户以为 `deny: ["env:GITHUB_TOKEN"]` 在拦 |
| 2 | `ValidateEnvironment.SubPaths` 是死字段，且类型（单个 string）与注释承诺的"列表"矛盾 | 写 E 组时去看校验器 | 注释承诺的 `to` 一致性检查从未存在；一个依赖可以有多个子路径，单值表达不了 |
| 3 | **`ngm build` 的别名键用 `from`**：同一仓库多个子路径互相覆盖 | 写 B 组的脚手架时顺手看自己的旧代码 | **最坏的一种**：覆盖后构建**仍然成功**，只是两个子路径解析到同一份代码——不报错，只是结果错 |
| 4 | `run:<引擎>` 判定顺序：引擎缺失被报成"权限被拒" | 加门禁后 M6 的旧用例变红 | 提示用户去加一条**永远用不上的**权限，退出码从"环境问题"(5) 变成"配置问题"(3) |
| 5 | wasm 模块缺失时报 "was not found on PATH" | 手工跑一次真 CLI | 指错了地方：模块是文件、按项目目录解析 |
| 6 | 清单校验按**进程 CWD** 找 wasm 模块 | 同上 | 从项目的上一级检查时，明明存在的模块被报成"找不到" |
| 7 | `engineRunTarget` 把 `.wasm` 当扩展名剥掉 | 自己写的权限目标用例 | 权限名变成 `run:engine`，与一个真叫 `engine` 的程序**共用同一个权限名**——"授权了一个、执行了另一个" |
| 8 | `build.md` 的 monorepo 别名配方是**错的** | 用真 esbuild 做对照实验 | 照着抄的用户在 monorepo 上会得到 `Could not resolve ".../packages/core/packages/core"`，或更糟：静默指向错误代码 |

**过程洞察**：8 处里**没有一处**是"代码写完那一刻"发现的。分布是——

- **3 处**（#1、#2、#5）来自复核时的"去验证而不是假设"
- **3 处**（#3、#4、#7）来自**写新功能时顺手看自己的旧代码**
- **2 处**（#6、#8）来自**手工跑一次真 CLI / 真工具**，而不是只看测试绿不绿

另有两处与本节同类但已在开工时收尾（`e7c785a`、`73a3a3e`）：在线 verify 的惰性取数、
以及**引擎非零退出时丢掉 stdout 诊断**（tsc 把 `error TS2322` 写在 stdout）。
它们由 v0.2 复盘的 §2.1 / §2.2 指出，属"上一次复盘的建议被真的执行了"。

**同类缺陷第三次出现**：`verifyOnLock`（v0.2）→ `permissions`（v0.3 D）→ `SubPaths`（v0.3 E）
都是"**声明了、注释写了、没有任何地方接线**"。这不是意外，是模式——见 §7 建议 1。

**我自己犯的错也记在这里**（不掩）：

1. 写文档配方时断言"esbuild 的 alias 是**精确匹配**"——**实测是前缀替换**。顺着这条线做对照实验，
   才发现旧配方本身在 monorepo 上是错的（#8）
2. 同一次纠正里我又写了"长键必须排在前面，否则子路径会被吞掉"——**也是错的**：
   esbuild 自己选最具体的匹配，与顺序无关
3. `A` 组的计划标题里我留下了 wazero **v1.12** 的实测数字（3 个模块 / +5.14 MB），
   而实际用的是 v1.9.0（1 个依赖 / +3.42 MB）——**ADR 里的数字必须对应实际使用的版本**
4. **三次**用过滤条件（`Select-String`）吃掉测试的多行失败输出，导致盲猜了轮次才看到真实报错

## 7. 对 v0.4 的建议

1. **把"声明了、没接线"做成机械检查**。同类缺陷已连续三个版本出现（`verifyOnLock` →
   `permissions` → `SubPaths`）。v0.2 复盘建议过"让验收条目成为测试里的注释锚点"，
   **这次没有落地**，于是又出现两次。最小可行做法：为每个配置字段配一条**从配置读到行为的**
   端到端断言；没有断言的字段，不得在文档里被描述为"已生效"
2. **继续扩真工具验收，并保留 skip 守卫**。本轮的 3 处缺陷来自"真的跑一次"，
   而 skip 守卫（该 job 装了工具，任何 skip 即红）保证绿灯意味着**真的跑了**，
   而不是"跳过之后绿的空集"
3. **ADR / 计划里的实测数字必须对应实际使用的版本**（§4 我的第 3 条）。数字一旦与版本脱钩，
   它就从证据变成了装饰
4. **"决定不发布"要按交付物处理**：留 ADR、留可证伪的翻案条件、让工具说出这个决定
   （而不是继续暗示"将来会有"）。比"留一个永远不做的待办"诚实得多
