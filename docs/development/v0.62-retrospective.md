## 1. 逐组验收

### 1.1 先量夹具，再动手

v0.59 的缺口表里那六条原因**都是猜的**（"要 OSV 结果" / "要配好的引擎" / "要真实工具名"）。
这一版先量夹具在不在：

| 命令 | 夹具现状（量到） |
|------|----------------|
| audit | **现成** ✓ `v3AuditProject(t, osvBody)` — 装好依赖的项目 + OSV 指向**本地替身**（`NGM_OSV_URL` 注入 ⇒ 不依赖公网） |
| build/typecheck/css/transform | **现成** ✓ `m6Catalog(t, proj, fakePath, kinds...)` — 把假引擎登记进给定能力类别 |
| integrations | 只要一个**已安装**的项目（`ngm.mappings.json` 由 `install` 生成）+ 真实工具名 |

⇒ **六条原因里有两条是彻底错的**（"缺夹具" ✗ —— 夹具一直在测试里 ✓），另四条只对了一半 ✓。

### 1.2 试着兑现：2 个成功，4 个卡在**权限**

| 命令 | 结果 |
|------|------|
| **audit** | ✅ 搬进实测（`TestV62…/audit`） |
| **integrations** | ✅ 搬进实测（`TestV62…/integrations`） |
| build / typecheck / css / transform | ❌ `ConfigInvalid: permission denied: run:fake-engine` |

**卡住的真正原因**（这一版的主要发现）：

```go
// internal/testutils/testutils.go
// enginePermissions 是本测试二进制内已声明的引擎权限（见 AllowEngines）。
var enginePermissions []string

// AllowedEngines 返回已声明的引擎（供写入配置的注入实现读取）。
func AllowedEngines() []string { return enginePermissions }
```

> **那个"注入实现"不存在** ✗：`AllowedEngines()` 在整个仓库里**只有它自己的定义**——
> 调用它的产品代码一处也没有。于是 `AllowEngines` 是**一个死的测试钩子**：
> 声明了权限、写进了变量、没有人读，命令照样被权限层拒。

顺带量到一处**顺序陷阱**（写进了测试注释）：`AllowEngines` 要在 `isolateUserEnv` **之后**调 ✗——
不过这一版发现，顺序其实**无关紧要** ✓，因为那个钩子根本没接线 ✗。

## 5. 过程洞察

### 5.1 "具名"不够，还要"量过"

v0.59 把测不到的原因**具名**了 ✓ —— 但那些原因是**猜的** ✗：这一版一试，
两条彻底错（夹具一直在）、四条只对一半（夹具在，卡在别处）。

> 缺口表的价值在"具名"，而它的**准确度**只能靠**再去量一次**。
> 与 v0.56 的"先量再归类"、v0.57 的"按行为而非名字"同族。

### 5.2 一个不生效的钩子比没有更糟

`AllowEngines` 存在、有注释、有文档性的名字（`AllowedEngines`）——于是读代码的人会**以为**
引擎权限在测试里已经处理好了 ✗。真相是它声明进了一个没人读的变量 ✗。

> 与本系列反复出现的那条同源：**"看起来在处理"是比"没处理"更危险的状态**——
> 因为前者不会有人再去看第二眼。（v0.45 的"假跳过"、v0.52 的"登记看着空气"、v0.56 的
> "指针指到空气"都是同一个形状；这是它在**测试基础设施**里的第一次现形。）
