# v0.58 计划 — **散文里的发布读数必须对得上事实源**

> 范围来源：v0.57 复盘候选 0（本版排在最前的那条）——同步发布读数时**手抄**，
> 于是抓到一行偏了一个版本的读数（`docs/README` 写着"55 个 tag 里 GitHub 上有 51 个"，
> 真值是 57 与 53），而**没有任何判据看着散文里的计数**。
>
> 一句话目标：把"读数"也立成**有来源**的东西——能离线派生的就派生，
> 派生不出来的至少要**处处相同、且算术关系成立**。

---

## 0. 事实源（全部离线可得）

| 事实 | 来源 |
|------|------|
| 已交付版本数 | `docs/development/` 里的**复盘文件数**（项目纪律：每版一份） |
| 同上（交叉核对） | 同目录的**计划文件数**——两边必须相等，否则事实源本身不可信 |
| 最新版本 | 那些文件名里最大的版本号 |

**不依赖 `git tag`**：CI 的 checkout 默认是浅克隆（没有 tag），
在测试里跑 git 会让这条判据在 CI 上退化或误红。

## 1. 要核对的读数（六类）

1. **版本总数**（中文"五十七个 tag 均已打/全部已打" · 英文"all fifty-seven tags"）
2. **交付区间的右端**（"v0.1 ~ v0.57 均已交付" / "delivered in source"）
3. **GitHub release 数**（英文表 `N of M` · 中文行"57 个 tag 里，GitHub 上有 53 个" · roadmap 的"57 个里的 53 个"）
4. **Gitee 发行版数**（同上，另一行）
5. **缺口数**（"缺 54 个" / "Gitee 发行版（54 个）" / "共五十四个版本" / "fifty-four historical artifacts"）
6. **工作流成功次数**（"worked forty-nine times"）

## 2. 判据

- **每处总数**都必须等于派生值（这是能抓上一轮那行错的那一条）；
- **同一事实处处相同**（同一个数在两处写成两个数，是这类误差最典型的形态）；
- **算术关系成立**：`缺口 == 版本数 − Gitee 数`；`成功次数 == GitHub 数 − 从未发布的 4 个`；
- 范围守卫：一处读数都没扫到、或缺 GitHub/Gitee 读数、或一条带版本的交付声明都没有 ⇒ Fatal。

## 3. 验收

```bash
gofmt -l . && go vet ./... && go build ./...
go test -count=1 -run 'TestV58' -v ./cmd/ngm
go test -count=1 ./...          # 整套，不手挑
bash scripts/check-docs-links.sh
```

**牙齿**：① 复现上一轮那行真实误差（把总数改成 55）⇒ 红；
② 破坏缺口算术（54 → 53）⇒ 红；③ 复现判据首次运行抓到的那处陈旧读数（交付行退回 `v0.11`）⇒ 红。
