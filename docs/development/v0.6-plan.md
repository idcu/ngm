## A — 真实形态的可复现证据（ADR-017 门槛 a）

**目标**：把"合成夹具"这顶帽子摘掉。现有的 7 个形态里有插件链，但插件**是我们自己写的最小插件**；
真实项目必然打开的形态——**代码分割**、**资产指纹**、**多插件链**——一个都没测。

- [x] A1 新增形态（只用已在 CI 装好的引擎，不引入框架）：
      ①**代码分割**（esbuild `splitting` + 多入口 + 动态导入 → 共享 chunk）；
      ②**资产指纹**（`--asset-names=assets/[name]-[hash]`）；
      ③**三钩子插件链**（`onResolve` + `onLoad` + `onEnd`，且打开 splitting）。
      探针从 7 个形态扩到 **10 个门禁形态 + 3 个观察项**。
- [x] A2 **先测稳定性，再决定它进不进闸门**：把测量做成了探针的一个模式
      （`PROBE_STABILITY=20 bash scripts/probe-reproducibility.sh local`）——
      同一目录重复构建 N 轮、数"不同取值"的个数。结果：**10 个门禁形态在 20 轮里各只有 1 个取值** ✓；
      对照（每轮改一字节的源文件）给出 **20** 个取值 ✓，因此这台仪器被证明分辨得出字节差异。
      这条纪律来自 metafile 那一轮，而**那一轮的数字这次没有复现**（见下）。
- [x] A3 路径无关：`treeA == treeB` ✓（本机两次运行同为 `124f03b1de58091a`）。
- [ ] A4 跨机器：探针工作流的 `push.paths` 含探针文件本身，**推送即触发**；
      ⚠️ **本环境读不到 CI 结果**（无 `gh`、无 token），因此本项**如实标注为未取得**——
      不得由"工作流没红"推断为通过。裁决仍记为"门槛 a 只走完一半"。

> **A 组的两条附带产出**（都比形态本身更值得读）：
>
> 1. **一条旧结论被实测推翻**：v0.5 记的"原始 metafile 20 轮 20 个取值"**没有复现**
>    （38 入口、20 轮 → 1 个取值）。移出产物树的决定仍正确，但理由应读作"**路径内容**"。
>    已在 [ADR-013 第五批](../adr/adr-013-remote-adapter.md)、v0.5 复盘与探针注释三处标出更正。
> 2. **对照必须是"确定会变"的东西**：第一版拿原始 metafile 当稳定性对照，于是仪器当场报
>    `BLIND INSTRUMENT`（在那个环境里它确实不变）。对照的判据现在是精确的：
>    每轮改一字节 → 必须给出 N 个取值。

**验收**：新形态有稳定性实测数字（N 轮）与两路径一致 ✅；不稳定的已降级为观察项 ✅（无需降级）；
跨机器结论**如实标注为未读** ✅。

## B — 门禁可判别化：spawn 预算

**目标**：把 v0.5 的方法论结论（**次数优先于秒数**）从"口号"变成 CI 里的门禁。

v0.5 证明了 3s 目标**既拦不住退化、也证明不了优化**（跨机器状态方差 ≥0.3s > 本轮收益 0.45s）。
而 spawn 次数与机器状态无关（v0.5 实测：commit 2.00 / tag 3.00 次每依赖）。

- [x] B1 把"每依赖 spawn 次数"写成**预算断言**：`TestV06VerifySpawnBudget`（8 依赖 × 两种 refType）——
      commit 型 **≤ 2**、tag 型 **≤ 3**，另加一条下限断言（计数器必须真的在数，
      否则"永远返回 1"的坏实现会让门禁一路绿）。已纳入 CI 验收组。
- [x] B2 **验证断言有牙齿**：把"多记一次账"放回去（
      见下条），预算用例报出 `3.00` / `4.00` 并指出超出多少、以及"每次多出来的 spawn
      是每个依赖都付的成本"；同时 `TestSpawn_OnlyOneFileCountsSpawns` 也红。两条网都验证过。
- [x] B3 口径写进 [metrics](../internals/metrics.md)：**3s 目标不是门禁**（它在噪声里不可判别），
      次数才是；秒数栏保留为"用户等待时间"的观测值。

> **B 组开门第一天就抓到一次真实的记账错误**：预算用例第一次运行报出 commit **3.00** /
> tag **4.00**（本应是 2 / 3）。根因是 **v0.5 的 C 组留下的**——把 `CatFileBatch` 收进唯一的
> 构造点（那里计数）时，漏删了它自己那句记账调用，于是每个 `cat-file --batch` 被记两次账。
> 也就是说：**仪器在说谎**，而它是本版用来替代秒数的唯一指标。
> 处置：删掉重复记账，加 `TestSpawn_OnlyOneFileCountsSpawns`（扫源码：计账点唯一）——
> 与既有的 `TestSpawn_OnlyOneFileBuildsProcesses`（扫源码：构造点唯一）成为一对。
> 这件事被记进 [metrics](../internals/metrics.md#仪器也会说谎而且比没有仪器更糟v06-实录)，
> 因为它比数字本身有用：**指标只有在被门禁守着时才可信**。

**验收**：CI 里存在一条会因 spawn 增加而失败的断言；已用人为回归验证过它会红；
口径写进 metrics 与相关文档。

## C — store / mirror 的磁盘增长数据（**只测不做**）

**目标**：E2（内容寻址 store / mirror 的 GC）挂账的理由是"缺实测的磁盘增长数据"。
本版把这个数据补上，**不实现 GC**——有数据再排期。

- [x] C1 测量：`TestV06StoreGrowthInventory`——一个仓库、**12 个 commit、每个只改 1 个文件**。
      结果：content store **160.2 KiB/commit**（= 整棵树），源码真实增量的 **20.0×**；
      同一份历史的 Git 对象库只有 10.3 KiB，即 store 是它的 **187×**。
- [x] C2 数字写进 [metrics](../internals/metrics.md#磁盘增长内容寻址-storev06)，
      并据此给出判断——**做**，但**第一步是先立 ADR**：store 跨项目共享，
      "删哪些 digest 安全"是设计问题（见下）。**本版仍不实现 GC。**

> **C 组的结论为什么不是"直接开做"**：数据的确把 E2 从"缺数据"推到了"该排期"，
> 但"该做"与"能立刻动手"是两件事。`~/.ngm/content` 是**跨项目共享**的，
> 而默认 `hardlink` 落地模式下，已落地的 vendor 文件在 store 被删后仍读得到、
> 可 **`ngm verify` 会报层 2 缺失**——草率删除会把"完整性可验证"变成"可能已被别人删掉"。
> 因此它的下一步是一份 ADR（可达性 + 保留策略），不是一次提交。

**验收**：有实测数字 ✅；结论是"**做（先立 ADR）**"——三选一里最明确的那一个。

## D — 交付：Gitee 附件补传

**现状**：GitHub 侧 3 × 7 已就绪；Gitee 侧 21 个文件待人工上传，而
[安装指南](../guides/installation.md)把 Gitee 列为国内推荐源——**在传完之前那三版会 404**。

- [x] D1 把上传做成**一条命令**：`scripts/upload-gitee-assets.ps1`——**从 GitHub 取字节**
      （两个源必须是同一份字节；本地重编会得到另一份，那样"一致"就没法核对了），
      按 `SHA256SUMS` 逐个核对，上传后**再从 Gitee 下载一遍比对**；
      幂等（已存在且一致即跳过）、`-Force` 才覆盖、缺 token **明确失败且不动远端**。
      已验证：`-DryRun` 清单自洽（6 条 ↔ 6 个附件，v0.4.0 实测）、无 token 与坏 tag 均 exit 1；
      **上传路径未经真实令牌验证**（编写环境无 Gitee 凭据），已在脚本头与清单里写明。
- [x] D2 校验步骤写进[发布清单](./README.md)：第 3~5 步现在是一条命令 + `-DryRun` 预检，
      并写明"先 DryRun、再正式跑"的顺序与幂等语义。
- [ ] D3 **实际传入 21 个附件**（`v0.2.0` / `v0.3.0` / `v0.4.0` 各 7 个）——
      **卡在凭据上**：需要 `GITEE_TOKEN`（本环境没有）。在此之前那三版对国内用户仍取不到。
- [ ] D4 传完后把结果（日期 + 抽查的 `sha256`）补进发布清单的补发记录表。

**验收**：脚本在缺 token 时明确失败 ✅；有 token 时一条命令传完并打印校验结果 ✅（工具就绪）；
清单里的手工步骤只剩"填 token、跑命令、看输出" ✅。
**D 组未完成的部分不是工程，是凭据**——这一点写在验收里，免得下次读到时误判为"没做"。

## 本版明确不做（避免范围蔓延）

| 方向 | 为什么不是现在 |
|------|---------------|
| 实现 `remote` adapter | [ADR-017](../adr/adr-017-remote-adapter-release-decision.md) 的门槛 a / b 都未成立；技术可行 ≠ 要发布 |
| 实现 store / mirror 的 GC | 等 C 组的数据 |
| 重新定义 3s 目标本身的数值 | 本版先让**次数**成为门禁（B 组），秒数口径的改动等次数门禁稳定后再谈 |
| `read:` / `write:` 在 ngm 自身路径上的施加 | 只有出现真实拦停需求才动（v0.5 的裁决，见[安全模型](../architecture/security-model.md)） |
| 路线图"后续探索（不承诺）"里的方向 | 均无实测需求支撑 |
