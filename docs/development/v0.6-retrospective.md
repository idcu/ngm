### 1.1 A — 真实形态的可复现证据（ADR-017 门槛 a 的一半）

| 新增形态 | 它代表的真实做法 | 本机结果 |
|----------|----------------|---------|
| **代码分割**（两入口 + 动态导入 → 共享 chunk） | 路由级懒加载；chunk 名里带内容哈希 | 两路径一致 ✓ · 20 轮稳定 ✓ |
| **资产指纹**（`--asset-names=assets/[name]-[hash]`） | Vite 对静态资源的默认命名 | 同上 ✓ |
| **三钩子插件链**（`onResolve` + `onLoad` + `onEnd` + splitting） | Vite / Astro 的插件组合 | 同上 ✓ |

探针从 7 个形态扩到 **10 个门禁形态 + 3 个观察项**；本机两次运行给出同一
`treeA=124f03b1de58091a`。

**先测稳定性，再决定进不进闸门**——本批把它做成了探针的一个模式（A2）：


| 项 | 结果 |
|----|------|
| 10 个门禁形态（同一目录重复 20 轮） | 各 **1** 个取值 → STABLE ✓ |
| 对照（每轮改一字节的源文件） | **20** 个取值 → 仪器被证明分辨得出字节差异 ✓ |

**A4（跨机器）已取得**（2026-10-02）：推送触发的 `repro-probe`（`9324266`）**三平台全绿**，
compare 报：

```
REPRODUCIBLE ACROSS MACHINES: 3 platform(s) agree on treeA=124f03b1de58091a (esbuild=0.28.2, tsc=5.6.3)
```

逐形态也逐个相同（三个新形态在三平台同值）：`esbuild-split=805bb7be…`、

**CI 的 `treeA` 与本机 Windows 那次完全相同**——跨机器这一维因此是 **3 个 runner + 1 台开发机**。

> 方法上值得记一句：这三行是**读出来的**，不是由"工作流没红"推断的。三份
> `probe-result.json` 都取回本机，用仓库自己的 `scripts/compare-probe-results.mjs`

> 拿到凭据后第一件事就是回来补上——**"没测出来"不许读成"通过"**，这是本项目的老纪律。

#### 一条旧结论**不复现**，因此被更正（本版最重要的一条）

v0.5 记着"原始 metafile 20 轮 **20** 个取值"，并据此把 metafile 移出产物树、降级为观察项。
v0.6 复测**不支持**这句话：esbuild 0.28.2、空闲 Windows、**38 个入口**、20 轮，
原始 metafile 与产物**都只有 1 个取值**。

- 移出产物树的**决定仍然正确**，但理由应读作"**路径内容**随机器/目录变化"
  （macOS 的 `/var` 符号链接 + 插件传绝对路径），而不是"字节抖动"。那一半在 CI 上可复现。
- 更正写进了**三处**：[ADR-013 第五批](../adr/adr-013-remote-adapter.md)、
  [v0.5 复盘](./v0.5-retrospective.md) 的同一段、以及探针里那段注释本身。
- 它同时改了对照的设计（见 §5.2）：把一个**在本机不复现**的东西当对照，
  只会让新装的稳定性仪器永远报"瞎"——**而它当时确实这么报了**。

### 1.2 B — spawn 预算：门禁开门第一天就抓到一次记账错误

**预算（现在是一条 CI 门禁）** `TestV06VerifySpawnBudget`：一次完整在线 verify、
8 个依赖 × 两种 refType：

| 形态 | 每依赖 spawn | 预算 | 构成 |
|------|-------------|------|------|
| commit 型 | **2.00** | ≤ 2 | `ls-tree` + `cat-file --batch` |
| tag 型 | **3.00** | ≤ 3 | 上面 2 次 + `ls-remote` |

另加一条**下限**断言（`>= 依赖数`）：只写上界的话，"计数器坏了、永远返回 1"这类实现
会让门禁一路绿——**那正是本版要治的病**。

**它第一次运行就报出 commit `3.00` / tag `4.00`**（本应是 2 / 3）。查下去发现
**不是代码变慢，而是仪器在说谎**：v0.5 的 C 组把 `CatFileBatch` 从"自己 exec"收进
唯一的构造点（那里计数）时，**漏删了它自己那句记账调用**，于是每个 `cat-file --batch`
被记两次账。

- **为什么藏了一个版本**：门禁断言测的是"该不该起"（拒绝了几个），计数偏高它看不出来；
  而唯一的读数只被 `t.Logf` 打印、从不作断言（"印出来不等于被检查"，v0.5 复盘 §5.2）。
- **处置**：删掉重复记账，并加两条**互相独立**的网——①预算用例（管"起了几个"）；
  ②`TestSpawn_OnlyOneFileCountsSpawns`（扫源码，管"只能在一个地方记账"），
  与既有的 `TestSpawn_OnlyOneFileBuildsProcesses`（守"构造点唯一"）成为一对。
- **两条都验证过有牙齿**：把重复记账放回去，预算报 `3.00` / `4.00`、不变量报
  "catfile.go counts a spawn outside spawn.go"，两条同时红 ✓。
- 预算已纳入 CI 验收组；[metrics](../internals/metrics.md#仪器也会说谎而且比没有仪器更糟v06-实录)
  记下了这件事，因为**它比数字本身有用**。

**口径（B3）**：**3s 目标不是门禁**（它在噪声里不可判别，v0.5 已证），次数才是。
秒数栏保留为"用户等待时间"的观测值。

**三平台复测**（这是"次数门禁"真正该有的性质——与机器无关）：

| 平台 | commit 型 | tag 型 | 预算 |
|------|----------|-------|------|
| Windows x86_64 | 2.00 | 3.00 | ≤ 2 / ≤ 3 |
| macOS arm64 | 2.00 | 3.00 | 同上 |
| Ubuntu x86_64 | 2.00 | 3.00 | 同上 |

三处都 PASS，且数字**完全相同**——对比之下，v0.5 的秒数在同一台机器上两轮就差 0.3s。
它顺带证明了另一件事：[ADR-016](../adr/adr-016-mirror-url-local-read.md) 的"读 config 文件"
快路径在**三个平台上都生效**（否则 tag 型会是 4.00）。

### 1.3 C — store 增长：数据到手的结论是"做，但先立 ADR"

证据用例 `TestV06StoreGrowthInventory`（**只测不做**）：一个仓库、12 个 commit、
每个只改 1 个文件（树 = 20 文件 × 8 KiB）。

| 量 | 值 |
|----|----|
| content store（12 commit 后） | **1.88 MiB**（**160.2 KiB/commit**，恰好是整棵树） |
| 同期源码的**真实增量** | 96.0 KiB |
| 放大比 | **20.0×** |
| 同一份历史的 Git 对象库（层 1 上界） | 10.3 KiB → store 是它的 **187×** |

**为什么不去重**：布局是 `content/sha256/<digest>/tree/`，**按整棵树**寻址，
所以同一仓库的每个新 commit 都完整复制一遍内容树。两层分工很清楚：
**层 1 有 `git gc` 可跑，层 2 没有任何人回收——只增不减。**

**结论：数据支持排期做 GC，但第一步不是写代码，而是先立 ADR**：store 跨项目共享
（`~/.ngm/content`），"删哪些 digest 安全"是设计问题——默认 `hardlink` 模式下，
已落地的 vendor 文件在 store 被删后仍读得到，但 **`ngm verify` 会报层 2 缺失**。
草率删除会把"完整性可验证"变成"可能已经被别人删掉"。数字与方法见
[metrics](../internals/metrics.md#磁盘增长内容寻址-storev06)，[ADR-003](../adr/adr-003-vendor.md)
的补录也据此更新（挂账理由从"缺数据"变为"缺一个决策"）。

### 1.4 D — Gitee 补传：**已完成**（三版各 7/7，两源已比对）

`scripts/upload-gitee-assets.ps1`：**从 GitHub 取字节**（两个源必须是同一份字节；
本地重编会得到另一份，那样"一致"就没法核对了）→ 按 `SHA256SUMS`（同一个文件）逐个核对
→ 上传后**再从 Gitee 下载一遍比对**。

| 已验证 | 结果 |
|--------|------|
| `-DryRun`（v0.4.0，真实 GitHub API） | 列出 7 个附件；清单自洽 **6 条 ↔ 6 个附件** ✓ |
| 无 token 时 | **exit 1** 且明确说明"本次没有改动任何东西" ✓ |
| 不存在的 tag | **exit 1** 并提示"先让 release 工作流跑完" ✓ |
| **真实上传（2026-10-02）** | `v0.2.0` / `v0.3.0` / `v0.4.0` 各 **7/7**：6 个二进制 + `SHA256SUMS`，**每个都从 Gitee 取回重新核对** sha256 ✓ |
| **两源直接抽查（D4）** | 三个 tag 的 `SHA256SUMS` 在 Gitee 与 GitHub 上**逐字节相同**；抽查 `v0.4.0` 的 `ngm-linux-amd64`（从 Gitee 下载）= `2b2dd4f422fbb8a8…`，与清单里的值**完全一致** ✓ |

**过程中查出并修掉三处脚本缺陷**（都是 Gitee API 的坑，已写进发布清单）：
`target_commitish` 必须是分支名（写成 tag 名时 Gitee **不报错**、回一个没有 `id` 的 JSON）；
"release 不存在"返回 JSON `null` 而 PS 5.1 把它变成字符串 `"null"`（"查不到"判不出来）；
字符串 body 按 ISO-8859-1 编码使中文变 `???`。另有两处改进：下载重试
（本机到 github.com 的连通性实测会抖，`curl: (28)` 重试 4 次仍失败）、
`-GitHubProxy`（**清单仍优先直连取得**——它是校验的信任锚）。

**幂等**：同名附件已存在且 sha256 一致时跳过（重跑安全）；不一致时**报错并让你决定**，
`-Force` 才覆盖——绝不静默覆盖。发布清单里"21 个文件逐个下载再上传"的手工步骤
因此变成**三条命令**（每个 tag：DryRun → 设 token → 正式跑），
**剩下要人做的只有"填 token、跑命令、看输出"**。

## 3. 设计偏离登记

| # | 计划原话 | 实际做法 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | A2：新形态本机跑 N 轮测稳定性 | 把它做成了探针的**模式**（`PROBE_STABILITY`），并给它配了对照 | 一次性的临时测量无法被别人复现；而定型成模式之后，"形态进闸门前的必做测量"就成了一条路径而不是一段记忆 |
| 2 | A2：不稳定的一律降为观察项 | 10 个形态都稳定，**没有降级**；但把"对照"从原始 metafile 换成了"每轮改一字节" | 原计划隐含"metafile 不稳定"这个前提，而它**不复现**；一个在该环境不会失败的对照等于没有对照 |
| 3 | B1：预算用"在线 verify（100 依赖）" | 用 **8 个依赖** | 每依赖的**斜率**才是被断言的量，8 个足够让"每依赖多一次"无法被常数项吸收；100 依赖会把这个用例变成分钟级 |
| 4 | C2：据数字给出"做/不做/等数据" | 给出"**做，但先立 ADR**" | 数据解决的是"要不要"，而跨项目共享的 store 还需要"删什么安全"——那是设计决策，混进实现里会变成一个没人审过的删除策略 |
| 5 | D1：一条命令上传 | 加了 `-DryRun` 预检与**幂等**语义 | 上传是**不可逆的远端写**；"先看清要做什么"与"重跑安全"是这类命令的两个基本要求 |
| 6 | ADR-013 第四批：metafile 字节不稳定 | 保留原文，加**更正**指向第五批 | 决策快照不改写；但**不可复现的实测不能继续当结论用**，尤其它正被引用来支撑一个门禁设计 |

## 5. 过程洞察

### 5.1 仪器也需要门禁

`git.SpawnCount()` 在 v0.5 被装上时**没有任何不变量守着**，于是"第二个记账点"
可以在一个版本里安静地存在——而它是本版用来**替代秒数的唯一指标**。
现在两个方向都有网：构造点唯一（`exec.Command` 只许出现在 `spawn.go`）、
计账点唯一（`noteSpawn()` 只许出现在 `spawn.go`）。

> 更一般的说法：**一个被用来判定的量，自己也需要被判定。**

### 5.2 对照必须"确定会变"

第一版稳定性对照用的是"原始 metafile"——一个**在该环境里不变**的东西。
空跑保护当场把它拦下来了：`BLIND INSTRUMENT: the control came out STABLE`。
若没有这条保护，"10 个形态全部稳定"这个结论**看起来完全正常**，而它什么都没证明。

> 对照的判据要写成**精确的等式**（N 轮 → N 个取值），不能写成"应该有多个取值"。

### 5.3 不可复现的实测不能当结论

v0.5 的 metafile 数字当时或许真测到过（负载不同、并行完成顺序不同），
但它**今天在这台机器上复现不出来**。这类结论的危险在于：它会被后来的人**引用来解释现象**，
甚至支撑一个设计决定。处置方式不是删掉它，而是**保留原文 + 加更正 + 指明现在的理由是什么**。

### 5.4 读不到的 CI 不能算通过

A4 的工作流**已经触发**（推送含探针文件），但没有凭据就看不到结果。
"没红"与"通过"在这里必须严格分开——这与本项目反复防的"没测出来读成通过"是同一类。

### 5.5 跨工具边界的编码问题

`.ps1` 无 BOM 的 UTF-8 在 PS 5.1 下被按 ANSI 解码：中文乱码只是表面，**它会吃掉引号、
造成语法错误**。同类的边界还有：Git Bash 的 `/tmp` 与 Windows 路径、
`curl` 对 `-F file=@` 里反斜杠的处理。**跨工具时，把"人看着一样"的东西当成一样是危险的。**

### 5.6 我这一版犯的两处错

- **行尾转换用错了工具**（§4.6）：多层 shell + 转义 = 反斜杠丢失，而后果是静默改坏文件内容。
  教训：能交给目标工具自己做的（PowerShell 的字符串替换），不要经过两层转义。
- **没先在本机把 `.ps1` 跑一遍就写完了它**：编码问题在第一次运行才暴露。
  教训与 §5.5 同源——**新脚本的第一次运行应当发生在写它的人的机器上**。
