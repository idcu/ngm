# v0.55 复盘 — **子命令之前的 flag 不许被静默丢弃**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：`ngm --json verify` 从前**进得去、出不来**——token 被 `head` 吞掉，
> 命令照常跑完，用户要 JSON 却拿到人读文本，而退出码是 **0**、stderr **0 字节**。
> 这一版把根级白名单立成一张**运行时表**，其余 token 一律拒绝，并让 v0.54 的信封
> 自动跟上（"你把 flag 写错位置了"也是机器可读的）。登记表 **6 → 5**。

---

## 1. 逐组验收

### 1.1 起点：量出"走错通道、还一声不响"

在**有 lock 的项目**上（这个前提很重要，见 §1.2）：

| 调用 | 读数 | 归属 |
|------|------|------|
| `verify --json`（对照） | exit 0 · stdout **JSON 报告** 1104 字节 | 正确位置 |
| `verify`（对照） | exit 0 · stdout **人读文本** 91 字节 | 正确位置（没要 JSON） |
| **`--json verify`** | exit 0 · stdout **人读文本** 91 字节 · stderr **0 字节** | **最坏的一种** |
| `--bogus verify` | exit 0 · 人读文本 · stderr 0 字节 | 未知根级 flag **被静默忽略** |
| `-- verify` | 同上 | 裸分隔符同样被吞 |

它**不是** v0.54 那类"解析失败"，也不是"命令不存在"——是 **`dispatch` 自己**：
`head`（子命令之前的 token）里只认三个白名单值，其余**进了 head 就没有下文**。

> 失败有三种便宜的形状：报错、静默失败、**静默成功**。
> 这一条是最坏的那种——**走错通道、还一声不响**：脚本拿到散文、退出码还是 0，
> 连"出事了"都不知道。

### 1.2 夹具的第一版不够硬（牙齿 A 替我发现的）

第一版形状用例跑在一个**空项目**上。牙齿 A（把静默丢弃放回去）红了——红在
"stderr 没有说清"上，而**"退 3"那条断言没响**：空项目上 `verify` **自己也退 3** ✗。

也就是说那条断言分不出"拒绝了"与"命令自己失败了" ✗。
改成**共享一个能成功的项目**之后，牙齿 A 报出的是：

```text
exit = 0，想要 3（根级用法错误）——**静默丢弃**回来了?
提了 --json 的根级错误没有给信封（invalid character '✓' looking for beginning of value）
```

第二行尤其好：**JSON 解析器在 stdout 上撞见了 `✓`**——那正是"要 JSON 却拿到人读报告"
这件事本身。

### 1.3 处置：白名单立成**运行时表**，其余一律拒绝

```go
// rootFlags 是根级**唯一**接受的 token（v0.55 立成一张表）。
var rootFlags = map[string]bool{"--version": true, "-h": true, "--help": true}
```

`dispatch` 照着它校验 ✓；v0.55 那条判据也**从它取**"哪些该被接受" ✓。
校验与动手是**两个循环**（先全部核对、再执行）——否则 `--version --bogus` 与
`--bogus --version` 会给不同结果，而"顺序敏感"不是一条能记住的规则。

用户看到的东西：

```text
$ ngm --json verify                 （改前：exit 0 · 人读报告）
unknown root flag: --json           ← stderr
{"version":1,"error":{"code":"Usage","exitCode":3,"message":"unknown root flag: --json",
  "hint":"root level accepts only --help/--version; a command's flags go after the command (e.g. `ngm verify --json`)"}}
```

**退出码 3**、人读那侧说清了是哪个 token、机器那侧给了一份**能照着做**的信封 ✓
（v0.54 的信封在这里第二次派上用场：它让"你把 flag 写错位置了"也是机器可读的）。

### 1.4 判据 ✅

读数：**5 种形状被拒 · 顺序无关 · 对照不变**，另有**派生的样本**逐个命令跑过。

| 组 | 内容 |
|----|------|
| 形状 | `--json` · `--bogus` · `--dir=<p>` · 裸 `--` · **连子命令都没有** |
| 顺序 | 两种写法结果必须一致，且都退 3 |
| 白名单对照 | **遍历 `rootFlags`**（不手抄）——每个都必须仍被接受、且仍有输出 |
| 派生样本 | **每个命令的第一个布尔 flag** 放到命令之前 ⇒ 必须被拒 |

### 1.5 牙齿 ✅

| 探针 | 结果 |
|------|------|
| 把"静默丢弃"放回去 | 红：四种形状都报 `exit = 0，想要 3`；`--json` 那条报"JSON 解析器撞见 `✓`" |
| 把"校验"与"动手"合成一次 | 红：`` `--version --bogus` 退 0，而 `--bogus --version` 退 3 `` |

## 2. 一处红是**好的红**（v0.53 的纪律）

我在这版登记表里写了"来源：运行时白名单" ✗——而 v0.53 那条纪律**当场抓到那是假的**：
`root_flag_placement_test.go` 里当时**没有读任何源码或运行时表** ✗。

处置不是"加一条具名例外" ✗，而是**让来源真的成立** ✓：

1. 白名单从散在 `switch` 里的三个 `case` 变成**运行时表** `rootFlags` ✓（`dispatch` 读它 ✓）；
2. 拒绝一侧的样本从派生表取（`boolFlagsOfCommand`）✓。

> **登记写着"来自运行时"，那它就得真的读运行时**——这条纪律的价值不在"填过表"，
> 而在"填的内容会被核对"。它与 v0.46 那条"覆盖集从哪来"是同一件事的第三次现形。

## 3. 判据自己的一处不完整（也修了）

派生样本里 `why` 与 `engines` 的第一个布尔 flag **正好就是 `--json`** ✗——
于是那两个用例里用户**确实提了** `--json` ✓，而我断言了"stdout 必须为空" ✗。

它不是特例 ✓：那是**同一条规则**在两种输入下的两半 ✓——提了就写信封、没提就留空 ✓。
改成按 `tok` 判断之后，派生样本同时覆盖了两半 ✓。

## 6. 过程洞察

### 6.1 判据的夹具决定判据的牙齿

第一版形状用例跑在空项目上，"退 3"那条断言**看起来在查、其实查不出东西** ✗：
被测命令自己也会退 3 ✗。换成能成功的项目之后，同一条断言立刻变成精确的 ✓。

> 这与 v0.53 那条"判据要照着**事实**判、不是照着字面判"是同一族：
> **断言要在一个能把两种原因分开的世界里跑**，否则它只是在数一个恒等于真的等式。

剩下的 5 条：2 条"未做"（`tree` 去重需先立 ADR · 联网复核需真实网络）+
**3 条"故意"**（`duration.go` 的 10 处不带建议、internal 的 118 处空 hint、
4 个 GitHub release 与 51 个 Gitee 发行版已暂缓）✓——
