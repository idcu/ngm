## 0. 起点：那件没有被写进任何文档的事

2026-01-26，Koi Security 披露 **PackageGate**（评估报告 §4.2）：

- npm / pnpm / vlt / Bun 共 **6 个零日**；
- 其中 **npm 那一条正是"Git 依赖的恶意 `.npmrc` 覆盖 git 二进制路径 →
  绕过 `--ignore-scripts` 实现 RCE"**；
- pnpm（2 周，2 个 CVE）、vlt（8 天）、Bun（3 周）都修了；
- **npm 以 "works as expected" 关闭了报告**——"用户有责任审查自己安装的包"。

而 ngm 的 `docs/COMPETITIVE-ANALYSIS.md`（事实截止 2026-09-29）**完全没有提到它**，
README 也没有。**一个把全部赌注押在"Git 依赖安全"上的项目，错过了 9 个月前发生的、
由对手官方背书的验证。**

## 1. 处置

1. **`COMPETITIVE-ANALYSIS.md`**：在"Git 依赖安全控制点"之后新增一节 PackageGate——
   事故本身 + **为什么 ngm 在这条路径上天然免疫**（三点，逐条可核对到代码）。
2. **README（根）**：加"为什么用 ngm"（现在只有"为什么你可能不应该用"）——
   以 PackageGate 开头；并补一节"什么时候你该用 / 不该用"。
3. **可执行的对照 demo**（`scripts/packagegate-demo.sh` + Windows 入口 `.ps1`）：
   同一份"含 `.npmrc` 与 postinstall 的 Git 依赖"，在 npm 侧与 ngm 侧分别发生什么。
   - ngm 侧是**可断言**的（脚本未执行、`.npmrc` 只是被 vendor 的普通文件）；
   - npm 侧默认只做**静态对照**（版本行为不同，硬断言会是假证据），
     `--with-npm` 开关留给有 npm 的人自己跑、自己看。
4. 不写"ngm 更安全"这类无法证伪的话：写的每一条都要能指到一处代码/一条命令。

## 2. 验收

```bash
bash scripts/packagegate-demo.sh          # 本机（git bash）实跑一遍
go test -count=1 ./...                    # 全量（文档改动的机械网都在这套里）
bash scripts/check-docs-links.sh
```

**牙齿**：demo 里的每条 ngm 侧断言都要能红（把恶意 fixture 的某处改坏 ⇒ 断言失败）。
