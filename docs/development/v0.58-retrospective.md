# v0.58 复盘 — **散文里的发布读数必须对得上事实源**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：把"发布读数"立成**有来源**的东西——能离线派生的派生，
> 派生不出来的至少要求**处处相同、算术自洽**。
> 判据的**第一次运行就抓到一处真的陈旧读数**（roadmap 里写着"v0.1 ~ **v0.11** 均已交付"，
> 那是 45 个版本前的说法），而它此后成了回归用例。

## 1. 逐组验收

### 1.1 起点：手抄会漂，而没人看着

v0.57 同步发布读数时抓到一行偏了一个版本的：

```text
docs/README.md:  "55 个 tag 里，GitHub 上有 **51 个** release"      ← 真值是 57 与 53
```

而当时的核对只有 `scripts/check-release-status.sh`——它查的是
**"tag 与 release 是否存在"**（以及"每个 tag 都有复盘"），**不是散文里的计数**。
于是这类误差只能靠下一次同步时的人眼发现。

### 1.2 事实源：全部离线可得

| 事实 | 来源 | 读数 |
|------|------|------|
| 已交付版本数 | `docs/development/` 的**复盘文件数** | **57** |
| 同上（交叉核对） | 同目录的**计划文件数** | **57** ✓ 相符 |
| 最新版本 | 那些文件名里最大的版本号 | **v0.57** |

**刻意不依赖 `git tag`**（虽然本地数出来也是 57）：CI 的 checkout 默认浅克隆，
没有 tag——在测试里跑 git 会让这条判据在 CI 上退化或误红。

### 1.3 判据：六类读数、三种写法

| 判据 | 抓的是 |
|------|-------|
| 每处**总数** == 派生值 | 上一轮那行错（55 ≠ 57） |
| 同一事实**处处相同** | "同一个数在两处写成两个数"——两处只要不同，至少一处是错的 |
| **算术关系**：缺口 == 版本数 − Gitee 数 | "缺 54 个" · "Gitee 发行版（54 个）" · "共五十四个版本" · "fifty-four historical artifacts" 四处联动 |
| **算术关系**：成功次数 == GitHub 数 − 从未发布的 4 个 | "worked forty-nine times" |
| 交付区间右端 == 最新版本 | 陈旧状态行 |

读数：**18 处（含 4 条交付行）· 57/53/3/54** 全自洽 ✅

### 1.4 判据的第一次运行就抓到一处**真的**陈旧读数 ✅

```text
docs/internals/roadmap.md:  **v0.1 ~ v0.11 均已交付**          ← 45 个版本前的说法
```

它一直在那里，而没有任何判据问过它。这一版把它改成 `v0.1 ~ v0.57`，
并在牙齿 C 里把"退回 `v0.11`"变成一条回归用例。

### 1.5 牙齿三道 ✅

| 探针 | 结果 |
|------|------|
| **复现上一轮那行真实误差**（总数 55 / GitHub 51） | 红，且**双重命中**：`里的总数是 55，而事实源是 57` ＋ `GitHub 的 release 数这里写 51，别处写 53——同一件事有两份读数` |
| 破坏缺口算术（`共五十四个版本` → 五十三个） | 红：`` `共 N 个版本` 写着 53，而 版本数(57) − Gitee(3) = 54 `` |
| 复现首次运行抓到的那处（交付行退回 `v0.11`） | 红：`交付区间的右端写着 v0.11，而事实源里最新的版本是 v0.57` |

### 1.6 判据自己改了三处（如实记）

| # | 第一版怎么错的 | 怎么改的 |
|---|--------------|---------|
| 1 | 版本区间**按全文匹配** ⇒ 把"从未发布的那四个 tag"、"Gitee 只有 `v0.1.0` 与 `v0.5.0` ~ …"也当成交付声明 | 只在**含"均已交付"/"delivered in source"的那一句**里查 |
| 2 | 中文总数模式太宽 ⇒ 在发布清单里报到历史陈述"那**四个** tag"与表格单元"两组均已交付" | 要求"个 tag 均**已**/**全部**"；跳过表格行；无版本号的交付句跳过 |
| 3 | **正则的填充类把数字吃掉了**：`[^，。\n]{0,6}` 贪婪吃掉" 有 5"，`(\d+)` 只匹配到 `7` | 填充类**排除数字**（`[^，。\n\d]{0,6}`）——探针一条就照出来了 |

> 第 3 条最值得记：**正则读出来的数与文件里的不一样** ✗——而这条判据的整个价值
> 就在"读出来的数要对"。它的症状（报了个文件里根本没有的 `7`）看起来像文档错，
> 实际是**读的人**错。**读数说谎的第四种形态：不是写错，是读错。**

## 5. 过程洞察

### 5.1 记账之外，还要给记账本身找来源

v0.57 的主题是"**来源要按行为派生**"，这一版把它用到**文档里的数字**上：
数字也是一种"覆盖集"——它描述事实，就该有事实源。
凡是**能离线派生的**（版本数、最新版本）就派生；派生不出来的
（GitHub/Gitee 的个数）至少要**处处相同、算术自洽**——那已经足够抓住上一轮那类误差。

> "同一件事有两份读数"本身就是一种可检的错：**两处只要不同，至少一处是错的**，
> 不需要知道哪一处对。

### 5.2 读数会说谎的第四种形态：**读错**

前三版记过三种（写错 · 漏写 · 释义不全），这一版是第四种：**判据自己读错** ✗。
症状很典型——它报了一个文件里根本不存在的数字（`7`），看起来像文档错了，
实际是正则的填充类贪婪地把数字吃掉了一半。

> **判据的读数也要能被核对**：一条探针（把那行原样喂进去、把匹配组打出来）
> 比读十遍正则便宜。

### 5.3 判据在**我自己**头上抓到一个错（交付时刻）

v0.58.0 发布后同步读数时，我把缺口那几处（`缺 N 个` · `Gitee 发行版（N 个）` ·
`共 N 个版本` · `N historical artifacts`）从 **55** 改成了 54 ✗——
理由是"release 数涨了一个" ✗。

而缺口是 `版本数 − Gitee 数`：**Gitee 侧一个也没变**，所以它一直是 **55** ✓。
判据当场报了**五处**同时红：

```text
`缺 N 个` 写着 54，而 版本数(58) − Gitee(3) = 55
`Gitee 发行版（N 个）` 写着 54，而 … = 55
`共 N 个版本` 写着 54，而 … = 55
`N historical artifacts` 写着 54，而 … = 55
```

> 也就是说：**我对自己写的这些数的模型是错的**，而算术关系把它抓住了。
> 这正是这类判据的价值所在——**不在于替我记住约定，而在于让写错的人当场看见**。
