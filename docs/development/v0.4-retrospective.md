> 结论：**v0.3 复盘的三条建议逐条落地，v0.3 计划里最后一个未打勾的框也结项了**。
> 新增 `ngm typedecl` 与 `ngm verify --signatures / --require-signed`；
> 立 ADR-014 并记录 ADR-013 翻案条件的实测进展。三平台 CI 全绿。
>
> 本轮三个交付里有两个是**先测、再决定**，而它们各自都产生了与预期不同的结果——

## 1. 逐条对照 v0.3 复盘的建议

| 建议 | 落地 | 证据 |
|------|------|------|
| 1. 把"声明了、没接线"做成机械检查 | ✅ `cmd/ngm/config_coverage_test.go` | `TestConfigKeysAreExercisedByTests`（含**双向**性质） |
| 2. 继续扩真工具验收 | ✅ `typedecl` 走**真 tsc** | `TestV04RealTscTypeDecl` |
| 3. ADR 里的实测数字必须对应实际使用的版本 | ✅ 已同步（v1.9.0 / +3.42 MB） | [ADR-011 §实现记录](../adr/adr-011-wasm-runtime.md) |
| 4. "决定不发布"按交付物处理 | ✅ 留 ADR + 可证伪翻案条件 + 工具说出决定 | [ADR-014](../adr/adr-014-self-report-signatures.md) |

### 1.1 建议 1 落地的样子

每个**多段驼峰**配置键（如 `verifyOnLock`、`minimumReleaseAge`、`tokenEnvVars`）
必须在某个测试里被碰过；接受三种"确实在设置这个字段"的形态——JSON 键 ✓、结构体字段选择器 ✓、
结构体字面量键 ✓。豁免清单**只允许变短**：一个键一旦被覆盖却还留在豁免里，检查会失败
（防止"修好了没人删豁免"，久了清单就没人信）。

**它拦不住什么**写在测试里 ✗：单段名（`permissions` 正是这么漏的 ✓）、
"出现了但没断言行为" ✗、以及非 JSON 的配置面（结构体字段 / flag）✗。

判据定在"能做到"的地方，而不是"听起来严格"的地方——后者需要人工维护，
而人工清单在这个项目里已经连续失效三次 ✓。

## 2. 本轮发现并修复的缺陷

| # | 缺陷 | 由什么发现 | 影响 |
|---|------|-----------|------|
| 1 | **`git.tokenEnvVars` 从未被读取**：`newProjectEnv` 在**读配置之前**调用 `MergeTokenEnvVars(nil)`，用户写的 host → 环境变量名映射一条都不生效 | 新加的配置覆盖检查首次运行 | **落在安全路径上** ✗：用户以为自己的 token 已被脱敏，实际会原样打进日志与报错。这是同类缺陷的第 4 例 |
| 2 | `TypeDeclResult.Files` 列输出目录时按**进程 CWD** 解析 | 写 `typedecl` 的行为断言时 | 引擎在项目目录里写了文件、ngm 却在别处找 → 症状不是报错而是一句错话："文件明明在那儿，却说没有产出" |
| 3 | `--json --sandbox` 把沙箱段落写进 **stdout** | 为新加段落设计输出纪律时回看既有代码 | 污染了那份"CI should use this"的 JSON ✓ |

（其中 #1 位于**已发布代码**里；#2、#3 是本轮新增代码里的缺陷，在写断言时发现。）

### 重复出现的错误形态（第二次确认）

| 时间 | 位置 | 症状 |
|------|------|------|
| v0.3 A | 清单校验按 CWD 找 wasm 模块 | 存在的模块被报成"找不到" ✗ |
| v0.4 | `Files` 按 CWD 列输出目录 | 引擎写了文件、ngm 说"没产出" ✗ |

共同点：**配置/命令行里的相对路径，本该相对项目目录，却相对了进程 CWD**。
它不崩 ✗，只给出一个"看起来合理但相反"的结论 ✓ ——比崩溃难发现得多 ✓。
`--dir=` 的存在本身就说明这两者可以不同 ✓，因此这类地方必须显式带基准 ✓。

### 文档漂移（本轮第三批）

改 `observability.md` 时发现：命令表里 `why` / `tree` / `outdated` / `audit`
仍标着 **"planned (v0.2)"、"当前 exit 3"** ✗ ——v0.2 就把它们交付了 ✓；
verify 自己的退出码表**漏了 5**（`--sandbox` 缺 Deno 时返回它 ✓）。

规律很清楚 ✓：**一个版本交付后，散落在各页的散文表格会滞后** ✓。
本轮已把"文档说没做、实际做了"与反向的错误同样对待 ✓ ——
前者同样有害：它会让读者绕过一条已经可用的命令 ✓。

## 3. 过程洞察

### 3.1 这一版的性质变了

v0.1–v0.3 是"造能力" ✓；v0.4 是"证明能力" ✓✓。四个交付里三个由**测量**驱动：

- 签名检查 —— 先答 ADR-013 的三个问题，再决定"不做"
- 机械化检查 —— 直接来自 v0.3 复盘的建议 1 ✓
- 可复现性第二批 —— 检验"用户能否本地复现远端产物" ✓

**测量推翻了我两处"以为"** ✓✓：esbuild alias 不是精确匹配 ✗；sourcemap 不嵌绝对路径 ✗。
两次都是**朝好的方向** ✓ ——但这不改变"先写断言、再被推翻"这件事本身应当被记录 ✓：
**先猜后测的两种下场都值得写下来** ✓。

### 3.2 机器检查的有效性与边界

它**首次运行就抓到一个真缺陷** ✓✓（第 4 例 ✓，且在安全路径上 ✗）。但它**有盲区** ✓：
单段名拦不住 ✓（`permissions` 正是这么漏的 ✓）、出现不等于断言 ✓。
所以它没有替代人工核对 ✓，只是把"哪些键从没被测过"这件事从记忆里挪进了 CI ✓。

### 3.3 本轮我犯的三处错（都记下）

1. **两个子测试复用同一个 slug** ✗ —— mirror 以 slug 为键，而 fixture 仓库是临时目录；
   第二次 seed 后，mirror 的 origin 指向**上一个子测试已删除的目录** ✓，后续
   `install` 去 fetch 就失败 ✓。改为各自 slug ✓（原因写进了测试 ✓）
2. **gitconfig 里写 Windows 反斜杠路径** ✗ —— 在 git 配置里反斜杠是转义符，
   直接报 `fatal: bad config line` ✓。改用正斜杠 ✓（原因也写了 ✓）
3. **又用过滤条件吃掉多行失败输出** ✗ —— 导致盲猜了轮次才看到真实报错 ✓（同类错误第二、三次 ✓）

### 3.4 规矩的复核

本轮复用了三条既有的规矩，均有效：
- **先立 ADR 再改代码** ✓（ADR-014 先定"不做"，才去改 `verify` 的措辞 ✓）
- **断言要有证据** ✓（ADR-013 的实测记录逐条对应真实运行 ✓）
- **只追加不改判定** ✓（签名层与沙箱层同形 ✓；顺带用同一纪律修掉了 `--json` 被污染的问题 ✓）

## 5. v0.5 候选（按证据强度排序，非路线图承诺）

1. **可复现构建第三批**：真实应用（带插件 / loader / 压缩链）与更大规模 ✓ —— 前两批都是小型合成项目 ✓
2. **跨机器一致性**：同一 commit 在不同机器上的产物比对 ✓ —— 与第 1 条同属 ADR-013 的翻案条件 ✓
3. **deno 真引擎覆盖** ✓（等其 `bundle` 脱离实验状态 ✓，v0.2 起挂账 ✓）
4. **单个依赖内部并行哈希** ✓（v0.2 复盘 §2.3 起挂账 ✓）

> `remote` adapter 依旧**不是候选** ✓：ADR-013 决定不发布，翻案条件是第 1、2 条 ✓。

---

## 6. 对 v0.5 的建议

1. **优先把"可复现性"这个开放问题收敛掉** ✓。它是 ADR-013 唯一写明的翻案路径 ✓，
   而目前状态是"在收敛、未成立" ✓——再放着就会变成一句没人复核的旧话 ✓
2. **新增配置字段时，先把断言补上再写实现** ✓。第 4 例就是这样被当场抓住的 ✓
3. **改散文表格时先看一遍代码** ✓。本轮三批漂移都出在同一个地方：版本交付后文档没跟上 ✓
4. **保留"让仪器自己报告失败"的写法** ✓。本次可复现性探针靠它才没变成"什么都没测出来" ✓
