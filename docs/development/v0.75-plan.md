# v0.75 计划 — **标准的第一个实现（canonical-json）+ 两处修正**

> 来源：用户提出"暂时还没有库文件，是否可以现写一个，我推到远端仓库，具体你来统筹安排"。
>
> 一句话目标：**按 v0.74 的标准写一个真实可用的库**（用户直接推送即可），
> 顺手把"照着标准做"才暴露出来的两处标准缺陷修掉。

---

## 0. 起点

v0.74 交付了标准与自检器，但**没有任何一个库按它写过**——而判断标准好不好用，
唯一诚实的办法是照着它做一遍。因此本版做两件事：

1. 写一个**真实可用**的库（不是 fixture）：`canonical-json`——确定性 JSON 序列化与哈希；
2. 把它当"标准的第一个用户"，看哪些条款写错了、写漏了、写过头了。

## 1. 为什么是这个库

| 维度 | 理由 |
|------|------|
| 真实价值 | "同一个值 ⇒ 同一串字节"是所有缓存键 / 内容哈希 / 可复现构建的前提；`JSON.stringify` 做不到（键序敏感） |
| 零依赖 | 不引第三方，减少供应链面（也顺带证明自己不需要 ngm 去解析任何传递依赖） |
| **免构建** | 仓库就是产物（`src/index.js` + `src/index.d.ts`）——ngm 不替依赖构建，这一条是标准里最硬的约束，用它来验证最合适 |
| 可判定 | 确定性有明确的正面/反面用例（键序、`-0`、`1e21`、UTF-8 字节），哈希有已知向量可钉 |
| 与项目同源 | ngm 自己的全部纪律就是"同一输入 ⇒ 同一字节"；这个库把那套纪律做成了通用工具 |

## 2. 交付

| 项 | 内容 |
|----|------|
| 库文件 | 13 个（`src/index.js` · `src/index.d.ts` · 4 组测试 · `package.json` · `ngm.json` · README · LICENSE · `.gitattributes` · `.gitignore` · CI） |
| 库测试 | **25 个**（Node 内置 test runner，零依赖）：确定性 · 拒绝路径 · 哈希对账（WebCrypto × node:crypto）× 已知向量 · 类型面对账 |
| 库仓库 | 已 `git init` + 提交 + 打 tag **v1.0.0**（待用户 `git remote add` 并推送） |
| 标准修正 | ① `ngm.json` 示例补 `runtime`（必填三件之一）+ 新增必做判据 `ngm-json-valid`；② LF 条款补"自检看工作树字节、Windows 检出要保持 LF"的边界 |
| 自检器 | 判据从 22 → **23 条**（12 条必做常驻 + 2 条条件 + 9 条推荐） |

## 3. 验收

```bash
node --test                                     # 库：25/25
bash scripts/check-library-standard.sh <lib> --strict   # 库：全绿、exit 0
# 牙齿：删掉 ngm.json 的 runtime ⇒ ✖ ngm-json-valid + exit 1
```
