# v0.25 计划 — 文档里手工写下的字段清单，不许与实现脱节

> 范围来源：[v0.24 复盘](./v0.24-retrospective.md) §7 候选 1（"同类多处事实源的普查"）。
>
> 一句话目标：v0.24 把**退出码**的四处事实源串成了一条判据。
> 这一版去问同一个问题的其它答案：**还有哪些"手工写下的清单"是第二份事实源？**

---

## 0. 为什么有这一版

v0.24 证明了一件事：**同一个事实被写在多处**，而其中几处**没有任何网**。
退出码只是其中一例。普查之后，候选有两类：

| 候选 | 是不是第二份事实源 |
|------|------------------|
| `cli.md` 的《`--json` 的形状》表 | ✅ 机器接口的顶层键——v0.16 手写下来的，**没有任何东西守着它** |
| `configuration.md` 的三张「字段」表（`ngm.json` / `dependencies` / `supplyChain`） | ✅ 用户照着写配置的那份清单 |
| `ngm.lock` 的字段 | ❌ 只在 `locking.md` 一处描述，实现侧是结构体——不构成第二份清单 |
| `ngm.engines.json` 的字段 | ❌ 同上 |

## 1. 判据必须先量一遍（本版的纪律）

第一版判据是"**活文档里所有反引号驼峰标识符都必须是 json 字段**"。
探针跑出来的结果是 **62 个 token 里 27 个不成立**——Go API（`resolve.Normalize`）、
配置键（`importMap`）、Git 配置键（`core.hooksPath`）、占位符（`vX.Y`）、
甚至是 `t.Logf`——都被卷了进来。

这类误报的真正代价不是"网红了"，而是**人会去放宽判据**，直到它什么都抓不到。
所以收紧到：**只查那两张表**里的键。

## 2. A 组 — `--json` 形状表 vs 实现

`cli.md` 的表里点名的每个键，必须在**该命令的报告实现**里作为 json tag 存在。

- 按命令映射到实现文件（`verify` → `internal/verify`，`tree`/`why`/`outdated` → `internal/observability`，…）；
- 映射的两条**指向 CLI 层自己**（`integrations` / `engines` 的报告结构体在 `cmd/ngm/`）；
- 一条**豁免**：`engines info` 行括号里的引擎名是举例，不是字段名（名单自带过期绊线）。

## 3. B 组 — `configuration.md` 三张字段表 vs schema

三张表的键必须在 schema 的 json tag 里存在。

- `ngm.json` / `dependencies` → `internal/config`；
- `supplyChain` → **也是 `internal/config`**（`SupplyChainConfig` 的 json tag），
  而 `internal/supplychain` 是**策略的解析与判定**（方法形态），里面没有这些 tag。

## 4. 已知限制（写进网里，也写进复盘）

两张网都只证明"**表里写了的键都真的存在**"；
**不**证明"**该写的键都写了**"——从文档里删掉一个键，它们不会红。
反向的判据需要知道"哪个类型是顶层报告"，列为 v0.26 候选。
