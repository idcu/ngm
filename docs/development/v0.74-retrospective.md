# v0.74 复盘 — **JS Git 库的标准（梳理 + 可执行自检）**

> 一句话结论：把"一个能被 Git 依赖消费的 JS/TS 库该长什么样"写成**一页标准 + 一个判据**
> （`docs/guides/js-git-library-standard.md` + `scripts/check-library-standard.sh`，22 项）。
> **产品代码 0 行**——这一版改的是"库该怎么写"这件事的**可判定性**。

---

## 1. 逐组验收

### 1.1 标准页的三类条款（每条都带"为什么"，不是最佳实践清单）

| 类 | 条数 | 举例 |
|----|------|------|
| 必做（自检红 ⇒ exit 1） | 10 | 入口可解析（与 `InferEntry` 三层同口径）· 无安装钩子 · 无 `.npmrc` · 无 LFS / 子模块 / 逃逸 symlink · 文本统一 LF · 有许可证 · 产物已提交 |
| 推荐（提醒；`--strict` 下计入） | 9 | `type: module` + 条件 `exports` · 提供类型 · 发布范围 · `engines` · semver tag · Git 依赖写进 `ngm.json` |
| 禁止 | 5 | 靠安装钩子才可用 · 把 Git 依赖写在 `package.json` 并指望被装 · LFS / submodule / 逃逸 symlink · 提交随构建变化的文件 · 移动 tag |

### 1.2 自检器（22 项）

```
必做 13：package.json 存在/合法/name/semver · 入口可解析 · 产物已提交 · 无钩子 ·
        无 .npmrc · 无子模块 · 无 LFS · symlink 不逃逸 · LF · 许可证
推荐  9：type=module · exports 条件 · 类型 · 发布范围 · README · engines ·
        .gitattributes(LF) · semver tag · git 依赖落在 ngm.json
```

**牙齿（实测四条）**：

| 弄坏什么 | 结果 |
|---|---|
| 加 `postinstall` | ✖ no-install-hooks（必做）+ exit 1 |
| 放一个 `.npmrc` | ✖ no-npmrc + exit 1 |
| 入口指向被 `.gitignore` 排除的 `dist/` | ✖ dist-committed + exit 1 |
| 删掉 `version` | ✖ pkg-version + exit 1 |
| （`--strict`）package.json 有 git 依赖、ngm.json 没声明 | ✖ git-deps-in-ngm-json + exit 1 |

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么 |
|---|---------|---------|-------|
| 1 | 用 grep 判 CRLF | 改用 **node** 扫字节 | 见 §4.1：CR 的转义写法被工具链改写过一次，判据静默按错的模式搜索 |

## 4. 缺陷清单

| # | 缺陷 | 谁发现 | 处置 |
|---|------|-------|------|
| 1 | **CR 的转义被改写**：脚本里 `$'\r'` 落盘成了 `$'\\r'`，grep 于是把 `\r` 当正则（`r` 字母即命中）——fixture 明明是 LF 却报 CRLF | 自检器自己的第一次运行（标准页的"统一 LF"条款当场自相矛盾） | CR 判定改用 node 读字节（`b.includes(13)`）；并在 `record` 处写下这条教训 |
| 2 | 同上：`IFS=$'\t'` 也被改写成 `$'\\t'` | 修第 1 条时顺带核对 | 分隔符换成 `|`（无需转义） |
| 3 | fixture 里把 `"github:me/base": "v0.4.1"` 当成"git 依赖"（值其实是版本号） | 自检器（该条报告"没有 Git 依赖"） | 修正 fixture 为 npm 的真实形态 `"base": "github:me/base#v0.4.1"`，检查随即生效 |

## 5. 过程洞察

### 5.1 判据也会说谎——而且它看起来和真相一模一样

CRLF 那条最危险：它**报了红**，看起来像在认真工作，而它其实在按错误的模式搜索。
这类缺陷没有"测试失败"帮忙暴露——只有"被检查的对象自相矛盾"时才会浮出来
（标准页要求 LF，fixture 确实是 LF，它却说有 CRLF）。教训写进了脚本注释：
**判据里凡是"需要转义才能表达"的字符，都是事故位**——换成不需要转义的表达方式。

### 5.2 标准的价值不在"写了什么"，在"能不能判"

10 条必做里，真正会被人违反又不易察觉的是"入口指向未提交的产物"和
"靠安装钩子才可用"——前者在 ngm 下表现为"装了个空目录"，后者表现为"静默少跑一步"。
两条都被做成了机械检查。反过来，那些只能靠人判断的（代码风格、测试覆盖率）
**没有**写进必做项——写进去只会让标准变成一张没人核对的清单。

### 5.3 "以后统一"这句话需要一个判据才成立

用户要的是"自家库文件都按这个标准统一"。若只有一页文档，统一靠记忆；
有了 `scripts/check-library-standard.sh`，统一变成 `bash scripts/... <dir>` 的一条命令。
这也是本项目反复验证过的那条：**规则只写一处、并且能跑**——
v0.67 的 demo、v0.71 的索引判据、本版的自检器，是同一门手艺的三次应用。
