# v0.35 复盘 — 建议要承认**成因**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：`res.Err != ""` 是一支，却覆盖**成因完全不同**的失败。
> 这一版让**最贴近成因的那一层**写下的话送到用户眼前——
> 而那句话产品**早就写好了**，两次被丢掉：一次被 `merr.Error()` 字符串化，
> 一次被一行**没人读的赋值**。

---

## 1. 逐组验收

### 1.1 两种成因 → 两句不同的建议 ✅

| 成因 | 行动行 |
|------|-------|
| mirror 不在（`--offline` 冷启动） | `→ run once without --offline to populate the mirror, or use \`ngm install\`` |
| 网络被策略拒 | `→ add "net:github.com" to \`permissions.allow\` in ~/.ngm/config.json (a permission that is neither allowed nor denied is refused)` |

判据三条：① 每条行动行命中**自己成因**的标志（`` `ngm install` `` / `permissions.allow`）；
② 两句话**不相同**；③ 两条用例都真的失败。

读数：`operational causes: 2 advices, distinct=true`。

### 1.2 四张网一起 ✅

| 网 | 读数 |
|----|------|
| v0.32 报告式失败有下一步 | **9 条用例 · 9 失败项 · 9 行动行** |
| v0.33 建议要指名道姓 | 9 行 → 命令 ×6 · **配置键 ×2** · 版本 ×1 |
| v0.34 建议要承认失败的形状 | 9 条用例 → **6 种不同解法** |
| v0.35 建议要承认成因 | 2 种成因 · **两句不同的话** |

> 附带的一件事：`permissions.allow` 被 **v0.33 的锚点检查逐段核对通过**
> （它是 `internal/config/config.go` 里真实存在的键）——
> **这一版的修复顺带被上一版的判据验证了。**

### 1.3 牙齿 ✅

| 探针 | 结果 |
|------|------|
| 回退"优先用链上的建议"（退回 v0.34 的通用话） | 两条断言**同时**开火：<br>`the advice does not acknowledge **this** cause (expected "permissions.allow" in it)`<br>`both operational causes were given the same advice: one branch cannot be right for both — a missing mirror is fixed by fetching, a denied host by allowing it` |

## 5. 过程洞察

### 5.1 "算好了又丢掉"——第三次，而这次有三种丢法

| 版本 | 丢在哪 | 形态 |
|------|-------|------|
| v0.28 | 包装链 | 外层 `Wrap` 给了空 hint，内层的建议再也看不到 |
| v0.34 | 渲染的门 | `if DriftKind != None && Remediation != ""`——建议算好了、被门拦住 |
| **v0.35** | ① 字符串化 ② **死赋值** | `merr.Error()` 只留 message；`derr = errs.New(...)` 下一句就没人读它 |

**同一族缺陷，三个不同的丢法。** 而三次都不是靠重读代码发现的，
是**判据在问"用户到底看到了什么"**。

### 5.2 死代码里的建议，是最难发现的一种

```go
res.Err = digestCheck.Detail
derr = errs.New(errs.CodeGitFetch, …, "the local mirror is cold; run once without --offline …")
```

这行**看起来在做事**：构造了一条带建议的错误，赋给了一个在作用域里有名字的变量。
而它下一句就离开分支，`derr` 之后再没被读过。

- `go vet` **不报**（只看"声明未使用"，不看"赋值未读"）
- 测试**不报**（它不影响任何输出）
- `gofmt` 更不报

它只在有人问"**这句话到底给了谁**"时才现形。这也解释了为什么这一族能连着三版出现：
**每一处丢法都不会让任何东西变红。**

### 5.3 判据的三次推进，每一次都是上一次的边界教的

| 版本 | 判据能说什么 |
|------|------------|
| v0.33 | 这句话点名了一个**真实存在**的东西 |
| v0.34 | 这句话点的是**这一类失败**该指的方向 |
| v0.35 | 同一个分支的**不同成因**，要给出**不同**的话 |

没有一次是"想出来的下一步"——v0.34 的边界（"判得出方向，判不出措辞"）写在复盘里，
才让 v0.35 知道该往哪儿推。**把边界写在明处，就是给下一版留的路标。**

### 5.4 修法比计划更简单，因为换了个方向

计划里写的是"把错误码穿进 `remediationFor`"——那是**让猜的人拿到更多线索**。
实际做的是"**让知道的人直接说**"：`ErrHint` 优先（沿用 v0.28 的 `inheritedHint`）。

好处不只是少改代码：

- 不用维护"成因 → 建议"的映射表；
- **新增一种成因时自动正确**——某一层新写的建议会自己浮上来，不需要有人记得更新这张表。

这正好是 v0.33 那条经验的镜像：**核对的对象应来自运行时/源码，而不是抄一份常数。**
这里的"常数"是成因清单，这里的"运行时"是链上的建议。
