# v0.80 复盘 — **嵌套 monorepo 的明确处置 + subPath 端到端的阻塞事实**

> 一句话结论：`subPath` 端到端被两条**设计上正确**的行为挡在"必须有真远端"这一步
> （`--offline` 拒绝无 lock 的离线安装 · 地址校验拒绝单标签主机名与 IP 字面量）——
> 这是**结论**而不是失败：本机没有替代路径，那一跑必须等一次真人推送。
> 而没有远端也能做的部分（嵌套 monorepo）在这一版里从"用错理由红"改成了"**说出来**的没查过"。

---

## 1. subPath 端到端：推到能推的最远处

### 1.1 三条试过的路径（都有据）

| 路径 | 结果 | 结论 |
|------|------|------|
| 预置 mirror（`git clone --mirror` 到 `~/.ngm/mirror/<host>/<org>/<repo>.git`）+ `install --offline` | `GitFetch: --offline: no ngm.lock to install from` + hint"an offline install can only materialise what the lock already pins" | **设计如此**：离线安装不凭空造 lock。要**解析**就得有远端 —— 这条拒绝是对的 |
| 本地 `git daemon`（`git://localhost`，默认端口 9418）：`--detach` 在 Git for Windows 上不起 | 改后台运行 ✓；`git ls-remote git://localhost/jsonkit` ✓ 三个写法（`localhost` / `localhost.` / `127.0.0.1`）都通 | daemon 侧没问题 |
| 同上，`ngm add 'git://localhost/jsonkit#path=packages/stable-stringify@v0.1.0'` | `ConfigInvalid: invalid git address: "localhost"`；`127.0.0.1` 同样被拒 | **ngm 的地址校验刻意拒绝单标签主机名与 IP 字面量**（`unknown host "localhost"; use a short name (github/gitee/gitlab) or a full domain`） |

### 1.2 因此得到的结论（写下来，省下一个人半天）

- `subPath` 端到端**必须**有一个真的远端；本机没有替代路径。
- **不**为跑通测试放宽地址校验：那是一条产品决策（"仓库的身份由 host+path 定义"），
  不该由测试的方便来改。要不要允许 `localhost` / 局域网 IP 是**另一个决定**（见 §5 候选 3）。
- 顺带验证了两条既有的诚实行为：`--offline` 不会假装成功；`mappings` 为空时
  vendored 扫描器报 `exit 2`（"一个都没查"≠"全查过且都合格"）——它正是这样回报的。

## 2. 嵌套 monorepo：把"用错理由红"改成"说出来的没查过"

```
packages/inner（自己带 workspaces: ["units/*"]）
  — nested-monorepo   它是 monorepo 根（声明：units/*；约 1 个子包没有被体检）——嵌套 monorepo 是未验证的形态，本工具不递归
  — entry-resolvable  monorepo 根不是包——入口由各子包自己声明（**嵌套形态：它的子包没有被体检**）
结论句：已查的判据全部通过，**但这不是一次完整体检**：检测到嵌套 monorepo，它的子包没有被体检
--json：ok=true · complete=false · skipped=19（孙辈一条判据都不出现）
```

四条断言各守一件事（`TestV80NestedMonorepoIsReportedAsIncomplete`）：

| # | 守什么 | 为什么 |
|---|--------|--------|
| ① | 记录里点名**声明的模式**与"约 N 个子包**没有被体检**" | "不适用"要能被读懂：说清**没查到什么** |
| ② | 包专属判据记不适用、**孙辈不出现** | 之前红的是"找不到入口"——**用错理由红，等于没红** |
| ③ | `ok` 与 `complete` **互不顶替**（这一组是 `ok:true, complete:false`） | "已查的都通过"与"符合标准"**必须能分开**：一次没查全的体检不能被读成合格 |
| ④ | 删掉嵌套根自己的 README ⇒ 仍红（`--strict`） | 嵌套形态**不是免检牌**：根能承担的判据照旧生效 |

## 3. 缺陷清单

| # | 缺陷 | 谁发现 | 处置 |
|---|------|-------|------|
| 1 | 嵌套 monorepo 以"找不到入口"（必做失败）出现 | v0.79 造 `jsonkit` 时顺带想到，本版实测 | 见 §2：五处改动（检测在子模式也跑但不递归 · `nested-monorepo` 记录 · 包专属判据的措辞 · 汇总口径 · `--json` 的 `complete` 并向上传播） |
| 2 | 我自己在 `jsonkit` README 里写的子路径语法是错的（`#<sub>`） | 本版查 `ParseAddSpec` 的注释与 `addspec.go` 时对照出来 | 改成 `#path=<sub>`（并写明 `@ref` 可前可后）；**真实造物里的错误示例会教错人**，比文档里的错更值得抓 |
| 3 | 我的第一条牙齿写错杠杆：删 LICENSE 不会红（该包有 `license` 字段） | 跑取证脚本 | 换成 `postinstall`（必做项）——**牙齿也有"打偏"这种失败模式** |

## 4. 过程洞察

### 4.1 "被挡住"本身可以是交付物

`subPath` 端到端这一版没跑成，但**为什么没跑成**被查清了：两条拦路的行为
**都是设计上正确的**，而且都有据（命令输出 + 源码注释）。
写下来之后，"要不要为本地测试放宽地址校验"就变成一个**明确的决定**，
而不是某天某个人对着 `invalid git address: "localhost"` 猜。

如果当时为了让测试变绿去改校验，得到的将是一条**宽松了的**地址规则，
而它换来的"绿"掩盖的是"本机没有远端"这条事实。

### 4.2 错理由的红，比不红更贵

`entry-resolvable` 那条红线本身没有说错话（入口确实找不到），
但它把注意力引向**错的修复方向**：给这个仓库加 `main`。
而正确的事是"它是个 monorepo 根，去看它自己的子包"。
**判据的输出是给下一个人的第一句话**；这句话必须指向真因。

### 4.3 我自己的牙齿打偏了三次（v0.76 起）

v0.76：以为 vendored 副本会因为"缺 tag"红（其实是 vendored 已经对了）；
v0.79：以为删 LICENSE 会红（该包有 `license` 字段）；v0.79 的另一条：以为
`packages/*` 能匹配到被删掉的目录。三次的共同点：**我在想"什么能弄坏它"，
而没有先查"这条判据读的是哪个字段"**。
现在的习惯是：写牙齿前先看一遍判据的实现（一次 `grep` 的成本，换一次不返工）。

## 7. 需要仓库所有者做的三件事（与 v0.79 相同，只多了 1 个 tag）

1. **推 jsonkit**（`d:/repos/mine/jsonkit` 已备好并已初始化 git + `v0.1.0` tag）：

   ```bash
   cd d:/repos/mine/jsonkit
   git remote add origin <你建的远端 URL>   # Gitee 或 GitHub 空仓库
   git push -u origin main --tags
   ```

   （`git init` / commit / `v0.1.0` tag 我这边已经做完，你只需要建仓 + 推送。）

2. **推 ngm 的 tag**（15 个）：

   ```bash
   git push origin main --tags
   git push gitee  main --tags
   ```

3. （可选）`GITEE_TOKEN`；以及 §6 候选 3 那个产品决定（要不要允许 `localhost` / 内网 IP）。
