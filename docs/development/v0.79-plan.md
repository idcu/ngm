# v0.79 计划 — **把"扫 vendored 产物"固化成一条命令 + 第二个库（monorepo 形态）**

> 来源：[v0.78 复盘](./v0.78-retrospective.md) §7 候选 2（v0.76 候选 4，**两版落空**）与候选 3 的前提。
>
> 一句话目标：标准的前一半（"库该长什么样"）已经在跑；把**后一半**也变成一条命令
> ——"**我拿到的依赖**长什么样"。顺带造出第二个库，让 `subPath` 有真实样本。

---

## 0. 起点

- v0.76 的候选 4 连着两版没做，两次的理由都是"它不属于产品代码"。
  它真正属于的是**标准**：标准写了"每个依赖都要符合"，那就得有一条命令能对
  "我 vendor 了什么"整体回答"合不合格"，而不是靠人记得逐个跑。
- `subPath` 端到端缺一个 monorepo 形态的远端库（v0.78 §2 第 4 条）。

## 1. 计划

| # | 项 | 验收 |
|---|----|------|
| 1 | `scripts/check-vendored-standard.sh`（+ `.ps1` 转调同一实现） | 真实项目上跑通；文本点名不合格的依赖与判据；`--json` 的 id 带依赖名前缀 |
| 2 | 包装器**不许少跑判据** | 某依赖在报告里的判据条数 == 直接跑标准自检器的条数 |
| 3 | 边界：没有 mappings / 映射指向不存在的目录 | 前者 exit **2**（没有查过 ≠ 查过且合格）；后者 `vendored-dir-missing` 必做失败 |
| 4 | 第二个库 `jsonkit`（monorepo：根 `workspaces` + 两个子包各自带 `ngm.json`） | 根与**每个子包单独**都过标准自检；两个实现真的能跑 |
| 5 | 文档 | 标准页 §5.3（扫产物）+ §5.1 补"vendored 子路径"一行；计划/复盘；逐版表与读数 |

## 2. 不做

- 不把 vendored 扫描塞进 `ngm` 命令表（它是**标准**的工具，不是产品的命令；
  要变成命令就得付四张契约网的代价，而那笔账的价值取决于有没有人用）；
- 不替仓库所有者推送（推送仍是要人做的事）；
- 不动 `ngm.vendor/` 的任何内容（扫描是**只读**的）。
