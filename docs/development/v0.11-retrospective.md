**决策 1 的关键新事实**（它改变了判断的性质）：`remote` 在代码里**不存在**
（`catalog.go` 里 `AdapterRemote` 只产出"按决定排除 → exit 5"）。因此"发布它"

**这是"成本结构变了判断"，不是"技术条件没满足"**——所以 ADR-020 明确说：
触发重开的条件是**真实需求 / 本地算力证据 / 跨生态标准**，而不是"等技术上做完"。

**决策 4 的关键洞察**（本版最值得记住的一条）：

> ADR-018 卡住的原因是"按**可达性**删除需要一个项目注册表"，
> 而**孤儿不需要注册表**——"本 store 里没有任何清单引用它"是**由构造可判定**的事实。
>
> 两者是**不同的问题**，不是同一个问题的难易版本。

### 1.2 A4 的实现 — `store prune --orphans`

| 计划项 | 结果 | 证据 |

| 场景 | 行为 | 判定 |

| `prune --orphans` | `removed 1 ... freeing 21 B` + `2 referenced blob(s) untouched` | ✅ |

### 4.1 一个不算缺陷但值得记的摩擦：权限门禁是**四次**才走通的

C 组第一次真实安装，连撞四道门：`net:github.com`未授权→ `read:` 缺target
→ `run:git` 未授权 → `run:esbuild` 未授权。

**每一次的报错都给出了可以直接照抄的修复**（`add "net:github.com" to permissions.allow` /
`write it as read:<value>`），所以这**不是 bug，是设计**——默认拒绝 + 精确提示。

但它也说明一件事：**从零到跑通，权限配置是最大的一段路**。
而这正是 ADR-012/v0.3 权限模型的**预期代价**（"权限是唯一被施加的资源限制"）。
**记在这里不是为了改它**，而是为了让下一个读者知道：这段摩擦是有意的，
且已有三份文档解释它（security-model / ADR-012 / configuration）。

### 4.2 D1 的补充：为什么"报错指向网络"值得单独说

D1 的报错是：

```
GitFetch: git clone --mirror ... failed (exit 128): fatal: unable to access
'https://127.0.0.1/...': CONNECT tunnel failed, response 502
  hint: check network connectivity and the git host
```

用户读到"网络连通性"，会去查网络——**而网络是好的，端口是被 ngm 自己丢掉的**。
这与 v0.10 的 D1（报错指错文件）是**同一族**：信息的价值取决于它是否指向正确的位置。
**已知限制 + 如实记录**，是这类问题在没有修复前唯一诚实的处理方式。

## 5. 过程洞察

### 5.1 "当一次用户"抓到的三个问题，没有一个是代码审查能抓的

D1/D2/D3 分别是：端口被丢、输出自相矛盾、文档命令跑不通。
它们的共同点是**"内部一致性"检查全都通过了**——锚点检查绿、链接检查绿、
单测绿、门禁绿。**它们全部是"与真实世界接触的那一寸"上的问题**：

- 端口：只有在真的连一个非默认端口的server 时才暴露；
- 输出矛盾：只有在新功能加了、旧文案没改时才暴露；
- 文档命令跑不通：只有照着抄一遍时才暴露。

> 十一版都在做"内部一致性"，而这一组证明了它的**边界**：
> **它证明不了"对外真的能用"**。这不是新增检查能解决的——
> build / vet / 锚点 / 门禁全部通过时，项目仍然可能**一条命令都跑不通**。

### 5.2 三条"不做"的 ADR，比四条"待定"更有用

上一版状态页挂着四条"需要你决策"。这一版把它们写成 ADR，
**三条的结论是"不做"**，每条都写明了**重新考虑的触发条件**：

- `remote`：真实需求 / 本地算力证据 / 跨生态标准；
- `symlink`：具体的工具要求 + 实测数字；
- 3s 目标：已经是观测值，无需触发条件。

差别在于：**"待定"会一直看起来像待办**，而"不做 + 何时重启"是一条**可执行**的结论。
写ADR 的成本是一份文档，收益是**把模糊变成具体**。

### 5.3 "由构造可判定"是一个可复用的判据

ADR-023 的洞察值得单独记下来，因为它是**可迁移的**：

> "这个 digest 还有没有人要" → 需要**项目注册表**（ngm 没有）→ 不可判定
> "本 store 里有没有清单引用它" → **由构造可判定**（引用只可能来自 `trees/` 下的清单）

当一条设计卡在"缺某个注册表"时，先问一句：**有没有一个更弱、但由构造可判定的版本？**
本例中弱的那个版本恰好覆盖了 90% 的实际收益（孤儿是持续安装累积的产物），
却**不需要**那个缺失的基础设施。这比"等注册表"或"不做"都好。

### 5.4 一条纪律的延续：断言要有据

`TestV11RunProcessWaitDelayIsBounded` 的阈值取法：
"必须小于 5s"会在慢机器上假红，"必须小于 25s"又抓不住回归（修复前实测 25.3s，卡在边界）。
最终取 **20s**——同时满足"远小于 40s（抓得住）"与"远大于 4s（不假红）"。

这与 v0.9 的"先验分布本身对不对"、v0.10 的"先确认契约再写断言"是同一条线：
**断言的阈值也是设计，必须说明它为什么取那个值**。

### 5.5 "修了一处"不等于"修了这个毛病"——本版最该记住的一条

`WaitDelay` 缺陷在**三个地方各写了一遍**。我第一版只修了当时看到的那一处
（adapter），修完跑全量，**问题挪到了 `internal/git`**——又是一条 15 分钟超时。

讽刺的是，`newGitCommand` 的注释里**已经写着这句话**：

> 三个出口分散着写，就一定会漏——这与 `field_wiring_test.go` 要治的是同一种病：
> **规则写在第二个地方，就一定会有一处不一致**。

> **我做的事正是那条纪律要防的事**：修的时候按"我看到的那一处"修，
> 而纪律要求的是"**按规则的定义处**修"——对`WaitDelay` 而言，git 的唯一构造点
> `newGitCommand` 才是正确的位置（这也是为什么最终把常量放在那里）。

**判据可以推广**：发现"同一个机制散在多处"时，
不要逐处修补，而是**先找到（或建立）唯一的构造点**，让规则在那里写一次。
`internal/testutils` 里的 `runGit`（测试夹具）会另起进程，因此**测试侧也需要同样的处理**——
这也是为什么这一版的验收要跑**两轮**全量：第二轮才暴露出 git 路径那一处。

### 5.6 一条测试缺陷的通用形状：`buildEnv` 继承 `os.Environ()`

`TestBuildEnv_AllowPrompt` 在本机恒红，原因是这台机器的环境里**已经有**
`GIT_TERMINAL_PROMPT=0`，而 `buildEnv` 继承 `os.Environ()`——
它经 `t.Setenv` 清掉后，**两种环境都绿**。

这类缺陷的形状值得记：**断言在"被测对象行为正确"时也会红**，
因为它同时断言了"环境是空的"这件事，而后者不写出来。
与 v0.9 的"测出来的分布要先用分布本身对不对验一遍"同族：
**测具要先确认它测的是自己声称测的东西**。

### 5.7 "超时"必须与"失败"分开——否则 CI 的红没有信息量

全量 `go test ./...` 在本机连续两次 20min / 25min **超时**。第一反应是"还有别的地方
没修好"（因为 D4 就是这么找到的）。但这次不同：**把 `cmd/ngm` 的 97 个测试分 4 片跑，
每片都 PASS，97/97 全绿**——它是**慢**，不是**坏**。

机制：97 个测试函数、大量 git 子进程、41 处 `t.TempDir()`（Windows 上
`os.RemoveAll` 逐文件删除很慢），串行累积必然超过 Go 默认的 10m。

处置：`ci.yml` 与 `release.yml` 都显式写 `-timeout 40m`，**并把理由写进注释**。
这与 `metrics.md` 那条纪律同源——**次数优先于秒数**：一个可判别的"有没有失败"
不该被一个与平台相关的时长上限误伤成"有 bug"。

> 顺带一条：`release.yml` 也跑同一条命令，所以**它当时也有这个风险**——
> 一份"发布前必须全绿"的工作流，会因为机器慢而拒绝发布一个其实没问题的版本。
> 两处一起改了，而不是只改 CI。

### 6.1 一个被修掉的"仪器说谎"（本版的第二个 WaitDelay）

`versionProbeTimeout = 5s`（`internal/adapter/subprocess.go`）**名不副实**：
`exec.CommandContext` 只杀直接子进程，而 npm 装的CLI 在 Windows 上是
`.cmd` / sh 包装**再起一个进程**；那个孙进程继承 stdout 管道写端，
于是 `cmd.Wait()` 一直等 `io.Copy`——**实测 ctx 5s、实际 25.3s**，
在 `go test ./...` 全量跑时曾把一条测试拖到 **9 分钟**（单独跑只要 4.35s）。

> **"上限在什么时候生效"本身是它的可靠性指标**：全量跑时不生效、
> 单独跑时生效，说明这个上限在最需要的时候不可靠。

修法是 `cmd.WaitDelay`（2s宽限期后强行关闭管道）。**这里有一个本版最重要的过程教训**：

> **第一处修完只是把问题挪了个位置。** 修好 adapter 后，全量跑仍然 15 分钟超时——
> 这次卡在 `testutils.runGit` → `cmd.Run()`，也就是**`internal/git` 的构造点**。
> 同一个缺陷在三个地方各写了一遍，而本项目的纪律一直是"**规则写在第二个地方，
> 就一定会有一处不一致**"（`newGitCommand` 的注释就写着这句话）。
> **我第一版修的时候只看了自己当时看到的那一处**——这正是那条纪律要防的事。

最终三处都补上（每处都做了**双向牙齿测试**）：

| 位置 | 为什么重要 | 去掉 `WaitDelay` 后 |
|------|-----------|------------------|
| `internal/adapter/subprocess.go` | 引擎版本探测（声称 5s 上限） | 40.23s → 红 |
| `internal/git/spawn.go`（**唯一构造点**） | **git 是安全关键路径**：每次 fetch / ls-remote / digest 重放 | 40.49s → 红 |
| `internal/security/sandbox.go` ×2 | 跑**用户自己的 postinstall 钩子**，派生后台进程的脚本不该让 `ngm install` 无限期挂住 | — |

修好之后，那条从 15 分钟超时降到 **65.8s** 通过。

**这是 v0.6"仪器会说谎"的同一个形状**，只是这次发生在一个**超时**上：
标了 5s 的量实际是 25s，而它此前**没有任何检查**（门禁守的是 spawn 次数，不是时长）。
新增的 `waitdelay_test.go`（两处）都做了对照断言——**一个"永远返回错误"的实现
也能让"有界"这条变绿**，所以必须有"正常路径仍然成功"那条在旁边。
