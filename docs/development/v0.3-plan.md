# v0.3 实施计划 — 引擎生态与协议

> 范围以 [internals/roadmap.md](../internals/roadmap.md) 为唯一事实源。前置：v0.2 完成。
> 本阶段以"接入生态"为主：所有能力仍遵循第三方优先与唯一事实源约定。
> 前置：**v0.2 已完成**（见 [v0.2 复盘](./v0.2-retrospective.md)）。

## 设计复核结论（2026-09-30，开工前）

复核方式与 v0.2 相同：对每一项**去验证而不是假设**，并把"必须先改的东西"与
"可能不该做的东西"都记下来。本轮产出了三条硬事实、一条排序强制，以及一处已当场修复的文档缺陷。

| 复核项 | 结论 |
|--------|------|
| **wasm 运行时选型** | **被已发布的承诺限定**：发布构建固定 `CGO_ENABLED=0`（`scripts/build-release.sh:46`、`build-release.ps1:55`），六平台交叉编译出单静态二进制。因此依赖 cgo 的运行时（wasmtime-go 一类）**不可用**——这不是偏好问题。可选范围收窄到纯 Go 实现（如 wazero）。另需定义 **ABI**：模块如何收输入、吐产物、报错。**需要 ADR** |
| **remote adapter 的信任边界** | **与本项目的立身相冲突**：ngm 的价值是"不把第三方放进信任链"（Git 直连 + 本地可证明），而 remote adapter 会把**源码送出本机**。三个必须先答的问题：发给谁、如何证明对方没有替换字节、失败如何不静默降级。**需要 ADR**；且复核的诚实结论是——**若这三个问题答不上来，不发布比发一个说不清的更强** |
| **沙箱与 postinstall 的先后** | **顺序被 ADR-009 强制**（不是排序偏好）：ADR-009 决策 5 写明"将来若要为 `prompt`/`allow` 提供执行入口，**必须先有沙箱 ADR**（v0.3），并修订本 ADR"。沙箱自身也要先立 ADR——它执行的是**依赖自带的代码**，是整个项目里唯一"运行他人代码"的能力 |
| **权限词表现状** | **已解析、未施加**：`GlobalPermissions{allow,deny}` 的结构与读取在 M0 就留好了（`internal/config/config.go:170`），但**没有任何地方执行它**。与 v0.2 的 `verifyOnLock` 同类缺陷。文档侧已当场修正（见下） |
| **tsconfig `paths` 能否解析 `github:` 前缀**（B 组的关键假设） | **可以，但有一条硬约束**：实测真实 tsc 7.0.2，`baseUrl` **已被移除**（`error TS5102`）→ 生成器**不得**写 `baseUrl`，否则用户开箱报错。去掉后 `paths` 生效（`tsc --noEmit` exit 0），并用**对照实验**确认它确实生效而非被忽略（故意制造类型不匹配 → `error TS2322` 指向 vendor 里的值） |
| **各工具别名的语义差异**（B 组） | Vite / esbuild 的 alias 是**前缀**匹配，Deno import map 有尾斜杠约定 → 生成器不能一套字符串套四家，必须按工具语义分别处理 `github:org/repo` 与其子路径。**这是 B 组的主要实现风险** |
| **mappings v1 的真实形状**（E 组） | `{version, mappings:[{from,to,main?,types?}]}`；v1 **已允许同一 slug 多条**（monorepo 子路径就是不同条目），但**没有字段表达"这是哪个子路径"** → v2 的增量正是补这个，使消费者能把 `to` 与声明对上 |
| **`engines validate` 的既有机制**（A 组） | 已能区分 `unimplemented`（wasm/remote 现在一律报这个，exit 5）与 `unavailable` → 实现 A 组时**不需要改结构**，只需按能力探测 |

### 建议推进顺序（按依赖关系与证据强度，不按组号）

```
E mappings v2 ─┐
B 集成脚手架 ──┴─> 不依赖新 ADR，且直接交付 v0.3 的目标（"接入生态"）
D 权限词表 ──> ADR-012 沙箱 ──> postinstall 执行入口（并修订 ADR-009）
A wasm（ADR-011：纯 Go 运行时 + ABI） ／ remote（ADR-013：信任边界，可能不发布）
```

1. **E 与 B 先做**：它们是 v0.3 既定目标里可立即交付的部分，且复核已把 B 的不确定性
   从"不知道能不能成"降到"按工具语义分别生成"（并附一条禁令：不得生成 `baseUrl`）。
2. **D 必须先于 C**：沙箱要按 default-deny 映射权限，而权限词表当前只有结构、没有施加。
3. **C 必须先于任何 postinstall 执行**：ADR-009 的明文要求。
4. **A 放最后**：它需要两份 ADR，且 remote 的结论可能是"不发布"——
   不该让一个可能被否掉的项目阻塞其他四组。

### 本轮复核发现的文档缺陷（已当场修复）

| 缺陷 | 影响 |
|------|------|
| `configuration.md` 的成熟度横幅仍写着"写下 `minimumReleaseAge` 不会真的拦住任何依赖" | v0.2 之后该字段**已生效**。把**已生效说成没生效**与反向的错误同样有害：它让人以为门禁没在跑 |
| 同页全局配置段缺少 `permissions` 的成熟度说明 | 读者会以为 `"deny": ["env:GITHUB_TOKEN"]` 已经在拦——它没有 |

## A — wasm / remote adapter

> **前置（按纪律先立 ADR 再改代码）**：
> - **ADR-011**：wasm 运行时与 ABI——运行时必须是**纯 Go**（发布构建 `CGO_ENABLED=0`），
>   并定义模块如何收输入 / 吐产物 / 报错
> - **ADR-013**：remote adapter 的信任边界——**默认禁用**，必须回答"发给谁、
>   如何证明对方没替换字节、失败如何不静默降级"；**答不上来就不发布**

- [ ] `wasm` adapter：宿主运行时（纯 Go 实现）选型评估后引入；沙箱内执行引擎，输入输出沿用 subprocess 协议语义
- [ ] `remote` adapter：自托管构建服务的协议定义（请求 / 产物 / 失败语义）、认证、超时与重试
- [ ] 两类 adapter 进入引擎清单与 `engines validate` 覆盖范围

**验收**：wasm 引擎可在无外部二进制的环境完成 transform；remote 端到端在本地 mock 服务上验证；失败路径退出码与 Hint 明确。

## B — 集成脚手架

- [x] `ngm integrations add vite|esbuild|deno|webpack`：生成各工具配置
- [x] **一并生成 tsconfig `paths`**（解决 `github:` 前缀的类型解析，见 [build.md](../guides/build.md)）
- [x] 生成策略：不覆盖已有配置，冲突时报错并给出**行级 diff**
- [x] Webpack 集成（`resolve.alias`）
- [x] `ngm integrations` 命令进入 CLI 参考与 help

**验收**：
- hermetic：`TestV03IntegrationsAcceptance`——生成内容、幂等、冲突、**全有或全无**、`--json`，
  以及 `ngm build` 为每个子路径给出各自的别名
- 真工具：`TestV03IntegrationsRealTools`——真 esbuild 打包 monorepo 子路径、真 tsc 用生成的
  `paths` 解析 `github:` 前缀（两者都在 CI 的 `engine-integration` job 里跑）
- Vite / Webpack / Deno **未用真工具验证**（CI 未安装这三个工具），只做内容断言并在
  [P5](../modules/p5-integrations.md) 的诚实说明里写明

**三处与原计划的偏离**：
1. tsconfig 拆成 `ngm.tsconfig.json`（ngm 拥有、可重生成）+ 新项目的 `tsconfig.json` 用 `extends`
   指向它。原计划是"一并生成"，但 `tsconfig.json` 属于用户、常带注释，直接改写是破坏性的
2. esbuild 的产物是 **`ngm.esbuild.cjs`（CommonJS）**而不是 `.mjs`：实测 ESM 的模块解析
   不认 `NODE_PATH`，因此只有全局安装 esbuild 的项目会 `ERR_MODULE_NOT_FOUND`；
   `require` 两种安装都能用
3. 已存在的 `tsconfig.json` / `deno.json` 报 **skipped + 一行提示**（exit 0），不是冲突——
   文件本身没有错，只是需要用户加一行。把它报成冲突会让人以为出了问题

**过程中发现并修掉的产品缺陷**（原计划之外）：
`ngm build` 的别名表以 `from` 为键，同一仓库的多个子路径会互相覆盖——**覆盖后构建仍可能成功**，
只是两个子路径解析到同一份代码。已改为以**导入标识符**为键（`mappings.Mapping.Specifier`，
定义在协议层，`ngm build` 与 `ngm integrations` 共用一份）。
同一次实测还确认：esbuild 在多个别名都能匹配时选**最具体**的那个，与 `--alias:` 顺序无关——
因此 `build.md` 里原先"长键必须排在前面，否则子路径会被吞掉"的说法是错的，已按实测改写。

## C — Deno sandbox

> **前置**：**ADR-012（沙箱与执行边界）**。ADR-009 决策 5 **明文要求**先有沙箱 ADR，
> 才谈 `postInstallPolicy` 的执行入口；沙箱执行的是**依赖自带的代码**，
> 是整个项目里唯一"运行他人代码"的能力。实现后需**修订 ADR-009**。
> 另：**D 组的权限词表必须先于本组**（沙箱要按它做 default-deny 映射）。

- [x] `ngm verify --sandbox`：core Go 决策 + Deno 沙箱执行依赖自带的 `verify.js`；权限按 [安全模型](../architecture/security-model.md) 的 default-deny 映射（[ADR-012](../adr/adr-012-sandbox.md)）
- [x] 有脚本要跑时缺 Deno → exit 5 并提示，**不得静默降级**（无脚本时不需要 Deno，见 ADR-012 决策 6 的实现补充）
- [ ] 沙箱内可执行：依赖自带 `verify.js` ✅；自述文件签名检查与用户自定义 audit hook **仍待实现**（同一套权限映射已就绪）

**验收**：沙箱内禁止访问 `~/.ssh` / `~/.git-credentials` / 网络（除非白名单）✅ 真 Deno 用例
（`TestSandbox_RealDeno_BlocksEscapes` 用一个真私钥文件做靶子、`TestV03SandboxRealDeno/the_boundary_holds_through_the_CLI` 走完整 CLI）；
无 Deno 环境的行为测试 ✅（`TestV03SandboxAcceptance` 的"无脚本不需要 Deno"）；
`--sandbox` 与默认 verify 的结果一致性（对象相同、权限不同）✅（`--sandbox does not change the verdict`）。

**实现后复查发现的第三处问题（已修）**：
沙箱最初**继承**了用户的 `run:` 授权，而安全模型里写着"沙箱内不派生任何子进程"——文档与代码不一致。
实测确认了哪一边对：`--allow-run` 允许的进程**不受 Deno 权限约束**（给 `--allow-run=cmd` 后，
脚本用 `cmd /c type <path>` 读到了自己被禁止读取的文件）。于是改为**从不映射 `run:`**，
并把"可执行的程序"从授权结构里删掉（类型层面无法表达），同时把 `env:` 也改为**必须显式授权**
（它的默认档位是为 git 定的，不该延伸到不可信脚本上）。

**实现过程中的两处修正**：
1. **探测形式写错了**：第一版用 `deno run … -e "0"` 做能力探测，而 `deno run` 不接受 `-e`
   （那是 `deno eval` 的形式）——于是在完全够用的 Deno 1.45.2 上判定"不支持"，功能整个被挡在门外。
   改为写一个真实脚本文件再跑，那正是沙箱实际走的路径。
2. **"缺 Deno 就报错"细化为"确有脚本要跑时才报错"**：一个依赖都没提供 `verify.js` 时报
   "沙箱不可用"与事实不符。细化只减少误报，"绝不非沙箱执行"的约束不变（ADR-012 决策 6 已注明）。

## D — 权限与凭证

> **现状（复核时的实测）**：`GlobalPermissions{allow,deny}` 的**结构与读取已存在**
> （`internal/config/config.go:170`），但当时**没有任何地方施加它**——与 v0.2 的
> `verifyOnLock` 同类。这一点已在第一次提交中修掉。

- [x] `permissions` 命名空间（`read:` / `write:` / `net:` / `run:` / `env:`）**解析与执行**（对齐 [configuration](../guides/configuration.md) 示例）
- [x] 权限违例的错误码与 Hint（指向具体配置键）：`exit 3` + 可直接粘贴的那一行
- [x] 凭证纪律落地审计：ngm 输出、lock、vendor、mirror config 中不得出现 token（`TestV03CredentialDiscipline`，含"扫了 0 个文件即失败"的空转守卫）
- [x] `run:<引擎>` 的施加（`adapter.Runner` 的 preflight，排在可用性之后）

**验收**：权限矩阵测试（允许 / 需配置 / 默认禁止三档）✅ `internal/security` 的单元测试 +
`TestV03PermissionsAcceptance`（6 条）；凭证泄露自动化检查纳入 CI ✅（随 `go test ./...` 与
acceptance job 一起跑）。

**第二次提交的范围与一处顺序发现**：

`run:<引擎>` 的判定最初放在 `runChain` 的每次迭代开头，结果 M6 的"引擎缺失 → exit 5"用例
变成了 `exit 3 permission denied: run:ngm-definitely-not-a-real-engine`——**提示用户去加一条
永远用不上的权限**，而真正的问题（工具没装）没有被说出来，退出码也从"环境问题"变成了"配置问题"。
现改为 `Runner.preflight` 的第三步（能力 → 可用性 → 权限），并加了一条断言把这个顺序钉住
（`a missing engine still exits 5, not a permission error`）。

既有验收测试因此需要显式声明它们要执行的引擎：`testutils.AllowEngines(t, ...)`，
由 `cmd/ngm` 注入的写入器在每个新隔离的 HOME 里落成 `permissions.allow`。

**第一次提交的范围与三处判断**：

1. **施加点在知道真实 URL / 真实出口的那一层**。`net:` 判定放在 `vendor.Mirror.Ensure` 与
   `resolve` 的 `ls-remote`，而不是调用方——调用方只看得到 slug（`github:org/repo`），
   而 mirror 可能来自**本地路径**。按 slug 主机名判定会把本地 fetch 当成网络访问拦下，
   并提示用户去加一条与他操作无关的权限（初版正是这样，16 个验收测试因此变红）。
2. **`run:git` 先于 `net:` 判定**。读已存在 mirror 的 origin URL 本身要跑 git；顺序反了，
   一个 `run:git` 被拒的配置会被报成"net 权限不足"。
3. **`env:` 默认允许透传**。ngm 不读取、不解析 token，只是把环境交给 git——默认拦下所有 token
   会让认证在无人配置的情况下直接坏掉。这条权限的用途是**收窄**（`deny: ["env:GITHUB_TOKEN"]`），
   而不是默认开启。

**一处会影响既有项目的行为变化**：`net:` / `run:` 默认"需配置"，升级后第一次访问远端会 `exit 3`
（提示给出行）。本地 mirror 与 `file://` 不受影响，因此离线与 CI 预置镜像场景无需改动。

## E — mappings v2（monorepo）

- [x] 协议扩展：monorepo 子路径依赖的映射（`path` 字段与 `to` 的关系）、多入口场景
- [x] `mappings validate` 覆盖新字段校验；向后兼容 v1（读取旧文件）
- [x] 协议版本策略：遵循 [schema 版本策略](../guides/configuration.md)
      **结论：`version` 保持 1**——`path` 是可选字段，按策略"同一大版本内只新增可选字段"不递增版本号。
      本节标题里的"v2"指协议扩展，不是版本号（原计划措辞会误导，已在此改写）

**验收**：v1 文件在新工具下可用 ✅（`TestRead_V1FileWithoutPathStaysReadable` + 端到端里"去掉 path 后仍 exit 0 只给警告"）；
monorepo fixture 映射正确 ✅（`TestV03MappingsMonorepoAcceptance`：两子包各自映射到不同 vendor 目录、`path` 显式、
篡改 `path` → exit 3）。
**类型解析（tsconfig paths）在 monorepo 下通过**：机制已在设计复核中用**真实 tsc 7.0.2** 验证
（`paths` 可解析 `github:` 前缀 + 对照实验确认真的生效），而**生成** tsconfig 属于 B 组的交付
（`ngm integrations add`），因此该项的端到端验收留在 B 组。
