# v0.68 复盘 — **把重复的那 4 个 spawn 拿掉**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：评估报告量出的两条结构性浪费都被拿掉了，而且**判据是计数器，不是秒表**。
> 实测：`Put(带材料)` **0 spawn**、`Put(不带材料)` **4 → 2**、
> `install(fresh, 1 依赖)` **10 → 6**、跨层菱形里叶子节点的解析次数 **2 → 1**。

---

## 1. 逐组验收

### 1.1 P1#4：6 spawn → 2（`ArchiveMaterial`）

**修复前的路径**（评估报告逐行量出）：`install` 先 `BuildArchiveDigest`（`ls-tree` +
`cat-file`）算一遍；`Put` 内部再 `BuildArchiveDigest` 一次 + 自己 `ListTree` +
`CatFileBatch` —— 同一份 (mirror, commit) 的树与内容**读了两遍**，
digest 阶段共 **6 个** git 子进程，其中 4 个是纯重复。

**处置**：

| 层 | 改动 |
|----|------|
| `internal/git` | 新增 `ArchiveMaterial`（条目 + 内容 + 清单记录 + digest）+ `BuildArchiveMaterial`；`BuildArchive` 变成它的薄包装——**不存在"优化过的一条路"与"老的一条路"各算各的** |
| `vendor.Put` | `Meta.Material`（`json:"-"`）非 nil 时跳过重算（**0 spawn**），但**仍核对 Commit / Digest 两个身份字段**；不传时内部 `BuildArchiveMaterial` 一次（**4 → 2**） |
| `cmd/ngm` | `installFresh` / `update` 一次算好、把材料带下去 |

**读数**（`internal/vendor` 的断言，仪器 = `git.SpawnCount`）：

```
Put(带材料)   → 0 个 git spawn（内容与清单仍然真的落进 store）
Put(不带材料) → 2 个（ls-tree + cat-file 各一次）——此前是 4
```

**端到端**（`cmd/ngm` 的读数测试）：`install(fresh, 1 依赖)` = **6 个 spawn**，
构成 = 解析（fetch 1 + ls-remote 1 + 上游 manifest 1）+ 晾晒期日期 1 + digest 阶段 **2**；
修复前是 10。

**安全边界没有让步**：`Put` 的身份核对两条（commit 不符 / digest 不符）都有断言；
`installFromLock` 的"lock 声明值 vs 实际内容"校验**保持原样**（见 §3 偏离 1）。

### 1.2 P1#3：先与 `seen` 对账，再解析（跨层菱形）

修复前：`ResolveGraph` 每层**先 `resolveBatch` 再并入 `seen`**，于是跨层菱形
（A→B→D 且 A→C→D）里 D 被完整解析两次——第二次含一次真实的 `EnsureMirror`
（对已存在的 mirror 就是一次 `git fetch`）。复杂度 O(节点) → O(边)。

处置：把"并入"拆成两个阶段——**先与 `seen` 对账**（已见过的 Key 只做
`mergeIntoExisting`：来源合并 + 冲突检测），再对真正的新节点 `resolveBatch`。

**读数**（`internal/resolve` 的外部测试，判据 = `EnsureMirror` 的调用次数，与机器无关）：

```
calls["github:w/leaf"] == 1     （修复前为 2）
leaf.RequiredBy == 两条来源     （跳过解析的那条路径没有丢掉它该做的事）
```

## 2. 未达成项

| # | 项 | 状态 |
|---|----|------|
| 1 | `installFromLock` 的 digest 阶段（4 → 2 已做，但"每次未命中都要重构一遍材料"仍在） | 有意保留：那一次构造**就是校验本身**（lock 的声明值 vs 实际内容）——复用上面的计算会把它变成同义反复 |
| 2 | `Put` 的 `Material` 只做了身份核对，没有做"内容与清单记录的一致性"自检 | 判断：不必要。"材料由 `BuildArchiveMaterial` 产出"是本进程内的构造事实；再哈希一遍全部内容等于把省下的钱又花回去，而它防的场景（本进程内的内存被篡改）不在威胁模型里 |
| 3 | 性能的**时间**读数（本版只有计数读数） | 有意：`git/spawn.go` 的既定口径是"次数优先于秒数"（跨机器方差 ≥ 收益，ADR-022）；秒表留给端到端复核 |
| 4 | `verify` 路径的 `replayDigestFromEntries`（它自己 `ListTree` + 读 store，不经过 `ArchiveMaterial`） | 超出本版范围：verify 有自己的 spawn 预算门禁（2/3 次/依赖），且它的形状（从 store 读字节、不从 mirror 读）与 install 不同 |

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么 |
|---|---------|---------|-------|
| 1 | 让 `Put` "接受调用方已算好的 digest" | 接受的是**整套材料**（条目 + 内容 + 记录），并**保留**不带材料时的重算路径 | 只传 digest 省不下那两个 `ListTree`/`CatFileBatch`（仍是 4 个 spawn）；而 `installFromLock` 的重算**不能省**——它是"lock 与内容是否相符"的唯一检测 |
| 2 | `BuildArchive` 与新材料构建"共用实现" | `BuildArchive` 直接退化成 `BuildArchiveMaterial` + `Manifest()` | 上一版的教训（v0.66 的 tree.go 重复过滤）：**同一件事只允许有一种写法**；两份实现一定会分叉，而这里分叉的后果是"两条路径算出不同的 digest" |
| 3 | 计划里 §2 的读数"`Put(无 material)` → 2（was 4）" | 与实测一致 | — |

## 4. 缺陷清单

| # | 缺陷 | 谁发现 | 处置 |
|---|------|-------|------|
| 1 | digest 阶段每依赖 6 个 spawn、其中 4 个纯重复 | 评估（逐行） | `ArchiveMaterial` + 身份核对 |
| 2 | 跨层菱形重复解析（含真实 fetch） | 评估 | 先对账再解析 |
| 3 | （过程）`Put` 内部"digest 重算 + 单独 ListTree + CatFileBatch"是**三件事描述了同一份数据** | 评估（同上） | 收敛为一次 `BuildArchiveMaterial`——即使不传材料，也从 4 降到 2 |

## 5. 过程洞察

### 5.1 "已有仪器"让性能优化第一次有了**与机器无关的判据**

这一版的两个断言都不是时间：`git.SpawnCount()`（次数）与 `EnsureMirror` 的调用次数。
它们在任何机器上给出同一个数——而"install 快了多少秒"不会。
这也是项目一开始就把 spawn 计数器做出来（v0.05）的回报：
**四版之后，它接住了第一个真正需要它的优化。**

### 5.2 优化最容易伤到的不是性能，是**校验**

`Put` 内部的"重算 digest 并比对"看起来纯属浪费（调用方刚算过），
但它是 installFromLock 里"lock 与内容是否相符"的**唯一检测**。
把两条路径一起"优化"掉，就会得到一个"自证有效"的 store——
本版因此把边界写成两处注释（`Put` 内与 `installFromLock` 内），
并让带材料的路径**仍然核对身份字段**。

> 一句话：**省掉的是重复的劳动，不是重复的检查。**

### 5.3 又一次"同一份事实要有唯一写法"

`BuildArchive` 退化成了薄包装而不是"另写一条快路径"。
这与 v0.66 的 tree.go（过滤条件只有一处）、v0.45（按 flagset 块派生）、
v0.57（来源按行为派生）是同一族决定：
**允许分叉的地方，就会分叉**——而这里分叉的后果是 digest 不一致。
