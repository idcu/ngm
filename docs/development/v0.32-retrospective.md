# v0.32 复盘 — 报告式失败也要说话

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：v0.31 量出非零退出有两种形态，其中**报告**只被断言过"存在"。
> 这一版给它补上契约——**每一条失败项都要配一行"接下来做什么"**——
> 并当场抓出**两处真实缺口**（`audit` 无修复版本时、`tree --osv` 查到漏洞时）。
> 这是本轮系列里**第一次由新网直接抓出产品缺陷**。

| 用例 | 失败项 | 行动行 |

| 探针 | 结果 |
|------|------|
| 把两处新增行动行的 `→` 记号去掉 | 两条用例各自变红，报同一句话：<br>`this report has 1 failing item(s) but only 0 next-step line(s) — a user reading it learns what is wrong but not what to do` |

公告 ID、严重度与修复版本。

## 5. 过程洞察

### 5.1 这一版是**由网抓出产品缺陷**，不是由人

前几版的产品缺陷都是我在读代码/试跑时撞见的。这一版不同：

1. v0.31 把非零退出分成两类，并断言报告那一类**存在**；
2. v0.32 把断言抬到"它该说的话都在"；
3. **跑第一次就抓到两处**——一次是 `audit`（我在探针里读到的），一次是 `tree`（**网报的**，
   我原本没把 `tree` 算进"报告"这一类）。

第 3 步那次 `tree` 的发现尤其值得记：**我并没有想到要去看它**。
判据一旦写成"这一类里的每一条都要满足 X"，它就会去检查我以为已经没问题的东西。

### 5.2 判据不该要求版式统一

第一版判据按 `^✗ ` 认失败项。跑到 `tree` 时它报：

```
a failing report with no failing item (`✗`) in it:
  github.com:my-org/app
  github:x/dep@v1 (tag) → 176b9f0 ✗ 1 known vuln(s)
```

红的是**我的正则**，不是产品——`tree` 把 `✗` 写在行中。
处置：判据改成只数记号本身（**不要求版式统一，只要求该说的话都在**）。
这与 v0.31 "判据不该要求世界符合我的预期"是同一条教训的第二次：
**第一次是"我以为错误身份有很多种"，这次是"我以为失败项都在行首"。**

### 5.3 同一族里"做对的那个"是最有说服力的对照

`tree` 在**没查**漏洞时写着 `vulnerability data not consulted; run \`ngm audit\``——
**提示是有的**。而**查到**漏洞时反而一句不说。

也就是说：这不是"没人想到要给提示"，而是**提示写在了不需要它的那一支上**。
找出"同一族里做对的那个"比讲道理有用得多：它证明这条建议在本项目里是**可行且已被采纳的**风格，
缺的只是有人把它挪到需要的那一支。
