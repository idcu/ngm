## 已修的两条（2026-11-19）

拿到名字与细节之后，两条用例的原因都清楚了，而且**都不是**"CI 环境坏了"这么笼统：

### 1. `TestV129CacheWriteFailureIsAWarning` —— 真缺陷（POSIX 上 `ngm audit` 会直接失败）

失败行：`v129_osv_hardening_test.go:54: a cache write failure must not fail the query:
ConfigInvalid: read the OSV cache: open .../not-a-dir/abc…json: not a directory`

`readCache` 只把 `ENOENT` 当"没有缓存"，其余读错误一律折成 `ConfigInvalid`。
用例把 `CacheDir` 指到一个普通文件上：Windows 上探到的是另一种 errno，于是绿；
Linux/macOS 上是 `ENOTDIR`，于是 `QueryOSV` 直接报错——**缓存读不出来就让审计失败**，
而缓存是优化、不是证据。修法：任何读失败都按未命中处理（同一条原则文件里本来就写着，
只是那一句只覆盖了"缓存损坏"）。

### 2. `TestV127ValidateProbesOncePerEntry` —— 判据自身的环境依赖

失败行：`v127_probe_count_test.go:70: engines validate exit = 5`

`validate` 总会连内置清单（esbuild / tsc / postcss）一起校验，所以它的退出码说的是
"这台机器装没装那三样"，与本用例的命题（每条清单只探测一次）无关。开发机上装了 → 0，
CI 的 hermetic job 没装 → 5。修法：接受 0 或 5，只把 3（探针被拒、探测根本没发生）
当致命——那才会让"探测次数"这句话变成空话。

这两条合起来说明一件事：**CI 的红不是一种红**。它至少混了"POSIX 上的真缺陷"与
"判据偷偷依赖开发机"两类，而两者在没有名字与首行细节时长得一模一样。

## 本轮所做的处置（只做一件：让失败变得可读）

`.github/workflows/ci.yml` 新增三个 `if: failure()` 的 annotation 步骤：

- `failure annotations — packages`：退出码 + 失败包名（≤9 条）；
- `failure annotations — tests`：失败用例名（≤10 条）；
- `failure annotations — real-engine tests`：真引擎 job 的 `FAIL` / `SKIP` 用例名。

为什么是 annotation：`GET /repos/{owner}/{repo}/check-runs/{id}/annotations` **不需要
token**，而 job summary 只在 run 页面上人读、日志与 artifact 都要认证。这 12 天里
公开侧能拿到的只有"exit code 1"，诊断因此只能靠猜。

名字在工作流命令里是**行协议**：`::` 会伪造一条新命令，所以每个名字都过一遍
字符白名单（`tr -cd 'A-Za-z0-9_.-/'`）——与 `internal/core/verify/github.go` 的
`ghEscape` 同一个顾虑。

## 为什么不在同一次里顺手"修"

修需要先知道是哪一层坏了。现在能猜的方向至少有三个（runner 镜像漂移、工具链版本、
某个包的启动期失败），每一个都对应一种"把红改绿但没说清为什么"的做法：换 runner
镜像、放宽超时、跳过某组测试。这个项目对"把没查成写成没问题"最敏感（`ADR-026`
的同一族教训），所以顺序是**先让失败自述，再按名字修**。

下一次跑完，`check-runs/{id}/annotations` 里就会有包名、用例名与退出码。
