### 过程中发现并修掉的三处（不在原六条里）

1. **`ngm.json` 与 `ngm.mappings.json` 写出后是 0600**。三份 `writeFileAtomic`
   里**只有 lock 那份**有 v0.66 加的 `Chmod(0644)`。而这两个文件与 lock 一样，
   是要**提交进 Git、供团队共享**的。同一条缺陷在另外两个文件上还活着。
2. **`#path=..\..\x` 能通过校验**。addspec 那份只按 `/` 切分，反斜杠被当成
   一个普通段名；Windows 上 `\` 是分隔符。
3. `#path=/etc` 与 `--path=/etc` 处置不同（前者去斜杠后接受、后者拒绝）。
   两条都是既有测试钉住的决定，**不是缺陷**——用 `TestV82LeadingSlashIsTrimmedNotRejected`
   把这个不对称钉住，让"顺手统一"变成一次会红的改动。

## 2. 最值得记的两条

### 2.1 「规则写在第二个地方」的代价，这次是**可见的**

三份 `writeFileAtomic` 逐行相同、只差临时文件前缀。v0.66 在其中一份
（lock）修了 0600 权限，**另外两份至今没有**——于是 `ngm.json` 与
`ngm.mappings.json` 每次原子写之后都是 0600。

这不是"少了一处优化"，是**同一条缺陷在两个文件上还活着**，而它之所以活着，
正是因为修复写在实现里而不是规则里。合并到 `internal/atomicfile` 之后，
一处修改同时修好三个文件，并且 `ngm sbom --out` / `ngm attest --out`
（此前是裸 `os.WriteFile`，中断会留下截断文件）也一起走同一条路径。

subPath 那份是同一形态的**第二次**：config 认两种分隔符、addspec 只认 `/`，
于是 `\` 形态在一个入口能过、另一个入口过不了。

### 2.2 「绿」不等于「看见了什么」——这次轮到我自己的判据

`TestV82WriteIsWorldReadable` 在 Windows 上是 `t.Skip`（那里的 `Chmod`
只影响只读位，测不出 0600/0644）。**于是它在这台开发机上是绿的，
却什么也没看**——正是我 v0.81 才批评过的形态。

补了一条**平台无关**的源码级判据 `TestV82ChmodHappensBeforeRename`
（权限必须在 rename 之前设置；带空跑保护）之后，故意删掉 `tmp.Chmod` ⇒
**在本机也红了**。

> 一般的话：**一条判据在自己的开发机上恒绿时，先问它到底跑了没有。**

## 4. 额外销账一条：`pkg:git/…` 的 purl type 已核对

计划 §3 里"purl type 合规性（未核对规范）"这一条，本版核对完毕并销账：
`git` 是**已注册**的 purl type（来源：purl-spec 的 `purl-types-index.json`
与 git 类型定义），语法、必填段、version（"Ideally a commit or tag"——
ngm 给的正是 commit）、subpath 都对得上。

记录了一条**规范自身的歧义**（name 自身含 `/` vs 解析器按最后一段切分），
并说明为什么不影响往返、因此不改形状。见
`TestV82PurlMatchesTheRegisteredGitType`。

> 值得记的是：**核对只花了几分钟**。它在清单里挂了很久，
> 而"未核对"与"忘了"在清单里长得一样——这正是 v0.82 的主题。
