## A — 在线 verify 的成本与方差

目标不是"更快"，而是**把"贴着线"变成一个能站住的结论**：要么最大值进线，要么写下"不可达 + 根因"。

- [x] A1 **先立 ADR**：[ADR-015](../adr/adr-015-commit-ref-resolution.md)。开工前的读码把假设改了两次——
      ①commit 型**并不发 `ls-remote`**（`ResolveRef` 对它是纯字符串处理）；
      ②它发的是"读 mirror 的 remote.origin.url"那次子进程，而结果对 commit 分支**根本用不到**。
      因此决定收紧成：**commit 型不做 ref 解析，零子进程**。ADR 里回答了那两个问题：
      怎么证明本地已有该 commit（不需要——"是否存在"由必须读它的 digest 重放负责），
      以及会不会漏掉"远端不再提供它"（不会——`ls-remote` 列的是 ref，回答不了某个未引用 commit 的存在性，
      也就是说这件事**从来就查不了**）。**已实现**：commit 型 3.00 → **2.00 次/依赖**。
- [x] A2 **仪器先于改动**：`git.SpawnCount()`（`internal/git/spawn.go`，三个启动点都记账）。
      第一次测量就给出了清单：在线 verify **commit 型 2.00 次/依赖 / tag 型 4.00 次/依赖**
      （4 次 = config + ls-remote + ls-tree + cat-file，与 v0.1 复盘写的"每依赖 4 次"吻合）。
      门禁式断言在 `TestV05RefResolutionSpawns`（commit **0** 次 / tag **≥1** 次，两条互为对照）；
      清单打印在 `TestV05VerifySpawnInventory`（证据，不作门禁）。
- [x] A3 复测：**5 次采样 + 受控对照**。⚠️ 结果与预期不同，两条都要读：
      ①**A4 确实快了 15–18%**（受控 A/B：对照组中位 2.416s / 最大 2.433s → 实验组中位 **1.969s** /
      最大 **2.078s**）；②但复核里那次 3.068s **不是**取数策略造成的——今天同一台机器上
      **对照组**（等于没做优化的状态）最大只有 2.433s。也就是说**跨机器状态的方差大于本次收益**。
      结论：A3 的"最大值 < 3s"在今天的采样里**对照组也满足**，因此不许写成"A4 让它达标了"。
      真正的收获是下面这条方法论：**次数优先于秒数**——`git.SpawnCount()` 不受机器状态影响，
      而秒数会（同一份代码今天的采样相差 0.3s）。
- [x] A4 mirror 的远端地址改用**本地文件读取**，形状不符时回退子进程（[ADR-016](../adr/adr-016-mirror-url-local-read.md)）。
      依据：第 4 次 spawn 是 `git config --get remote.origin.url`（**30.6 ms/次，约占每依赖 spawn 成本的 17%**），
      而该值就明文写在 mirror 的 `config` 里（git 自己写的，ngm 从不改写它）。
      **已实现**：tag 型 **4.00 → 3.00 次/依赖**。
      过程中被断言抓住一处**只有实测才会知道**的细节：Windows 本地路径 URL 在 config 里是
      `C:\\Users\\...`（**未加引号但用了转义**），而 `--get` 回来是单反斜杠——
      第一版原样返回文件文本，于是与 git 不一致。现在只实现 `\\` → `\` 一种还原，其余回退。
      验收：三条断言（**永不与 git 不一致** / 常见形状**确实**走快路径 / 不敢承诺的一律回退，
      含 include·多值·引号·旧式点号·extensions 五类"必须拒绝"的夹具）；
      门禁 `TestV05RefResolutionSpawns` 断言 tag 型**恰好 1 次** spawn——
      对照组（临时关掉快路径）下它准确报出 `got 2` ✓。

**验收**：100 依赖在线 verify 的**最大值 < 3s**（≥5 次采样）。
若达不到，退而求其次是**同等具体**的结论：写下未达标、根因、以及"这条目标是否定错了"
（例如把目标改成"中位 < 3s 且最大值 < 4s"）——**但不允许**再出现"单次读数达标"。

## B — 可复现性：把翻案条件判掉

[ADR-013](../adr/adr-013-remote-adapter.md) 决定不发布 `remote` adapter，并留下可证伪的翻案条件：
"产物可由用户本地复现"。它已经"在收敛"两个版本了；**再放一版就会变成一句没人复核的旧话**。

- [x] B1 触发 `workflow_dispatch`（本环境此前无法触发，本轮由使用者提供凭证后完成），
      确认 `compare` job 给出四层判定。**结果：`REPRODUCIBLE ACROSS MACHINES`**——
      3 个平台（Linux x86_64 / Windows x86_64 / macOS arm64）× **7 个形态**产物字节一致，
      `treeA=7412c584ca107988`。**但这花了四次迭代，而前三次红的是探针自己**：
      ①整棵树不同（macOS 上连同一台机器的两个目录都不同）；
      ②逐形态定位 → `esbuild-plugin`；③再拆成两个文件 → `plugin.metapaths` 差异、
      **`plugin.appjs` 一致**；④metafile 移出产物树、降级为观察项。
      根因：**第一版探针把 esbuild 的 metafile 当成了产物**，而它的字节根本不稳
      （本机专项实测 20 轮：`app.js` 1 个取值、metafile **20** 个取值；递归排序后仍是 20 个，
      变的是数组元素顺序），且其中的路径字符串在 macOS 上会因 `/var` → `/private/var`
      符号链接而与目录名有关。产物的可复现性从头到尾都成立。
- [x] B2 据结果判定翻案条件，写进 [ADR-013](../adr/adr-013-remote-adapter.md)：
      **条件第 1 条的技术前提已具备实测支撑**（"先实测某个真实引擎能做到"那半句）；
      **结论仍是不发布**，但理由构成变了——剩下的是产品问题（用户是否愿意抽样构建一遍）
      与"合成夹具 vs 真实项目"的差距。**发布与否是另一个决策，须另立 ADR 修订 ADR-013**
      （该 ADR 自己的纪律），已登记为 v0.5 收尾项。
- [x] B3 "引擎版本一致"这一层的前提写进 ADR（版本不同的两份字节恰好相同纯属巧合），
      并把 **`node` 也纳入这一层**：它一直**被打印却没有被判定**——第一次跑就显示
      macOS 是 v22.23.2、Linux 是 v22.23.3。**印出来不等于被检查。**

> 本组顺带产出一条对用户的提醒（写进了 ADR-013）：**把 esbuild 的 metafile 放进产物目录的项目，
> 在 macOS 上会得到依赖机器的字节**——它是诊断文件，别拿它做可复现性判定。

**验收**：ADR-013 里"翻案条件"一节给出**成立或不成立**的结论 + 可复现的命令与结果；
不得再以"在收敛"结束。✅ 已满足（结论：技术前提成立、仍不发布、发布需另立 ADR）。

## C — 权限施加点的机械核对

v0.5 复核只重审了沙箱（唯一运行他人代码的路径）。其余施加点至今靠人工记忆，
而人工清单在本项目**已经连续失效五次**（`verifyOnLock` / `permissions` / `SubPaths` /
`git.tokenEnvVars` / `engines.typeDecl`）。

- [x] C1 枚举权限面（`read:` / `write:` / `net:` / `run:` / `env:`）在代码里的**每一处施加点**。
      做的第一件事不是读文档而是**数出口**——于是两处缺口当场现形（详见下）。
- [x] C2 做成机械检查（与 `internal/config/field_wiring_test.go` 同型）：
      `internal/security/enforcement_test.go` 三张网——①每个命名空间必须登记施加点与
      "改了配置行为就变"的测试，且该测试**真的存在**（扫源码，不靠名字形状猜）；
      ②文档的施加点表必须提到该命名空间；③**HTTP 出口必须登记**
      （`TestHTTPEgressIsRegistered`：新增一个 `net/http` 出口而不登记就红）。
      另有 `internal/git` 侧的 `TestSpawn_OnlyOneFileBuildsProcesses`：
      git 子进程只能有一个构造点。**三条检查都验证过会红**
      （名单腐烂、出口未登记、构造点被搬走各试过一次）。
- [x] C3 缺陷处置：两处都**接线**（没有降到"改文档"），并各自补端到端断言。见下。
- [x] C4 **裁决 `read:` / `write:`**：两者默认允许，且**不在 ngm 自身路径上施加**——
      "读项目、写 vendor 与 lock"本就是 ngm 的职能，第一个真正需要拦下的场景是沙箱
      （那里 `read:` 按依赖子树授予、`write:` 恒不授予）。这条裁决写进了安全模型的表，
      并由 C2 的检查要求"不许留白"。

### 本组查出的两处缺口（都属于"声明了、不生效"）

**① `run:git` 只挡住了三个出口中的一个。** 文档写着施加点是
"`git.Run`（**所有** git 子进程的出口）"，而包里有一处 `RunAllowFailure`
（`cat-file -e` / `merge-base --is-ancestor`）与一处 `CatFileBatch`（digest 重放）
**各自直接 exec**。实测：`deny: ["run:git"]` 下前者照样执行成功（`err == nil`），
后者启动了 1 个进程。处置：三个出口收进唯一的构造点 `newGitCommand`
（门禁与计数都只在那儿），并由 `TestSpawn_GateOnEveryExit` 逐个出口断言
"拒绝 + **计数器为 0**"——只看错误码会漏掉"报错了但进程还是起来了"。

**② `ngm audit` 的 OSV 查询没有 `net:` 门禁。** `internal/supplychain` 里一个
`CheckNet` 调用都没有，于是写着 `allow: ["net:github.com"]` 的用户，
`ngm audit` 照样连上 `api.osv.dev`——同一个配置文件，`ngm install` 会 `exit 3`
而 `ngm audit` 不会。处置：判定放进 `queryRemote`（**只有它知道最终主机**，
`NGM_OSV_URL` 可改端点），在发起请求前执行；命中缓存与 `--offline` 不碰网络，因此不需要它。
端到端断言 `TestV05AuditNeedsNetPermission`：不授权 → `exit 3` 且替身**零命中**；
授权 → 同一个调用通过。顺带发现**三条既有验收**此前正是靠"没有门禁"才一直能连本地替身
（现在它们显式授权 `net:127.0.0.1`，顺便成了这道门禁的活证据）。

> 两处的共同点与 A/B 组同型：**规则写在第二个地方，就一定会有一处不一致**。
> 因此 C 组的产出不只是两个修复，而是三条让"下一个出口"无法悄悄漏掉的机械检查。

**验收**：权限面上没有"声明了、不生效"的项；每项有一条"改了配置 → 行为变了"的端到端断言；
`read:` / `write:` 的裁决已写进文档，且被检查要求不得留白。

- [x] 在线 verify（100 依赖，≥5 次采样）**最大值进线**，或给出"同等具体"的未达标结论
      → 最大 **2.078s < 3s**；但**对照组（未优化）也过线**（2.433s），
      因此真正的结论是"这条目标线在噪声里不可判别"（复盘 §2.3）
- [x] ADR-013 的翻案条件有**成立 / 不成立**的明确结论
      → 技术前提**成立**；ADR-013 **仍不发布**；发布与否须另立 ADR
- [x] 权限面的机械检查在 CI 里生效（缺断言即失败）
      → 三张网，都在 `go test ./...` 的覆盖内
- [ ] `v0.2.0` / `v0.3.0` / `v0.4.0` 三版在 GitHub 与 Gitee 均可取到，附件数 7、`SHA256SUMS` 一致
      → **GitHub 侧满足（3 × 7）；Gitee 侧 21 个附件待人工上传**（本版唯一残项）
- [x] 文档同步：命令参考 / 退出码 / 配置字段三处与实现逐条对齐（v0.5 复核已做一轮，
      本版改动后需再对一次）→ 已随本轮改动同步；配置字段与退出码本版未改语义
