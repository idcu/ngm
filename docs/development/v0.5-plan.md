## A — 在线 verify 的成本与方差

目标不是"更快"，而是**把"贴着线"变成一个能站住的结论**：要么最大值进线，要么写下"不可达 + 根因"。

- [x] A1 **先立 ADR**：[ADR-015](../adr/adr-015-commit-ref-resolution.md)。开工前的读码把假设改了两次——
      ①commit 型**并不发 `ls-remote`**（`ResolveRef` 对它是纯字符串处理）；
      ②它发的是"读 mirror 的 remote.origin.url"那次子进程，而结果对 commit 分支**根本用不到**。
      因此决定收紧成：**commit 型不做 ref 解析，零子进程**。ADR 里回答了那两个问题：
      怎么证明本地已有该 commit（不需要——"是否存在"由必须读它的 digest 重放负责），
      以及会不会漏掉"远端不再提供它"（不会——`ls-remote` 列的是 ref，回答不了某个未引用 commit 的存在性，
      也就是说这件事**从来就查不了**）。**已实现**：commit 型 3.00 → **2.00 次/依赖**。
- [x] A2 **仪器先于改动**：`git.SpawnCount()`（`internal/git/spawn.go`，三个启动点都记账）。
      第一次测量就给出了清单：在线 verify **commit 型 2.00 次/依赖 / tag 型 4.00 次/依赖**
      （4 次 = config + ls-remote + ls-tree + cat-file，与 v0.1 复盘写的"每依赖 4 次"吻合）。
      门禁式断言在 `TestV05RefResolutionSpawns`（commit **0** 次 / tag **≥1** 次，两条互为对照）；
      清单打印在 `TestV05VerifySpawnInventory`（证据，不作门禁）。
- [ ] A3 复测：`NGM_BENCH=1` **至少 5 次**采样，metrics 里同时给**中位与最大**。
      ⚠️ **A1 不会改善这个基准**：它是 100 个 **tag** 型依赖，而 tag 型仍是 4 次/依赖。
      按实测成本表（config 30.6ms / ls-remote 77.8ms / ls-tree 36.4ms，每依赖约 183ms），
      要让它进线得砍掉 **A4** 那一次。
- [ ] A4 **（本轮新增，A3 的前置）** mirror 的远端地址改用**本地文件读取**，形状不符时回退子进程。
      依据：第 4 次 spawn 是 `git config --get remote.origin.url`（**30.6 ms/次，约占每依赖 spawn 成本的 17%**），
      而该值就明文写在 mirror 的 `config` 里（git 自己写的，ngm 从不改写它）。
      **前提**：手写解析必须处理 include / 引号 / 多值等情形，因此**只接受最简单的形状**，
      其余一律回退到子进程——不允许"猜一个地址"，那会把"解析能力不足"变成"问了错的远端"。
      验收：等价性断言（fast path 的结果必须与 `git config --get` 逐字相同，含 SSH / 带空格 / 多值 /
      含 include 四类夹具）+ 回退路径的断言 + A3 的采样。

**验收**：100 依赖在线 verify 的**最大值 < 3s**（≥5 次采样）。
若达不到，退而求其次是**同等具体**的结论：写下未达标、根因、以及"这条目标是否定错了"
（例如把目标改成"中位 < 3s 且最大值 < 4s"）——**但不允许**再出现"单次读数达标"。

## B — 可复现性：把翻案条件判掉

[ADR-013](../adr/adr-013-remote-adapter.md) 决定不发布 `remote` adapter，并留下可证伪的翻案条件：
"产物可由用户本地复现"。它已经"在收敛"两个版本了；**再放一版就会变成一句没人复核的旧话**。

- [ ] B1 触发一次 `repro-probe`（手动 `workflow_dispatch`），确认 `compare` job 对**新形态**
      （loader 链 / CSS 压缩链 / esbuild 插件 + metafile）给出四层判定：自检成立 / 无构建失败 /
      引擎版本一致 / 产物哈希一致。
- [ ] B2 据结果**判定**翻案条件，并写进 ADR-013：

| 情形 | 结论怎么写 |
|------|-----------|
| 三平台字节一致，且用户抽样本地复现可行 | 条件**成立** → 该不该发布 remote adapter 成为一个新决策（另立 ADR，不在本版直接发布） |
| 任一平台不一致，或"引擎版本不一致"拦下 | 条件**不成立**，写下反例与根因；挂账条件改为可证伪的新条件 |
| 探针本身没能给出结果 | **写"未测量"**，并说明探针为什么没跑成——不得读成"通过" |

- [ ] B3 把"**引擎版本一致**"这一层的前提写进 ADR：版本不同的两份字节恰好相同纯属巧合，
      因此比对必须拒绝它。

**验收**：ADR-013 里"翻案条件"一节给出**成立或不成立**的结论 + 可复现的命令与结果；
不得再以"在收敛"结束。

## C — 权限施加点的机械核对

v0.5 复核只重审了沙箱（唯一运行他人代码的路径）。其余施加点至今靠人工记忆，
而人工清单在本项目**已经连续失效五次**（`verifyOnLock` / `permissions` / `SubPaths` /
`git.tokenEnvVars` / `engines.typeDecl`）。

- [ ] C1 枚举权限面（`read:` / `net:` / `run:` / `env:` / 写权限）在代码里的**每一处施加点**，
      对每处要求三件事齐全：定义位置、读取位置、**读到的值真的改变了分支或输出**。
- [ ] C2 做成机械检查（与 `internal/config/field_wiring_test.go` 同型）：
      **缺断言即失败**，而不是"下一个人记得核对"。
- [ ] C3 查出缺陷时的处置沿用复核已定的判据：**要么接线、要么从配置面与文档里一起删掉**；
      不允许"保留但文档含糊"。

**验收**：权限面上没有"声明了、不生效"的项；每项有一条"改了配置 → 行为变了"的端到端断言；
若某处判定为"仅声明与展示"，必须在文档里写明。

## D — 交付：v0.2 ~ v0.4 补发布

**这是当前唯一的"用户拿不到东西"的问题**：仓库里 v0.2 / v0.3 / v0.4 都已交付，
但补发前发行源上只有 `v0.1.0`——三个版本的产物在 GitHub / Gitee 上都取不到。

- [x] D1 逐个确定每版的交付提交（该版最后一次提交），打**附注 tag**（`git tag -a`）。
      **已完成**：`v0.2.0 → 51e5e29`、`v0.3.0 → f78d0c0`、`v0.4.0 → 03e6426`
      （各自"加复盘"那次提交，因此 tag 的树里同时含有该版代码与它自己的复盘）。
      推送前另核对了三项前提：流水线与发布脚本在三个落点上与当前一致、
      `GO_VERSION=1.27` 满足各落点的 `go 1.22.0`、三个落点当时的 CI 都是绿的。
- [x] D2 让 `release.yml` 在各自 tag 上重建产物（流水线**先跑全量测试**再交叉编译六平台）。
      **已完成**：三次运行 `completed / success`（14:17 触发 → 14:19:34 / 14:19:56 / 14:20:00 发布）。
- [ ] D3 核对 GitHub release 的 7 个附件 ✅ **已核对**（三次各 7 个：6 平台二进制 + `SHA256SUMS`）；
      **Gitee 侧附件仍需人工上传**（无 API token），共 3 × 7 = 21 个文件。
- [ ] D4 抽查：两个源同一文件名的 `sha256` 必须相同（共用同一份 `SHA256SUMS`）——**待 D3 完成后做**。
- [x] D5 把"**版本交付即打 tag**"写进[发布清单](./README.md)的第 0 步，
      并说明代价：不发 tag 等于"这版只存在于源码里"。

**验收**：`v0.2.0` / `v0.3.0` / `v0.4.0` 在 GitHub 与 Gitee 上各有 7 个附件，
`SHA256SUMS` 一致；三项抽查记录写进[发布清单](./README.md)或对应复盘。

> **当前状态**：GitHub 侧已满足（3 × 7）；**Gitee 侧未满足**——在传完之前，
> [安装指南](../guides/installation.md)把 Gitee 列为国内推荐源，那三版走推荐路径会 404。
> 补发记录与待传清单见[发布清单](./README.md)。

## E — 挂账项里**可验**的部分

- [x] E1 `deno bundle` 继续挂账（条件：上游把 bundle 标为稳定；截至 2026-10-01 仍是
      "experimental and subject to changes"，来源见 [ADR-012 补测](../adr/adr-012-sandbox.md)）。
      **已完成可验的那一半**：`deno bundle` 的实验性提示必须真的到达用户。
      做这件事时发现它**此前到不了**——提示由 deno 的翻译器产出（`inv.Notes`），
      而 bundle 的结果类型里没有这个字段，写好了没人读；对照之下 css 路径**恰好相反**，
      引擎的 stderr 被整个丢掉。两条通道都已修，验收
      `TestV05EngineChannelsAcceptance`（4 条，**验证过回退修复即红**）。
      另外顺带固定了版本闸门：低于 2.4 时 exit 5 并指向 esbuild——这条路径此前没有任何测试。
- [ ] E2 复核里登记过、本次**不做**的一项：内容寻址 store / mirror 的 GC
      （见 [ADR-003 补录](../adr/adr-003-vendor.md)）。理由：**没有实测的磁盘增长数据**
      支撑它的优先级；等有数据再排期，而不是因为"迟早要做"就塞进本版。

**验收**：E1 有断言；E2 保持挂账并写明缺的是哪一项数据。

## v0.5 总验收

- [ ] 在线 verify（100 依赖，≥5 次采样）**最大值进线**，或给出"同等具体"的未达标结论

## 本版明确不做（避免范围蔓延）

| 方向 | 为什么不是现在 |
|------|---------------|
| `remote` adapter 的发布 | 它的翻案条件正是 B 组要判的东西；**判完再议**，本版不发布 |
