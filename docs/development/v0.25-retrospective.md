## 1. 逐组验收

### 1.1 判据先量：朴素版误报 27/62 ✅（这一步救掉了整版）

第一版判据是"活文档里所有反引号驼峰标识符都必须是 json 字段"。探针结果：

| 误报类型 | 例子 |
|---------|------|
| Go API | `resolve.Normalize` · `testutils.GitInit` · `adapter.Runner` |
| 配置键 | `importMap` · `minimumDependencyAge` |
| Git 配置键 | `core.hooksPath` · `gpg.ssh.allowedSignersFile` |
| 占位符与散文 | `vX.Y` · `xxxUsage` · `t.Logf` |

62 个 token 里 27 个不成立。

> **误报的真正代价不是"网红了"，而是人会去放宽判据，直到它什么都抓不到。**
> 所以收紧到"只查那两张表里的键"——判据的**范围**也是判据的一部分。

### 1.2 A 组 — `--json` 形状表 vs 实现 ✅

`cli.md` 的表里点名的每个键，必须在**该命令的报告实现**里作为 json tag 存在：

```
`--json` shape table: 9 commands, 48 documented keys checked against the implementation
```

与 v0.16 那张网的分工：**v0.16 证明"运行时的输出确实长这样"，这一张证明"文档写下来的形状没跟实现脱节"。**

### 1.3 B 组 — `configuration.md` 三张字段表 vs schema ✅

```
configuration.md: 3 field tables, 19 documented keys checked against the schema
```

用户的动作是照着这三张表写配置——**表里多一个键，用户就写不出一份能读的配置。**

## 5. 过程洞察

### 5.1 判据先量再写；**误报会逼你放宽判据**

D1/D2 两次都是"网报了一大堆问题，而问题在网这边"。
如果在一个"网红了就要人处理"的环境里，这种误报的结局是**判据被放宽到无害**——
而"无害"与"无用"在这里是同义词。**先量一遍，再决定判据写到多宽。**

### 5.2 映射是这类网唯一会骗人的地方

这两张网不解释实现、也不执行命令，它们只做一件事：**把文档里的名字拿到实现里找**。
于是唯一的出错方式是**找错了地方**——而找错地方的表现是"报出一堆不存在的字段"，
**看起来和"文档真的错了"一模一样**。
所以映射表要写在显眼处、每条都要有"命中文件数 > 0"的守卫、教训要写在注释里。

### 5.3 网的边界要写下来，否则它会被当成更宽的保证

两张网都只证明"**写了的都真的存在**"。它们**不**证明"该写的都写了"。
这一句写进了网的文档注释里，也写进了计划与复盘——
因为一张"看着字段清单"的网，很容易被读成"字段清单是完整的"。
