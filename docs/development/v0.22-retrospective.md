## 5. 过程洞察

### 5.1 "实测退 0"未必是缺陷——先问"这个状态本来就该退这个码吗"

`update --all` 在漂移 + `verifyOnLock` 下退 **0**。第一反应是"声明写错了"，
但停一下就会发现：**`update` 的语义就是修好漂移**（重新解析、重新锁定），
更新之后哪还有漂移？所以 0 是**正确**的，错的是"拿漂移当触发条件"。
**读数与预期不符时，有三个可能**：产品错了、声明错了、**我的触发条件根本不该产生那个码**。
先排除第三个，再谈前两个——否则会去"修"一个没坏的东西。

### 5.2 全局且不可逆的操作，必须在网的结构里体现出来

`t.Setenv("PATH", t.TempDir())` 是全局的、且要到测试结束才还原，而夹具要用 git 建。
第一次把"缺 Deno"的用例混在主循环里，结果是**后面的夹具全建不起来**（`git not in PATH`）。
处置是把它们拆成专属测试，主网用 `exitCodeElsewhere` 记住"这 3 条在别处测"。
**"测试的顺序依赖"不该靠纪律记着，该被写成结构**。

### 5.3 环境变量和夹具一样会泄漏

本版第三次踩"状态耦合"：D2 的 `FAKE_EXIT` 残留。前两次是目录共享与 OSV 端点残留。
合起来得到一条通用规则：**每个用例要么重建它依赖的一切，要么显式设置它依赖的一切**——
"上一条设过"不是依赖，是巧合。
