# v0.94 计划 — **把"等推送"那件事做掉（并把前提纠正过来）**

> 来源：README / 各版复盘里挂着"需要推一个 monorepo 远端库"的那条（从 v0.79 起）。
>
> 一句话目标：`subPath` 端到端做成**常驻判据**——顺带纠正那条前提里两处想当然。

---

## 1. 先质疑前提

那条前提是："没有一个 monorepo 形态的远端库可推 ⇒ `subPath` 端到端做不了"。
两处需要分别验：

| 假设 | 验证 | 结论 |
|------|------|------|
| 起个本机 `git daemon` 就有"远端"了 | 真起了一个（`git daemon --export-all`，`git://127.0.0.1:9419`，克隆成功） | **半条腿**：地址能解析、回环主机 v0.83 已放开（ADR-029 ✓），但**抓取协议只有 ssh / https**（`git.defaultProtocol`，`protocol.go` 只认这两个）⇒ install 会把 canonical 重建成 `https://127.0.0.1/…` 去连 443 ✗ |
| 端到端必须过"抓取"那一关 | 读 `subPath` 的实现位置 | **不必**：过滤子目录、写 `path`、按子包 `exports` 推入口，全在 vendor / mappings 层 |

⇒ 结论：**用仓库既有的本地镜像设施**（`seedMirror` + `--offline`）就能把 subPath 的契约
走完整；而"真正的 fetch 端到端"仍然需要一个 https/ssh 远端（那条另说）。

## 2. 计划

| # | 项 | 验收 |
|---|----|------|
| 1 | 真实 monorepo（根 + `packages/a` + `packages/b`）⇒ `init → add #path= → update --all --offline → install --offline → verify → mappings validate` | 六步全绿 |
| 2 | 契约断言：只有子包被 vendor · 声明 `path` 对 · mappings 指向子包 `exports` | 兄弟包一个文件都不许进来 |
| 3 | 反面：不存在的子路径 | `add` 只写声明（发现不了，合理）；`update` 明确失败且不留半个 vendor |
| 4 | 把探路时踩到的三件事写进测试注释（免得下一个人重走） | 显式端口被拒 · 路径至少两段 · Windows daemon 残骸要杀进程树 |

## 3. 不做

- 不推 tag / jsonkit（仓库所有者的动作）；
- 不做"https 远端的 fetch 端到端"（需要 TLS 或真远端；本地自签证书那条要单独论证）；
- 不改 `git.defaultProtocol` 只支持 ssh/https 的判断（那是设计：`git://` 无完整性保护）。
