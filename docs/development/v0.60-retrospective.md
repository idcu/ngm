# v0.60 复盘 — **两条通道对"写不出去"必须判法一致**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：人读路径从前**忽略**写失败（`fmt.Fprintf` 的返回值被丢掉），
> 于是"报告只写出去一半"与"成功"在退出码上**分不出来**——
> 而 JSON 路径**一直**检查 ✓。这一版把两条通道调成**同一条规则**：
> 在**唯一入口**包一层记账 writer，命令本来成功而 stdout 写失败 ⇒ **6**。

---

## 1. 逐组验收

### 1.1 起点：同一条通道里判法不一致（实测）

| 调用（stdout 永远写失败） | 改前 | 改后 |
|--------------------------|------|------|
| `ngm verify`（人读） | exit **0** · stderr 空 ✗ | exit **6** · `write report: …` ✓ |
| `ngm why` | exit **0** ✗ | exit **6** ✓ |
| `ngm outdated` | exit **0** ✗ | exit **6** ✓ |
| `ngm tree` | exit **0** ✗ | exit **6** ✓ |
| `ngm engines list` | exit **6** ✓（它检查了 `tw.Flush()`） | exit **6** ✓（走自己的分支，消息不变） |
| `ngm --help` | exit **0** ✗ | exit **6** ✓ |

`engines` 那一行是本版最有力的依据：**同一份代码里已经有人决定"写失败算失败"** ✗——
只是其余几处把错误丢了。

### 1.2 处置：唯一入口包一层，而不是逐命令加检查

```go
// dispatch（唯一入口）：
acc := &writeAccounting{w: stdout}
code := dispatchInner(args, acc, stderr)
if code == 0 && acc.err != nil {
    fmt.Fprintf(stderr, "write report: %v\n", acc.err)
    return errs.CodeInternal.ExitCode()   // 6
}
return code
```

三点设计：

| 决定 | 为什么 |
|------|-------|
| 包在 `dispatch` 里（唯一入口） | 一处覆盖**所有**命令与 usage/`--help` 那类写；不必改十几个调用点与签名 |
| 只折算 `code == 0` 的情形 | **业务失败优先**：命令自己退了非 0（如"上游漂了"），写不出去不改变那件事 |
| `Write` 返回**真实错误** | 本来就检查错误的命令（`engines`）仍走自己的分支 ⇒ 行为不变、消息不变 |

### 1.3 判据 ✅

`TestV60TheHumanChannelTreatsWriteFailureTheSameWay`：**6 个写失败场景退 6** +
**6 条对照仍退 0**（对照才是重点——否则"什么都退 6"也能通过）。

读数：**6 write-failure case(s) exit 6 · 6 control(s) still exit 0** ✅

### 1.4 牙齿 ✅（而且"红得刚好"）

把那层记账去掉（回到旧行为）⇒ 红 **5 处**：`verify` · `why` · `outdated` · `tree` · `help` ✓——
**`engines` 不在其中** ✓，因为它本来就检查错误 ✓。

> 牙齿的形状在这里也是判据的一部分：**该红的 5 处红、不该红的那处不红**，
> 比"全红"更能说明判据看的是它对的东西。

### 1.5 判据侧的一处连带：V57 抓到新站点

包装里那处 `return errs.CodeInternal.ExitCode()` 是一处**新的退 6 站点** ⇒
v0.57 的判据当场报"不在登记里" ✓ ⇒ 登记并写明它是"人读通道的写失败" ✓。
读数从 **29 处 / 21 个函数** 变成 **30 处 / 22 个函数** ✓。

## 5. 过程洞察

### 5.1 "不一致"本身就是证据

这一版最好的论据不是"应该退 6"，而是**同一份代码里已经有人这么做**：
`engines` 检查了 `tw.Flush()`，其余的路径不检查 ✗。
于是问题不是"该选哪个语义"，而是"**为什么同一件事有两套判法**"✓。

> 与 v0.57 那条"一个数字兜着两件事"同族：**同一件事有两种处理**，
> 通常意味着其中一处只是没人看。

### 5.2 一处包装 > 十几处检查——但有代价

在唯一入口包一层，覆盖面最广、改动最小 ✓。代价是**位置远离症状** ✗：
读 `verify.go` 的人不会立刻知道"写失败会退 6"。所以
它必须在**文档**（`cli.md` 的全局约定 + `observability.md` 的码 6 行）与
**判据**（本版那条网）里写清——**远离症状的改动，靠文档与判据补回它的可见性**。

### 5.3 假失败比假成功好

改前：写失败 → 退 **0**（**假成功**：脚本会以为验证通过了 ✗）。
改后：写失败（含管道被打断）→ 退 **6**（**假失败**：`| head` 也会失败 ✗）。

> 两害相权：**假失败**会让人多看一眼，**假成功**会让人错过。
> 惯例（`EPIPE` 安静退出）值得考虑，但那是**下一个决定**——先把两条通道拉齐。
