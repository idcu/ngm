# v0.51 复盘 — **失败路径上也要有机器可读的那一份**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：`--json` 的命令失败时，脚本此前只能拿到"退出码 + 空 stdout + 一段人读文本"——
> 这一版补上**错误信封**，并把 v0.16 规则④**带着证据**改写成
> "要么为空、要么恰好一份报告或信封"。
> 而它带出的第二件事：**"归一化清单"那条挂了四版的候选**，这一版收成了一处共享助手。

---

## 1. 逐组验收

### 1.1 错误信封 ✅

```json
{
  "version": 1,
  "error": {
    "code": "ConfigInvalid",
    "exitCode": 3,
    "message": "no ngm.lock found at /path/to/ngm.lock",
    "hint": "run `ngm install` to resolve dependencies and create the lock"
  }
}
```

| 字段 | 与人读那侧的关系 |
|------|-----------------|
| `code` | 同一个显示名（`NgmError.DisplayName`，`Labeled` 覆盖也算） |
| `exitCode` | **等于进程退出码**（v0.16 第③条规矩的同一件事） |
| `message` | 同一条消息 |
| `hint` | **逐字相同**——v0.50 立的那条纪律，在失败路径上继续成立 |

实现只有一处：`runErr`（`cmd/ngm/main.go`）——它是**唯一**的错误渲染点。
"用户要的是机器可读输出"这件事只有命令内部知道，于是命令在 `fs.Parse` 之后
把 ctx 标一下（每个命令**一行**），`runErr` 从 ctx 里读。

> 为什么不给 300 个 `runErr(ctx, …)` 调用点各加一个参数：
> 那是一次机械的大改；而 ctx 本来就从命令流到 `runErr`。

读数：**9 条失败路径**带着完整信封与同一句话（另有若干条是**报告**式失败，
它们本来就有报告可给）。

### 1.2 规则④改写（带证据的契约变更）✅

| | 原规则（v0.16） | 新规则（v0.51） |
|---|---|---|
| 失败时 stdout | **必须为空** | **要么为空**（命令不接受 `--json`）**、要么恰好一份**报告或错误信封 |
| 理由 | "我没有报告可给"不能用半份 JSON 表达 | **同一条理由仍然成立**——报告不许半份；而**错误信封不是报告** |

`docs/guides/cli.md` 的四条规矩与形状说明同步改过，并写明了改动的原因与版本。

### 1.3 "归一化清单"收成一处 ✅（被这一版带出来的）

改完信封之后，**v0.43 的布尔 flag 网红了四条** ✗——因为信封里的锁文件路径
在 JSON 里是**转义**过的（`C:\\…`），而那张网拿**原样**的路径去 `ReplaceAll`，
匹配不上，于是判据把"两次跑的路径不同"当成"`--json=true` 与 `--json` 不等价"。

这是"**本次运行生成的路径跑进被比较的输出**"的**第四次**：

| 版本 | 形态 |
|------|------|
| v0.45 | `store prune` 印 content store 的绝对路径 |
| v0.47 | hint 里印隔离 home 的 `~/.ngm/config.json` |
| v0.50 | 两个通道各跑一次，两边路径不同 |
| **v0.51** | 错误信封里的锁文件路径（**且在 JSON 里是转义的**） |

前三次都在各自的网里**当场补一个 `ReplaceAll`** ✗ ——于是换一张网又踩 ✗。
这一版立**一处共享助手** `normalizeRunPaths`（按原样 / JSON 转义 / 斜杠三种形态替换），
并把四个网（v0.43 / v0.45 / v0.47 / v0.50）迁过去。

> 这条候选在 v0.47、v0.48、v0.49、v0.50 的候选表里挂了**四版**，
> 而它自己的形态正是 v0.44 那条教训（"未证明/未处理会一直挂"）的活标本。
> 它最终被**做掉**的代价：一个 25 行的助手 + 四个网各一行迁移。

## 5. 过程洞察

### 5.1 契约可以改——但要带着证据改，并把原意说清

规则④的原意是"**报告**不许半份"。错误信封不是报告，所以它不违反原意——
但如果只改代码不改文本，规则就自相矛盾；只改文本不说原意，下一个人会以为规则被随意放松了。
**处置办法：在新规则旁边写上旧规则、以及为什么它当初那么写。**

### 5.2 第四次同一个形状 ⇒ 收成一处

前三次都在各自的网里补一行 ✗，于是换一张网又踩 ✗。
这一次的代价（一个助手 + 四行迁移）**小于**它已经造成的三轮调试。

> 候选表里挂着的"归一化清单"，本身就是 v0.44 那条教训（"未证明会一直挂"）的标本：
> **一个挂了四版的候选，被做掉的成本是一小时。**

### 5.3 判据也会写错——而错法往往与产品无关

v0.51 的新网第一版就红了，报的是"信封里 exitCode=0，而进程退 2"。
真相：那两条路径产出的是**报告**（本来就有报告可给），而我把报告当信封读。

**两种形状都合格时，判据必须分别对待**——这与 v0.48 "建议不该被兜底遮蔽"、
v0.50 "判据要贴着契约的句子写"是同一族：**判据要认清它面对的到底是什么。**
