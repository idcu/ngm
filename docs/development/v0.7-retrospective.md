# v0.7 复盘 — 让 store 的占用可见、残骸可回收

> 体例与各版一致：逐组验收 → 未达成项 → 设计偏离登记 → 缺陷清单 → 过程洞察 → 指标 → 后续。
>
> **本页是补写的**：v0.7 交付时**没有写复盘**，而"进入下一版前先完成上一版的复盘"
> 是本项目的既定纪律（[开发总览 §验收机制](./README.md#验收机制)）。补写的直接触发是
> v0.8——它回头改动了 v0.7 的三处交付面。**这件事本身记在 §5.2。**

## 1. 逐组验收

对照 [v0.7 计划](./v0.7-plan.md) 原文逐条核对。范围来源是
[ADR-018](../adr/adr-018-store-reclaim.md) 决策 2，性质是"**两个低风险、且没有删除真实数据路径**的工具"。

### 1.1 A — `ngm store usage`（只读）

| 计划项 | 结果 | 证据 |
|--------|------|------|
| A1 报告根路径 / digest 数 / 合计字节 / 逐条体积与来源，读不出来就标"meta 不可读"、**不猜** | ✅ | `internal/vendor/content_maintain_test.go` 的 `TestContentStore_UsageReportsWhatTheStoreHolds`；`cmd/ngm/store_acceptance_test.go` 的 "usage reports what the store holds" |
| A2 排序**确定**（体积降序、同体积按 digest 升序），可 diff 可快照 | ✅ | 同一测试连跑 3 轮比对 digest 串；另断言体积降序 |
| A3 解包残骸**单列一行**，并提示可以用 `ngm store prune` 清掉 | ✅ | CLI 输出 `unpack residue: N (...) — ... "ngm store prune" removes them` |
| A4 **只读**（前后字节数不变） | ✅ | 同一测试的 `before == after`；CLI 侧 "usage is read-only" |

> 规划时**没写**"根路径该报什么"，实现报的是 `sha256/` 子目录——那是当时**唯一**的布局。
> 这一点在 v0.8 被改掉了（§3 偏离 1）。

### 1.2 B — `ngm store prune`（只清残骸）

| 计划项 | 结果 | 证据 |
|--------|------|------|
| B1 **只删** `.unpack-*`，绝不动任何 `sha256/<digest>/`；前缀收成常量 | ✅ | `unpackPrefix` 单点定义；`TestContentStore_PruneOnlyRemovesUnpackResidue` 断言 digest 目录一个不少 |
| B2 `--dry-run` 可用 | ✅ | 同一测试断言 dry-run 后残骸**仍在**；CLI "prune --dry-run removes nothing" |
| B3 报告删了什么、释放多少字节，以及**"留下了 N 份内容树没动"** | ✅ | CLI "prune removes residue and keeps every tree" 断言 `kept 2 content tree(s) untouched` |
| B4 幂等（没有残骸时 0 删除、`exit 0`） | ✅ | `TestContentStore_PruneOnlyRemovesUnpackResidue` 的第二轮 + CLI "prune is idempotent" |

**计划之外补的一条测试**（当时记为"落地时新增"）：一个"长得像残骸但前缀不对"的目录
（`.unpackX-not-a-temp`）**必须被留下**。它守的是"按名字前缀判断"这条规则——
一旦两处写法不一致，后果不是"没清干净"，而是**删错东西**。

### 1.3 v0.7 总验收

| 计划项 | 结果 |
|--------|------|
| `store usage` 只读且输出确定 | ✅ |
| `store prune` 只清残骸、`--dry-run` 可用、幂等，**没有任何代码路径删除真实内容树** | ✅ |
| 文档同步：命令参考、help 快照、ADR-018、路线图与总览 | ✅（`testdata/help.golden` 随命令一起更新） |
| CI 验收组纳入新用例 | ✅ `TestV07StoreAcceptance` 在 `.github/workflows/ci.yml` 的验收组里 |

## 2. 未能达成的项

**功能上：无**（两组都在计划内完成）。

**纪律上：一项**——**本版没有复盘**。这不是"以后再补"的待办，而是当时就缺的一步：
v0.7 在路线图与总览里被标成"已交付"，却没有任何一页记录它的实施结果与偏离，
连"偏离登记"这条最常用于后续版本的输入都缺失。**v0.8 是在这页之前发生的**，
也就是说 v0.8 开工时手里没有 v0.7 的复盘可读。见 §5.2。

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | （未规定）`usage` 报告的"根路径" | 报 `~/.ngm/content/sha256/` | 当时层 2 只有这一种布局，报它最具体。**v0.8 改成报 store 根**——现在有两种布局，"根"只能是 `~/.ngm/content` |
| 2 | B1 写着"只删 `sha256/.unpack-*`" | 把"残骸"定义收成常量 `unpackPrefix`，扫描写成**目录列表**（当时只有一项） | 若 `Put` 与 `Prune` 各写一个字面量，两边写歪就会删错东西。**v0.8 往列表里加 `trees/` 时，这一步没出任何问题**——单点定义在下一版就还了账 |
| 3 | （未规定）`Usage` 统计与 `Prune` 判断"是否是残骸"的实现细节 | 两者共用同一常量，但**统计与删除是两段代码** | 有意的：`usage` 只读，`prune` 会删。共用一个**规则常量**，不共用一段会删东西的代码 |

## 4. 本轮发现并修复的缺陷

**交付当时没有留下缺陷记录**（这也是 §5.2 的代价之一：补写时只能靠代码与测试回溯）。

能回溯到的是 **v0.8 回头改到的三处**，它们都在 §7 里——其中**没有一处是"v0.7 写错了"**，
三处都是"层 2 换布局之后，v0.7 的交付面必须跟着说清"。

## 5. 过程洞察

### 5.1 删除类命令的输出必须包含"留下了什么"

`prune` 只做一件小事（清 `.unpack-*`），但它的输出里刻意加了一句
**`kept N content tree(s) untouched`**。理由在实现时就写进了注释：一个删除类命令
如果只说"删了什么"，用户就得自己猜"它是不是顺手删了别的东西"——而在这个项目里，
那个猜测的代价是**别的项目某天突然验不过**。

这条在 v0.8 被继续用：`store usage` 新增 v2/v1 分组时，v1 那一行**总是**打印
（包括 `0`），因为它同时是"迁移收敛到什么程度"的读数。

### 5.2 **本版没有复盘**——纪律漏掉的一步，以及它为什么值得记下来

v0.7 的组很小（两个工具、714 行新增、两组验收都在计划内），于是"复盘"这一步被**顺手跳过**了：
代码绿了、文档同步了、路线图标了"已交付"，看起来齐了。

**为什么这不是小事**：

- 复盘是本项目**唯一**系统性地记录"计划 vs 实际"的地方。跳过它，偏离就只留在
  代码注释和 commit message 里——那些地方**不会有人按版本去读**。
- v0.7 的偏离 1（`usage` 报的是 `sha256/`）正好是 **v0.8 第一个撞上的**：
  层 2 有了第二种布局之后，"根路径"立刻需要重新定义。若当时有复盘，"报告的根是什么口径"
  会是一条被写下来的决定，而不是一个待重新发现的细节。
- 更实在的一点：**v0.8 是在没有 v0.7 复盘的情况下开工的**——而"上一版复盘"正是
  下一版**候选池与教训的输入**（v0.6 → v0.7 就是这么传递的）。

**处置**：本页补写，并把 v0.7 的偏离与 v0.8 对它的改动合并登记（§3 / §7）。
**为什么不留着**：补写一页的成本远低于让一个版本永远没有"实施结果"的记录；
而且补写是在 v0.8 刚刚改过它的交付面时做的，证据还热。

> 这条与 v0.6 复盘 §5.4 那句是同一类：**能自动检查的都给门禁，不能自动检查的（文档、复盘）
> 就必须写进流程**——否则它会稳定地漏掉，且漏得没有声音。

### 5.3 危险规则要"单点定义"

见 §3 偏离 2。一句话总结：**`unpackPrefix` 只有一处定义**，所以 v0.8 增加一个扫描目录时，
"什么算残骸"这件事不需要重新判断一次。规则越危险（这里是"删东西"），越要让它只有一种写法。

## 6. 指标

本版**不产生性能指标**（两个工具都不在热路径上）。它产生的是一组**占用数字的入口**，
而那组数字本身在 v0.6 已经量过（[metrics · 磁盘增长](../internals/metrics.md#磁盘增长内容寻址-storev06)）：

| 量 | 值 | 本版之后是否可见 |
|----|----|----------------|
| 层 2 每 commit 的放大 | **20.0×**（1.88 MiB / 12 个 commit） | ✅ `ngm store usage` 可读出身 |
| 层 2 的回收者 | **没有人**（层 1 有 `git gc`） | ✅ 且明确**不提供**会删内容树的命令 |

## 7. 后续（v0.8 对 v0.7 交付面的三处改动）

| # | v0.7 交付的样子 | v0.8 改成 | 触发 |
|---|----------------|-----------|------|
| 1 | `usage` 报"内容树"一栏、根路径是 `sha256/` | 按布局分组：`blobs (deduplicated content)` / `tree manifests (v2)` / `content trees (v1 legacy)`；根路径改为 store 根 | 层 2 有了第二种布局（[ADR-019](../adr/adr-019-content-addressed-blobs.md)） |
| 2 | `Prune` 只扫 `sha256/` | 扫 `sha256/` **与** `trees/`（v2 的清单临时目录落在后者） | 同上；因为"残骸"是单点定义，这一步是加一个列表项 |
| 3 | `usage` 读 meta 用 `ReadMeta`（当时只有 v1） | v1 那栏改用 `readMetaV1`（**精确**），双布局的 `ReadMeta` 留给消费方 | 双布局之后，`ReadMeta` 对"这个 v1 条目"不再精确 |

> 三处都不是缺陷，而是"接口在下一版被重新定义"。这类改动**正是复盘存在的理由**：
> 它让"v0.7 交付的是什么"有一个随时间更新的说法，而不是散在各版的 commit message 里。
