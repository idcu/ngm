## 2. 未能达成的项

本版**没有未达成的计划项**。但有两项需要如实说明：

1. **"收敛"这一项以计划之外的方式交付**：C1 写的是"某个 digest 以 v2 写成功后删除 v1 目录"，
   隐含"旧条目会在重新安装时逐个回收"。实现后发现**这条路径基本不可达**（缺陷 D5），
   于是交付方式改为"把出路交给用户，并让 `usage` 打印出来"。
   **没有为了兑现计划里那句话去动 `install` 的短路**——理由见 §5.3。
2. **blob 的回收仍然不做**（本版"不做"清单里的一条，按计划执行）：
   去重改的是斜率，不是终点；回收仍受 [ADR-018](../adr/adr-018-store-reclaim.md) 那两个条件约束。
3. ~~**`v0.5.0` ~ `v0.8.0` 四版都还没打 tag/发布**~~ → ✅ **已于 2026-10-02 补打并处置**。

   这是收尾核对时发现的，与代码无关，但与"交付"的定义有关：
   [发布清单](./README.md#发布清单每个版本)的第 0 步写着"**版本交付即打 tag**"，
   而它之所以被补上，正是因为 v0.2~v0.4 当年"在仓库里存在、在任何发行源上都取不到"。
   **同一个错误又犯了四次**：v0.5 ~ v0.8 都已交付，但没有一版打了 tag。

   **处置（两步，缺一不可）**：

   - 四个附注 tag 已补并推 `origin`：`v0.5.0` → `3c3640f`、`v0.6.0` → `7ce4566`、
     `v0.7.0` → `bf6ba5e`、`v0.8.0` → `9af7f7f`（各版的"最后一次提交"，
     手法与发布清单第 0 步一致）；
   - **并且给它装了门禁**：`scripts/check-release-status.sh`（CI job `release-status`）
     要求**有复盘 ⇔ 有 tag**。判据为什么是复盘文件而不是计划里的状态行，见 §5.6。
     四个反例已验证它会红（缺 tag / 缺复盘 / 轻量 tag / 根本看不到 tag）。

   **仍未完成的一半**：GitHub release 要等镜像转发 tag 后由 `release.yml` 生成，
   Gitee 侧附件是人工上传（`scripts/upload-gitee-assets.ps1`）。
   见 §5.6——**它为什么值得单独一条洞察，而不是一条待办**。

   > **当天稍晚的更正**：镜像**确实**把四个 tag 转到了 GitHub（`ls-remote` 可见、
   > 附注对象完整），但 `release.yml` **一次都没跑**——`/actions/workflows/370079274/runs`
   > 只有 v0.1.0 ~ v0.4.0 四次，而同一时段的分支推送照常触发 CI。
   > 于是补发不能被"等镜像"卡住：`release.yml` 加了 `workflow_dispatch`（填 tag 手动触发），
   > 与 tag 推送跑同一份脚本与断言。**这条也说明 §5.6 的教训不止于 tag**：
   > 交付链上"以为会自动发生"的环节，都可能只是**没发生而且没有声音**。

4. ⚠️ **CI 在 `main` 上连红四次**（`775c21f` → `9af7f7f`），而本页与之前的每一份"验收"
   都是按本机结果写的。根因是 [v0.8 计划](./v0.8-plan.md) 里一个写错相对路径的链接
   （`./adr/…` 应为 `../adr/…`），CI 的 `docs link check` 因此失败；**同一时段所有 Go 测试
   在三平台都是绿的**（那个 job 的 14 个兄弟全部 success）。

   **真正的问题不是那个链接，而是我用来验证的检查器**：本地跑 `check-docs-links.ps1`、
   CI 跑 `check-docs-links.sh`，两份实现，而 `.ps1` 因为**按 GBK 解码 UTF-8**（PS 5.1 的默认）
   把 ASCII 标点也吃掉了——坏链在它眼里**凭空消失**，于是它一直打印"all docs links OK"。
   处置：**只保留一份实现**（`.ps1` 转调 `.sh`），并补上 BOM 断言防同类编码事故。

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | B1"解包到临时目录，再逐文件搬进 blob 池" | **直接从 Git 条目构建**（`ListTree` + `CatFileBatch`），不再物化中间树 | 两个非理论的好处：①mode 以 Git 为准（否则 Windows 上可执行位不可表示，同一 commit 会算出**不同的清单**）；②store 不再创建 symlink（Windows 用户不再需要开发者模式才能填充 store） |
| 2 | `sha` 是"blob 内容的 sha256" | `sha = H(mode ‖ 内容)`，blob 按 mode 落盘 | hardlink **共享 inode**，mode 无法随条目而异。不这么做，`scripts/*.sh` 落地后会**静默丢可执行位**（缺陷 D3）。代价：同内容两种 mode 存两份（可忽略） |
| 3 | `symlink` 落地模式保持"整目录链接" | v2 下退化为**逐条目 hardlink**，并如实报告实际 mode | 没有"一棵已物化的树"可链。磁盘收益不变。**这是本版唯一一处用户可见的行为变化** |
| 4 | 读路径双支持只提到 `Entries` / `Has` | `ReadMeta` 也双布局（v2 优先、回落 v1） | `verify` 的层 2 检查就是调 `ReadMeta` 的（缺陷 D1）；不修它，升级后**每个新装依赖都会报"meta 不可读"** |
| 5 | （未提） | 新增 `ContentStore.ReadFile(digest, rel)` | `env.ContentReader` 原先自己拼 v1 的树路径（缺陷 D2）。让"取字节"成为布局无关的入口，否则换布局就得再改一遍消费方 |
| 6 | （未提）`TreePath` 的去留 | 保留，但收窄语义：只用于 v1 兼容路径与"能否整目录链接"的判断 | 删掉它就得让 `usage`/`prune`/symlink 判断各自重算一遍 v1 路径；保留 + 写清"不要用它读内容"更省 |
| 7 | （未提）symlink 模式对旧数据的处理 | v1 数据仍走"整目录链接"老语义 | 升级不该让旧 store 的行为也变（"两种布局各自保持自己的语义"是这套方案的自然结果） |
| 8 | C1"写成功后删 v1，空间在重新安装时逐个回收" | 代码保留（异常状态仍生效），但**如实说明它基本不可达**；出路交给用户 | `install` 见到 `Has` 为真就短路，而健康的 v1 条目 `Has` 正是真。改这条短路会破坏"无网络也能安装"的承诺 |
| 9 | C2"分别报告" | 分组 + 明确两个数的口径 | v2 明细报的是**逻辑体积**（共享 blob 会重复计算），与 `blobs` 一行并列，免得被读成磁盘占用 |
| 10 | （未提）`usage` 里 v1 那一行的打印条件 | **总是**打印（含 `0`） | 它同时是"迁移收敛到什么程度"的读数——只在非零时打印会让人以为"没有这一栏就是没有残留" |

## 4. 本轮发现并修复的缺陷

按发现顺序。**D1–D7 是"实现与既有契约不符"**，D8–D10 是工程卫生与数字错误。

| # | 缺陷 | 后果（如果不修） | 发现方式 |
|---|------|----------------|---------|
| D1 | `Has` 认 v2、`ReadMeta` 只认 v1 | `verify` 会对**每个新装依赖**报 "content store meta.json is unreadable" —— 全新的依赖也验不过 | 跑测试（`TestVerifyVendorTree_*` 一改布局就红） |
| D2 | `env.ContentReader` 仍拼 v1 的 `TreePath` | v2 下 mappings 的入口探测**静默取不到**文件（不是报错，是"看起来没有入口"） | 读码（ADR-019 §阶段 A 的解耦清单里就有这一处） |
| D3 | blob 身份不含 mode | 走 hardlink 时**静默丢可执行位**（`scripts/*.sh` 变成不可执行） | 跑测试 + 推演 hardlink 的 inode 语义 |
| D4 | `symlink` 模式在 v2 下静默退化为 copy/hardlink | 与文档承诺的行为不符 | 跑测试（旧用例报 `mode=hardlink`） |
| D5 | 健康的 v1 条目**永不收敛** | 用户以为"升级后空间自己会变好"，实际不会 | **交付前复核时**发现的（不是测试报的） |
| D6 | `Entries` 用"读清单是否成功"作 v2 判据 | 清单损坏会被当成 v1 → 回落到一棵可能已被删的树，报出误导性差异 | 写 `ReadMeta` 时顺手发现的一致性缺口 |
| D7 | `Prune` / `Usage` 漏掉 `trees/` 下的 `.unpack-*` | `usage` 少报一块占用；`prune` 清不掉 v2 的残骸 | 读码（`Put` 的临时目录位置变了） |
| D8 | `links.go` 的 `linkTree` 成了死代码 | 两套落地逻辑并存（第二套没人走，但会被误读为"两条路径都要维护"） | 自查（加 `linkEntries` 时没删旧的） |
| D9 | 验收测试与文档把 v1 路径写死 | `cmd/ngm` 的 m2/m4/m5 与 `store usage` 的断言会红 | 跑测试 |
| D10 | 我把"放大比"写成 `~1.9×` | 文档给出一个**按该页口径算不出来**的数字 | 收尾复核时按口径复算（见 §5.2） |
| D11 | **两条死锚点**：`#7-v06-候选项…`（标题是"候选"，链接多了一个"项"） | 点进去不跳转，只是**静默跳到页首** | 收尾审计（见下） |

## 5. 过程洞察

### 5.1 "先解耦、再换布局"这条顺序，值得当作默认做法

计划的顺序（A 等价重构 → B 换布局 → C 收敛）兑现成了两个可检验的事实：

- A 阶段结束时**既有测试一字未改全绿**；
- B/C 阶段结束时 **`verify` 的判定逻辑（`compareTrees`）一个字都没动**。

这条顺序之所以有效，是因为它把"**判定逻辑**"与"**数据在哪**"分开动：
判定逻辑只看条目（path / size / symlink / content），而条目可以从两种布局生成。
**反过来做（先换布局、再改消费方）会让安全关键路径与存储改动同时处在不可验证的状态**——
而那正是本项目最忌的"看起来通过"。

### 5.2 计划的"验收尺子"必须**带口径**（D10 的教训）

ADR-019 把尺子写得很具体（"12 个 commit 后应从 1.88 MiB 降到百 KiB 量级"），
但**"放大比"这个口径没有跟着写**。结果我在写文档时把新值算成了 `~1.9×`（用"总量 ÷ 一棵树"），
而 [metrics](../internals/metrics.md#磁盘增长内容寻址-storev06) 里 v0.6 的 `20.0×` 用的是
**"每 commit 增量 ÷ 源码真实增量"**——同一份数据，两种算法差了三倍。

**处置**：①数字改为 `0.6×` 并在 metrics 里**显式写出口径**；②同一段里补上另一种读法
（"已存下 0.37 棵树"），让下一个读者不必再去猜是哪种算法。

**教训**：一个数字只要可能被两种方式算出，就必须在它旁边写清是哪一种。
这与 v0.6 的"仪器说谎"是同一族问题——**数字的可信度取决于它的口径是否被写下来**。

### 5.3 "`Has` 为真就短路"是承诺，不是优化（D5 的处置）

`install` 在 `Store.Has` 为真时**不调用 `Put`**，代码注释写得很清楚：这不是性能优化，
而是 `locking.md` 的承诺——"配合 content store 或 vendor，环境无网络也能安装与构建"。

C1 那句"空间在它被重新安装时逐个回收"之所以不成立，根因就是这条承诺。
**处置没有去动短路**，而是：

1. 把"不会自动迁移"写进 ADR-019 修订、层模型、命令参考；
2. 让 `ngm store usage` 在 v1 遗留非零时**打印出路**（`rm -rf <root>/sha256 && ngm install`），
   并加断言钉住这句话（`TestV08StoreUsagePointsAtV1Legacy`）。

**为什么值得记**：计划里一句乐观的措辞，很容易被实现成"为了兑现它去放松一条承诺"。
这里选择了**改措辞 + 给用户出路**，代价是一页文档，而不是一次语义倒退。

### 5.4 内容寻址 + hardlink：**地址里必须包含一切会被共享的东西**

这是 D3 的一般形式。blob 池按内容寻址，而落地层用 hardlink——**inode 是共享的**，
于是"文件系统层面会共享的属性"（这里是可执行位）**必须进入地址**，否则两个引用者会互相污染。

代价（同内容两种 mode 存两份）是可接受的，因为主导场景是"同一文件在多个 commit 里不变"
（正是 20× 的来源），那里 mode 一致、去重照旧。

> 这条与 ADR-019 原文里"按 `mode` chmod"那句是直接冲突的：**对 hardlink 而言 chmod 改的是 blob 自己**。
> 写 ADR 时看不出来，动手时才暴露。

### 5.5 交付前的"再读一遍计划"要真的逐条读

D5 与 D10 都不是测试能报的，是**在收尾时把计划与 ADR 逐条对着实现读**发现的。
本版这两处恰好一个改动了交付方式（C1）、一个改动了文档数字（D10）——
都不是"代码错"，而是"话与事实不符"。这与 v0.5 复盘记的"状态行滞后"是同一类形态，
且**它们都不会自己浮出来**。

### 5.6 写进清单≠会发生：`v0.5.0` ~ `v0.8.0` 都没打 tag

**事实**：`git tag` 里只有 `v0.1.0` ~ `v0.4.0`；v0.5 ~ v0.8 四版都已交付、都没打 tag。
发布清单的**第 0 步**就是"交付即打 tag"，而它的由来正是 v0.2~v0.4 的同类事故。

**为什么写下来还是漏了**：这一步有三个特征，恰好凑成"必然被漏"的组合——

1. **不在代码的同一条流里**：写代码、跑测试、改文档都是"改完就在眼前"，
   打 tag 是**流程动作**，没有编译错误、没有测试失败来提醒你漏了；
2. **没有任何自动提醒**：仓库不会因为"已交付但未发布"而报红（本页写这一条时，
   连"是否漏了 tag"都要靠人手工 `git tag` 去数）；
3. **后果延迟且无声**：漏掉的当天什么都没坏——v0.2~v0.4 是**几天后**才被发现取不到的。

对照 v0.6 复盘 §5.4 的纪律"**读不到的 CI 不能算通过**"，这是同一条纪律的另一面：
**不能自动检查的交付动作，只写进文档就会被稳定地漏掉。**

**处置（本版做了三件事）**：

1. 补打四个附注 tag 并推 `origin`（`v0.5.0` → `3c3640f`、`v0.6.0` → `7ce4566`、
   `v0.7.0` → `bf6ba5e`、`v0.8.0` → `9af7f7f`）；
2. 把"四版未发布"写进发布清单的显眼位置 + 本页，并**点名它已是第 5 次**；
3. **把它机械化**：`scripts/check-release-status.sh`（CI job `release-status`）要求
   **有复盘 ⇔ 有 tag**（按 `vX.Y` 配对），缺一边即红。

**为什么判据是"复盘文件"而不是计划里的"状态：已交付"**：后者是散文，格式历来不统一
（v0.1 写"本计划已全部完成"，v0.2~v0.4 干脆没有这一行）。**一个会漏的判据当门禁，
等于没有门禁**——那正是 §5.2 说的"仪器说谎"的另一种形态：它看起来在检查。
而复盘与 tag 的位置在发布清单里是同一处（"版本的最后一次提交是该版的复盘提交"），
所以两条可以互推，判据因此是**结构性的**而不是**措辞性的**。

**门禁自己也被反例测过**（本项目的既有纪律：断言必须有牙齿）。四种情形都会红：
缺 tag、缺复盘、轻量 tag（`git tag` 而不是 `-a`）、以及**根本看不到 tag**。
最后一种顺带修掉了一个真 bug：脚本原先在命令替换里用 `grep`，而"无匹配"时 `grep` 返回 1，
在 `set -e -o pipefail` 下会让**整个脚本静默退出、一个字都不打印**（实测 0 字节输出，
退出码 1）。也就是说：最该吵闹的那个场合，它反而无声——**这正是"仪器必须能自证"的理由**，
而它只有在反例里才暴露。

**仍未完成的一半**：GitHub release 要等 Gitee 镜像转发 tag 后由 `release.yml` 生成
（本环境读不到 CI 结果，因此**无法自证**），Gitee 侧附件是人工上传。

> 一般的教训：**凡是靠人记的步骤，只要它有前两次的先例，第三次一定会发生**——
> 这条已经被这个项目自己验证了两次（v0.2~v0.4、v0.5~v0.8），所以这次不停在"写下来"。

### 5.7 "读不到的 CI 不能算通过"——而它其实**读得到**

v0.6 复盘 §5.4 定下这条纪律时，前提是"本环境没有 `gh`、没有 token，读不到 Actions 结果"。
本版收尾时发现这个前提**是错的**：**公开仓库的 Actions 结果是公开 REST API**
（`/repos/{owner}/{repo}/actions/runs`、`.../runs/{id}/jobs`、`.../actions/workflows/{id}/runs`），
不需要任何凭据。于是：

- "CI 在 `main` 上红了四次"这个事实，是**一条 URL** 读出来的（此前四五个小时里，
  我按"读不到"处理，只用本机 Windows 结果自证）；
- 失败定位到**唯一一个 job**（`docs link check`）与**唯一一个失败 step**，也是一条 URL；
- 连"tag 是否触发了 Release"（§2 第 3 条）同样是读出来的——而它此前被当成"无法自证"的事。

**处置**：把这条写进纪律——**"读不到"必须先验证，而不是假定**。
本项目已经因为"假定读不到"付过一次代价（四次红着推）；这与 §5.2 的
"数字要带口径"是同一族：**你以为的观测边界，本身也要被观测。**

> 具体一条命令：`git` 之外不需要工具——
> `curl -s https://api.github.com/repos/idcu/ngm/actions/runs?per_page=5`。
> 本地没有 `curl` 时用任意 HTTP 客户端；关键是**这件事不需要凭据**。

### 5.8 两个检查器 ≈ 一台会说谎的仪器（docs 链接检查）

`check-docs-links` 有两份实现（`.sh` 给 CI、`.ps1` 给 Windows 本地），文件头还写着
"二者规则须同步演进"——**那正是它后来的样子：没有同步演进，只是没人看出来**。

`.ps1` 的失效机制值得记下来，因为它是**编码**问题而不是逻辑问题：

- PowerShell 5.1 对**没有 BOM** 的 `.ps1` 按系统 ANSI（本机 GBK）解码；
- 更致命的是它读文件内容时用 `Get-Content -Raw` 而**没有指定编码**，于是 **UTF-8 的正文
  被当成 GBK 解码**；
- GBK 是**双字节**编码：错位的字节对会把紧跟其后的 ASCII 字符一起吞掉。实测结果是一个
  闭合的 `)` 消失，正则 `\(([^)]+)\)` 因此**跨行吞掉整段文本**，
  而那段文本里正含着那条坏链——**它凭空消失了**；
- 这同一个机制还让 `.ps1` 自己**解析不过**（报错行号与实际差 14 行，因为换行被吞了）。

**两条处置**（都属于"把规则收成一种写法"）：

1. `.ps1` **不再实现规则**，只转调 `.sh`——本地与 CI 由构造保证一致；
   找不到 bash 时**明确失败**（exit 2），而不是降级成"什么都没查"；
2. CI 加一条断言：**含非 ASCII 的 `.ps1` 必须有 UTF-8 BOM**
   （`build-release.ps1` 当时是**发布脚本**，只是侥幸解析通过）。

> 一般化：**同一件事有两份实现时，你不该问"哪一份对"，而该问"为什么有两份"**。
> 这与 v0.7 复盘 §5.3"危险规则要单点定义"是同一条，只是这次的危险不是删数据，
> 而是**你以为检查过了**。
