# v0.78 复盘 — **monorepo 的另外两个信号 + 自检器与产品读同一份事实 + 发布读数实测**

> 一句话结论：把 monorepo 的另外两个信号（pnpm / lerna）接上，**又掉出四处误伤**——
> 其中最刺眼的一处是**自检器比产品严**（标准推荐 `exports`，而自检器不读它）；
> 顺带用联网工具**实测**了两个源的发布读数，把靠记忆的历史数字替换掉。

| 源 | 实测 | 此前文档写的 |
|----|------|-------------|
| GitHub **tags** | **65 个**，`v0.1.0` … `v0.65.0`，**无缺口** | "60 of 77"——把 release 数当成了 tag 数（两者混成一列，谁也看不出来） |
| GitHub **releases** | 最新是 **`v0.64.0`**（`v0.65.0` 有 tag 无 release）；已列表连续到至少 `v0.57.0` | "60 of 77"（2026-10-05 的读数，数字其实是对的） |
| Gitee **releases** | **3 个：`v0.2.0` · `v0.3.0` · `v0.4.0`** | "`v0.1.0`, plus …"——**点错了是哪三个** |

**总数没有"未数完"这个选项**：两列放在一起就能**推导**——
GitHub tags 65（实测）− 4 个从未跑过工作流（`v0.5.0`…`v0.8.0`）− 1 个跑过但失败（`v0.65.0`）
= **60 个 release** ✓ 与旧读数一致。也就是说旧读数**数字对、口径错**：
它把两列合成了一列，于是"65 个 tag"与"60 个 release"再也分不开——
下一个读它的人只会以为自己看到的是其中某一个。**读数必须带日期与方法**，这次就是靠这条
把两处旧数抓出来；而"两列各自成立、且能互相解释"是这一版给读数加的**新口径**。

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么 |
|---|---------|---------|-------|
| 1 | 子包清单用逗号在 bash 与 node 之间传 | 改成**换行**分隔 | 实测：`{packages,apps}/*` 被逗号切成两条垃圾模式（glob 里逗号是合法的） |
| 2 | 花括号 glob 当作"读不出的写法"直接报错 | 实现**一层展开器**（可递归多组） | npm 与 pnpm 都支持 `{a,b}`；报错会把一个合法形态判红——那正是本版要消灭的东西 |
| 3 | `engines` 只在"没有根清单"时跳过 | 所有 monorepo 根都跳过 | lerna 的根有清单但没有 `engines`，被当成"没做到"；根不发布 ⇒ 这条判据在根上没有意义 |

## 4. 缺陷清单

| # | 缺陷 | 谁发现 | 处置 |
|---|------|-------|------|
| 1 | **自检器比产品严**：只写 `exports` 的包被判"找不到入口"（必做红），而 `InferEntry` 一直读 `exports` | 造 pnpm fixture（子包只写 `exports`——即标准第 1 条推荐的写法） | 自检器的候选层次与 `parseExports` **逐字对齐**（字符串 / `"."` 字符串 / 条件映射，`types` → `import`/`module`/`default`/`require`）；候选里补 `index.cjs`；`types-provided` 认 `exports.types` |
| 2 | pnpm 形态的根（**合法地**没有 `package.json`）被判必做红 | 同上 | `pkg-json-exists` / `pkg-name` / `pkg-version` / `license` 在"mono-root 且无根清单"时记为不适用 |
| 3 | 花括号 glob 被当成字面路径 ⇒ 必做红 | 写牙齿时（`{packages,apps}/*`） | 新增一层花括号展开；模式之间改用换行分隔 |
| 4 | `engines` 在 monorepo 根上被要求 | lerna fixture 的根 | 归入"根的包专属判据"，记 `—` 并写明理由 |
| 5 | Gitee 三个 release 的**点名**写错（写成"`v0.1.0`, plus …"） | 联网实测 | 按 API 输出改正（`v0.2.0` · `v0.3.0` · `v0.4.0`），并给读数加上日期与方法 |

## 5. 过程洞察

### 5.1 "自检器比产品严"是一类独立的错误

它不表现为漏判（该红不红），也不表现为普通的误判（标准没写清），而是
**同一份事实在两个地方各写了一遍**：产品读 `exports`，自检器不读。
两边都"没错"，合起来就是错的——一个照标准做的库会被标准自己的工具判红。

判据：**标准里推荐的东西，产品必须真的读**；不读，就不该推荐（ADR-014 那条纪律的另一面）。

### 5.2 误伤的第六个、第七个…都是同一种形状

v0.77 修了两处（显式 CJS · monorepo 根），v0.78 又掉出四处（exports · 无根清单 ·
花括号 glob · 根的 engines）。共同点：**判据把"某一种形态"当成了"包"的定义**。
所以 §5.1 那张形态覆盖表本身就是本标准的**验收清单**：
它写了六种形态，而每一种都必须跑得通——表里少写一种，误伤就少发现一处。

### 5.3 读数属于"会过期的事实"

GitHub 的 65 个 tag 与 Gitee 的 3 个 release 都是**当时**的读数。
这一版把两道保险加上：读数后面写**日期**，并在文档里写清**方法**（哪个 API、什么口径）。
旧数字之所以能挂那么多版，就是因为它既没有日期，也没有人问过"它现在还是这样吗"。

## 8. 需要仓库所有者做的两件事（都不是代码）

1. **推 tag**（把本机的 13 个新 tag 送到两个源）：

   ```bash
   git push origin main --tags     # GitHub 镜像（会顺带触发 release.yml 补 release）
   git push gitee  main --tags     # Gitee
   ```

   推完 GitHub 的 tag 覆盖就从 65/78 变成 78/78，`v0.65.0` 那个"有 tag 无 release"的缺口
   也会被 `release.yml` 补上（前提是镜像侧的 workflow 仍在）。
2. **一个 monorepo 形态的库**（候选 3 的前提）：如果愿意，我可以先把仓库准备好
   （两个子包 + 各自 `package.json`/`ngm.json` + 根 `workspaces`），你只需要 `git push` 一次；
   之后 `subPath` 与 `ngm add <slug>@<ref>#<subpath>` 就有了真实端到端样本。
