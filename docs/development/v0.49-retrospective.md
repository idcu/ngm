# v0.49 复盘 — **"注释比实现说得多"那一族的收口**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：`internal/config` 的 **30 处**校验全是裸错误（包顶注释却写着"带可操作 hint"）——
> 这一版把它们全部补上字段级建议，并留一条**静态**判据钉住这一族。
> 过程中**上一版的断言红了，红得对**：v0.48 钉的其实是"兜底那句话"，
> 而这一版的目的正是让兜底退场。
> 另外又抓到一处"**夹具不造它自称的状态**"（v0.31 的复发），
> 而这次露马脚的不是人眼，是**建议里的字样**。

---

## 1. 逐组验收

### 1.1 三十处校验，零裸错误 ✅

| 项 | 改前 | 改后 |
|----|------|------|
| `validate.go` 的裸错误 | **30** | **0**（1 条登记例外，5 处是 `%w` 包装） |
| 带字段级建议的校验点 | 1 | **25** |

读数：`config validation: 0 bare error(s) (exemptions 1, all present), 5 %w wrapper(s)`。

例外只有一条，且**写了理由**：`project file is nil`——那是调用方的编程错误，用户写不出这个状态。

### 1.2 用户看到的东西变了 ✅

| 形状 | 改前（兜底） | 改后 |
|------|-------------|------|
| `schemaVersion: 2` | `fix the reported field, or run ngm config validate for details` | `set schemaVersion to 1 in ngm.json, or upgrade ngm` |
| 缺 `version` | 同上 | `add a version like 0.1.0 to ngm.json (it is free-form, but must not be empty)` |
| `refType: "banana"` | 同上 | `set refType to one of [commit tag branch] — ngm does not guess it from ref` |
| `vendor.mode: "nope"` | 同上 | `set vendor.mode to local (vendor into the project) or global (share one store)` |
| `minimumReleaseAge: "two weeks"` | 同上 | `write supplyChain.minimumReleaseAge as an ISO 8601 duration, e.g. P7D or PT12H` |

**兜底没有消失**——它退到了它该在的位置：**解码类**失败（JSON 的形状就不对，
这一层只知道"解析器在看这个文件"）仍然给那句"fix the reported field, or run `ngm config validate`"。

### 1.3 兜底不再遮蔽（三处统一）✅

新增 `errs.WrapUnlessHinted`：**内层有建议时不附加兜底**。三个调用点统一：

| 位置 | 角色 |
|------|------|
| `internal/config/io.go` | 加载器（每条命令都走它） |
| `cmd/ngm/config.go` | `config validate` 命令 |
| `cmd/ngm/add.go` | v0.48 的局部修法——这一版收回成共用助手 |

### 1.4 静态普查（新网）✅

`validate.go` 里：

- `errors.New(` 只允许出现在**例外表**里（键 = 去空白的整行，值 = 为什么）；
- `fmt.Errorf(` 只允许出现在**带 `%w` 的包装**里；
- 例外表的键必须**仍然存在**于文件里（删了代码却留着登记 ⇒ 登记看着空气）；
- **可达性守卫**：一个错误构造都没看到 ⇒ 红（文件被改名/清空时不许静默通过）。

### 1.5 动态面扩大到 23 条 ✅

读数：**`failure surface: 23 paths (21 error-text, 2 report-style, 0 silent)`**，
身份 `ConfigInvalid: 20` · `GitFetch: 1`。

其中三条是这一版新加的校验类变体（`refType` / `vendor.mode` / `minimumReleaseAge`），
用来证明**建议真的到得了用户眼前**（不是只写在源码里）。

### 1.6 牙齿 ✅

| 探针 | 结果 |
|------|------|
| 某处退回 `errors.New` | 静态普查红：`validate.go:57 造了一个没有建议的错误：return errors.New("version is required")` |
| 兜底改回 `errs.Wrap`（重新遮蔽） | 动态面红：`the advice does not acknowledge **this** failure's shape (expected one of [`version`] in the hint)` |

## 2. 上一版的断言红了，**红得对**

v0.48 给两条 `schemaVersion` 用例登记的是 `adviceMust: {"config validate"}`。
这一版它们红了——因为建议变成了字段级的（`set schemaVersion to 1 …`），
**不再包含 `config validate`**。

真相是：**v0.48 那条登记钉的其实是"兜底那句话"**，
而 v0.49 的目的正是让兜底退场。于是登记跟着改：从"兜底的字样"改成"**这条失败自己的字段名**"。

> 判据会随版本变红，是因为它记的是**当时的用户所见**——
> 这不是判据的脆弱，是它**忠实地在记东西**。要紧的是分清：
> 这次红是"产品退步了"还是"我换了一种更好的说法"。

## 3. 又一处"夹具不造它自称的状态"（v0.31 的复发）

`manifest-schema-version-is-absent` 这条用例，夹具写的是 `schemaVersion: 0`，
名字声称在测"**版本字段缺失**"——而它实际撞的是 **`version is required`**。

原因：`schemaVersion: 0` 是**合法**的（加载时按当前版本补上），
所以那条用例从来没有造出它自称的那个状态。

**这次露马脚的不是人眼，是建议里的字样**：新判据要求"建议承认**这一条**失败的形状"，
而它给的是 `version`——与用例名声称的 `schemaVersion` 对不上。

处置：
1. 那条改名成 `manifest-version-is-absent`，夹具也改对（补上 `schemaVersion: 1`，**去掉** `version`）；
2. **新增一条实测边界**：`missing-schema-version-is-not-a-failure`（`expectZero`，附原因）——
   它钉住"缺省合法"这个事实，哪天变了会红。

> v0.31 那条教训当时写的是"**让夹具不再造出它自称的状态** ⇒ 红"，
> 靠的是一条断言（"这条失败用例退了 0 ⇒ 红"）。
> 这一版给出的是**第二种探针**：不用等它退 0，**看建议里的字样**就能发现张冠李戴。

## 7. 过程洞察

### 7.1 "注释比实现说得多"是一类债，不是一句话

v0.48 在 `validateDepPath` 上撞见它，v0.49 回头一数：**30 处**。
这类债的形态很特别——注释描述**意图**，实现描述**现状**，
而**没有人会在意两者差的那一处**，直到某条路径把"现状"端到用户面前。

> 可以推广成一句可查的问法：**包顶的承诺，在这族的每一处都成立吗？**
> 这一版把"每一处"变成了静态判据（新错误必须带建议）。

### 7.2 建议里的字样，是"张冠李戴"的第二根探针

v0.31 发现"夹具不再造出它自称的状态"时，靠的是"这条失败用例退了 0"。
这一版发现同样的问题，靠的是**建议里的字样与用例名对不上**（`version` vs `schemaVersion`）。

**同一条教训有了第二根探针**：前者要求夹具跑出失败，后者只要求**建议承认这一条的形状**。
后者更早、更省（不用等到行为变化就能发现名字错了）。

### 7.3 上一版红了，先分清两种红

判据随版本变红，可能是：
- **产品退步**（用户看到的东西变差了）→ 修产品；
- **说法变好**（用户看到的更具体了，只是不再包含旧字样）→ 改登记。

分不清这两者，就会把"更好的说法"当成退步回退掉——
而分清它们的前提是：**知道那条断言当初在钉什么**（v0.48 的注释写了"钉的是兜底那句话"，所以这一版能一眼判出是后者）。
