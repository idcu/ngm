# v0.76 复盘 — **端到端：由用户自己的库驱动 ngm**

> 一句话结论：`canonical-json`（用户自己的库，已推 Gitee）第一次真正驱动了 ngm——
> install / verify / mappings / why / sbom / attest 全部跑通，**vendored 副本上还能跑通库自己的
> 25 个测试**。沿途抓到一个自检器误报（非 git 目录的 tag 检查）并修掉。
> **ngm 产品代码 0 行**；自检器去掉一处误报、多出"不适用"这一结论。

## 1. 逐组验收（全部是真实输出）

### 1.1 install（第一次真实拉取）

```
gitee:idcu/canonical-json@v1.0.0 (tag) → 9688ac013dbc520f010242461af2e5493e57de8c
installed 1 dependencies; wrote ngm.lock and ngm.mappings.json
```

commit 与库仓库 HEAD 一致（`9688ac0`）。**首次尝试被权限系统拦下**：
`ConfigInvalid: permission denied: net:gitee.com` + 提示"既没允许也没拒绝一律拒"——
默认拒绝按设计工作；实跑改用独立 HOME（只放开 `net:gitee.com`），不动用户真实配置。

### 1.2 四件产物

| 产物 | 值（节选） |
|------|-----------|
| `ngm.lock` | `archiveDigest: sha256:ca32db3e…` · `vendorPath: gitee.com/idcu/canonical-json` · **`requiredBy: ["(root)"]`**（v0.73 的图，第一次出现在真实依赖上） |
| `ngm.mappings.json` | `main: ./src/index.js` · `types: ./src/index.d.ts`（**命中 `ngm.json` 第 1 层**——标准里那条"最优先入口声明"在真实库上生效） |
| vendor 树 | `.gitattributes` `.github/` `src/` `test/` `LICENSE` `README.md` `ngm.json` `package.json`——**没有 `.git`、没有 `node_modules`** |
| 行尾 | vendored 文本文件**全部 LF**（`.gitattributes` 的纪律穿过了 Git → ngm 的整条往返） |


## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么 |
|---|---------|---------|-------|
| 1 | 直接改全局 `~/.ngm/config.json` 放开 `net:gitee.com` | **独立 HOME**（演示配置） | 不动用户的真实配置；与测试的 `isolateUserEnv` 同一手法，且让实跑可复现 |
| 2 | 自检器的 tag 检查失败于非 git 目录 | **新增"不适用"结论**（`—`，显式打印、不计入） | vendored 副本没有 `.git` 是正常的；"没有 tag"在那里不是缺陷。而"静默跳过"仍然是敌人——所以它必须被打印出来 |

## 4. 缺陷清单

| # | 缺陷 | 谁发现 | 处置 |
|---|------|-------|------|
| 1 | 标准自检器把 **vendored 副本**判为"没有 semver tag"（误报） | dogfooding（把自检器指向 ngm 自己的 vendored 输出） | 引入 `skip`：不是 git 仓库 ⇒ `— …（不适用）`，不再计入；`--json` 多 `skipped` 字段。实测：库目录 `✔`、vendored 副本 `—`，两侧 exit 0 |
| 2 | 实跑第一遍 verify 红了 | 我自己的环境不一致（上一行命令设的 HOME 不跨命令保留） | 记录在案：ngm 的行为是对的（真实 home 的 store 里当然没有这份内容），这条写进复盘而不是改产品 |
| 3 | **自检器的结论此前没有任何判据守着**（v0.74 的 CR 转义、v0.76 的 vendored 误报，两次都靠人跑出来才发现） | 本版（复盘时回看两次缺陷的共同点） | 新增 `TestV76LibraryStandardCheckerHoldsItsVerdicts`（pass / fail / skip 三种结论各钉一个场景）+ 登记进 `net_coverage_sources_test.go`。按停止清单的纪律，这张网**指着一个已发生的缺陷**才建：它指的是两个 |

## 5. 过程洞察

### 5.1 两半分别验证过，不等于拼起来能用

库过自检、ngm 过全量测试——直到这一版才第一次在同一个真实场景里相遇。
第一次 install 就撞上权限系统（好事：默认拒绝按设计工作），第一次 verify 又撞上
环境不一致（好事：漂移分类与提示都说得清）。
**"端到端"不是把两条绿线画在一起，而是让它们在同一条链上跑一遍。**

### 5.2 免构建的好处，在 vendored 副本上才看得见

在别人项目的 `ngm.vendor/` 里直接 `node --test` 得到 25/25 通过——不需要 npm install、
不需要构建步骤、不需要网络。这是"仓库即产物"这条设计在**消费者现场**的样子。
反过来也说明标准的第 3 条（入口指向的产物必须已提交）为什么是硬约束。

### 5.3 把自检器指向自己的产物，是新的检验方式

这一版的误报不是从"写库"里来的，而是从"**用自检器扫 ngm 自己的输出**"里来的。
vendored 副本是这份标准的**极端用户**（没有 git、没有 tag、没有构建），
拿它当输入能暴露"只在作者视角成立"的条款。这个手法值得留给后面的版本。
