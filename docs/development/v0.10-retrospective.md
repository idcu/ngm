## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | A3"失败不留半棵树" | 改为"残骸可被 `verify` 认出 + 恢复后再落地会先清空" | `Materialize` 先清空目标再重建，**只承诺"下次重建前清空"**；重建中途失败时已落地的文件会留下。按原措辞写会得到一条**与代码事实不符**的断言（要么永远红、要么被写成空断言） |
| 2 | （未提）断言的层 | 断言 `errs.FormatHuman(err)`，不是 `err.Error()` | `NgmError.Error()` 按设计只给 message + cause，hint 由呈现层渲染。第一版断言 `Error()` 直接红了——**红得对**：它证明"我以为的契约"不是"代码的契约" |
| 3 | B2 未写严格性 | 显式点名的根不存在 → 失败；默认根缺失 → 跳过 | 两种情形语义不同：前者是**调用方写错了**，后者是"这里确实没有要查的东西" |
| 4 | B3 只说"纳入根 README" | 顺带把路径空间统一到**相对仓库根** | docs 相对的路径空间在加入第二个根之后会处处需要特判（也直接造成了 D1） |

## 5. 过程洞察

### 5.1 断言之前先确认**契约**，而不是确认"我以为应该怎样"

A 组两组断言里有三条第一版是错的，全部错在**同一个地方**：我把"常识上应该如此"
（失败不留残骸、hint 在错误里）当成了契约。处置不是改实现去迎合，而是：

1. 读实现与文档，确认**它承诺什么**（`Materialize` 的注释写得很清楚："重复调用是幂等的：
   先清理目标目录再重建"）；
2. 把断言改成**那些承诺**。

> 这与 v0.9 §5.1 的"不变量"是同一族：**断言要有据**。区别是那里管的是数字的口径，
> 这里管的是行为的契约——两者错了都表现为"要么永远红，要么永远绿"。

### 5.2 报错信息也是产品：指错文件比不给信息更糟

D1 是这一版的教训。一个写着 `docs/README.md:4` 的错误信息，会让读者去翻一份**没错**的文件，
然后怀疑检查器——而检查器本身是对的。**信息的价值取决于它指向的位置是否正确。**

它与 v0.8 复盘 §5.8（"会说谎的仪器"）、v0.9 §5.2（"误报比漏报更贵"）是同一条线上的第三点：
**检查器、数字、错误信息，三者都会因为一个细节而失去可信度。**

### 5.3 "静默跳过"的边界要写清：显式参数 vs 默认值

B2 把两种"根不存在"分开了：

- **显式点名**的东西不存在 → 失败（调用方写错了）；
- **默认**的东西不存在 → 跳过（这里确实没有要查的）。

这条区分在别处也有先例（v0.8 收尾给 `release status --published` 加的：线上缺 release 是
**告警**，但"tag 在某版本上不存在"是**失败**）。写清这条边界，是为了让"什么都没查"
永远不会被读成"查过了没问题"。

### 5.4 牙齿测试又一次先于代码发现问题

D1 不是在代码审查里发现的，而是**牙齿测试的输出自己露出来的**：我种的是根 README 的坏锚点，
输出却说 `docs/README.md`。这一版两个缺陷（D1、D2）都是"跑一次真的"逼出来的，
没有一个是"读代码觉得不对"找到的——这与本项目一贯的经验一致。
