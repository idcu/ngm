## 1. 逐组验收

### 1.1 六条形状进错误面 ✅

| 形状 | 变体 |
|------|------|
| 清单字段类型错 | `"name": 123` · `"dependencies": "nope"` |
| `schemaVersion` 未知 | `2`（太新）· `0`（缺失） |
| 子路径非法 | `--path=../escape` · `--path=/etc` |

读数：**20 条路径（18 错误文本 · 2 报告式 · 0 静默）· 身份 2 种**（`ConfigInvalid` 17 · `GitFetch` 1）。

### 1.2 三种形状**本来就合格** ✅

六条全部：exit 3 · `cause:` 说清哪里不对 · `hint:` 给出下一步。
`schemaVersion` 的两条尤其干净（`schemaVersion 2 not supported; this build supports v1`）。

**这一版没有在这三种形状上找到缺陷**——干净本身也是读数。

### 1.3 但抓到了一处**建议错位** ✅

```
$ ngm add github:x/dep@v1 --ref-type=tag --path=/etc
（修前）
ConfigInvalid: invalid dependency
  cause: path "/etc" must be relative (no leading slash)
  hint:  the accepted shape is `<host>:<org>/<repo>[@<ref>]` with --ref-type=tag|branch|commit; see `ngm add --help`
        ^^^^^^^^^^^^^^ 这是**仓库标识**的形状，而用户错的是 **path**
```

根因：`internal/config` 的 `validateDepPath` 返回**裸 `fmt.Errorf`**（没有建议），
于是用户能看到的唯一一句建议只能是调用方那句兜底——**而它讲的是另一件事**。

（`config` 包顶部的注释写着"返回的错误是给用户看的：包含字段路径与可操作 hint"——
但这条校验的实现并没有 hint。**注释比实现说得多**，这本身也是一条读数。）

### 1.4 处置（两处）✅

| # | 改动 | 为什么 |
|---|------|-------|
| 1 | `validateDepPath` 带上真建议（`use a path relative to the repository root, e.g. packages/core …`） | 它是唯一知道该怎么改的那一层 |
| 2 | `add.go` 的包装**不遮蔽**内层建议（内层有建议时不用兜底那句） | v0.35 那条原则（最贴近成因的那一层最知道该怎么办）在另一处落地 |

修后：

```
ConfigInvalid: invalid dependency
  cause: path "/etc" must be relative (no leading slash)
  hint:  use a path relative to the repository root, e.g. `packages/core` (no leading `/`, no `.` or `..`)
```

### 1.5 新判据：建议要**承认这一种失败的形状** ✅

错误面表多了一张旁表 `surfaceAdviceMust`（这条路径的建议必须命中其中之一）：

- 四条清单形状 ⇒ `config validate`
- 两条子路径 ⇒ `relative`

旁表用**键必须在用例表里存在**的守卫钉住（名单自己要有牙齿——与 v0.15 / v0.22 / v0.31 同一族）。

### 1.6 牙齿 ✅

把"不遮蔽内层建议"那一步去掉（让包装重新遮蔽）⇒ 红：

> `the advice does not acknowledge **this** failure's shape (expected one of [relative] in the hint)`

## 2. 修完自己又带坏的一处（**网没红**）

`validateDepPath` 开始返回 `errs` 错误之后，输出变成：

```
  cause: ConfigInvalid: path "/etc" must be relative (no leading slash)
         ^^^^^^^^^^^^^ 同一个错误上，代码名重复了一次——读起来像两个错误
```

**两张网都没响**（它们看的是"有没有建议""建议承不承认形状"，不看 cause 行）。
是我按习惯把输出**逐行读了一遍**才看到的。

处置：`errs.causeLine`——内层**代码与顶层相同**时只写 message；
**不同**时保留前缀（那说明这一段是由另一类失败引起的，例如底层的 `GitFetch`，不该被吞掉）。

> 教训值得单列：**一次修复的"顺带影响"不在任何判据的视野里**。
> 判据守的是它被写下的那件事；其余部分只有**读输出**能发现。
> 这条与本项目"每版都要把用户看到的原文打出来"的习惯是同一件事的两面。

## 6. 过程洞察

### 6.1 三种形状全都合格——**干净也是读数**

它们与"坏 JSON / 缺字段"是不同失败面（JSON 能解析、字段也在，只是值不合形状），
而三条都走到了正确的校验分支、给出正确的建议。**这一版的价值不在修它们，而在证明它们。**

### 6.2 "注释比实现说得多"

`config` 包顶写着"返回的错误是给用户看的：包含字段路径与可操作 hint"，
而这一族校验里没有 hint。**当注释描述意图、实现描述现状时，没有人会在意差的那一处**——
直到某条路径把"现状"端到用户面前（这次是 `--path`）。

### 6.3 一次修复的顺带影响，只能靠**读输出**发现

判据守它被写下的那件事（§2）。这不是判据的缺点，是它的定义：
**判据是抽样，输出是全集**。所以本项目每版都要求把用户看到的原文打出来。

### 6.4 我在**修文件**上栽了两次（如实记）

这一版改错误面那张表时，我用 shell 正则给 20 条用例补字段 ✗：

- 正则 `\}, \[\]string\{[^\r\n]*\}` 里 `[^\r\n]*` 是**贪婪**的，越过了字段边界 ✗；
- 于是"改坏 → 撤销 → 撤销时又吞掉了行尾的 `}`" ✗，来回四轮才恢复 ✗。

教训：**批量改源码用编辑器工具，不要用 shell 正则**——
shell 那一侧的引号、转义、行尾（CRLF）三层叠加，出错时**报错信息本身也在骗人**。
