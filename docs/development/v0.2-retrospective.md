# v0.2 复盘

> 结论：**计划 A–F 六组任务全部实现，逐条验收有可执行证据，三平台 CI 全绿**。
> 性能项 2 条中 **1 条达标、1 条仍差 1.1×**（在线 `verify`）。
> 本轮另发现并修复 **6 处"文档承诺了、代码没做到"或"声称了、其实没测量"的缺陷**，

>
> **不能据此宣称 v0.2 达到全部性能目标**，也不能宣称三个新引擎都经过真实引擎验证
> （见 §2）。

## 2. 未能完全达成的项

### 2.1 在线 `verify` 仍在目标之外（3.4s vs < 3s，差 1.1×）

- **已达标的**：`--offline` 100 依赖 **11.12s → 1.97s ✅**（目标 < 5s）
- **已做的**：依赖级并发（默认 8，实测拐点：4→8 收益显著，8→16 已无收益）+
  成功路径少一次 git spawn
- **剩下的**：每个仓库一次**必需**的 fetch。100 依赖 = 100 次 fetch
- **跨过它需要**：把"先 fetch、再在本地 mirror 上解析"改为"先 `ls-remote` 判定、
  只在需要对象时才 fetch"（惰性 fetch）。这会改动 [locking.md](../architecture/locking.md) /
  [observability.md](../architecture/observability.md) 已写明的语义，**属设计变更而非调优**，
  因此不在 v0.2 内擅自实施 → v0.3 候选
- **不接受的口径**："3.4s 已经很接近 3s 了"。未达标就是未达标，详见
  [metrics §性能目标](../internals/metrics.md)

### 2.2 三个新引擎只有"真实引擎"以外的一半被证明

CI 里跑**真实外部引擎**的只有 esbuild（`engine integration` job）。
tsc / deno / postcss 的验收全部使用**假引擎**——它们证明的是 ngm 的 argv 翻译与错误语义，
**没有证明**这三个工具的真实 CLI 与我们的调用方式一致（例如 `deno bundle` 的参数面随版本变化）。

这是刻意的取舍（测试不得依赖公网与机器上装了什么），但**必须写清楚它证明了什么、没证明什么**。
→ v0.3 候选：为 tsc / postcss 增加真实引擎 CI job（二者安装简单、无实验特性）。

### 2.3 `--deep` 的单个依赖内部仍是串行哈希

依赖级并发已覆盖主要收益（12.65s → 2.28s），但一个依赖内部的逐文件哈希没有并行。

## 3. 设计偏离登记（每条都写明"为什么不是照做"）

| # | 计划原文 | 实际做法 | 理由 |
|---|---------|---------|------|
| 1 | `ngm tree` 标注漏洞 `✗` | 改为**显式 `--osv`** 才查询 | 让"打印一棵树"静默发起网络查询，与"命令是否触网必须可预期"冲突 |
| 2 | 新增内置引擎条目 | 新增条目一律 `optional`（未安装不算 issue） | 否则"没装 tsc"会让 `engines validate` 对**所有**用户报 exit 5，而那些人根本没打算类型检查 |
| 3 | 内置 `deno` 条目 | deno **不进内置清单**，需在 `ngm.engines.json` 声明 | 内置后按名字排序会排到 tsc 前面，悄悄成为多数 TS 项目的默认类型检查器；且其 bundle 是 ≥2.4 实验特性 |
| 4 | `install --frozen-lockfile` / `--offline` | 保留为**两个独立 flag** | 它们约束的是两件事：frozen 管"装什么"、offline 管"怎么拿"。可复现只需前者 |
| 5 | `postInstallPolicy` 三种行为 | v0.2 **只记录不执行**（ADR-009 决策 5） | 执行依赖脚本需要沙箱前置；无沙箱时开入口等于在最没约束的时刻引入最危险的能力 |
| 6 | （计划未写）`verifyOnLock` 的失败语义 | 按 `verify` 自己的退出码返回，**不折成 0、也不套用策略失败的 exit 3** | `3` 表示"配置/策略本身非法"，与"上游动了"是不同类别；混用会让 CI 分不清。已补录为 [ADR-009 决策 6](../adr/adr-009-supply-chain-policy.md) |

> 第 5、6 两条例外：**验收标准跟着范围调整，而不是假装达成**。计划里 A 组的
> "三种 postInstallPolicy 行为测试"已按收窄后的范围改写（见 §1 与 v0.2-plan）。

## 4. 本轮发现并修复的缺陷

| # | 缺陷 | 由什么发现 | 影响 |
|---|------|-----------|------|
| 1 | `.gitignore` 的裸模式 `ngm` 吞掉了目录 `cmd/ngm/`（30 个文件） | 提交后核对"提交内各顶层目录文件数" | **新克隆的仓库无法构建**（v0.1 遗留） |
| 2 | `errs.Wrap` 包装配置错误时丢失原退出码 | 策略校验故意传非法值做端到端验证 | 配置错误被报成 `exit 5`，CI 无法区分"配置错"与"引擎缺失" |
| 3 | `ngm css` 不转发引擎的 warnings | 实现 postcss 的"`--minify` 不静默忽略"时 | 那条提示**永远到不了用户**——不静默的设计等于白做 |
| 4 | audit 报告的 `FromCache` 字段声称了未测量的事 | 自查（写完之后重读自己的报告结构） | 报告里出现一个恒为"启用缓存"的字段，语义是假的 |
| 5 | `verifyOnLock` 有文档承诺、无任何实现 | **对着计划逐条核对验收标准** | 文档说"v0.2 生效"，实际从不触发 |
| 6 | v0.1 复盘 §3.4 第一条建议（"按仓库合并 git 调用"）前提不成立 | 去实现它时测量发现 | 本基准 100 依赖分属 100 个仓库，无可合并；**已撤回并写明原因**，避免后人照做无用功 |

**过程洞察**：6 处里只有 2 处（#3、#4）是写代码当时发现的，其余 4 处来自
**"做完之后再验证一次"**——重跑一遍、对着计划核对、去核实文档里自己写的引用。
这类缺陷不会在"命令跑通了"的那一刻暴露。

另有两处**环境层**的失败，一并记录（它们差点被误判为代码回归）：

- **macOS runner 更新后无法加载 Go 1.22 构建的二进制**（`missing LC_UID Load Command` /
  `signal: abort trap`，测试二进制启动即崩、`0.002s FAIL`）。二分定位到"与代码提交时间上的巧合"，
  修复为 CI 与发布流水线同步升到 Go 1.27。**发布产物若用旧工具链构建，用户拿到手会崩**——
  这比 CI 红灯严重得多。
- **ubuntu 镜像自带 `tsc`** → `engines validate` 因此多出一条**信息级**版本比对，
  打破了我那条"干净清单只允许 esbuild 的 issue"的断言。修的是测试的假设（只拦 `unavailable`），
  不是代码。

> 两次失败都发生在我看不到日志的时刻（Actions 日志接口需要 admin 权限，匿名读不到）。
> 为此加过**临时诊断步骤**：把失败尾部经 `::error::` 发到 annotations（匿名 API 可读）——
> 定位后已移除。这个手法在"平台相关、本地复现不了"的失败上值得再用。

## 6. v0.3 候选（按证据强度排序，非路线图承诺）

1. **惰性 fetch**——在线 `verify` 达标的唯一已知途径（§2.1）
2. **`refType=commit` 跳过 `ls-remote`**——字面量没有"重新解析"可言；同样改动语义，需先立 ADR
3. **真实引擎 CI 覆盖扩展到 tsc / postcss**（§2.2）
4. **单个依赖内部并行哈希**（§2.3）
5. 路线图原有：wasm / remote adapter、集成脚手架、Deno 沙箱（`postInstallPolicy` 执行入口的**前置**）、
   权限与凭证、mappings 协议 v2

## 7. 对 v0.3 的建议

1. **先做一次设计复核**，像 v0.2 开工前那样。那次复核的产出是实质的：它发现
   `resolve.Node.RequiredBy` 必须从"依赖名"改成"节点 Key"，否则来源链在 monorepo 下会指错节点——
   这属于"先改数据结构、再谈功能"的那类结论，事后补代价高得多。
2. **任何触及联网语义的优化都先立 ADR**（惰性 fetch、commit 跳过 ls-remote 都在此列）。
   它们的共同点是：能显著提性能，但会改变"在线 verify 意味着什么"。
3. **"文档承诺"与"代码实现"之间要有一条机械化的核对**。本轮 6 处缺陷里有 5 处属于这一类，
   而它们全都是靠人工核对发现的。最小可行的做法：让 `docs/development/v0.2-plan.md` 的
   验收条目成为**测试文件里的注释锚点**，或在复盘时留出"逐条对证据"的固定步骤（本轮即如此）。
