## 为什么在 v0.5 之前做这件事

v0.3 复盘 §7 留下的**唯一待办**是：

> 每个配置字段都要有一条"从配置读到行为"的端到端断言；
> **没有断言的字段，不得在文档里被描述为已生效**。

它来自一个连续三个版本出现的模式：

```
verifyOnLock（v0.2） → permissions（v0.3 D） → SubPaths（v0.3 E）
```

共同点：**声明了、注释写了、没有任何地方接线**。它不会崩，只会给出一个"看起来合理
但相反"的结论。v0.4 修了第 4 例（`git.tokenEnvVars`）。

**所以本轮复核的第一个动作，就是去查还有没有第 5 例。** 下面是结果。

## 实测 1：配置字段接线核对

**方法**：枚举三处配置来源（项目清单 `ngm.json`、引擎清单 `ngm.engines.json`、
全局配置 `~/.ngm/config.json`）+ 全部 CLI flag，对每个字段要求三项证据：

| 要求 | 缺了会怎样 |
|------|-----------|
| (a) 定义位置 | —— |
| (b) 读取位置 | 缺 = 声明了没人读 |
| (c) 读到的值**是否真的改变了某个分支 / 输出** | 缺 = 读了但没用 |

只有三条齐全才算"已接线"。

### 确认未接线（4 项）

| # | 字段 | 定义位置 | 证据链 |
|---|------|---------|--------|
| 5 | `ngm.json` → `types` | `internal/config/config.go:66` | 全仓库 `\bTypes\b` 的命中里，属于 `config.ProjectFile` 的**只有定义本身**（其余全是 `internal/mappings` 的**另一个** `Types` 字段）。`Main` 有三处真实分支（`build.go:71`、`typecheck.go:75`、`typedecl.go:73`），`Types` 一处都没有 |
| 6 | `ngm.json` → `vendor.commit` | `internal/config/config.go:134` | 同 struct 的 `mode`（`env.go:205/228`）、`linkMode`（`env.go:218`）、`globalPath`（`env.go:206`）都在 `cmd/ngm/env.go` 被读，唯独 `Commit` 没有。ngm 从不执行 `git add` / `git commit`，写入路径只有 lock / mappings / vendor / integrations 产物——**不存在"是否提交 vendor/"的分支** |
| 7 | `config.EngineRef`（`primary` / `fallbacks` / `options`） | `internal/config/config.go:94-98` | 全仓库仅命中定义与上一行注释；**零实例化、零字段访问**。是死类型 |
| 8 | `ngm update --concurrency` | `cmd/ngm/update.go:53` | 定义在 `:53`，而 `:199` 写着 `_ = maxConc // …此 flag 预留给未来的解析阶段`。实际并发来自 `cmd/ngm/env.go:167` 的 `resolve.DefaultConcurrency`，**与传入值无关** |

> 这 4 项与前三例**同型**：不报错，只是默默不生效。而 `types` 与 `vendor.commit`
> 在 `docs/guides/configuration.md:94 / :104-106 / :195` **被描述成会生效的** ——
> 那正是 §7 建议要禁止的形态。

### 弱接线（3 项，需裁定，不自动算缺陷）

| 字段 | 位置 | 现状 |
|------|------|------|
| `runtime` | `config.go:64` | 被校验合法性（`validate.go:40-41`）、被填默认值（`config.go:327-328`）、被 `init` 写入。**但没有行为分支**：`RuntimeDeno`（`config.go:36`）除定义与 `ValidRuntime()` 外无任何引用，node 与 deno 行为完全一致。文档 `:16` 却把它与 `name` / `version` / `dependencies` 并列为"v0.1 已生效" |
| `version` | `config.go:63` | 仅"必填校验"（`validate.go:37`）+ 经 json 标签整体回显。比 `types` 多一层影响：**缺失即报错** |
| `Entry.supportedInput` | `catalog.go:69` | 只在 `ngm engines info` 打印（`engines.go:167`），`engines list` 无此列，**不参与能力选择**。v0.4 计划已把它定性为"接了线、没测" |

**裁定依据（建议沿用复盘自己的判据）**：若"生效"指**改变行为**，`runtime` 是缺陷；
若只指**被校验并回显**，则不是。这个区别必须写进文档，而不是留给读者猜。

### 一处必须避免的误判（核对时差点报成缺陷）

`EnginesConfig` 的五个 `transform` / `bundle` / `typeCheck` / `typeDecl` / `css`
字段在代码里**搜不到直接引用**，看起来像第 9 例。但它**不是缺陷**：它们经
`AsMap()`（`config.go:109-129`）以 `any` 原样交出 → `cmd/ngm/engine.go:82` →
`adapter.SelectionFor` → `ResolveSelection` → `resolveSelectionMap`（`selection.go:105-150`
读 `primary` / `fallbacks` / `options`）→ `runner.go` → `subprocess.go:483 mergedOptions`
→ 最终**真的进入 argv** ✓。

结论：那是**经由 helper 的间接接线，功能有效** ✗不是缺陷。
顺带说明第 7 例的性质：`config.EngineRef` 是死类型，但**同名功能由 `adapter.Selection`
完整实现** —— 缺陷是"多了一个没人用的类型"，不是"`options` 不生效"。

#### 文档核对顺带查出的两处真缺陷（不属于"文档漂移"）

a. **`ngm lock migrate` 不存在，却被 4 处引用**：`internal/lock/schema.go` 的两条错误提示
   （用户看得到）与 `configuration.md`、`locking.md`。用户照做只会得到"未知命令"。
   处置：提示改为唯一真实可行的路径（删除 `ngm.lock` 重跑 `ngm install`），并在常量旁写明
   "MAJOR 变更必须与迁移命令同时交付，否则提示里不得引用它"。
b. **`esbuild does not type-check` 的 hint 把内置引擎说成"未适配"**：
   `tsc / deno are not adapted in this build`——`typescript` 自 v0.2 起就在内置清单里。
   处置：hint 改为指向内置的 `--engine=typescript` / `"typeCheck": "typescript"`。

> 两处的共同点与 §"确认未接线"同型：**不报错，只是给出一句会把人引开的话**。
> 这类缺陷靠读代码读不出来，只有在"把文档/提示与实现逐条对上"时才现身——
> 这正是本轮把它列为待办的理由。

#### 补测：安全模型里的同类问题（Deno 2 的假失败）

沙箱是**唯一运行他人代码**的路径，因此先重测它。CI 此前装的是 `deno-version: v1.x`，
而仓库声明的下限是 **Deno >= 2.0**——下限从未被验证过。用真实 Deno 2.4.0 重测后：

| 事实 | 结论 |
|------|------|
| 同一组 argv（`--allow-read=<dir>` + 全部 `--deny-*` + `--no-remote`）在 2.4.0 上 | **边界照样成立** ✓（目录外读、写都被拦下） |
| 权限错误的 `name` | `PermissionDenied` → **`NotCapable`** |
| 我们的验收夹具 | **只认旧名字**，于是把"已被正确拦下"报成 `outside: READABLE` / `write: ALLOWED`——一次**假失败** |

处置：4 处夹具（3 处在 `cmd/ngm`、1 处在 `internal/security`）改为**同时接受两种类名**，
并把实际类名打进输出；另修掉 1 处**弱断言**（`TestSandbox_RealDeno_NetOnlyWhenGranted`
的第二个子用例原本只断言"不含 blocked"，类名改名后它**因为错误的原因通过**）。
两个 Deno 版本上全套测试均为绿（各自实测）。ci.yml 改为 `deno-version: v2.4.0`，
并写明"按能力探测"说的是 ngm 的判定方式，而"CI 装哪个版本"是一个必须等于声明下限的选择。
证据与原文见 [ADR-012 补测](../adr/adr-012-sandbox.md)。

#### 挂账两项（自 v0.2 起）：一项结项、一项仍未结项

**a. 单个依赖内部并行哈希** ✅ **已做**。两处：

| 位置 | A/B（同一份代码，只改并发度；`GOMAXPROCS=1` 作串行对照） | 结论 |
|------|--------------------------------------------------------|------|
| `--deep` 的逐文件校验（`internal/vendor`） | 373.6ms → **178.6ms**（2000 × 8 KiB，**2.09×**） | 纯文件哈希，接近核数收益 |
| digest 清单重放（`internal/git`） | 278.9ms → **244.1ms**（2000 × 8 KiB，**1.14×**） | **与预期相反**：成本大头是 git 子进程，不是哈希 |

第二条值得单独记：它推翻了我"并行哈希能显著加速 digest"的预期。**这条路径的下一个优化是"少开
子进程"，不是"开更多线程"**——结论写进了基准文件的头部注释，免得下一个人重蹈。
两个基准都留在仓库里（`internal/git/archive_bench_test.go`、`internal/vendor/integrity_bench_test.go`），
A/B 命令写在注释里，**别人可以复现**（不需要为了测量而改代码）。

**b. deno 真引擎覆盖** ⚠️ **结了一半**，另一半的**条件仍未成立**：

- ✅ **稳定的一半已覆盖**：`ngm typecheck --engine=deno`（`deno check`）此前从未被真工具验证过
  （假引擎接受任何参数）。新增 `TestV05RealDenoTypeCheck` 并进 CI 的真引擎 job。
  实测结论：干净项目 exit 0、类型错误 exit 1，且 **deno 的诊断走 stderr**——
  这一条对本项目特别重要，因为 v0.2 的缺陷正是"引擎把诊断写在 stdout 而被丢掉"。
- ❌ **bundle 那一半**：`deno bundle` 至今仍标注 **"experimental and subject to changes"**
  （Deno 2.4 官方发布说明，2025-07-02，另注 "it is here to stay"——不会再被移除，但接口仍可变）。
  拿它当 CI 门禁会让红灯来自上游的接口变动，因此**继续挂账**，
  结项条件写死为"上游把 bundle 标为稳定"。

#### 可复现性最后一档 ✅ 已扩到插件 / loader / 压缩链

探针（`scripts/probe-reproducibility.sh`）补了三种形态：**loader 链**（`.png` → dataurl、
`.txt` → text 再压缩）、**CSS 压缩链**（esbuild `--minify`）、
**esbuild 插件（JS API）+ metafile**——最后一项是刻意的：真实项目（Vite / Astro）走的就是插件链，
而 metafile 里记着每个输入输出的路径，正是"绝对路径泄漏进产物"最可能出现的地方。
本机两次运行给出同一 `treeA=6e5cb4d34ce3af63`，对照组敏感。

顺带取得一个**跨机器数据点**：本机用旧夹具跑出的 `treeA=eef8b785e0e3f968` 与 CI 上
Ubuntu / macOS / Windows 三个 runner **完全相同**。

同时把"跨机器"从**人读三行 annotation** 改成**机器判定**（`scripts/compare-probe-results.mjs`
+ 工作流新增 `compare` job），判四层：各平台自检成立 / 无构建失败 / **引擎版本一致** /
产物哈希一致；只收到一份结果也算失败（"没测出来"不得读成"通过"）。
最后一层是此前最容易漏的：版本不同的两份字节恰好相同纯属巧合。
结果与边界见 [ADR-013 第四批](../adr/adr-013-remote-adapter.md)。
**新形态的跨平台结果仍需一次 CI 运行**（本环境无法触发 `workflow_dispatch`），因此
ADR-013 的翻案条件**仍未成立**。

#### 顺带补上两处入口缺口

- **`ngm transform`**（v0.5）：`transform` 能力在 adapter 层早已实现，却没有任何命令驱动它——
  于是 `engines.transform` / `engines.defaultTransform` 对用户没有可观察的效果。
  与 v0.4 给 `typeDecl` 补入口同型。验收：`TestV05TransformAcceptance`（假引擎，进 CI 验收组）+
  `TestV05RealEsbuildTransform`（真 esbuild，进真引擎 job）。
- 补入口时**当场发现一处协议缺陷**：`genericInvocation` 的 transform 分支
  **只转发 loader 与 target**，`--format` / `--minify` / `--sourcemap` 被**静默丢弃**——
  自定义引擎的用户会拿到未压缩的产物而没有任何提示。已修，并加了一条**完整 argv 精确比对**
  的断言（`TestBuildInvocation_GenericTransformForwardsEveryOption`），防止它被改回去。
  它一直没被发现的原因与上面几例相同：**没有入口，就没有人会走到那里**。
- 随后又发现**另一处同型缺陷，且是一对**：两条"把话说到用户那里"的通道**各丢了一半**。
  两种结果类型里同名的 `Warnings` 字段含义不同，于是——

  | 路径 | 引擎的 stderr | ngm 的说明（Notes） |
  |------|--------------|-------------------|
  | bundle | ✅ 转发 | ❌ **丢失**——`deno bundle` 的"实验特性"提示写好了没人读 |
  | css | ❌ **丢失**——postcss 的警告到不了用户 | ✅ 转发 |

  第一项尤其要紧：那句提示是"我们没说过它稳定"的**全部依据**。
  处置：两个字段分家（`Warnings` = 引擎原话、`Notes` = ngm 的话，四个适配器方法一并统一），
  CLI 两端都打印（ngm 的话带 `note: ` 前缀）；
  验收 `TestV05EngineChannelsAcceptance`，并**回退修复验证过断言会红**。
  顺带固定了此前完全没有测试的 `deno bundle` 版本闸门（< 2.4 → exit 5 且指向 esbuild）。
- 本命令的**第一版自己**又制造了一次同类缺陷：CLI 自己判"没 loader 就报错"，
  于是清单里声明好的 `engines.transform.options.loader` 被挡在门外（adapter 本来会用它），
  并且把"必须有 loader"这条 **esbuild 专属**规则强加给了所有引擎。
  处置：那条判断交回 adapter（单一事实源），CLI 只负责推断与不猜；
  验收 `TestV05TransformAcceptance` 的 `a loader declared in the engine's defaultOptions is honoured`。
  **教训**：把规则抄到第二个地方，就一定会有一处不一致——这正是本页反复出现的形态。
