# v0.5 开工前复核

> 版本收尾之后、动手之前：把"我们以为的"换成"我们测到的"。

- **区间**：v0.4 交付之后（`main @ 984f923`）
- **日期**：2026-10-01
- **方法**：去验证而不是假设。每条结论都要有可执行证据；**没有测的一律写成"未测量"**，
  不写成"保持"或"没问题"。
- **范围**：本轮只做了第 1 项实测（配置接线）。其余复核项见文末"未做的复核项"。

## 为什么在 v0.5 之前做这件事

v0.3 复盘 §7 留下的**唯一待办**是：

> 每个配置字段都要有一条"从配置读到行为"的端到端断言；
> **没有断言的字段，不得在文档里被描述为已生效**。

它来自一个连续三个版本出现的模式：

```
verifyOnLock（v0.2） → permissions（v0.3 D） → SubPaths（v0.3 E）
```

共同点：**声明了、注释写了、没有任何地方接线**。它不会崩，只会给出一个"看起来合理
但相反"的结论。v0.4 修了第 4 例（`git.tokenEnvVars`）。

**所以本轮复核的第一个动作，就是去查还有没有第 5 例。** 下面是结果。

## 实测 1：配置字段接线核对

**方法**：枚举三处配置来源（项目清单 `ngm.json`、引擎清单 `ngm.engines.json`、
全局配置 `~/.ngm/config.json`）+ 全部 CLI flag，对每个字段要求三项证据：

| 要求 | 缺了会怎样 |
|------|-----------|
| (a) 定义位置 | —— |
| (b) 读取位置 | 缺 = 声明了没人读 |
| (c) 读到的值**是否真的改变了某个分支 / 输出** | 缺 = 读了但没用 |

只有三条齐全才算"已接线"。

### 确认未接线（4 项）

| # | 字段 | 定义位置 | 证据链 |
|---|------|---------|--------|
| 5 | `ngm.json` → `types` | `internal/config/config.go:66` | 全仓库 `\bTypes\b` 的命中里，属于 `config.ProjectFile` 的**只有定义本身**（其余全是 `internal/mappings` 的**另一个** `Types` 字段）。`Main` 有三处真实分支（`build.go:71`、`typecheck.go:75`、`typedecl.go:73`），`Types` 一处都没有 |
| 6 | `ngm.json` → `vendor.commit` | `internal/config/config.go:134` | 同 struct 的 `mode`（`env.go:205/228`）、`linkMode`（`env.go:218`）、`globalPath`（`env.go:206`）都在 `cmd/ngm/env.go` 被读，唯独 `Commit` 没有。ngm 从不执行 `git add` / `git commit`，写入路径只有 lock / mappings / vendor / integrations 产物——**不存在"是否提交 vendor/"的分支** |
| 7 | `config.EngineRef`（`primary` / `fallbacks` / `options`） | `internal/config/config.go:94-98` | 全仓库仅命中定义与上一行注释；**零实例化、零字段访问**。是死类型 |
| 8 | `ngm update --concurrency` | `cmd/ngm/update.go:53` | 定义在 `:53`，而 `:199` 写着 `_ = maxConc // …此 flag 预留给未来的解析阶段`。实际并发来自 `cmd/ngm/env.go:167` 的 `resolve.DefaultConcurrency`，**与传入值无关** |

> 这 4 项与前三例**同型**：不报错，只是默默不生效。而 `types` 与 `vendor.commit`
> 在 `docs/guides/configuration.md:94 / :104-106 / :195` **被描述成会生效的** ——
> 那正是 §7 建议要禁止的形态。

### 弱接线（3 项，需裁定，不自动算缺陷）

| 字段 | 位置 | 现状 |
|------|------|------|
| `runtime` | `config.go:64` | 被校验合法性（`validate.go:40-41`）、被填默认值（`config.go:327-328`）、被 `init` 写入。**但没有行为分支**：`RuntimeDeno`（`config.go:36`）除定义与 `ValidRuntime()` 外无任何引用，node 与 deno 行为完全一致。文档 `:16` 却把它与 `name` / `version` / `dependencies` 并列为"v0.1 已生效" |
| `version` | `config.go:63` | 仅"必填校验"（`validate.go:37`）+ 经 json 标签整体回显。比 `types` 多一层影响：**缺失即报错** |
| `Entry.supportedInput` | `catalog.go:69` | 只在 `ngm engines info` 打印（`engines.go:167`），`engines list` 无此列，**不参与能力选择**。v0.4 计划已把它定性为"接了线、没测" |

**裁定依据（建议沿用复盘自己的判据）**：若"生效"指**改变行为**，`runtime` 是缺陷；
若只指**被校验并回显**，则不是。这个区别必须写进文档，而不是留给读者猜。

### 一处必须避免的误判（核对时差点报成缺陷）

`EnginesConfig` 的五个 `transform` / `bundle` / `typeCheck` / `typeDecl` / `css`
字段在代码里**搜不到直接引用**，看起来像第 9 例。但它**不是缺陷**：它们经
`AsMap()`（`config.go:109-129`）以 `any` 原样交出 → `cmd/ngm/engine.go:82` →
`adapter.SelectionFor` → `ResolveSelection` → `resolveSelectionMap`（`selection.go:105-150`
读 `primary` / `fallbacks` / `options`）→ `runner.go` → `subprocess.go:483 mergedOptions`
→ 最终**真的进入 argv** ✓。

结论：那是**经由 helper 的间接接线，功能有效** ✗不是缺陷。
顺带说明第 7 例的性质：`config.EngineRef` 是死类型，但**同名功能由 `adapter.Selection`
完整实现** —— 缺陷是"多了一个没人用的类型"，不是"`options` 不生效"。

## 处置结果（本轮收口）

### 裁定

**"生效" = 改变行为。** 只被校验与回显不算——否则这个词对读者没有信息量。
`configuration.md` 据此改为三档标注（改变行为 / 声明与展示 / 已移除）。

### 逐项处置

| # | 项 | 处置 | 证据（可执行） |
|---|-----|------|---------------|
| 5 | `ngm.json` → `types` | **接线**：mappings 的入口推断改走 `config.ProjectFile`（此前按 JSON 键另解析一份，字段本身无人读） | `TestDeclaredTypesEntryReachesTheMappings` |
| 6 | `ngm.json` → `vendor.commit` | **删除**（字段 + 5 处文档），并在 `configuration.md` 与 `config.go` 注明这是有意的破坏性变更 | `VendorConfig` 注释；`configuration.md §vendor` |
| 7 | `config.EngineRef` | **删除**（死类型）。同名功能由 `adapter.Selection` 完整实现，因此不影响任何行为 | `go build ./...`；`TestResolveSelection_*` |
| 8 | `ngm update --concurrency` | **删除 flag**（值被 `_ =` 原样丢弃；不在 usage、不在文档）。需要时按真实需求重新引入 | `cmd/ngm/update.go` |
| 弱 1 | `runtime` | **保留 + 文档撤回"已生效"**：它是宿主运行时的声明，ngm 不干预宿主。断言固定它**真实**的契约（校验 / 回显 / 必填） | `TestRuntimeIsValidatedAcceptedAndEchoed` |
| 弱 2 | `version` | **保留 + 文档撤回**：必填声明 + 回显，不参与解析 | `TestProjectVersionIsRequired` |
| 弱 3 | `Entry.supportedInput` | **判定为已接线（仅展示）**：`engines info` 打印，`engines list` 无此列，不参与能力选择；在检查表与文档里写明这一点 | `TestDeclaredSupportedInputIsListed` |

### 机械检查比人工复核多查出的 3 项（一并处置）

`internal/config/field_wiring_test.go` 首次运行点了 **10** 项，比本节预测多 3 项——
都是"已接线、没断言"，与 §7 的判据同类：

| 字段 | 处置 | 证据 |
|------|------|------|
| `ProjectFile.schemaVersion` | 补断言 | `TestUnsupportedSchemaVersionIsRejected` |
| `GlobalFile.schemaVersion` | 同上 | 同上 |
| `Entry.version` | 补断言（声明版本与本机实际版本的比对是**信息**，退出码 0） | `TestDeclaredEngineVersionIsComparedWithTheLocalOne` |

### 检查形态

`internal/config/field_wiring_test.go`：用 `reflect` 枚举 11 个配置 struct 的
JSON 字段（键为 `Struct.Field`），要求每个字段都在 `wiredFields` 表里登记一条覆盖
它的测试函数，并在运行时扫描 `*_test.go` 验证该函数**真的存在**。它不靠名字形状猜，
因此单段名的 `types` / `commit` 不再漏网（`config_coverage_test.go` 的 `camelKey`
只匹配多段驼峰，那正是它自己写明的限制）。

### 本轮登记、未修的一处

`BuiltinDefaults.Runtime`（"项目没写 runtime 时补 node"）对**显式** `ngm.json`
是不可达的：`decodeProject` 先 `Validate()`（空 runtime 直接报错），之后才
`mergeProject`。行为与文档一致（runtime 是必填），因此不修，只登记。

1. **把 §7 的建议机械化** —— 这是它**第三次**证明自己有效了（本次新增 4 例）。
   具体形态：一张"字段 → 端到端断言"的对照表，缺断言即失败。
   ⚠️ 现有 `config_coverage_test.go:49` 的 `camelKey` 正则只匹配**多段驼峰名**，
   因此单段名的 `types` / `commit` 按设计就拦不住（该文件 `:42-43` 自己也写了这条限制）。
   **真正的检查必须枚举字段本身，而不是靠名字形状去猜。**
2. **裁定并处置 4 项确认未接线 + 3 项弱接线** —— 每一项要么接线，要么从 struct 与
   文档里一起删掉。特别是 `types` 与 `vendor.commit`：它们**在文档里被描述为会生效**。
3. **挂账两项**（自 v0.2 起）：deno 真引擎覆盖（等上游 `bundle` 脱离实验）、
   单依赖内并行哈希。
4. **可复现性最后一档**：真实项目的插件 / loader / 压缩链仍未测（合成项目已证）。
