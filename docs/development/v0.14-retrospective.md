## 5. 过程洞察

### 5.1 换方向比再扫一遍有效

v0.13 的结论是"代码扫描边际递减"。本版换了个问法——**"文档承诺了什么，而实现做的是另一件事"**——
一次抓到四处，而且其中一处**成片出现**（同一事实在三个位置各错一遍）。
这类缺陷**既不会让任何测试变红，也不会被代码审查发现**：审查看的是代码是否自洽，
而它的问题在于**代码与文档之间**。

### 5.2 照文档写测试，会把文档的错误复制进测试

D6 是这一版最值得记住的一条：我写"esbuild 顶类型检查 → exit 5"时是**照抄 `build.md`** 的，
实测是 3。若当时为了让测试通过而改实现，就会把一个**正确的行为**改成文档描述的错样子。
同族的先例：v0.12 的 D1（测试预期 exit 4、实测 0）——**红的那一次挡住了错误的修改**。

> 可复用的判据：**写断言时要问"这个期望值是从哪来的"**。
> 来自运行结果 → 可以；来自另一份文档 → 先跑一遍再说。

### 5.3 "什么都没发生"的断言必须有对照（第三次）

B1 断言"目录没变"，B2 断言"没有内置默认"。两者的失效方式一样：
**一个恒为"没变/没有"的仪器能让它们永远变绿**。
所以 B1 配了"真的 add 一次必须让快照变"，B2 配了"同一命令在已声明时给出另一个退出码"。
从 v0.11 的 `waitdelay_test.go` 到 v0.12 的原子写入、v0.13 的 spawn 计数，这已是第三次——
**它现在可以当作本项目的网的标准形状来用。**

### 5.4 退出码是接口的一部分

A4 的价值不在措辞：`exit 3`（名字在这个 kind 下不存在 → **改名字**）与
`exit 5`（名字存在但干不了 → **换引擎**）指向两种不同的修复动作。
把两者混起来的文档，比没有文档更费时间。

### 5.5 "非测试代码 0 行改动"的版本在做什么

v0.10 实现 0 行改动（把检查推到最外圈），v0.13 不改行为（把形状固化成网），
本版同样不改行为（把文档与实测对齐 + 补三张网）。
这类版本看起来"没做什么"，但它决定了**下一个接手的人不必再相信一段没人验证过的文字**。
