# v0.54 复盘 — **解析阶段的失败也是机器可读的**

> 体例同各版：逐组验收 → 未达成项 → 设计偏离 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 一句话结论：v0.51 的错误信封写在 `runErr` 里，而它只在**命令内部**被调用——
> 解析失败与"命令不存在"都发生在它之前。这一版把那一类补上，
> 并在量的时候**又量出一处新缺口**（根级位置的 flag 被静默丢弃）。
> 登记表里做掉一条、添上一条——**这次棘轮没有往下走，原因写在 §5**。

## 1. 逐组验收

### 1.1 起点：六个变体，量出三类

| 变体 | 读数 | 归属 |
|------|------|------|
| `verify --json --bogus` | exit 3 · **stdout 0 字节** · stderr 3198 字节 usage | **缺口** |
| `verify --bogus --json` | 同上 | **缺口**（顺序不影响） |
| `nosuchcmd --json` | exit 3 · **stdout 0 字节** | **缺口**（分派阶段） |
| `audit --json=1` | exit 3 · **stdout 287 字节**（已有信封） | **不是**缺口：`=1` 是合法布尔值，命令真的跑起来了 |
| `verify --json --dir` | exit 3 · **stdout 231 字节**（已有信封） | 同上，命令内部 |
| `--json verify` | exit 3 · **stdout 0 字节** | **新缺口**（见 §4） |

> 前两条"我以为属于缺口"的（`--json=1` 与 `--json --dir`）**其实没走到解析失败**——
> 一个是因为 `1` 本来就是合法布尔值，一个是因为 `--dir` 缺值时命令仍然跑起来了。
> **先量再归类**，省掉了两处白改。

### 1.2 处置：从**原始参数**里问一次

新增两个函数（`cmd/ngm/root.go`）：

| 函数 | 职责 |
|------|------|
| `jsonAskedEarly(args)` | 扫原始参数：用户有没有提出要机器可读输出？支持 `--json` / `-json` / `=true` / `=1`；`=false` **不算**；值写坏（`=bogus`）**算**（那时信封会告诉他哪个值不合法） |
| `failEarly(args, stdout, msg, hint)` | 只在用户提了时写一份信封；**不打印人读文本**（flag 包已经打印过 usage） |

它**不是**"这个命令支不支持 `--json`"的判断（那要等命令自己解析 flag）——
它只回答"用户有没有提出这个要求"。三个调用点：缺子命令 · 未知命令 ·
**7 个接受 `--json` 的命令**的解析失败分支。

### 1.3 用户看到的东西变了

```
$ ngm verify --json --bogus      （改前：stdout 空）
{"version":1,"error":{"code":"Usage","exitCode":3,
  "message":"flag provided but not defined: -bogus",
  "hint":"run `ngm verify --help` for the flags it accepts"}}
```

`code` 是 `Usage`，而**退出码仍是 3**（数值是契约、名字给人读——v0.51 的
`DisplayName`/`Label` 正是为此存在的）。

### 1.4 判据（`TestV54…`）✅

读数：**14 组命令×顺序 + 2 条命令级**（未知命令 · 缺子命令）都带着合格信封。

四条断言 + 两条**对照**（它们才是这张网的重点）：

| 对照 | 要求 |
|------|------|
| `verify --bogus`（**没提** `--json`） | stdout **必须仍为空**——不许给没要的人塞 JSON |
| `install --json`（命令**不接受**它） | stdout **必须仍为空**——v0.51 规则④那句没变 |

### 1.5 牙齿 ✅（第二道第一次没咬住）

| 探针 | 结果 |
|------|------|
| `jsonAskedEarly` 永远说不 | 红，并**逐条点名**（`verify --json --bogus` · `--bogus --json` · `audit …` …） |
| 人读那侧**重复说一遍** | 红：`stderr 里 not defined 出现了 2 次（想要 1 次）——人读那侧重复了` |

> 第二道**第一次写错了位置** ✗：我把重复的那句打印到 `os.Stderr`，而判据看的是
> **命令收到的那个 writer**——于是它照样绿。
> 按"**回归会怎么发生**"重写（在命令的解析失败分支里补一句）才咬住。

## 6. 过程洞察

### 6.1 "解析阶段的失败"是一道**边界**，不是一类 bug

v0.51 把信封做进 `runErr` 时，choke point 选得对（唯一的错误渲染点）——
但它有一个**视野边界**：命令开始处理自己的参数**之前**的失败不经过它。

> 每一道 choke point 都有它的视野边界。**把边界写下来**（而不是等它变成缺口），
> 是 v0.51 那次复盘欠的一笔——这一版补上了。

### 6.2 棘轮持平也要写清楚

这一版**做掉一条、发现一条**，登记表从 6 条回到 6 条。
"做了很多却只持平"看起来像没进展——所以更要写清楚**是什么抵消了它**：
抵消它的是本次探针的**新发现**（根级 flag 被静默丢弃）。

> 棘轮的价值在于"不许悄悄变多"，不在于"必须每版变少"。

### 6.3 探针本身要按"回归会怎么发生"设计

牙齿二第一次没咬住，因为它模拟的**不是**真实的回归路径：
我把重复的文本打到 `os.Stderr`（进程级），而判据观察的是**注入给命令的 writer**。
真实的回归会是"有人在命令里补了一句打印"——按那条路径重写，它立刻咬住了。

> 这与 v0.53 那条"判据要照着**事实**判、不是照着字面判"是同一族：
> **牙齿要照着回归的路径咬，而不是照着我顺手能改的那个地方咬。**
