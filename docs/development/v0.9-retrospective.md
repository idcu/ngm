# v0.9 复盘 — 让 store 的读数说真话

> 体例与各版一致：逐组验收 → 未达成项 → 设计偏离登记 → 缺陷清单 → 过程洞察 → 指标 → 下一版候选。
>
> 范围来源：[v0.8 复盘 §7](./v0.8-retrospective.md)；实施计划：[v0.9 计划](./v0.9-plan.md)。
>
> 一句话结论：**本版不新增能力，只把 v0.8 换布局之后变得含糊的数字说清**——
> 共享/独占/孤儿三个数各自回答一个问题，且**两条不变量让"算错"立刻可见**；
> 顺带补上了文档锚点的检查（收尾审计查出 2 条死锚点，此前无人能发现）。

## 1. 逐组验收

### 1.1 A — `store usage`：共享 / 独占 / 孤儿

| 计划项 | 结果 | 证据 |
|--------|------|------|
| A1 blob 池按引用数切开 | ✅ | `ContentStoreUsage.BlobSharedBytes / BlobExclusiveBytes / BlobOrphans` |
| A2 每棵树报"丢掉它能回收多少" | ✅ | `ContentStoreEntry.ExclusiveBytes`（**只算 blob**，口径见偏离 1） |
| A3 孤儿单独报，并写明 `prune` 不碰它 | ✅ | CLI 里那一行 + `orphaned blobs are NOT removed by "ngm store prune"` |
| A4 清单读不出来时**标注** | ✅ | `UnreadableManifests`；CLI 说明"孤儿被多算、共享被少算"——两个方向相反，不能说"是下界" |

**验收**：三条新用例，断言的是**不变量**而不是固定数字（见 §5.1）。

**已验证有牙齿**：把"共享也算进独占"放回去，两条等式立刻红，报出
`Σexclusive(1566) != BlobExclusiveBytes(1536)`——差值 `30 = 2 × 15`，正是那个被两棵树各算一次的小文件。

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | A2"丢掉这棵树能回收多少" | **只算独占 blob**，不含该树自己的清单与 meta | 第一版把清单也算进去，于是**小树的 exclusive 超过了它的 logical**（清单约 1.4 KiB，比内容还大）。改为只算 blob 后得到两条**紧的**不变量（`exclusive <= logical`、`Σexclusive == BlobExclusiveBytes`），而"把共享算进每棵树"这种错法立刻可见。清单体积在上面那行按整池报 |
| 2 | （未提）"读不出来"怎么处理 | 新增 `UnreadableManifests`，并说明偏差**方向相反** | 坏清单的 blob 会失去引用：孤儿被多算、共享被少算。原打算写"是下界"——不准确，因为两个方向不一样 |
| 3 | B 组按 shell 脚本做 | 改成 Go 测试 | 锚点要按 Unicode 类别处理中文，而 `grep -P` 的 Unicode 行为依赖 locale；Go 测试还省掉一处 CI 接线 |
| 4 | B3"跳过不确定的锚点" | 改成"**两个变体都算存在**" | 第一版"整文件跳过"太粗（所有锚点都被跳过，检查等于空跑）；按标题放宽才能既保留覆盖率又不误报 |

## 4. 本轮发现并修复的缺陷

| # | 缺陷 | 后果（如果不修） | 发现方式 |
|---|------|----------------|---------|
| D1 | 链接检查把**行内代码里的示例**当坏链 | 任何"教人怎么写文档"的文档都会让 CI 红，而它与文档质量无关 | CI（`13bb391` 唯一失败的 job） |
| D2 | 我在本地**读漏了**那次失败 | 明知本地已红，却推了一笔红的 | 自查（§5.5 记了这件事） |
| D3 | A2 的口径第一版包含清单体积 | `exclusive > logical`，且 `Σexclusive` 与 `BlobExclusiveBytes` 对不上——两个数字都不自洽 | 跑测试（断言即不变量） |
| D4 | `usage` 的测试夹具用**同一个仓库的两个 commit** | 第一个 commit 的文件仍在第二棵树里 → "独占"恒为 0，测不出区别（**夹具比实现先错**） | 跑测试 |
| D5 | 规模夹具用计数器造 blob 名 | 10 万个名字的前两位全是 `00` → 全落进同一分片，量到的是夹具偏差（`max files/shard=20000`） | 跑测量（数字明显不合理） |

## 5. 过程洞察

### 5.1 读数的口径要能**自证**：用紧的等式，而不是"应该差不多"

A 组的断言刻意不写具体数字，而写两条**等式**：

- `BlobSharedBytes + BlobExclusiveBytes + BlobOrphanBytes == BlobBytes`
- `Σ(每棵树的 ExclusiveBytes) == BlobExclusiveBytes`

好处是**错法立刻可见**，而且错误信息自带诊断：把"共享算进每棵树"放回去，
报出 `1566 != 1536`，差值 `30 = 2 × 15` 直接指出那个 15 字节的共享文件被算了两次。

> 这与 v0.6 的 spawn 预算是同一族做法：**让"看不见的错"在数字上表现为不成立**。
> 区别是这里连一个魔数都不需要——不变量自己就是判据。

### 5.2 门禁的**误报**比漏报更贵

D1 是这条的实例：一个会因为"文档里写了链接示例"而变红的检查，与代码质量无关，
而人会很快学会忽略它。处置是**从检查器侧修**（剥掉行内代码），并验证两个方向：

- 行内代码里的 `[label](nope.md)` **不再**被报（误报封住）；
- 同一行、代码之外的 `[real](gone.md)` **仍然**被报（牙齿没被磨掉）。

B 组 B3 的"放宽而不是收紧"是同一条原则的另一种写法：
**规则不确定时，宁可漏报**——因为漏报只是少一次发现，误报会让人关掉门禁。

### 5.3 **夹具也是一种仪器**，而它先坏了三次

本版三次"数字不对劲"（D3/D4/D5）**全部**源自夹具或口径，而不是实现：

| 现象 | 真因 |
|------|------|
| `exclusive > logical` | 夹具里的清单体积比内容还大（口径没想清） |
| 两棵树的独占都是 0 | 夹具用同一仓库的两个 commit，第一个的文件仍在第二棵里 |
| 单目录 2 万个文件 | 夹具用计数器造名字，前两位恒为 `00`（真实 blob 名是均匀的 sha256） |

**处置**：D5 的教训写进了 metrics（"测出来的分布要先用分布本身对不对验一遍"），
D4 的教训写在用例注释里（"为什么不用同一个仓库的两个 commit"）。
这类错误有一个共同点：**它不会让检查变红，只会让数字变得"看起来合理"**——
只有把数字与另一条独立的事实交叉（例如"独占之和应该等于池里那一块"）才会暴露。

### 5.4 "只测不做"要有**触发方式与复核入口**

C 组的测量若塞进日常测试，会给每次 `go test ./...` 加几十秒 IO；若只跑一次不留痕迹，
下一个人又要重写一遍。于是：**用例默认 `t.Skip`，靠 `NGM_STORE_SCALE_BLOBS` 触发**，
跑法写进 [metrics](../internals/metrics.md#blob-池的规模v09-实测只测不做) 并附数据。
数字旁边写清"这只是数据，不是对更细分片的否决"——**只测不做**的边界也在那句话里。

### 5.5 我这一版犯的错

| # | 错 | 怎么发现的 | 处置 |
|---|----|-----------|------|
| 1 | 本地那次 `check-docs-links` 已经失败，而我读的是**另一行成功的输出**（`release-ok`），于是当成通过 | CI 报红后回看本地输出 | 记在这里：**判据是退出码**，不是"我想要的某一行出现了没有" |
| 2 | 第一版锚点检查写成"整文件跳过" | 跑一次即发现：`checked: 0` | 改成按标题放宽（偏离 4） |
| 3 | 夹具先错（D3/D4/D5） | 跑测试/跑测量 | 见 §5.3 |

## 6. 指标

### 6.1 blob 池的规模（本版的主指标）

| 量 | 值 |
|----|----|
| 分片数 / 单目录文件数（10 万 blob） | 256 / **341 ~ 437**（均衡） |
| 写入速率 | 3756 blob/s（26.6 s 写 10 万个 32 B blob） |
| `Usage()` 遍历整个池 + 清单 | **244 ms**，分配 28.7 MiB，堆峰值 13.3 MiB |

**结论**：两位 hex 分片在 10 万级仍有余量；`usage` 仍是毫秒级 —— 本版不改布局。

### 6.2 新增的读数（举例口径）

同一场景（两份内容共享一个文件）下，`usage` 现在能分开回答三个问题：

| 问题 | 数 |
|------|----|
| 去重省了多少 | `shared by 2+ trees` |
| 丢掉某一棵树能回收多少 | 该行的 `exclusive` 列（**不含**共享 blob） |
| 有多少空间没有任何人需要 | `orphaned`（并注明 `prune` 不碰它） |

### 6.3 规模与验证

| 项 | 值 |
|----|----|
| 提交 | 6 笔（A、B、C 三组 + 计划 + 文档登记 + 检查器修复） |
| 测试 | 14 个包全绿；新增 3 条 usage 用例 + 1 条锚点用例 + 1 条规模用例（默认跳过） |
| CI | `13bb391` 红一次（D1，`docs link check`）→ 修复后复核 |
| 锚点 | 48 个，全部验到（0 跳过） |

## 7. v0.10 候选（按证据强度排序，非路线图承诺）

| # | 候选 | 前置 / 说明 |
|---|------|------------|
| 0 | **`v0.5.0` ~ `v0.9.0` 的 GitHub release** | 需人工触发（Actions → Release → Run workflow）；`check-release-status.sh --published` 会报出来 |
| 1 | `remote` adapter 门槛 b：抽样构建的**成本数字** | 门槛 a 已满足；b 是"要不要发布"唯一剩下的条件，**且需要产品决策与一个真实项目** |
| 2 | **`symlink` 落地模式是否恢复** | v0.8 把它改成逐条目 hardlink；若确实有人依赖"整目录链接"，正确做法是**按需物化一棵 hardlink 树**——新决策，不是回滚 |
| 3 | 3s 目标的口径重定义 | 次数门禁（v0.6）已跑过几个版本，数据够了；它需要的是**决策**，不是测量 |
| 4 | blob 的回收（GC） | [ADR-018](../adr/adr-018-store-reclaim.md) 的两个条件未变（没有项目注册表）。本版把"孤儿字节"变成了可读的数——**决策所需的数据已经就位** |
| 5 | `deno bundle` 真引擎覆盖 | 等上游（截至 2026-10-02 未变） |
| 6 | 锚点检查扩到 README | 本版只扫 `docs/`；根 `README.md` 也有锚点链接，但不在链接检查的范围内（同一条边界，一起扩或一起不动） |
