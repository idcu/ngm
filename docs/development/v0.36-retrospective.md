## 3. 一个候选被**证伪**（如实记录）

候选 1 是"让死赋值这类缺陷能被机械发现"。我先写了最便宜的版本（纯词法：一次赋值之后该变量在函数里再没被读过），在全仓库跑：

```
scanned 96 files, 0 real dead write(s)   ← 命中的全是 `_`
```

**它连动机里那个例子都抓不到**：`internal/verify` 的 `derr` 在 `default:` 分支里被读过一次，
而那是**兄弟分支**——词法顺序看不见控制流。

要抓它得上 SSA（`golang.org/x/tools`），而本项目**没有这个依赖**（只有 wazero），
且本机网络不稳。所以这一版**不做**它，把结论记在这里：

> **"算好了又丢掉"这一族，靠词法检查抓不到；它需要控制流。**
> 在没有 SSA 的前提下，**判据（v0.32 ~ v0.36 那五张网）才是这一族真正的防线。**

## 5. 过程洞察

### 5.1 扫描抓到的，正是我**没想起来要看**的那个

`engines validate` 在此之前从未进过我的任何一张表——它不是"待办"，是**盲区**。
而它一被扫到就是 **7 个失败项、exit 5、一行下一步都没有**。

挑选与扫描的差别不在严格程度，而在**谁来提候选**：
挑选时是我的记忆提候选，扫描时是**输出的形状**提候选。

这与 v0.33 那条经验（核对的对象应来自运行时/源码，而不是抄一份常数）是同一个方向的第三次：
**判据的输入应当来自被检查的对象本身。**

### 5.2 判据自己造了一处假缺陷

第一版扫描把 `tree` 的一条**用法错误**报成"有失败项却没有下一步"。真相是：

```
MARKERS:
  ✗  known vulnerabilities (only with --osv; without it nothing is claimed)
```

那句 `✗` 在**解释记号本身**，不是失败项。修法是在判前去掉用法文本（`USAGE:` / `MARKERS:` 之后不判）。

这是"红的不是产品，是我的判据"的**又一次**——而这次方向不同：
前几次是**漏报**（点分路径、行首匹配、共享正则），这次是**假阳性**。
两种都要防：**漏报让网看起来没用，假阳性让人开始不信网。**

### 5.3 先量再上重装备

死赋值那条，我没有直接去写 SSA 分析，而是先写了 40 行词法版本跑全仓库——
**量完才知道这条路走不通**。若直接上 SSA：要么卡在没有 `x/tools` 的依赖上，
要么为一条自己都没证明通用的判据引入一个大依赖。

**"先用最便宜的办法量一下"**这一条在本项目里已经兑现过多次（v0.20 的两个候选被证伪、
v0.31 的错误身份只有 2 种、这一版的 0 真命中）。它的价值不在于省钱，
而在于**让"值不值得做"变成一个读数，而不是一个感觉**。

### 5.4 广度与深度是两种不同的网

v0.32 的"行动行数 ≥ 失败项数"（深度）挡住了 v0.34 那个"算好了又被渲染门丢掉"；
v0.36 的"扫描全部非零用例"（广度）抓到了 `engines`。
两者都不能替代对方：**深度保证"有"不等于"够"，广度保证"我没想到的地方也算数"。**
