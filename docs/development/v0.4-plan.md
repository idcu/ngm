## 设计复核结论（2026-10-01，开工前）

### 复核项 1：可复现构建（[ADR-013](../adr/adr-013-remote-adapter.md) 的翻案条件）

ADR-013 决定不发布 `remote` adapter，并留下可证伪的翻案条件："产物可由用户本地复现"。
本轮把它拿去实测——因为"没法验证"是那条结论的支点，而支点不该建立在假设上。

| 条件 | 结果 |
|------|------|
| 同一源码 + 同一 esbuild 版本 + **不同目录**，`--minify` | 字节一致 ✓ |
| 同上，**三平台**（linux / macOS / Windows）× 两个路径 | **六次构建字节全同** ✓ |
| 不 minify，同一路径、跨平台 | 字节一致 ✓ |
| 不 minify，且传入**绝对路径** | 字节**不同** ✗ —— 产物注释里嵌的是传入的路径 |

最后一行是机制上的关键：**路径是否泄漏取决于调用方传的是绝对还是相对路径**。
ngm 传相对路径、且把 CWD 固定为项目根——它已经站在"路径无关"那一侧。

**结论：条件在收敛，但未成立**（ADR-013 已补录）。仍缺：其他引擎（tsc / postcss /
wasm 模块）是否同样确定、真实项目（多文件 / 插件 / sourcemap）、以及用户仍需**抽样
构建一次**才能验证——那正是远端想省下的东西。

仪器留在仓库：`.github/workflows/repro-probe.yml`，**手动触发**，结果发成 annotation
（Actions 日志匿名读不到）。

> 复核过程本身记一笔：探针迭代了三次才给出答案，前两次"什么都没测出来"——
> 一次死在报告之前，一次把输出塞满 annotation 条数上限、哈希行与错误一起被挤掉，
> 而我把那份"空"读成了结果。**一个不能报告自己失败的探针等于没跑**，
> 这条最终写进了那份工作流的头部。

### 复核项 2：把"声明了、没接线"做成机器检查

[v0.3 复盘 §7 建议 1](./v0.3-retrospective.md)。同类缺陷**连续三个版本**出现：
`verifyOnLock`（v0.2）→ `permissions`（v0.3 D）→ `SubPaths`（v0.3 E）——共同特征都是
"字段齐备、注释完整、没有任何地方读它"，而且全靠人工核对才发现。v0.2 复盘提过一次
机械化核对，没落地，于是又出现两次。

**落地**：`cmd/ngm/config_coverage_test.go`——每个**多段驼峰**的配置键必须在某个测试里
被碰过（接受三种形态：JSON 键、结构体字段选择器、结构体字面量键），豁免清单**只允许变短**
（键一旦被覆盖还留在豁免里，检查会失败）。

判据刻意定在"能做到"的地方，而不是"听起来严格"的地方。**它拦不住什么**写在测试里：
单段名（`permissions` 就是这么漏的）、"出现了但没断言行为"、以及非 JSON 的配置面。

首次运行报出 **6 个从未被任何测试碰过的键**，逐个定性：

| 键 | 定性 | 处理 |
|----|------|------|
| `git.tokenEnvVars` | **真缺陷（第 4 例）** ✗ | 已修（见下） |
| `engines.defaultTransform` / `defaultBundle` / `defaultTypeCheck` | 接了线、没测 | `TestGlobalDefaultEnginesAreUsed` |
| `supportedInput` | 接了线、没测（且只在 `engines info` 展示，`engines list` 没有该列） | `TestDeclaredSupportedInputIsListed` |
| `engines.typeDecl` | **能力在 adapter 层已实现并有单测，但没有任何命令驱动它** | 记明豁免 |

#### 第 4 例：`git.tokenEnvVars` 从未被读取（安全相关）

`newProjectEnv` 在**读配置之前**调用 `git.MergeTokenEnvVars(nil)`，而配置在第 68 行才加载
——用户写的 host → 环境变量名映射**一条都不生效**。而 `internal/git/auth.go` 的注释明文
承诺"与全局配置 `git.tokenEnvVars` 合并时**配置优先**"。

后果落在安全路径上：用户写了

```json
{"git": {"tokenEnvVars": {"corp.local": "CORP_TOKEN"}}}
```

会以为 `CORP_TOKEN` 的值已在输出里被脱敏，实际上它会**原样打进日志与报错**。

修法：把脱敏集合的构造移到配置读取**之后**，喂给它 `Git.TokenEnvVars`；读不出配置时
退化为"只有内置表"——不比原来差，也绝不静默放宽。

断言带**反例**（`TestGitTokenEnvVarsFromConfigReachTheRedactionSet`）：没有配置时该值
**不该**在集合里。少了这一步，断言可能只是因为"所有环境变量都被收进来了"而通过。

#### 关于 `engines.typeDecl`

它不是"漏接线"，而是**能力有了、入口没有**：`typeDecl` 在 adapter 层能跑（tsc
`--emitDeclarationOnly`，有单测），但没有命令驱动它，因此这个配置键对用户没有任何效果。
正确做法不是补一条断言，而是**先给它一个入口**——那是一件功能，不是一次修复。
豁免里写明了这一点，以及"有入口那天把豁免删掉"。

### 重复出现的错误形态：相对路径按错了基准

本轮又多了一例，值得单独记下来：**已经两次**（下面两条都能指到具体提交与症状），
而且每次的症状都不是报错：

| 时间 | 位置 | 症状 |
|------|------|------|
| v0.3 A | 清单校验按**进程 CWD** 找 wasm 模块 | 从项目的上一级检查时，明明存在的模块被报成"找不到" |
| v0.4 | `TypeDeclResult.Files` 按**进程 CWD** 列输出目录 | 引擎在项目目录里写了文件，ngm 说"没有产出" |

共同点：**配置或命令行给的相对路径，本该相对项目目录解析，却相对了进程的 CWD**。
它不会崩，只会给出一个"看起来合理但相反"的结论——比崩溃更难发现。

`ngm` 的 CWD 与项目目录**可以不同**（`--dir=` 就是为此存在的），因此这类地方必须显式
带基准。将来若再做一次机械化检查，这是一个明确的候选：凡是把配置/参数里的路径交给
文件系统 API 的地方，都要能回答"基准是哪个"。

### 复核项 3（未做）：沙箱自述文件签名检查

v0.3 唯一未结项（C 组）。它不只需要沙箱，还要**先定签名格式与密钥管理**——
一份独立设计的体量，属 ADR 级别。没有那两样就实现，只会做出一个"看起来验过了"的检查。

## 候选任务（按证据强度排序，非路线图承诺）

1. **可复现构建的第二批实测**（其他引擎 / 多文件 / sourcemap）——仪器已就位，
   而它同时是 ADR-013 翻案条件的唯一路径
2. ~~**`typeDecl` 的 CLI 入口**~~ → **已完成**（`ngm typedecl`，v0.4 首个交付项）：
   配置检查的豁免清单因此**清空**（从 1 项到 0 项）。过程中新测试抓到一个真缺陷：
   `TypeDeclResult.Files` 曾按**进程 CWD** 找输出目录——引擎在项目目录里写文件、
   ngm 却在别处找，症状不是报错而是"文件明明写了、却说没有产出"。
   与 wasm 清单校验曾按 CWD 找模块是同一类错（见下方"重复出现的错误形态"）
3. **沙箱自述文件签名检查**（需 ADR）
4. 从 v0.2 起挂账的两项：deno 真引擎覆盖（等其 `bundle` 脱离实验状态）、
   单个依赖内部并行哈希

> `remote` adapter **不是候选**：ADR-013 已决定不发布，翻案条件即第 1 项。
