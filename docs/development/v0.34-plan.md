# v0.34 计划 — 建议要**承认失败的形状**

> 范围来源：[v0.33 复盘](./v0.33-retrospective.md) §7 候选 1。
>
> 一句话目标：v0.33 的判据是"行动行必须点名一个**真能执行**的东西"——
> 但一行**与失败毫不相干**的 `ngm install` 也能过。这一版把**失败的性质**写进判据。

---

## 0. 判据

每一类失败登记它的**解法**，断言：**报告里的每一条行动行都必须命中该类的解法之一**。

| 失败形状 | 解法（至少命中一个） |
|---------|-------------------|
| 落地完整性失败（critical） | `ngm install` |
| 漂移（expected / unexpected） | `ngm update` |
| **检查未能完成**（mirror 不在 / 网络被拒） | `ngm install` · `ngm verify` |
| 漏洞（有修复版本） | `Fixed in:` |
| 漏洞（无修复版本） | `supplyChain.osvIgnoreSeverities` |
| `tree --osv` 看到漏洞 | `ngm audit` |

依据不是我的口味：`driftKind: expected` ⇒ `run ngm update` 是
`observability.md` 的输出示例里**产品自己写下的**对应关系。

## 1. 已知要修的一处（立这一版时实测到的）

`verify` 的 **"检查未能完成"** 那一支（`res.Err != ""`）：

- `remediationFor` 为它**算好了**建议（`internal/verify/verify.go` 里的一支）；
- 但渲染门是 `if d.DriftKind != DriftNone && d.Remediation != ""`，
  而这一支的 `DriftKind` 是 `None` ⇒ **建议被算出来又丢掉**；
- 用户看到 `✗ … — check incomplete`（exit 4），看不到任何下一步。

**这与 v0.28 修的缺陷是同一形状**——只是丢的地方从"包错的链"换成了"渲染的门"。
另外那句话本身也没点名命令（v0.33 的判据本该抓它，但它从没出现在用户眼前）。

## 2. 判据的边界

仍然**判不出"建议对不对"**：它只能判"这一类的建议**是不是这一类该给的方向**"。
一行 `→ run \`ngm install\`` 出现在**完整性失败**上是对的，出现在**漂移**上就会被这张网抓住——
这比 v0.33 强一格，但离"读得懂人话"还很远。
