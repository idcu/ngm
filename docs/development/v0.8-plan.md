# v0.8 实施计划 — 层 2 换布局（ADR-019 分阶段落地）

> **状态：已交付**（A / B / C 三阶段全部完成）。实测：同一场景的放大比 **20.0× → 0.6×**
> （12 个 commit 的占用 1.88 MiB → **59.9 KiB**）。实现时发现三处 ADR 没写到的点，
> 见文末与 [ADR-019 §修订](../adr/adr-019-content-addressed-blobs.md#修订v08-实现时发现并改掉的五处)。
>
> 范围以 [internals/roadmap.md](../internals/roadmap.md) 为唯一事实源。
> 本计划实现 [ADR-019](../adr/adr-019-content-addressed-blobs.md)（blob 池 + 树清单）。
> 前置：[ADR-018](./adr-018-store-reclaim.md)（为什么不做 GC）、
> [v0.7 计划](./v0.7-plan.md)（`store usage` / `store prune` 已交付）。
>
> **为什么分阶段**：换布局这件事本身不难，难的是**消费方**（`verify` 层 2 检查与 `LinkTree`）
> 目前都假定"store 里有一棵已物化的树"。直接换布局会让两边同时改动，
> 而 `verify` 是**安全关键路径**——它的任何偏差都是"看起来通过"。
> 所以顺序是：**先让消费方与布局解耦（等价重构），再换布局。**

---

## 一个先决发现（读码时确认的）

`internal/vendor/integrity.go` 的 `verifyTrees` **只比对四要素**：路径集合、
大小（`--deep` 时用 sha256）、symlink 目标、目录结构（由路径集合隐含）。
**它不做 mode 比对**——而 ADR-008 说明过为什么不能靠文件系统推断 mode
（Windows 上 100755 不可表示）。

这决定了抽象的形状：消费方需要的"内容树"可以表示成一组条目
`{path, size, sha256, symlink 目标}`，**mode 不必参与**。因此：

- v1（旧布局）：条目可以靠**扫描树目录**得到（与今天的行为完全等价）；
- v2（新布局）：条目直接来自 `manifest.json`（而且它**带着** Git 给的 mode，
  比 v1 更完整——只是消费方暂不需要）。

## 阶段

```
A 消费方与布局解耦（等价重构：数据仍是 v1，行为不变）   ← 本版先做
B Put 改为写 v2（blobs + manifest），读路径 v2 优先、回落 v1
C 收敛与观测：v1 在被重写时回收；usage 分别报告两种布局
```

### A — 消费方与布局解耦（**行为等价**）

- [x] A1 `ContentStore.Entries(digest)`：返回该 digest 的条目集合
      （v1 阶段 = 扫描树目录）。字段：`path / size / symlink 目标 / 字节在哪`。
      另有 `EntriesUnder(entries, subPath)` 在**条目层**收窄 monorepo 子路径。
- [x] A2 `verify` 的层 2 检查改用 `Entries`：
      原 `contentTreeFor()`（返回目录）已删除、原 `replayDigestFromStore()`（读目录里的文件）
      改为 `replayDigestFromEntries()`；子路径在条目层收窄（与原来等价）。
- [x] A3 `integrity.go` 抽出 `compareTrees(left, right, deep)`，浅/深与"目录/条目"两个维度
      **共用同一段判定逻辑**；新增 `VerifyVendorAgainstEntries`。
- [x] A4 新增验收测试 `TestVerifyVendorAgainstEntriesAgreesWithVerifyVendorTree`：
      同一对树，两种入口必须给出**完全相同**的结论（含等长篡改、缺文件、symlink）。

**验收**：✅ **既有测试一字不改全部通过**（14 个包全绿；`verify` 的浅/深、symlink、
monorepo 子路径、hardlink/copy 降级都在其中）。本阶段**没有产生任何行为变化**——
它的价值是让 B 变成纯布局改动。

### B — 写 v2（含双布局读取）

- [x] B1 `Put` 改为：逐文件写 `blobs/<aa>/<sha>`（临时文件 + chmod + 原子 rename），
      再写 `manifest.json`（条目按 path 升序）+ `meta.json`。
      **实现时比计划更进一步**：直接从 Git 的条目（`ListTree` + `CatFileBatch`）构建，
      **不再解包一棵中间树**——mode 以 Git 为准（否则 Windows 上会算出不同的清单），
      且 store 不再需要创建 symlink。见 [ADR-019 §修订](../adr/adr-019-content-addressed-blobs.md#3-不再解包一棵中间树直接从-git-的条目构建)。
- [x] B2 `Entries` 与 `Has`：先按 v2 找清单，没有再回落 v1。
      判据是**清单存在性**而不是"读清单是否成功"——否则损坏的清单会被静默当成 v1，
      从而回落到一棵可能已被收敛删除的树。`ReadMeta` 同样双布局（`verify` 正靠它一字未改）。
- [x] B3 `LinkTree.Materialize` 按条目落地（v2 链接 blob；v1 链接树内文件）——
      A 阶段完成后这一步确实没动 `verify`。
      **一处行为变化**：`symlink` 模式在 v2 下退化为逐条目 hardlink（ADR-019 §修订 2）。
- [x] B4 部分失败的清理：**清单最后就位**（`trees/.unpack-*` → rename），
      于是"清单不存在 = 这份 digest 不存在"，不会留下半个可被引用的内容树；
      发布失败时同一 digest 的 v1 目录**不删**。

**验收**：✅ 双布局都能读（`TestContentStore_V1LegacyStoreStaysReadable`、
`TestContentStore_V1KeepsWholeDirSymlinkMode`）；✅ 同一 digest 在两种布局下 `Entries` 一致
（`TestContentStore_EntriesAgreeAcrossLayouts`）；✅ 既有 `verify` 用例除"断言写死了 v1 路径"
的部分外一字未改（那些改的是断言，不是判定逻辑）；✅ 探针不受影响（产物与 store 布局无关）。

### C — 收敛与观测

- [x] C1 某个 digest 以 v2 写成功后，删除同 digest 的 v1 目录（内容等价）。
      **实施时发现这条路径基本不可达**：`install` 在 `Has` 为真时短路（那是"无网络也能安装"
      的承诺），而健康的 v1 条目 `Has` 正是真——**所以旧条目不会被自动迁移**。
      不改这条短路，而是把出路交给用户：`usage` 在 v1 遗留非零时打印
      `rm -rf <root>/sha256 && ngm install`（层 2 是派生物）。见
      [ADR-019 §修订 5](../adr/adr-019-content-addressed-blobs.md#修订v08-实现时发现并改掉的五处)，
      断言见 `TestV08StoreUsagePointsAtV1Legacy`。
- [x] C2 `ngm store usage` 分别报告：blob 数与体积、树清单数与体积、v1 遗留的数量与体积。
- [x] C3 文档：层模型 / 命令参考 / 配置 / metrics / 能力矩阵 / ADR-019 修订同步。

**验收**：✅ `usage` 能说出两种布局各占多少；✅ 重跑 `TestV06StoreGrowthInventory`——
**12 个 commit 的占用从 1.88 MiB 降到 59.9 KiB（20.0× → 0.6×）**，
比 ADR-019 写死的"百 KiB 量级"尺子更具体。那把尺子的断言已**翻转**为
"不得接近 N 棵树"，于是它同时成了去重的回归门禁。

## 实施时的三处发现（都不是照做能得到的）

1. **可执行位无法只靠"内容寻址"承载**：落地层用 hardlink，而 hardlink 共享 inode。
   于是 blob 的身份改为 `H(mode, 内容)`——代价是"同内容、两种 mode"存两份（可忽略）。
   少了这一步，`scripts/*.sh` 落地后会**丢可执行位**（静默错）。
2. **`symlink` 模式在 v2 下没有整棵树可链**：退化为逐条目 hardlink，如实报告实际 mode。
   本版**唯一一处用户可见的行为变化**。
3. **收敛不是自动的**：`install` 在 `Has` 为真时短路（那是"无网络也能安装"的承诺），
   而健康的 v1 条目 `Has` 正是真——于是旧条目**不会被重写**。处置是把出路交给用户
   （`usage` 打印 `rm -rf <root>/sha256 && ngm install`），而不是为了迁移去动那条短路。

三条都记在 [ADR-019 §修订](../adr/adr-019-content-addressed-blobs.md#修订v08-实现时发现并改掉的五处)。

## 本版不做

- blob 的回收（ADR-018 的那两个条件未成立；**去重改的是斜率，不是终点**）
- digest 定义、层 1、lock 的任何改动
