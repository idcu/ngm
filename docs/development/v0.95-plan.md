# v0.95 计划 — **把"fetch 那一半"也搬到本地来（https + `git http-backend`）**

> 来源：[v0.94 复盘](./v0.94-retrospective.md) §5 候选 2。
>
> 一句话目标：v0.94 证明了 `subPath` 的契约不需要远端；这一版证明
> **抓取那一半也不需要真人推送**——本机 https + 真正的 `git http-backend`。

---

## 1. 为什么还能本地做

v0.94 查到：抓取协议只有 ssh / https（`git.defaultProtocol`），所以"本机 `git daemon`"
是死路。但 https 这一侧没被排除过——它只缺三样东西，先探：

| 前提 | 实测 |
|------|------|
| 443 端口空闲 | ✅ 空闲（ngm 不接受显式端口，只能用默认端口） |
| `git http-backend` 在 | ✅ `…/libexec/git-core/git-http-backend.exe` |
| git 能走 TLS | ✅ git 2.56 + curl(Schannel) |

⇒ 方案：本机 443 上起一个 https 服务，把请求交给**真正的 `git http-backend`**（smart HTTP），
证书用现场生成的自签证书。

## 2. 计划

| # | 项 | 验收 |
|---|----|------|
| 1 | CGI 桥：Go handler ⇒ `git http-backend`（`GIT_PROJECT_ROOT` / `PATH_INFO` / `GIT_HTTP_EXPORT_ALL`） | `info/refs?service=git-upload-pack` 回 200 |
| 2 | 自签证书（SAN 含 `127.0.0.1`）+ https 443 | 就绪探测通过 |
| 3 | `init → add https://127.0.0.1/acme/lib.git@v1.0.0 → update --all → verify` | 全绿，且 `ngm.lock` 钉的 commit = 上游 HEAD |
| 4 | **服务端请求计数 > 0** | 排除"从热镜像读出来"的假端到端 |

## 3. 一条边界（要写进注释，不要留给猜）

Git for Windows 默认走 **schannel**（Windows 证书库），而 `GIT_SSL_CAINFO` 是 **OpenSSL
构建**的开关 ⇒ **被忽略**（现象：`schannel: SEC_E_UNTRUSTED_ROOT`）。
于是自签证书的本地端到端只剩"关校验"这一条路——因为另外两条都不该走：
**测试不能往系统证书库装东西**，也不能为了测试切 TLS 后端。

因此这条判据验的是"ngm 构造 https URL + smart HTTP 能谈 + ref 能解析 + 内容能落盘"，
**不是**"TLS 链校验"（那归 git 与操作系统）。

## 4. 不做

- 不推 tag / jsonkit（仓库所有者的动作）；
- 不把这类端到端接进 CI 的"必须"一档前先看它在 ubuntu 上的表现（443 在 CI 上可能被占）——
  若那天真的撞上，判据会**明确失败并说清原因**，那是设计，不是缺陷。
