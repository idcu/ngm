# v0.15 复盘 — 把两条对外契约钉成网

> 体例与各版一致：逐组验收 → 未达成项 → 设计偏离登记 → 缺陷清单 → 过程洞察 →
> 指标 → 下一版候选。
>
> 范围来源：[v0.14 复盘](./v0.14-retrospective.md) §7 候选 #2 与 §5.2；
> 实施计划：[v0.15 计划](./v0.15-plan.md)。
>
> 一句话结论：**两条"用户照着做就会撞上"的契约此前没有任何网看着**——文档示例是否成形、
> 用法错误的退出码与流向。钉住它们的过程中，探针**当场暴露了一个产品缺陷**
> （21 个命令的解析错误绕过调用方注入的 writer，直接写进程 stderr）。

### 1.2 B 组 — 用法错误的退出码与流向（**计划外追加**）

| 契约 | 结果 |
|------|------|
| ① 错的 flag ⇒ `exit 3`（`CodeConfigInvalid`） | ✅ 21/21 命令 |
| ② 该命令**自己的用法**出现在 **stderr**（不是根帮助、不是 stdout） | ✅ 21/21 |
| ③ 用法错误时 **stdout 为空** | ✅ 21/21 |
| ④ **没有任何字节绕过注入的 writer**（把进程 `os.Stderr` 收进管道，跑完断言为空） | ✅ 修复后 21/21；**修复前实测泄漏 800 字节** |
| 对照：同一命令 `--help` ⇒ exit 0、用法在 stdout、stderr 空 | ✅ 21/21 |

**顺带的修复**（本版唯一的产品代码改动）：

```
newFlagSet(name string)                    →  newFlagSet(name string, stderr io.Writer)
   未调用过 fs.SetOutput                        fs.SetOutput(stderr)
```

22 个调用点（`store.go` 两处的名字带空格，正则第一次没覆盖到，是"补扫残留"抓到的）。
另外删掉 `errSilent`——**它从未被引用过**，而注释写着"让 `flag.ContinueOnError` 静默"。

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么不是照做 |
|---|---------|---------|---------------|
| 1 | A 组："扫文档里的 `ngm` 示例，比对命令表与 flag" | 第一版跑出来 **6 处命中，全是误报**，于是**连收三次判据** | 误报来源：把 `#` 当提示符（其实是注释）、把 `ngm --version` 的**输出**（`ngm 0.0.0-dev (git:dev, …)`）当命令、把整行里与 ngm 无关的 flag（`node --test`、`--alias`、`--kind`）算进来。**误报是设计缺陷，不是可以容忍的噪音**——放宽容忍度等于训练人忽略这张网 |
| 2 | 计划里没有 B 组 | 追加 B 组（用法错误的退出码与流向） | 写 A 组时顺手跑了一个探针，**探针自己把 21 行泄漏打到了终端上**。这条不写进计划就是"看见了但没记"，那正是本项目最反对的事 |
| 3 | B 组原设想只断言"用法在 stderr" | 增加到四条契约，其中第④条（进程 stderr 不泄漏）是**实现过程中**才成形的 | 只断言"用法在 stderr"会漏掉真正的缺陷：用法确实进了注入的 stderr，而**错误行从旁边溜走了**。"流是接口的一部分"要用流来证明 |
| 4 | 计划说"8 个命令补 EXIT CODES 段：不做" | 保留决定，并把理由写进计划 | 那是**新增约定**（要求 21 个用法文本格式统一），不是修缺陷。区分"修错误的文档"与"发明新的规矩"，是这一版最该守住的边界 |

| # | 缺陷 | 性质 | 状态 |
|---|------|------|------|
| D1 | `flag provided but not defined: …` 绕过调用方注入的 writer，直接写**进程的 `os.Stderr`**（21 个命令全部如此；`fs.SetOutput` 从未被调用） | **产品缺陷**（与 v0.12 D2"hook 输出混进 stdout"同族：流是接口的一部分） | ✅ 已修 + 被契约④钉住（牙齿实测：摘掉 `SetOutput` ⇒ 报 800 字节泄漏） |
| D2 | `errSilent` 哨兵**从未被引用**，注释却描述了一个"已让 flag 包静默"的机制 | 注释撒谎（比没有注释更糟） | ✅ 已删，理由写在 `newFlagSet` 的注释里 |
| — | 文档侧：306 条示例**没有一条**是坏的 | **这是本版的"绿"**：v0.14 修掉的四处文档缺陷之后，这条线当前是干净的 | — |

**自己制造、当场处置的**：

| # | 现象 | 处置 |
|---|------|------|
| P1 | 探针文档一度进入扫描范围（我预期它会红——它确实红了） | 这是**故意的**：牙齿验证要求"把违规放回去看它是否变红"；证明完即删 |
| P2 | 例外名单是"第二份事实源"，有腐烂风险 | 加**过期绊线**：任何条目在当前文档里匹配不到就红，并要求一并删掉。名单因此不能悄悄留下空洞 |

## 5. 过程洞察

### 5.1 探针的价值不只是"证明网会红"，还是"暴露网看不见的东西"

B 组那个缺陷**不是在读代码时发现**的，也不是由任何既有检查发现的——
它是"往命令表里塞一个故意违规的命令"这个动作**顺手**打出来的 21 行终端输出。
这与 v0.12 的教训同源（五处静默失效是专项审计找到的）：**主动制造违规，是唯一能让
"安静的错误路径"出声的办法。**

### 5.2 注释会撒谎，要证明静默得看流

`errSilent` 的注释写得有条有理（"让 ContinueOnError 静默，我们用自定义 Usage 打印，
避免双重输出"），而它**从未被引用**；真正决定输出的 `fs.SetOutput` 也从未被调用。
一条**看着合理**的注释，可以让一个缺失的机制潜伏很久——本项目的处置不是"下次注意"，
而是**让流自己说话**（契约④把进程 stderr 收进管道）。

### 5.3 误报四次收紧，一次都不让

第一版 A 组的 6 处命中全是误报。它们的共同形状是：**判据比事实宽**。
处置依次是：`#` 不当提示符 → 版本输出不算调用 → 只扫代码不扫整行 → 负例用会过期的名单。
每一次都让网变窄，而**窄是对的**：一张会误报的网会训练人忽略它，
一张会漏报的网则等于没有（v0.13 已为此拒绝过一张网）。

### 5.4 顺序也是契约：先打 tag，再推分支

P4 的后半段值得单独记：`release status` 门禁的判据是"**有复盘 ⇔ 有 tag**"，
而我在 tag 建成之前就把复盘推了上去——门禁于是（正确地）红了。
这条纪律在[发布清单](./README.md#发布清单每个版本)第 0 步里写着（"交付该版本时**立刻**打 tag"），
我把它读成了"别拖到下次"，而它真正的含义是"**别让中间状态离开本机**"。
判据对一个"半成品状态"报错时，**先怀疑顺序，再怀疑判据**。

### 5.5 "绿着通过"也可以是结论

A 组 306 条示例一条不坏。这与 v0.13「一轮扫描没找到新缺陷」是同一类信号：
**上一版的修正生效了**，本版的价值从"发现"转成"不再退化"。
写复盘时不把它说成"发现有价值的问题"——**没有发现问题就是没有发现问题**。
