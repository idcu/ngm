## 1. 逐组验收

### 1.1 `COMPETITIVE-ANALYSIS.md` 新增 PackageGate 一节

补写"对手官方背书的最强验证"：事故本身（2026-01-26，npm / pnpm / vlt / Bun 共 6 个零日；
npm 那一条是 Git 依赖里的恶意 `.npmrc` 覆盖 git 二进制路径、绕过 `--ignore-scripts`；
pnpm 2 周 / vlt 8 天 / Bun 3 周修复；**npm 以 "works as expected" 关闭**），
以及"为什么这条路径在 ngm 上由构造不可能"的**三点逐条可核对**：

| 攻击需要什么 | ngm 的对应事实（可核对） |
|-------------|------------------------|
| `.npmrc` 被解释为配置 | 全仓库**零处**提到 `.npmrc`（`Select-String` 可复读）；它只是清单里的一个普通文件 |
| 安装时执行依赖脚本 | `postInstallPolicy` 默认 deny；开启后只在 Deno 沙箱（ADR-012） |
| 改写"用哪个 git" | `git` 只有一个构造点（`git/spawn.go`）+ `run:git` 门禁 |

### 1.2 README：补上"为什么你**该**用"

评估指出：README 有"为什么你可能不应该用"，没有"为什么你应该用"。
- **根 `README.md`（英文）**：新增 `## Why ngm — and when you should not use it`——
  PackageGate 开头，两个方向的答案都在（该用 / 不该用），并指向 `docs/README.md` 的诚实版；
- **`docs/README.md`（中文）**：在"你可能想用 ngm 的理由"里把 PackageGate 放在**第一条**。

### 1.3 可执行的对照 demo（`scripts/packagegate-demo.sh` + `.ps1` 入口）

设计（与评估的建议对应，但有两处刻意的取舍，见 §3）：

- **fixture**：一份"恶意 Git 依赖"——`package.json` 带 `postinstall`、`.npmrc` 指向一个
  会留标记的"假 git"、`postinstall.js` 只写一个标记文件（**不实现真攻击**：不联网、不改系统状态）；
- **ngm 侧（默认，5 条断言）**：postinstall 从未执行 · 假 git 从未被调用 ·
  `.npmrc` 被原样 vendor · `ngm verify` 通过 · lock 钉着具体 commit；
- **npm 侧（`--with-npm`，只观察不断言）**：同一份 fixture 交给 npm，打印它的行为；
- **隔离**：`NGM_HOME` 指向临时目录（不碰用户的 `~/.ngm`）、`mktemp -d` + `trap` 清理。

**实跑记录**（本机 Windows + git bash，v0.67 交付时）：

```
-- ngm side (asserted) --
  PASS  the dependency's postinstall hook never ran (no marker file)
  PASS  nothing followed .npmrc: the 'git' it points at was never called
  PASS  .npmrc was vendored as an ordinary file (present, byte-for-byte)
  PASS  ngm verify: the vendored content matches the digest replayed from the mirror
  PASS  ngm.lock pins a specific commit (the fixture's content is provable)
== result: 5 passed, 0 failed ==
```

`--with-npm` 的观察（同一台机器）也如实记下来——它顺带量到一个新事实：

```
npm error code EALLOWGIT
npm error Fetching packages of type "git" have been disabled
  note: this npm build disables git-typed dependencies by default (EALLOWGIT);
        on it the attack surface is closed by refusing the fetch itself.
```

**本机的 npm 已经默认拒绝 git 类型的依赖**（`EALLOWGIT`）。这不是"PackageGate 不存在"，
而是"新版本把这条路整个关掉了、受影响版本上没有"——demo 因此**不假装复现 CVE**，
它展示的是**结构差异**：即便把同一份依赖交给 npm，ngm 那一侧的五个断言也独立成立。

**牙齿**（项目纪律：每条判据都要验证它能红）：
把 fixture 里的 `.npmrc` 改名为 `.npmrc-disabled`（即"这个文件不在依赖里"）⇒
第 3 条断言 FAIL（`.npmrc is missing from the vendor tree`）、汇总 `4 passed, 1 failed`、
**exit 1** ✓——断言机制不是恒绿。

## 3. 设计偏离登记

| # | 计划写的 | 实际做的 | 为什么 |
|---|---------|---------|-------|
| 1 | npm 侧也"跑一遍给你看"（评估原文） | 降级为**观察模式**（`--with-npm`，不断言） | 不同 npm 版本在这条路径上的行为不同（本机直接 `EALLOWGIT` 拒装）——**硬断言会产生假证据**，而假证据比没有证据更糟。demo 的断言全部落在 ngm 一侧，那是唯一跨版本稳定、且属于本项目的可证事实 |
| 2 | fixture 里的"payload" | 只写标记文件 | 安全：这是**对照 demo**，不是攻击工具。断言检查"标记文件有没有出现"，与 payload 是否"成功"无关 |
| 3 | `.ps1` 自带实现 | 转调 `.sh`（`.sh` 是唯一实现） | 与 `check-docs-links` / `check-gitee-release-status` 同一纪律：**要检查的规则只允许有一种写法**（两份实现漂移过一次，那个事故写在 `check-gitee-release-status.ps1` 的注释里） |

## 5. 过程洞察

### 5.1 "我有这个证据，但没有把它变成别人的证据"

评估那句话值得原样抄在这里：**"一个把全部赌注押在'Git 依赖安全'上的项目，
错过了 9 个月前发生的、由对手官方背书的最强验证。"**

这不是文档没写全——是**判断一直在、事实一直在、而联系没有建立**。
本版的全部工作就是把那条联系写下来、跑一遍、指到代码。
**产品代码 0 行，但它可能是采用价值最高的一版之一**——这与 v0.13~v0.65 那 29 版
"产品代码 0 行"的性质完全不同：那些是**给自己做的**（契约网），这一版是**给用户做的**。

### 5.2 "跑一遍"暴露了"表"暴露不了的东西

demo 第一次实跑就量到本机 npm 的 `EALLOWGIT`：**一条静态表永远不会告诉你这个**。
它与 v0.18 的联网复核、v0.11 的端到端是同一族：**能跑的东西要跑**，
因为"我以为"与"这台机器上"之间隔着一整层现实。

### 5.3 demo 的牙齿要在 **fixture** 上做，不在断言上做

把断言改松/改紧都能让它"红一次"，但那证明不了什么。有效的牙齿是
**破坏 fixture**（`.npmrc` 不在依赖里）⇒ 断言 3 红、exit 1 ✓——
它证明的是"这条断言真的在看依赖的内容"，而不是"它会不会红"。
