# v0.79 复盘 — **把"扫 vendored 产物"固化成一条命令 + 第二个库（monorepo 形态）**

> 一句话结论：标准的前一半（库该长什么样）已经在跑，这一版把**后一半**也变成命令
> ——"我拿到的依赖长什么样"；造第二个库时**又抓到一处必然误伤**：
> vendored 的**子路径**看不见仓库根的 `.gitattributes`，于是 `gitattributes-lf`
> 对**每一个 `subPath` 依赖**都会红一次。

---

## 1. 逐组验收

### 1.1 `scripts/check-vendored-standard.sh`（新）

| 场景 | 结果 |
|------|------|
| 真实项目 `dogfood-app`（有 `ngm.vendor/` + mappings），`--strict` | 全部合格 · exit 0 |
| 真实项目 `dogfood-add`（1 个依赖） | 全部合格 · exit 0 |
| `--json` | `ok=true dependencies=1 checks=22`，id 前缀 = 依赖名（`gitee:idcu/canonical-json/pkg-json-exists` …） |
| 牙齿：给 vendored 副本塞一个 `postinstall` | `✖ no-install-hooks 声明了安装期钩子：postinstall …` + `不合格的依赖： gitee:idcu/canonical-json` + exit 1；恢复后 exit 0 |
| 牙齿：映射指向不存在的目录 | `✖ vendored-dir-missing` 必做失败 + exit 1 |
| 牙齿：项目里没有 `ngm.mappings.json` | 明确报缺哪份事实源 + **exit 2**（没有查过 ≠ 查过且合格） |

判据里另有一条**对账**：某个依赖在 vendored 报告里的判据条数，
必须等于直接对它跑 `check-library-standard.sh` 的条数（防止包装器少跑规则）。

### 1.2 第二个库 `jsonkit`（monorepo 形态）

```text
jsonkit/
  package.json            private + workspaces: ["packages/*"] + engines
  LICENSE  README.md  .gitattributes  .gitignore
  packages/stable-stringify/{package.json, ngm.json, README.md, src/index.js, src/index.d.ts}
  packages/deep-equal/{package.json, ngm.json, README.md, src/index.js, src/index.d.ts}
```

| 验收 | 结果 |
|------|------|
| 标准自检（monorepo 模式：根 + 两个子包）`--strict` | exit 0（根 9 条不适用：7 条包专属 + tag + LF 声明） |
| 每个子包**单独**自检 `--strict` | exit 0（两个都过） |
| 两个实现真的能跑 | `stableStringify` 键序无关且数组顺序保留 ✓ · `deepEqual` 键序无关且区分数组顺序 ✓ |

**为什么这么切**：两个包是"什么算同一份 JSON"的两面（字节稳定 vs 结构相等），
共用一份测试语料；而它们**互相不依赖**，所以各自能单独被消费——
这正是 `subPath` 要消费的形态。

## 3. 缺陷清单

| # | 缺陷 | 谁发现 | 处置 |
|---|------|-------|------|
| 1 | **vendored 子路径必然红**：`gitattributes-lf` 要求"仓库里有 LF 声明"，而 `subPath` 消费只复制子目录——声明在仓库根，消费者看不到 | 造 `jsonkit` 后**单独**体检两个子包（`--strict` exit 1，只红这一条） | 与 `semver-tag` 同一条先例：**看不到的事实明说"不适用"**。没有 `.git` 且没有仓库根信号 ⇒ `gitattributes-lf` 记 `—`，并写明"内容侧的 LF 由 `lf-only` 守" |
| 2 | v0.76 的判据断言"不是 git 仓库时**恰好一条**不适用" | 修完缺陷 1 后它立刻红（变成两条） | **这条红是对的行为**：它守的就是"不适用不许悄悄变多"。断言改成"恰好两条"，并加一条"这两条 id 都必须存在"——多一条要有人在这里写一个字 |

## 4. 过程洞察

### 4.1 "拿一个真实的东西去跑"比"再写一条断言"更能找出缺陷

`gitattributes-lf` 那处是**造第二个库**时掉出来的：不是新写的代码，
而是旧判据在**另一个形态**（子路径消费）下的必然失败。
这与 v0.77/v0.78 的形态覆盖是同一条规律，而这一次的形态不是"另一种打包方式"，
而是**标准自己在消费侧的形态**——所以 §5.1 那张表里又加了一行。

判据的适用边界必须跟着**用法**走：库的作者与库的消费者看到的目录**不一样**
（一个看仓库，一个看子目录），而判据此前默认自己看到的是前者。

### 4.2 被推迟三次的候选，值得问一次"它到底属于谁"

候选 4 连着两版没做，理由每次都很像："它不属于产品代码"。
第三次问的是**归属**而不是**优先级**：它属于**标准**（产物侧的那一半）。
把它放到标准那一侧，代价立刻从"要付四张契约网的账"降到"一支脚本 + 一组判据"。
**"不该做"常常是"放错了地方"的另一种说法。**

## 7. 需要仓库所有者做的三件事（都不是代码）

1. **推 tag**（v0.78 起就欠着，14 个）：

   ```bash
   git push origin main --tags     # GitHub 镜像（会触发 release.yml，补 v0.65.0 与之后的 release）
   git push gitee  main --tags     # Gitee
   ```

2. **推 `jsonkit`**（我已在 `d:/repos/mine/jsonkit` 备好，还没 `git init`）：

   ```bash
   cd d:/repos/mine/jsonkit
   git init -b main && git add -A && git commit -m "v0.1.0 — jsonkit：stable-stringify + deep-equal"
   git tag -a v0.1.0 -m "v0.1.0 — 初始版本"
   # 在 Gitee（或 GitHub）建空仓库 idcu/jsonkit，然后：
   git remote add origin <你的远端 URL>
   git push -u origin main --tags
   ```

   推完告诉我一声，我立刻跑 `subPath` 的端到端
   （`ngm add <slug>#packages/stable-stringify@v0.1.0` → install → verify → mappings 入口）。

3. （可选）`GITEE_TOKEN`：回填 Gitee 侧 76 个 release；没有它这条一直暂缓。
