# v0.94 复盘 — **`subPath` 端到端做成了（前提被纠正了两处）**

> 计划：[v0.94 计划](./v0.94-plan.md)
>
> 一句话结论：从 v0.79 起挂在"需要推一个 monorepo 远端库"上的那件事，这一版做成了常驻判据——
> 而真正花时间的不是实现，是**把那条前提拆开验证**：其中一半不成立，另一半不必要。

---

## 1. 前提被拆成两半，两半都不是原来想的样子

| 原本以为 | 实测 |
|---------|------|
| "起个本机 `git daemon` 就有远端了，只差没人推" | **半条腿**：`git daemon` 确实能用（真起了、真克隆成功了，tag 与子目录都在），回环主机也确实已放开（v0.83 ADR-029 就是为它开的）——但 `git://` 只是**地址写法**，**抓取协议只有 ssh / https**（`~/.ngm/config.json` 的 `git.defaultProtocol`，`internal/resolve/protocol.go` 只认 `ProtocolSSH` / `ProtocolHTTPS`）。实测：`install` 把 canonical 重建成 `https://127.0.0.1/acme/lib.git` 去连 **443** ✗ |
| "端到端必须过抓取那一关" | **不必**：`subPath` 的契约（过滤子目录、写 `path`、按子包自己的 `exports` 推入口）全在 vendor / mappings 层 |

⇒ 用仓库**既有**的本地镜像设施（`seedMirror`，镜像里是**整仓**——正是 monorepo 的真实形状）
+ `--offline`，把契约完整走了一遍。

## 2. 判据本体

`TestV94SubPathEndToEnd`（六步真实 CLI，全绿）：

```
init → add git://127.0.0.1/acme/lib.git#path=packages/a@v1.0.0
     → update --all --offline → install --offline → verify → mappings validate
```

四条断言（前两条是 `subPath` 契约的本体）：

| # | 断言 | 结果 |
|---|------|------|
| 1 | **只有子包被 vendor**（`packages/b` 一个文件都不许进来） | ✓ |
| 2 | mappings 指向**子包自己的 `exports`**（`src/index.js` + `src/index.d.ts`，且不含 `packages/b`） | ✓ |
| 3 | 声明里 `path: packages/a`（对用户可见的字段名是 `path`；`subPath` 是 lock/内部的名字） | ✓ |
| 4 | 反面：不存在的子路径 ⇒ `add` 只写声明（发现不了，**合理**：能不能写声明与远端里有没有那个目录是两件事）· `update` 明确失败且**不留半个 vendor** | ✓ |

## 3. 探路时踩到的三件事（写进注释，免得下一个人重走）

1. **显式端口被设计拒绝**：`git://127.0.0.1:54147/…` ⇒ `invalid git address`，hint 写着
   "ngm identifies a repository by host and path only, so it cannot carry a non-default port
   into the lock file, the mirror layout or the slug"——这条判断是对的（端口进不了 lock/mirror/slug）；
2. **路径至少两段**（`org/repo`）：`git://127.0.0.1/lib.git` 会被拒；
3. **Windows 上 `git daemon` 会 exec 出 `git-daemon.exe`**：只杀父进程会留下占着 9418 的残骸
   ——第一次跑测试时正是它把自己下一次运行搞坏（现象是"莫名其妙的 read error"）。
   修法是两侧都堵：起前查端口 + 收尾 `taskkill /F /T`。

> 这条也解释了 v0.80 的观察：当年"unknown host localhost"是**第一道**门，
> ADR-029 把它打开了；**第二道门**（传输层没有 `git://`）一直没人走到，
> 因为打开第一道门之后没人真的去跑一遍。
