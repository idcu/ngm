# v0.85 复盘 — **同一处读数，两种用法：CI 里它是门禁**

> 计划：[v0.85 计划](./v0.85-plan.md)
>
> 一句话结论：v0.84 做的那处"工作树状态"读数，在**本地**故意只打印、在 **CI** 里变成硬门禁——
> 判据的软硬不是它的属性，是**语境的属性**。顺带给 v0.84 新加的"未推送数"断言做了牙齿。

---

## 1. 交付

### 1.1 主测试 job：测试跑完，仓库必须还是干净的

```yaml
# build/vet/test（三平台）里，紧跟 go test 之后
- name: worktree must stay clean (a clean checkout means something wrote files)
  shell: bash
  run: |
    dirty="$(git status --porcelain)"
    if [ -n "$dirty" ]; then
      echo "::error::the checkout is no longer clean — something wrote files into the repo"
      echo "$dirty"
      exit 1
    fi
```

**为什么同一处读数在这里是硬的**：CI 的 checkout 是干净的 ⇒ "出现未跟踪/被修改的文件"
只可能来自一个原因——**有个步骤往仓库里写了东西**（测试把 fixture 落进仓库、
脚本生成产物忘了删…）。本地恰好相反：开发中途工作树**本来就该是脏的**，
那里恒红的门禁等于没有门禁（v0.84 复盘已论证）。

> 一般的话：**判据的软硬是语境的属性，不是判据的属性。**
> 同一句"工作树干净吗"，在 CI 是门禁，在开发机上只是读数——
> 把它按"哪个更严"来设计，两头都会错。

### 1.2 新 job `release-state`

`check-release-status.sh`（tag ↔ 复盘）+ `check-docs-links.sh`，跑在 ubuntu，**`fetch-depth: 0`**。

为什么单独一个 job、为什么必须取全 tag：默认 checkout 是 `fetch-depth: 1`，
而那支脚本在**看不见 tag** 时会把每个版本判成 `MISSING TAG` 并大声报错
（这是它刻意的行为：宁可吵闹也不要静默通过）。**一条会误报的门禁比没有门禁更坏**——
所以这里多付一点时间把 tag 取全，而不是让脚本去猜。

### 1.3 牙齿：v0.84 新加的"未推送数"断言

| 动作 | 结果 |
|------|------|
| 中文那处 `19 → 7` | `FAIL: docs/README.md: 「未推送的 N 个（中文）」写着 7，而 版本数(84) − 镜像 tag(65) = 19` ✓ |
| 改回 19 | `ok` ✓ |
| 英文那处 `19 → 3` | `FAIL: README.md: 「unpushed N（英文）」写着 3，而 版本数(84) − 镜像 tag(65) = 19` ✓ |
| 改回 19 | `ok` ✓ |

两处都红，且报错**给出算术**（这正是这条断言存在的理由：那处读数漏过两次）。
