## 性能目标与 v0.1 实测

测量方法：`NGM_BENCH=1 go test -count=1 -run TestBaseline -v ./cmd/ngm`（本地 fixture、无网络）。
环境：Windows 10 / 8 逻辑核（i3-10100 @3.60GHz）/ go1.27.1 windows/amd64 / git 2.56.0.windows.1。

**v0.5 起，上表里的"一次测量"改为三次采样取中位数**——原因是复测发现**单次读数会在目标线两侧摆动**
（见下）。只有一次读数的"达标"不足以支撑"达标"这个词。

| 操作 | 目标 | v0.1 实测 | v0.2 实测 | v0.5 复测（3 次：中位 / 极值） | 结论 |
|------|------|-----------|-----------|------------------------------|------|
| cold install（10 个依赖） | < 5s | 1.91s | 1.86s | 1.88–1.94s（**2 次**） | ✅ 大幅达标 |
| warm install（无变更） | < 500ms | 11ms（10 依赖）/ 107ms（100 依赖） | 13ms（10 依赖）/ 114ms（100 依赖） | 12ms（10 依赖）/ 119ms（100 依赖） | ✅ |
| verify（100 个依赖，在线） | < 3s | 18.77s | **3.4s → 2.51s**（[ADR-010](../adr/adr-010-online-verify-fetch-policy.md)） | 复核 3 次：2.556s / 2.201–3.068s；**A 组后 5 次：1.969s / 1.752–2.078s** | ✅ 达标，但**读下面那条警告** |
| offline verify（100 个依赖） | < 5s | 11.12s | **1.97s** | 2.167s / 1.740–2.328s | ✅ 达标（余量约 2×） |
| verify --deep（100 个依赖，离线） | — | 12.65s | 2.28s | 2.478s / 2.311–2.744s | 参考值（无目标） |
| archiveDigest 计算（100MB 仓库） | < 1s | 452ms | 446ms | 434–457ms（**2 次**） | ✅ |

> **采样次数写在格子里，是因为它有信息量**：三轮里有第三轮只补采了 verify 与 warm install，
> 因此 cold install（10 依赖）与 100MB digest 是 **2 次**。两个读数不构成分布，
> 那里只报极值、不报"中位数"——把 2 个数的中间值叫中位数，是给读者一个它撑不住的确定感。

> **结论要分开说，不能合并成一句"全部达标"**：
>
> 1. **offline verify 与 digest 重放**：稳定达标，且余量充足（1.74–2.33s vs 5s；434–457ms vs 1s）。
> 2. **在线 verify（100 依赖）**：中位数 2.556s 在 3s 以内，但**分布跨在目标线上**
>    （2.201s / 3.068s / 2.556s）。此前"2.51s ✅ 达标"是**单次读数**，它落在哪一侧有运气成分。
>    这条目标现在应当读作"**贴着线**"，而不是"已经解决"。
> 3. 主要成本仍是 **git 子进程启动**（每依赖一次 `ls-remote`），不是哈希或 I/O——
>    同一台机器上 `git ls-remote` 单次约 65ms，100 个依赖 ÷ 8 并发 ≈ 0.8s，其余是进程调度与
>    mirror 读写的叠加。**降低方差与降低成本是同一件事**：减少 spawn 次数，而不是换更快的机器。
>
> v0.2 完成时在线 verify 尚差 1.1×，由 [ADR-010](../adr/adr-010-online-verify-fetch-policy.md)
> 的"ref 问远端、对象按需取"在 v0.3 开工时补上（3.37s → 2.51s）；**v0.4 与本轮均未再改这条路径**，
> 因此上面的分布就是它当前的形态。
>
> 这条达标来之不易，三次改动各自解决一层问题，且每层都有实测：
>
> 1. **依赖级并发**（默认 8；实测 4→8 是拐点，8→16 已无收益）：5.09s→3.37s
> 2. **成功路径少一次 spawn**（commit 存在性检查改为惰性判定）
> 3. **不再无条件 fetch**（ADR-010）：只读 ref 广播，对象按需才取 → 2.51s ✓
>
> 顺带更正一条**前提不成立**的旧建议：复盘 §3.4 曾建议"按仓库合并 git 调用"，
> 但本基准的 100 个依赖是 **100 个独立仓库**，没有可合并的调用，收益为零。
> 那条建议成立于"多依赖共享同一仓库"的前提，本基准不满足（已在复盘中撤回并写明原因）。
>
> `verify` 的成本始终是 **git 子进程启动**（本机 `git ls-remote` 65ms/次），不是哈希或 I/O——
> 100 MiB 的单次 digest 重放只需 452ms。优化方向与预计收益见
> [v0.1 复盘](../development/v0.1-retrospective.md) §3.4。
>
> ngm 不宣称"比 pnpm/Bun 快"；上表用于**发现自己变慢了**，不是竞争性指标。

## 内部并行哈希（v0.5）

v0.2 复盘 §2.3 挂账的"单个依赖内部串行哈希"已在 v0.5 做掉。它的收益**不是**靠一次运行测出来的，
而是靠**两个可复现的基准**（A/B 对照 = 同一份代码 + `GOMAXPROCS=1`，不需要为了测量而改代码）：

```bash
# --deep 的逐文件校验（纯文件哈希，无子进程）
go test -run '^$' -bench VerifyVendorTreeDeep -benchtime 20x ./internal/vendor
GOMAXPROCS=1 go test -run '^$' -bench VerifyVendorTreeDeep -benchtime 20x ./internal/vendor

# digest 清单重放（含 git 子进程）
go test -run '^$' -bench BuildArchive -benchtime 20x ./internal/git
GOMAXPROCS=1 go test -run '^$' -bench BuildArchive -benchtime 20x ./internal/git
```

| 位置 | 串行 | 并行 | 收益 |
|------|------|------|------|
| `--deep` 逐文件校验（2000 × 8 KiB） | 373.6ms | **178.6ms** | **2.09×** |
| digest 清单重放（2000 × 8 KiB） | 278.9ms | **244.1ms** | **1.14×** |

**两个数字差这么多，原因比数字本身有用**：后者的大头是 `git ls-tree` + `git cat-file --batch`
两个子进程，能并行的那一段只占一小部分。因此——

> **digest 重放的瓶颈在 git 子进程，不在哈希。这条路径的下一个优化是"少开子进程"，
> 不是"开更多线程"。**（结论与实测数字写进了 `internal/git/archive_bench_test.go` 的头部。）

## git 子进程清单（v0.5 起）

**在线 verify 的成本几乎全在 git 子进程启动上**（v0.1 复盘 §3.3 的结论），
因此"起了几个 git"是比秒数**更稳**的指标——秒数含机器噪声（同一台机器 2.2–3.1s 摆动），
次数只含信号，而且可以被断言。

仪器：`git.SpawnCount()`（`internal/git/spawn.go`，**唯一的构造点**里记账）。

```bash
go test -count=1 -run TestV05VerifySpawnInventory -v ./cmd/ngm   # 打印清单（证据）
go test -count=1 -run TestV05RefResolutionSpawns -v ./cmd/ngm    # 门禁：commit 0 次 / tag ≥1 次
go test -count=1 -run TestV06VerifySpawnBudget -v ./cmd/ngm      # 门禁：整次 verify 的每依赖预算（v0.6）
go test -count=1 -run TestSpawn_OnlyOneFileCountsSpawns ./internal/git  # 门禁：计账点唯一
```

| 形态 | 每次依赖的 spawn | 预算（v0.6 起为门禁） | 构成 |
|------|-----------------|--------------------|------|
| commit 型 | **2.00** | ≤ 2 | `ls-tree` + `cat-file --batch`（digest 重放，与 refType 无关） |
| tag / branch 型 | **3.00** | ≤ 3 | 上面 2 次 + `ls-remote`（问远端） |

| 时间 | commit 型 | tag / branch 型 | 改动 |
|------|----------|----------------|------|
| v0.5 复核时 | 3.00 | **4.00** | —— |
| 现在 | **2.00** | **3.00** | [ADR-015](../adr/adr-015-commit-ref-resolution.md)（commit 不解析）· [ADR-016](../adr/adr-016-mirror-url-local-read.md)（远端地址读文件） |

> v0.1 复盘写的"每个依赖约 4 次 git spawn"在复核时**被新仪器复现**（4.00）✅——
> 一条跨三个版本的旧结论成立。现在它变成了 3.00，因此那句话需要按上表读。

#### 仪器也会说谎，而且比没有仪器更糟（v0.6 实录）

v0.6 装上门禁的**第一天**，`TestV06VerifySpawnBudget` 就报出 commit **3.00** / tag **4.00**——
比本页记的数字各多 1。查下去发现**不是代码变慢，而是计数器在说谎**：
v0.5 的 C 组把 `CatFileBatch` 从"自己 exec"收进唯一的构造点 `newGitCommand`（那里计数），
却漏删了它自己那句记账调用，于是每个 `cat-file --batch` 被**记两次账**。

- **为什么当时没发现**：门禁断言测的是"该不该起"（拒绝了几个），计数偏高它看不出来；
  而唯一的读数只被 `t.Logf` 打印、从不作断言——"印出来不等于被检查"（v0.5 复盘 §5.2）。
  本页当时写的 2.00 / 3.00 是**改动完成时**的真实值，之后才被这次重复计账带偏。
- **怎么修的**：删掉重复记账，并加两条**互相独立**的网——
  ①`TestV06VerifySpawnBudget`（管"起了几个"）、②`TestSpawn_OnlyOneFileCountsSpawns`
  （扫源码，管"只能在一个地方记账"）。两条都**验证过**：把重复记账放回去，两条同时红。

> 这条记在这里，是因为它对本页的读者最重要：**指标页上的数字只有在它被门禁守着时才可信**。
> 秒数没有门禁（也不该有，噪声太大），而次数有——这正是"次数优先于秒数"的第二个理由。

单次成本（同机实测，裸仓库）：`config --get` **30.6ms** / `ls-remote`（本地）**77.8ms** /
`ls-tree` **36.4ms**。按 tag 型 4 次计约 183ms/依赖，100 依赖 ÷ 8 并发 ≈ 2.2s——
与复核时实测中位 2.56s 吻合，因此**这条模型可以用来预测改动的收益**，而不是只用来事后解释。

### ⚠️ 秒数会被机器状态骗，次数不会

A 组做了一次**受控 A/B**（同一天、同一台机器、交替采样，5 次）：

| | 中位 | 最大 |
|---|------|------|
| 对照组（临时关闭 ADR-016 的快路径） | 2.416s | 2.433s |
| 实验组 | **1.969s** | **2.078s** |

改动本身值 −15%~−18% ✅。但同一次实验暴露了一件更要紧的事：
**复核时那三次采样里的 3.068s，在今天同一台机器上复现不出来**——对照组（等于复核时的代码）
最大只有 2.433s。**跨机器状态的方差大于这次优化的收益。**

因此本页的纪律是：**比较性能时次数优先于秒数**。
`git.SpawnCount()` 与机器状态无关（4.00 → 3.00 是确定的），
而秒数会（同一份代码在同一天的两轮采样相差 0.3s）。秒数只用来回答"用户等多久"，
不用来判断"改动有没有用"。

**v0.6 起这条纪律有门禁**：`TestV06VerifySpawnBudget` 断言每依赖的预算，超出即 CI 红
（见下一节）。因此"3s 目标"不是门禁，它是用户等待时间的观测值——这样写是为了让
**能被判别的量**去守门，而不是让一个在噪声里不可判别的数字充当门禁。

**三平台复测**（CI，2026-10-02）：Windows x86_64 / macOS arm64 / Ubuntu x86_64 三处
都是 commit **2.00** / tag **3.00**，且**数字完全相同**——这正是"次数"相对"秒数"的价值：
后者在同一台机器上两轮就能差 0.3s。它顺带证明 [ADR-016](../adr/adr-016-mirror-url-local-read.md)
读 config 文件的快路径在三个平台上都生效（否则 tag 型会是 4.00）。

## 磁盘增长：内容寻址 store（v0.6）

E2（content store / mirror 的 GC）自 v0.2 起挂账，理由一直是**缺实测的磁盘增长数据**。
v0.6 把它量出来了——证据用例（**只测不做**）：

```bash
go test -count=1 -run TestV06StoreGrowthInventory -v ./internal/vendor
```

形态：**一个仓库、12 个 commit，每个 commit 只改其中 1 个文件**（树 = 20 文件 × 8 KiB = 160 KiB）。

| 量 | 值 |
|----|----|
| content store（12 个 commit 后） | **1.88 MiB**（**160.2 KiB/commit**，恰好是整棵树） |
| 同期源码的**真实增量** | 96.0 KiB |
| 放大比 | **20.0×** |
| 同一份历史的 Git 对象库（层 1 的上界估计） | 10.3 KiB → content store 是它的 **187×** |

**为什么是线性且不去重**：布局是 `content/sha256/<digest>/tree/`，**按整棵树**寻址
（`internal/vendor/content.go` 的层 2 契约），所以同一仓库的每个新 commit 都会**完整复制**
一遍内容树。唯一能省的情形是**同一个 digest 再次出现**（跨项目引用同一 commit 时命中
`AlreadyPresent`）。

### 复测（v0.8：换布局之后）

[ADR-019](../adr/adr-019-content-addressed-blobs.md) 把布局换成 **blob 池 + 树清单**，
v0.8 落地。**同一把尺子、同一台机器**，同一份 fixture（12 个 commit、每个只改 1 个文件）：

| 量 | v1 布局（v0.6 实测） | v2 布局（v0.8 复测） |
|----|--------------------|--------------------|
| content store（12 个 commit 后） | **1.88 MiB**（160.2 KiB/commit，恰好是整棵树） | **59.9 KiB**（5.0 KiB/commit） |
| 同期源码的**真实增量** | 96.0 KiB | 96.0 KiB |
| 放大比（每 commit 增量 ÷ 源码真实增量） | **20.0×** | **0.6×** |

**0.6× 意味着"比源码的真实增量还小"**，这不是笔误：blob 池里只有两个 blob——20 个文件里
同内容的文件彼此也去重（`a`… 与 `b`… 各一份 8 KiB），12 个改动落在同一批重复内容上；
剩下的增长**全是清单**：每个 commit 一份约 3.7 KiB 的 `manifest.json`。

> **口径提醒**：这里的"放大比"是**每 commit 增量 ÷ 源码真实增量**（v0.6 的 20.0× 就是这么算的），
> 不是"总量 ÷ 一棵树"。同一份数据的另一个读法是"已存下 0.37 棵树"。

**这条复测同时是回归门禁**：`TestV06StoreGrowthInventory` 的断言从"至少要有 N 棵树"
**翻转**为"不得接近 N 棵树"——同一段代码，量的从"放大得有多严重"变成"去重是否真的生效"。

> **去重改的是斜率，不是终点。** blob 同样只增不减，回收仍受
> [ADR-018](../adr/adr-018-store-reclaim.md) 那两个条件约束；本页下面那段"谁来回收"
> 的结论一字未变。把 20.0× 降到 0.6× 只是让"必须马上做 GC"这件事变得更不紧迫——
> 而"不紧迫"**不等于**"不需要"：曲线仍然单调上升。

**两层的分工**（本页最该记住的一句）：

| 层 | 谁来回收 | 现状 |
|----|---------|------|
| 1 mirror（Git 裸仓） | **`git gc`** —— git 的既有能力，用户随时可跑 | 有出路 |
| 2 content store | **没有任何人** | **只增不减** |

**结论（v0.6 判定）**：数据支持排期，但第一步不是写代码，而是先立 ADR——**已办**：
[ADR-018](../adr/adr-018-store-reclaim.md) 决定**不做按可达性自动删除的 GC**
（缺项目注册表；误删会让别的项目某天突然验不过），当下只做 `ngm store usage`（只读报告）
与 `ngm store prune`（只清半成品），并把**写入侧去重**记为长期解法——
那条长期解法已由 [ADR-019](../adr/adr-019-content-addressed-blobs.md) 设计、**v0.8 落地**（见上节复测）。
下列理由正是那份 ADR 判定的依据。
store 是**跨项目共享**的（`~/.ngm/content`），"删哪些 digest 安全"因此是一个设计问题：
某个 digest 对 A 项目已废弃，对 B 项目可能正是它 vendor 的来源。
在默认 `hardlink` 落地模式下，已落地的 vendor 文件即使 store 被删**仍读得到**（inode 还在），
但 **`ngm verify` 会报层 2 缺失** —— 也就是说，草率删除会把"完整性可验证"变成
"可能已经被别人删掉了"。这条裁决必须先写下来（与 ADR-003 的补录对齐）。

> 与 v0.5 的挂账理由对照：那时写的是"缺数据所以不排期"。现在数据有了，
> **理由就从"不知道"变成"知道但需要一个决策"**——这两者在计划里应当有不同待遇。

### blob 池的规模（v0.9 实测，**只测不做**）

问题有两个：两位 hex 分片（256 个目录）在 10 万级是否还站得住，以及这一层唯一的读数入口
（`ngm store usage`）还跑不跑得动。实测（本机 Windows，10 万个 32 B 的 blob + 1 份真实内容树）：

| 量 | 值 |
|----|----|
| 分片数 | 256（两位 hex） |
| 单目录文件数 | **341 ~ 437**（均衡） |
| 写入速率 | 3756 blob/s（10 万个 26.6 s） |
| `Usage()` 遍历整个池 + 清单 | **244 ms**，分配 28.7 MiB，堆峰值 13.3 MiB |

**结论**：两位分片在 10 万级仍有余量（单目录几百个文件），`usage` 仍是"毫秒级、几十 MiB"
的量级——**不需要改分片**。这只是数据，不是对更细分片的否决。

```bash
NGM_STORE_SCALE_BLOBS=100000 go test -count=1 -run TestV09BlobPoolScale -v ./internal/vendor
```

> **这条实测顺手抓到一个夹具陷阱**：第一版用 `%064x`（计数器）造名字，于是 2 万个名字的
> 前两位**全是 `00`**——全落进同一个分片，量到的是夹具的偏差（`max files/shard=20000`）
> 而不是真实分布。真实 blob 名是 `sha256(mode‖content)`，前两位均匀；
> 夹具必须模拟这一点。**"测出来的分布"要先用"分布本身对不对"验一遍。**

## 诚实边界

1. **实测口径有限**：v0.1 的实测来自单一环境（Windows / 本机磁盘）与合成 fixture；
   真实仓库的 ref 数量、对象体积、网络延迟都会改变结果
2. **性能不是卖点**：Bun 无变更重装约 12ms，ngm 不应以速度竞争
3. **正确性优先**：refType + digest 的正确性比性能重要
4. **跨平台兼容是难点**：hardlink 需要同卷文件系统（Windows NTFS 可用），不支持时降级复制
5. **verify 的成本在子进程而非内容**：v0.1 每个依赖约 4 次 git spawn，
   100 依赖因此在 Windows 上约 11s（`--offline`）；见复盘 §3.3
