## 性能目标与 v0.1 实测

测量方法：`NGM_BENCH=1 go test -count=1 -run TestBaseline -v ./cmd/ngm`（本地 fixture、无网络）。
环境：Windows 10 / 8 逻辑核（i3-10100 @3.60GHz）/ go1.27.1 windows/amd64 / git 2.56.0.windows.1。

**v0.5 起，上表里的"一次测量"改为三次采样取中位数**——原因是复测发现**单次读数会在目标线两侧摆动**
（见下）。只有一次读数的"达标"不足以支撑"达标"这个词。

| 操作 | 目标 | v0.1 实测 | v0.2 实测 | v0.5 复测（3 次：中位 / 极值） | 结论 |
|------|------|-----------|-----------|------------------------------|------|
| cold install（10 个依赖） | < 5s | 1.91s | 1.86s | 1.88–1.94s（**2 次**） | ✅ 大幅达标 |
| warm install（无变更） | < 500ms | 11ms（10 依赖）/ 107ms（100 依赖） | 13ms（10 依赖）/ 114ms（100 依赖） | 12ms（10 依赖）/ 119ms（100 依赖） | ✅ |
| verify（100 个依赖，在线） | < 3s | 18.77s | **3.4s → 2.51s**（[ADR-010](../adr/adr-010-online-verify-fetch-policy.md)） | 复核 3 次：2.556s / 2.201–3.068s；**A 组后 5 次：1.969s / 1.752–2.078s** | ✅ 达标，但**读下面那条警告** |
| offline verify（100 个依赖） | < 5s | 11.12s | **1.97s** | 2.167s / 1.740–2.328s | ✅ 达标（余量约 2×） |
| verify --deep（100 个依赖，离线） | — | 12.65s | 2.28s | 2.478s / 2.311–2.744s | 参考值（无目标） |
| archiveDigest 计算（100MB 仓库） | < 1s | 452ms | 446ms | 434–457ms（**2 次**） | ✅ |

> **采样次数写在格子里，是因为它有信息量**：三轮里有第三轮只补采了 verify 与 warm install，
> 因此 cold install（10 依赖）与 100MB digest 是 **2 次**。两个读数不构成分布，
> 那里只报极值、不报"中位数"——把 2 个数的中间值叫中位数，是给读者一个它撑不住的确定感。

> **结论要分开说，不能合并成一句"全部达标"**：
>
> 1. **offline verify 与 digest 重放**：稳定达标，且余量充足（1.74–2.33s vs 5s；434–457ms vs 1s）。
> 2. **在线 verify（100 依赖）**：中位数 2.556s 在 3s 以内，但**分布跨在目标线上**
>    （2.201s / 3.068s / 2.556s）。此前"2.51s ✅ 达标"是**单次读数**，它落在哪一侧有运气成分。
>    这条目标现在应当读作"**贴着线**"，而不是"已经解决"。
> 3. 主要成本仍是 **git 子进程启动**（每依赖一次 `ls-remote`），不是哈希或 I/O——
>    同一台机器上 `git ls-remote` 单次约 65ms，100 个依赖 ÷ 8 并发 ≈ 0.8s，其余是进程调度与
>    mirror 读写的叠加。**降低方差与降低成本是同一件事**：减少 spawn 次数，而不是换更快的机器。
>
> v0.2 完成时在线 verify 尚差 1.1×，由 [ADR-010](../adr/adr-010-online-verify-fetch-policy.md)
> 的"ref 问远端、对象按需取"在 v0.3 开工时补上（3.37s → 2.51s）；**v0.4 与本轮均未再改这条路径**，
> 因此上面的分布就是它当前的形态。
>
> 这条达标来之不易，三次改动各自解决一层问题，且每层都有实测：
>
> 1. **依赖级并发**（默认 8；实测 4→8 是拐点，8→16 已无收益）：5.09s→3.37s
> 2. **成功路径少一次 spawn**（commit 存在性检查改为惰性判定）
> 3. **不再无条件 fetch**（ADR-010）：只读 ref 广播，对象按需才取 → 2.51s ✓
>
> 顺带更正一条**前提不成立**的旧建议：复盘 §3.4 曾建议"按仓库合并 git 调用"，
> 但本基准的 100 个依赖是 **100 个独立仓库**，没有可合并的调用，收益为零。
> 那条建议成立于"多依赖共享同一仓库"的前提，本基准不满足（已在复盘中撤回并写明原因）。
>
> `verify` 的成本始终是 **git 子进程启动**（本机 `git ls-remote` 65ms/次），不是哈希或 I/O——
> 100 MiB 的单次 digest 重放只需 452ms。优化方向与预计收益见
> [v0.1 复盘](../development/v0.1-retrospective.md) §3.4。
>
> ngm 不宣称"比 pnpm/Bun 快"；上表用于**发现自己变慢了**，不是竞争性指标。

## 内部并行哈希（v0.5）

v0.2 复盘 §2.3 挂账的"单个依赖内部串行哈希"已在 v0.5 做掉。它的收益**不是**靠一次运行测出来的，
而是靠**两个可复现的基准**（A/B 对照 = 同一份代码 + `GOMAXPROCS=1`，不需要为了测量而改代码）：

```bash
# --deep 的逐文件校验（纯文件哈希，无子进程）
go test -run '^$' -bench VerifyVendorTreeDeep -benchtime 20x ./internal/vendor
GOMAXPROCS=1 go test -run '^$' -bench VerifyVendorTreeDeep -benchtime 20x ./internal/vendor

# digest 清单重放（含 git 子进程）
go test -run '^$' -bench BuildArchive -benchtime 20x ./internal/git
GOMAXPROCS=1 go test -run '^$' -bench BuildArchive -benchtime 20x ./internal/git
```

| 位置 | 串行 | 并行 | 收益 |
|------|------|------|------|
| `--deep` 逐文件校验（2000 × 8 KiB） | 373.6ms | **178.6ms** | **2.09×** |
| digest 清单重放（2000 × 8 KiB） | 278.9ms | **244.1ms** | **1.14×** |

**两个数字差这么多，原因比数字本身有用**：后者的大头是 `git ls-tree` + `git cat-file --batch`
两个子进程，能并行的那一段只占一小部分。因此——

> **digest 重放的瓶颈在 git 子进程，不在哈希。这条路径的下一个优化是"少开子进程"，
> 不是"开更多线程"。**（结论与实测数字写进了 `internal/git/archive_bench_test.go` 的头部。）

## git 子进程清单（v0.5）

**在线 verify 的成本几乎全在 git 子进程启动上**（v0.1 复盘 §3.3 的结论），
因此"起了几个 git"是比秒数**更稳**的指标——秒数含机器噪声（同一台机器 2.2–3.1s 摆动），
次数只含信号，而且可以被断言。

仪器：`git.SpawnCount()`（`internal/git/spawn.go`，三个启动点都记账）。

```bash
go test -count=1 -run TestV05VerifySpawnInventory -v ./cmd/ngm   # 打印清单（证据）
go test -count=1 -run TestV05RefResolutionSpawns -v ./cmd/ngm    # 门禁：commit 0 次 / tag ≥1 次
```

| 形态 | 每次依赖的 spawn | 构成 |
|------|-----------------|------|
| commit 型 | **2.00** | `ls-tree` + `cat-file --batch`（digest 重放，与 refType 无关） |
| tag / branch 型 | **3.00** | 上面 2 次 + `ls-remote`（问远端） |

| 时间 | commit 型 | tag / branch 型 | 改动 |
|------|----------|----------------|------|
| v0.5 复核时 | 3.00 | **4.00** | —— |
| 现在 | **2.00** | **3.00** | [ADR-015](../adr/adr-015-commit-ref-resolution.md)（commit 不解析）· [ADR-016](../adr/adr-016-mirror-url-local-read.md)（远端地址读文件） |

> v0.1 复盘写的"每个依赖约 4 次 git spawn"在复核时**被新仪器复现**（4.00）✅——
> 一条跨三个版本的旧结论成立。现在它变成了 3.00，因此那句话需要按上表读。

单次成本（同机实测，裸仓库）：`config --get` **30.6ms** / `ls-remote`（本地）**77.8ms** /
`ls-tree` **36.4ms**。按 tag 型 4 次计约 183ms/依赖，100 依赖 ÷ 8 并发 ≈ 2.2s——
与复核时实测中位 2.56s 吻合，因此**这条模型可以用来预测改动的收益**，而不是只用来事后解释。

### ⚠️ 秒数会被机器状态骗，次数不会

A 组做了一次**受控 A/B**（同一天、同一台机器、交替采样，5 次）：

| | 中位 | 最大 |
|---|------|------|
| 对照组（临时关闭 ADR-016 的快路径） | 2.416s | 2.433s |
| 实验组 | **1.969s** | **2.078s** |

改动本身值 −15%~−18% ✅。但同一次实验暴露了一件更要紧的事：
**复核时那三次采样里的 3.068s，在今天同一台机器上复现不出来**——对照组（等于复核时的代码）
最大只有 2.433s。**跨机器状态的方差大于这次优化的收益。**

因此本页的纪律是：**比较性能时次数优先于秒数**。
`git.SpawnCount()` 与机器状态无关（4.00 → 3.00 是确定的），
而秒数会（同一份代码在同一天的两轮采样相差 0.3s）。秒数只用来回答"用户等多久"，
不用来判断"改动有没有用"。

## 诚实边界

1. **实测口径有限**：v0.1 的实测来自单一环境（Windows / 本机磁盘）与合成 fixture；
   真实仓库的 ref 数量、对象体积、网络延迟都会改变结果
2. **性能不是卖点**：Bun 无变更重装约 12ms，ngm 不应以速度竞争
3. **正确性优先**：refType + digest 的正确性比性能重要
4. **跨平台兼容是难点**：hardlink 需要同卷文件系统（Windows NTFS 可用），不支持时降级复制
5. **verify 的成本在子进程而非内容**：v0.1 每个依赖约 4 次 git spawn，
   100 依赖因此在 Windows 上约 11s（`--offline`）；见复盘 §3.3
