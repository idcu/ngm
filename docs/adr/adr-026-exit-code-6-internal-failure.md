# ADR-026：加一个退出码 **6 = 内部失败**

- **状态**：已定（2026-10-08）
- **范围**：退出码契约（`0..5` → `0..6`）与"结论算出来了却说不出去"这一类失败
- **上游**：[可观测性 · 退出码约定](../architecture/observability.md)（退出码的唯一事实源）· [v0.57 复盘](../development/v0.57-retrospective.md)（这条的实测来源）· [ADR-023](./adr-023-orphan-reclaim.md)（"不做/做"如何写成决定）

> **结论**：给"内部失败"一个自己的数字——**6**。它覆盖两类：
> ① **panic**（`runWithRecovery` 捕获）；② **结论已经算出来、却说不出去**
> （写 stdout 失败 / JSON 编码失败 / 读 stdin 失败）。
> 从 v0.57 起它们**已经在文档里被写清**，但仍然与"策略失败"共用数字 `1`——
> 于是 CI 无法用退出码区分"**上游漂了**"与"**我写不出去**"。

---

## 背景：一个数字兜着两件事

v0.57 把"码 1 的来源"从源码派生出来（**27 处站点 / 21 个函数**），量出五类，
其中最后一类与策略无关：

| 类别 | 站点 |
|------|------|
| 策略漂移 | `internal/verify/report.go :: ExitCode` |
| 引擎运行失败 | `internal/adapter/engine.go :: AsNgmError` · `runner.go :: runChain` |
| 漏洞超阈值 | `cmd/ngm/tree.go :: runTree` |
| 审计钩子否决或超时 | `cmd/ngm/audit_hook.go :: auditHookVerdict` |
| **内部失败** | `runWithRecovery`（panic）＋ **12 处"说不出去"** |

那 12 处是同一句话：命令已经跑完、结论也算出来了，但**说不出去**——
`write report` / `write json` / `marshal json` / `read stdin` / `write output` /
`write bundle` / `write css` / `write listing` / `encode report`。

当时的处置是**改文档**（语义列写成"策略失败**或进程内部失败**"）——那是必要的一步，
但它解决不了这件事：

```yaml
# CI 想知道的是"该不该重跑"
- 上游把 tag 挪了      → 1     → **重跑也没用**，要人看
- ngm 写 stdout 失败   → 1     → **重跑可能就好了**（磁盘满 / 管道断）
```

**两种该做的事不同，却拿到同一个数字。**

## 决策：加码 6

1. **语义**：`6 = 内部失败`——"ngm 自己没走完"（panic），或"结论有了但送不出去"。
   **不是**策略、**不是**完整性、**不是**配置、**不是**网络、**不是**引擎不可用。
2. **数值 6**（`0..5` 保持不变——它们是既有契约，一个也不动）。
3. **不追加区**：`1` 的四类策略来源**一个也不搬**。搬走的是"与策略无关"的那一类。
4. **每个命令的 usage 里补上它实际会退的 `6`**——本项目对 usage 的既有约定是
   "每个命令自己的用法里写着它**实际**会退哪几个"（见 `help.go`）。

## 代价（明说）

| 项 | 代价 |
|----|------|
| 契约扩展 | 四条判据（V21/V22/V24/V57）与四处文档必须同步；`p0-core` 的 `iota` 块加一行 |
| 既有脚本 | 把 `1` 当"漂移"的脚本**不受影响**（`6` 是新值，以前不可能出现）；把"非 0 即失败"当判据的脚本更不受影响 |
| 可测量性 | V22 要求"声明的码必须被测量"——`6` **可测**：`dispatch` 接受任意 `io.Writer`，传一个永远写失败的 writer 即可（v0.59 实测：`ngm verify --json` 在该 writer 下退 `1`，stderr 是 `write report: …`） |

## 替代方案（为什么没选）

| 方案 | 为什么不 |
|------|---------|
| **只改文档**（v0.57 已做） | 解决了"文档说谎"，没解决"CI 分不清"——两种该做的事仍拿同一个数字 |
| 映射到 **3**（配置/策略错误） | 不符：磁盘满 / 管道断不是配置问题，用户去改配置是**白费** |
| 映射到 **2**（完整性失败） | 更不符：完整性说的是内容对不上，与"写不出去"无关 |
| 加一个**区间**（如 6–9 都算内部失败） | 现在只有一个语义，留区间等于留**没人负责的空位**（ADR-025 的同一课） |

## 影响

- `internal/errs`：`CodeInternal = 6`（`String()` / `ExitCode()` 各加一条）。
- 13 处站点（12 处 IO ＋ panic）改用它——**数值不再散落**（原先各自写着字面量 `1`）。
- `docs/architecture/observability.md`：码 1 的语义回到"**策略失败**"（四类），
  新增码 6 一行；`docs/guides/cli.md` 的摘要与 `docs/modules/p0-core.md` 的 `iota` 块同步。
- **判据**：V57 的扫描从"码 1 的来源"扩成"**码 1 与码 6 各自的来源**"，
  两个方向对账照旧；V22 给 `6` 一条**专属实测**（不记缺口）。
