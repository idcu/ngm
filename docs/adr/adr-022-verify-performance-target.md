# ADR-022：verify 的性能目标改为"次数门禁 + 秒数观测"

- **状态**：已定
- **日期**：2026-10-03
- **范围**：`ngm verify` 的性能**目标与门禁**（不是它的实现）
- **上游**：[v0.1 复盘](../development/v0.1-retrospective.md)（目标出处）· [v0.5 复盘 §2.3](../development/v0.5-retrospective.md)（不可判别的实测）· [v0.6 复盘 §5.1](../development/v0.6-retrospective.md)（门禁）

> **结论**：**"在线 verify ≤ 3s"不再是验收目标**。
> 门禁是**每依赖的 git spawn 预算**（commit ≤ 2 / tag ≤ 3，CI 里跑），
> 秒数**保留为"用户等待时间"的观测值**，记录在 [metrics](../internals/metrics.md) 里，**不判**。
>
> **代价**：没有一个"用户体验"层面的门禁。若将来某次改动让 verify 慢了一倍而不增加 spawn 次数
> （例如单次 spawn 变慢、或 digest 重放变重），**CI 不会红**——只有人看 metrics 才会发现。
> 这条代价是刻意的：宁可少一道会误报的门禁，也不留一道在噪声里不可判别的门禁。

---

## 背景：目标是什么，以及它为什么失效

v0.1 的验收里包含"在线 verify（100 依赖）≤ 3s"。v0.5 专门量了它：

| 量 | 值 |
|----|----|
| 优化后（A 组改动）最大值 | **2.078s < 3s** |
| **受控对照**（未优化）最大值 | **2.433s —— 也过线** |
| 同一台机器两轮采样的差 | ≥ 0.3s |
| 本轮改动的收益 | 0.45s（**小于机器方差**） |

也就是说：**这条线在今天的机器上不可判别**——它在"未优化"时也满足，
而真正的收益（4.00 → 3.00 次/依赖）在秒数上被噪声淹没。
v0.5 复盘因此明确禁止把结果写成"A4 让它达标了"，纪律改为**次数优先于秒数**。

v0.6 把这条纪律变成门禁：`TestV06VerifySpawnBudget` 断言每依赖预算
（commit ≤ 2 / tag ≤ 3），并**验证过它有牙齿**（把重复记账放回去，两条网同时红）。

---

## 决策

1. **3s 从验收目标降级为观测值**：它在 [metrics](../internals/metrics.md) 里保留，
   标注口径（同一台机器的实测，含机器状态），**不参与通过/不通过**。
2. **门禁是次数**：每依赖的 git spawn 预算是唯一的性能门禁，在 CI 里跑。
   它满足门禁该有的三个性质：**可判别**（无机器噪声）、**可归因**（多了几次、在哪一型）、
   **可自证**（`TestSpawn_OnlyOneFileCountsSpawns` 保证计数只有一个记账点）。
3. **文档里不再出现"接近 3s"这类说法**：只有"观测值"与"预算"两种表述。
   v0.1/v0.5 的复盘保持原样（它们是历史记录）。
4. **重新立目标的条件（任一成立）**：
   - 出现**用户报告"verify 太慢"**（那时目标来自需求，而不是拍出来的数字）；
   - 出现"**spawn 次数已到预算下界、而秒数仍显著高于同机基线**"的实测——那说明瓶颈
     不在 spawn 数上，需要**新的**判别量（例如单次 spawn 的中位耗时），而不是回到秒数。

---

## 为什么不是"把 3s 改成 5s"

那是同一类错误换个数字：

- 目标必须是**判据**。把线放宽到"今天的机器能过"，只是把"不可判别"藏得更深；
- 一旦用它当门禁，机器状态就会决定 CI 的颜色——**假绿与假红同时增加**，
  而 v0.6 已经量过一次"仪器说谎比没有仪器更糟"（计数器被记了两次账）。

**门禁只留着能判别的量**，这是这条决策的全部内容。

---

## 后果

- **性能这件事在文档里分成两层**，此后不再混用：`次数` = 门禁（可判别，CI 红/绿）;
  `秒数` = 观测（回答"用户等多久"，不判）。
- **v0.1 的"2 条性能目标未达标"里的一条以"目标失效"结项**（不是"达标了"，也不是"放弃了质量"）：
  那条线在今天的机器上不承载信息。未达标清单因此需要按本 ADR 的口径重读。
- **不新增任何检查器**：本 ADR 收紧的是**表述**，不是加一道检查。
