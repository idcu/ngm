# ADR-047：`cmd/ngm` 拆包的触发条件

- **状态**：已定（暂不重构）
- **日期**：2026-11-20
- **范围**：`cmd/ngm`（`package main`）的结构
- **依据**：[全维度评估 2026-11-20 §2.3](../analysis/ngm-full-assessment-2026-11-20.md)

> **结论**：当前**不拆** `cmd/ngm`（44 个非测试文件、约 2.2 万行）。它是"收益/风险不匹配"
> 的结构债，不是缺陷；只有当下面任一触发条件出现、且有具体场景与数字时才启动拆包。

## 背景

评估报告把"package main 过大"列为结构性技术债：跨文件耦合靠约定而非接口，
`verifyUsage` 单条 105 行。但项目已有两道结构性守卫在源文本层守着这些约定：
`TestCmdContextIsTheOnlySkeleton`（14 命令 / 24 处骨架）与 `TestHintsNameFlagsTheCommandAccepts`，
它们让"约定失守"变成可见的红，而不是靠目录大小。

拆包本身有真实代价：`package main` 内部的命令实现、报告渲染、环境装配互相引用，
拆成多个包会引入 export/import 面、`internal` 边界调整、以及全部 golden 的重新验证；
而它不改变任何用户可见行为或退出码语义。

## 决策

1. **维持单一 `package main`**，不因"文件多/行数多"拆包——规模本身不是触发条件。
2. 拆包边界原则（若将来启动）：按职责分为"命令实现 / 报告渲染 / 环境装配"三类，
   沿用 `cmdContext` 骨架作为唯一入口；不为拆而新建接口层。
3. **触发条件（任一成立，且需附具体场景 + 数字）**：
   - 新增命令时反复踩同一处跨文件耦合，导致同类缺陷出现 **≥2 次**；
   - 出现由"约定失守"（而非逻辑错）造成的真实用户可见缺陷，且现有守卫抓不到；
   - 编译 / 测试时间因单包规模出现可观测的退化（给出前后对比数字）。
4. 不满足触发条件时，本 ADR 即"永久暂缓"的答案；下轮评估不必重开。

## 后果

- 一处"看起来该修"的结构债从待办变成**有门槛的决策**，避免凭口味重构。
- 现有两道骨架守卫继续承担"约定不失守"的职责。
