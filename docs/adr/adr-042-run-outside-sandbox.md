# ADR-042：为**项目脚本**开一个沙箱外的执行面（`ngm run`）

- **状态**：已定并已实施（v0.120）
- **日期**：2026-11-04
- **范围**：命令面、权限模型、退出码契约

> **结论**：`ngm run <script>` 只编排**用户自己写的项目脚本**：`package.json.scripts`
> 权威、`ngm.json.scripts` 回退，平台 shell 原样执行，`node_modules/.bin` 注入 PATH，
> 退出码原样透传。它由一条独立的 `run:script` 授权（默认拒绝），**与 install 期
> 依赖的 postinstall 策略是两套闸门**；用户显式调用之前，脚本不会被执行。

## 背景

装上 ngm 之后，跑项目脚本仍要拉 npm——两个工具并存、两套生命周期、两份环境变量。
评估（`docs/analysis/ngm-assessment-2026-11-04.md`）确认 ngm 缺少的只是“**编排**”这一层：
脚本发现、PATH 注入、参数透传、pre/post、退出码与信号转发。安装、registry、
peer 求解不在其中。

## 决策

1. **只做编排，不做安装器**。ngm 不生成 `node_modules/.bin` 的 shim，也不模拟 npm 的
   依赖安装；脚本里的命令能跑，是因为依赖已经以某种方式装好。
2. **沙箱外执行**。`run` 启动的进程继承调用者的环境与文件系统权限——这是用户
   显式要求执行自己的代码，把它塞进 Deno 沙箱既无意义（脚本本来就能做任何事），
   也会让“构建”这类正常工作无法完成。
3. **单独的权限闸门** `run:script`，默认 deny。理由：install 期的
   `supplyChain.postInstallPolicy` 管的是**别人的**代码；`run` 管的是**你的**代码。
   两条决策需要的证据不同，混成一条会让“我允许了构建脚本”顺带允许依赖的 postinstall。
4. **退出码不映射**。子进程的码原样透传（信号见 `128 + signal`），绝不折算成 0–6；
   ngm 自己的失败仍用 3（脚本缺失/冲突/权限/用法）与 5（平台 shell 不可用）。
   把脚本的 1 说成 ngm 的策略失败会污染整张退出码表。
5. **环境变量最小集**：`INIT_CWD`、`npm_lifecycle_event`、`npm_lifecycle_script`、
   `npm_package_name`、`npm_package_version`。不设 `npm_execpath`，不承诺
   `npm_config_*`——**这是契约，不是“近似 npm”**。模拟得越像，越容易被当成兼容层。

   > **补记（2026-11-19，v0.136）：`npm_config_*` 从"不设"扩展到"也不透传"。**
   > 原句只说了"不设"，而父进程环境里若有这一族（从 npm 脚本里调用 `ngm run`，
   > 或 CI runner 自带），它们会原样落进脚本——于是同一份脚本从 shell 启动与从
   > npm 启动行为不同，差别来自一段看不见的环境。现在整段前缀被剔除。
   > 触发这件事的是一个只在 Windows runner 上红的判据
   > （`TestChildEnvIsTheDocumentedMinimum`：那条 Windows 镜像的环境里有
   > `npm_config_*`，于是"没承诺"被读成了"没出现"）。
   > 定位依据见 [ADR-044](./adr-044-independent-ecosystem.md)：ngm 不是兼容层，
   > 也就没有理由继承 npm 的配置命名空间。

## 代价与边界

- 脚本看到的 `node_modules/.bin` 是既有的，ngm 不会为缺失的依赖补链；
  缺失时报的是平台 shell 的“找不到命令”，并在 stderr 追加一行诊断。
- Windows 无 POSIX 信号语义：130 只在子进程自己产生时透传；映射函数另有一条单测。
- 不做并发编排、watch、任务依赖图、`npm publish`、peer 求解。
- **不接进 install / verify / CI 自动流程**：`run` 只在命令行被显式调用时执行。

## 后果

- 用户可以 `ngm run build` 而不需要 npm（前提是依赖已装好）。
- 权限提示里给出可直接粘贴的 `{"permissions":{"allow":["run:script"]}}`。
- 退出码契约网新增“透传族”说明；`contracts/exit-codes.json` 不变（0–6 语义不变）。

## 补记（2026-11-24，W3 / E10–E11）：任务编排非目标固化与只读计划

本补记只固化边界，不推翻上面任何原决策。`ngm run --explain`（E10）让"将要执行什么"
可读，但**不把 ngm 变成任务编排器**；上面"代价与边界"里那句"不做并发编排、watch、
任务依赖图"在这里逐项钉死，避免日后被一句"顺手加上"复活。

### 非目标（逐项，均不实现）

1. **任务图**：不做 Bazel 式的任务依赖图，也不在 `ngm.json` / 全局配置里新增
   `dependsOn` 一类的编排字段。要表达先后关系，用项目脚本自己串（npm scripts /
   Just / Taskfile 仍由用户外置）。
2. **并行调度**：不并行跑脚本或任务；`run` 的 pre→main→post 是确定性的单链，
   第一步失败即短路，退出码原样透传。
3. **增量调度**：不做"输入没变就跳过"的增量执行；ngm 对脚本没有可证明的增量键，
   猜一个会带来"该跑没跑"的不可解释行为。
4. **watch 调度**：不做文件监听与自动重跑；watch 属于开发服务器/构建工具的职责，
   不在 `run` 的契约里。
5. **安装依赖型 `run`**：`run` 不安装依赖、不触发 install；依赖必须已由其它方式装好。
   `--explain` 也只读既有脚本与既有 `.bin` 目录，不补链、不安装。
6. **`.bin` shim**：ngm 不生成、不重启 `node_modules/.bin` 里的 shim，只把既有目录
   注入 PATH。shim 的来源与边界由 [ADR-043](./adr-043-vendored-bin-shim.md) 固定；
   本 ADR 与 capability matrix 都**不**宣称"已支持 shim 生成"。

### 反案门槛

上面任何一条若将来要反案，必须先**单开一份 ADR**，并同时给出两类证据，缺一不可：

- **实测收益**：在真实项目上量出的收益（例如并行把端到端耗时从 A 降到 B），
  而不是"竞品有""看起来更方便"这类直觉；
- **确定性风险**：新调度对退出码透传、失败短路、同输入同行为、离线复核带来的
  具体风险及缓解，证明它不会破坏"执行不变量"（spec §1.4）。

只写"支持"而不给这两类证据的改动，按非目标处理。`run --explain` 本身也不改变
这条纪律：它是只读计划，不授权、不执行、不写配置，文案固定为
"当前策略会拒绝/放行（未执行）"。
