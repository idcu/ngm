# ADR-044：ngm 是独立生态，npm / pnpm 只是迁移来源

- **状态**：已定（2026-11-19）
- **范围**：产品定位；影响 `ngm adopt`、`ngm run`、路线图取舍，以及"要不要为了更像 npm 而做某件事"的一类判断
- **背景**：2026-11-18 的评估报告把 ngm 的可用程度放在"一个项目能不能不用 npm"这个坐标里度量
  （§5 的六座硬山、三种项目分档）。那是一次**从 npm 视角看缺什么**的测量，读起来却像
  一份路线图：好像 ngm 的目标是把 npm 的每一格补齐。2026-11-19 维护者把定位说清楚了：
  **ngm 基本是一个独立的生态，跟 npm / pnpm 基本不会有关联。**

## 决策

1. **主轴**是"Git 依赖的可证明同一性"：声明 → commit → 内容 digest → 可离线重放 →
   可导出审计产物。任何功能先问"它让这条链更可信吗"，而不是"它让 ngm 更像 npm 吗"。
2. **npm / pnpm / Yarn / Bun 是迁移来源，不是兼容目标。** 我们不承诺它们的语义：
   registry 协议、semver 求解、peer dependencies、`node_modules` 布局、lifecycle 全族、
   publish。它们出现在 ngm 里只有两种身份：**输入**（一个项目已经长成这样，我们要能读）
   与**坡道**（帮它把 Git 依赖搬进 `ngm.json`）。
3. **`ngm adopt` 是坡道，不是主干。** 它读 npm 世界的既成事实（`node_modules` /
   `package-lock.json`），产出一份内容证明；它的存在**不**意味着 ngm 要像 npm 一样工作，
   也不构成对 pnpm / yarn 布局的长期承诺。
4. **`ngm run` 读 `package.json.scripts` 的理由是成本，不是兼容。** 项目本来就有那份文件，
   读它比要求用户抄一份便宜。承诺的契约只有 `ngm run --help` 里写下的那五条 lifecycle
   变量；`npm_execpath` 刻意不设，`npm_config_*` 不模拟——这一条从 v0.120 起没变，
   本 ADR 把它从"暂不"升级为"不打算"。
5. **路线图准入规则**：任何条目若**唯一**的理由是"这样更接近 npm"，不进路线图。
   它要进来，必须另有不依赖 npm 的理由（可证明性、离线、审计、安全边界）。

## 后果

- `docs/analysis/ngm-architecture-and-npm-gap-2026-11-18.md` §5 的缺口表降级为
  **迁移成本的观察**，不再是待办清单；报告本身保留（它回答的是"一个 npm 项目要付多少
  代价才能搬过来"，这个问题仍然有人问）。
- [ADR-043](./adr-043-vendored-bin-shim.md)（`.bin` shim 暂缓）多了一条独立支持：
  shim 模仿的正是 npm 的目录布局，属于本 ADR 第 2 条排除的那一类。
- [ADR-040](./adr-040-adopt-proof-layer.md) 的"不为 registry 条目解析来源"同样多了一条
  独立支持：那不是 ngm 的轴。
- README 里"它**不是** npm / pnpm / Yarn / Bun 的替代品"这句保留，但**理由升级**：
  不是"它只管 Git 依赖"（那听起来像功能不全），而是"它不是同类东西"。
- 评测 ngm 时的正确坐标变成：**这份依赖的内容身份能不能被独立复核**，
  而不是"npm 的哪一格还空着"。

## 重启条件

任一条出现即重新评估：

1. 出现**长期共存**诉求的用户群——不是"搬过来"，而是要求 ngm 与 npm 在同一
   `node_modules` 上共管同一批包（当前明确不接管）；
2. 需要 ngm 自己实现 registry 协议或 semver 求解才能满足一个**非迁移类**的需求
   （例如上游只发 registry、不发 Git）；
3. 产品定位正式变成"依赖的 CLI 安装器"——与 ADR-043 的重启条件 3 是同一句，
   两者必须一起改。
