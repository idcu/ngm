# ADR-018：内容寻址 store 的回收与去重

- **状态**：已定
- **日期**：2026-10-02
- **范围**：vendor 层 2（`~/.ngm/content`）。层 1（mirror）不在本 ADR 范围内——它由 `git gc` 管
- **前置**：[ADR-003 为什么纯 vendor 目录](./adr-003-vendor.md)（层 2 的契约与那份"补录"）、
  [ADR-008 archiveDigest 的定义](./adr-008-archive-digest.md)

> **结论（三句话）**：
>
> 1. **不做"按可达性自动删除"的 GC。** 它需要 ngm **没有**的东西——一份"哪些项目引用了哪些 digest"
>    的注册表；而误删的代价是把"完整性可验证"变成"可能已经被别人删掉了"。
> 2. 立刻可做的是两件**低风险**事：只读的 `ngm store usage`（体积与占用报告）与
>    `ngm store prune`（**只清半成品**，永远安全）。
> 3. 真正的长期解法是**在写入侧去重**（层 2 改为按文件内容寻址），而不是在删除侧回收——
>    它把下面那个 20× 放大从源头消掉。这需要一次存储布局变更，属**排期目标**而非本版实现。

---

## 背景：实测到了什么

v0.6 的量（`TestV06StoreGrowthInventory`，只测不做）：

| 量 | 值 |
|----|----|
| 一个 commit 的增量 | **一整棵树**（20 文件 × 8 KiB = 160.2 KiB） |
| 12 个 commit 后 | **1.88 MiB** |
| 同期源码的真实增量 | 96.0 KiB |
| 放大比 | **20.0×** |
| 同一份历史的 Git 对象库（层 1 上界） | 10.3 KiB → store 是它的 **187×** |

原因不是"没有 GC"，而是**布局**：`content/sha256/<digest>/tree/` **按整棵树**寻址
（[ADR-008](./adr-008-archive-digest.md) 的 digest 覆盖整仓）。同一仓库的每个新 commit
都完整复制一遍内容树；**唯一能省的情形是同一个 digest 再次出现**（跨项目引用同一 commit）。

两层分工因此很不对称：

| 层 | 谁负责回收 | 现状 |
|----|-----------|------|
| 1 mirror（Git 裸仓） | `git gc`（用户随时可跑） | 有出路 |
| 2 content store | **没有任何人** | **只增不减** |

---

## 三个选项

### A. 按可达性自动删除（`ngm store gc` 删"没人引用的 digest"）—— **不选**

它听起来是标准答案，但缺少一个前提：**ngm 不知道有哪些项目、也不知道它们引用了什么**。

- 项目散落在用户磁盘的任意位置，ngm 没有注册表，**也不可能去扫描整个磁盘**。
- 因此"没人引用"这个判断要么做不到，要么只能靠**猜测**（例如按时间）。
- 误删的后果不是"重新下载"这么简单：默认 `hardlink` 落地模式下，已落地的 vendor 文件
  在 store 被删后**仍读得到**（inode 还在），但 **`ngm verify` 会报层 2 缺失**。
  也就是说，另一个项目会在某个时刻**突然验不过**，而原因出现在几天前的一次 GC。
- 这正是本项目最忌讳的失败形态：**看起来成功的操作，在别处、在以后，变成一次无法解释的失败。**

> 若要重新考虑它，先要给出**可达性的来源**（项目注册表，或"GC 必须显式给出要保留的 lock 集合"），
> 以及"删错了怎么恢复"的答案。见本文末"什么条件下重新考虑"。

### B. 写入侧去重：层 2 改为**按文件内容寻址** —— **选为排期目标**

把 store 拆成"blob 池 + 树清单"：

```
content/
  sha256/<blob-sha256>        # 文件内容，只存一份
  trees/<digest>/manifest     # 路径 → blob + 模式（100644 / 100755 / 120000）
```

- **收益**：那 20× 消失。上表的实测里，12 个 commit 只改了 11 个文件，
  因此去重后新增 ≈ 源码真实增量（96 KiB 量级），而不是 1.88 MiB。
- **代价**：①存储布局变更，需要 schema 版本与**迁移/重建**路径（重建总是可行：从 mirror 重放）；
  ②`verify` 的层 2 检查与 `link` 层要改成"按 manifest 走"；
  ③digest 的定义**不变**（它仍是对整棵树的规范化哈希，[ADR-008](./adr-008-archive-digest.md) 不动）；
  ④跨项目共享的语义不变，且变得更好（共享从"整棵树"细到"每个文件"）。
- **为什么它是"真正的解法"**：GC 是"存了再删"，去重是"**不再重复存**"。
  对一个**只增不减**的存储，后者在根源上解决问题；而前者的正确性依赖一个我们没有的东西。

### C. 什么都不做，文档化安全的手工路径 —— **选为当下兜底**

`~/.ngm/content` 是**纯派生物**（层 1 的 mirror 才是权威；层 2 任何时候可从 mirror 重放）。
因此**手工整体删除是安全的**：

```
rm -rf ~/.ngm/content     # 下次 install/verify 会重建（代价：重新解包一次）
```

必须把它写进文档——用户今天就能用，而"什么都不做"如果不写下来，就等于没有出路。

---

## 决策

1. **不实现按可达性自动删除的 GC**（选项 A 不选），并把这**写成文档**：
   层 2 只增不减是已知的、有意的取舍，不是遗漏。
2. **当下提供两件低风险工具**（**v0.7 已实现**：`ngm store usage` / `ngm store prune`，
   验收见 [v0.7 计划](../development/v0.7-plan.md)）：
   - `ngm store usage`：**只读**报告（各 digest 的体积、合计、顶层占用），
     让"磁盘到底被什么占了"可回答。
   - `ngm store prune`：**只清半成品**——`Put` 的解包临时目录 `.unpack-*`
     （中断留下的残骸）。它**永远安全**：那些目录不在任何 digest 路径上。
     **它不删任何 `sha256/<digest>/`**。
3. **把选项 B 记为排期目标**：单独一个版本里做，先出布局 schema 与迁移方案，
   再改代码。它是本 ADR 里唯一能改变增长曲线的东西。
   → **schema 与迁移方案已出**：[ADR-019](./adr-019-content-addressed-blobs.md)
   （blob 池 + 树清单；**不就地迁移**；digest 定义不变）。实现仍单列一个版本。
4. **手工路径写进文档**（选项 C）：`rm -rf ~/.ngm/content` 是安全的，因为层 2 是派生物。
5. 本 ADR **不新增任何删除真实数据的代码路径**。将来若有人要加，先回到选项 A 的那两个问题。

> **修订（2026-10-03）**：[ADR-023](./adr-023-orphan-reclaim.md) 补上了决策 5 的一个**边界情形**——
> `ngm store prune --orphans` 会删除**本 store 里没有任何清单引用的** blob（带年龄门槛，
> 且在有清单读不出来时拒绝删除）。
>
> 它与本 ADR 的**不相交之处**：本 ADR 否掉的是**按可达性**删除（"这个 digest 还有没有人要"，
> 需要项目注册表），而孤儿是**由构造可判定**的（"本 store 里没人引用它"）。
> 两者是不同的问题——决策 1 与决策 5 的其余部分继续有效：
> **仍然没有任何路径会删掉"还有人要的内容"**。

---

## 什么条件下重新考虑"自动删除"

用**可证伪的条件**写：

1. 出现一份**项目注册表**（例如 `~/.ngm/projects.json`，由 `ngm install` 维护），
   且 GC 能在"注册表 + 现存 lock 文件"上判定可达性；**同时**给出"删错了怎么恢复"的答案
   （层 2 可以从 mirror 重放，因此"恢复 = 重新 install"，但**用户要能提前知道**某次删除会让谁失败）。
2. 或者：GC 只在**显式给出保留集合**时运行（`ngm store gc --keep-from ngm.lock ...`），
   把可达性判断的责任交给调用者——那时它退化成"一个带确认的删除工具"，而不是"自动回收"。

任一条成立时，本 ADR 应被**修订**而不是绕过。

---

## 后果

- **承认一条不利的对比**：pnpm 的 store **按文件**寻址，因此它天然没有这种放大；
  ngm 的层 2 按整棵树寻址，实测 20×。这条差别写进了
  [能力矩阵](../internals/capability-matrix.md)（连同"层 2 无人回收"）。
- 磁盘占用在选项 B 落地之前**会继续线性增长**；本 ADR 至少让它成为**已知的、可量化的**取舍，
  而不是"某天发现磁盘满了"。
- `ngm cache clean` 的语义不变（它清的是层 4 缓存），**不要**把它当成 store 回收——
  两者的对象不同，混淆会让人以为清过就安全了。
- v0.7 的两个小工具（`store usage` / `store prune`）**都不能减少已存的树**；
  它们的价值是"让占用可见"与"清掉残骸"，别把它们宣传成 GC。

## 补录（v0.11 / ADR-023）：层 2 有了**第一条**回收路径

上面那张"两层分工"表与"层 2 没有任何人回收"的说法，在 v0.11 之后**只对了一半**。
本 ADR 的结论没有被推翻，但边界变了：

- [ADR-023](./adr-023-orphan-reclaim.md) 落地了 `ngm store prune --orphans`：删掉
  **没有任何清单引用**的 blob（带年龄门槛，且"有清单读不出来"时拒绝删除）。
  关键洞察是 **"无人引用"由构造可判定**——引用只可能来自 `trees/` 下的清单，
  因此它**不需要**本 ADR 缺的那个项目注册表。**不同的问题，不是同一个问题的难易版本。**
- 因此本文里"没有任何人回收"应读作"**没有人按可达性回收**"：真正卡住的那件事
  （"这个 digest 还有没有人要"）**仍然没做**，选项 A/B 的修订条件一字未变。
- 表里那行"只增不减"同口径：**孤儿会被回收，被清单引用着的字节不会。**
- 顺带纠正一处会被误读的措辞：本文说"v0.7 的两个小工具都不能减少已存的树"仍然成立
  （`--orphans` 删的是 blob，不是整棵树），但那句话现在**不等于**"层 2 只增不减"。

本文不改写原文（决策记录是快照），差异以这段补录为准。
