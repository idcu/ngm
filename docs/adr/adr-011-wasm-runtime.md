# ADR-011：wasm adapter 的运行时与 ABI

- **状态**：已定
- **日期**：2026-10-01
- **范围**：`wasm` adapter 的运行时选型、模块 ABI、能力映射与失败语义

> **结论**：`wasm` adapter 基于 **wazero**（纯 Go）执行 **WASI preview1 命令模块**；输入输出
> **沿用 subprocess 协议的语义**（选项走 argv、产物走 stdout、非零退出即失败）；能力映射到 WASI
> 预开放目录，**默认全拒**；模块**内存上限可施加**。
>
> **代价**：二进制 **+5.14 MB**（实测 11.07 → 16.21 MB，**+47%**）；只支持 **WASI 兼容**的模块
> （期待 JS 宿主的 wasm 构建不在此列）；"网络天然不可达"既是优点也是限制——需要联网的引擎
> 无法以 wasm 形态出现；此外运行时本身成为**新增的信任对象**。

---

## 背景

### 为什么要有第三种 adapter

[引擎 adapter](../architecture/engine-adapter.md) 已定义三种调用方式：`subprocess`（默认）、
`wasm`（安全敏感场景）、`remote`（企业共享构建）。两者的差别不在"能不能跑"，而在**跑的时候给了什么**：

- `subprocess` 引擎是一个**操作系统进程**。它能做的远超它该做的，因此需要 ADR-012 的沙箱去收窄——
  而沙箱的收窄终究是**约束**，不是**移除**：`--deny-run` 是拒绝，不是"不存在这条系统调用"。
- wasm 模块**没有那些系统调用**。它不能派生进程、不能开套接字，因为它没有对应的导入。

也就是说：subprocess 沙箱是"允许清单"，wasm 是"没有清单可允许"。这才是 `wasm` adapter 存在的理由。

### 硬约束：发布构建不能有 cgo

`scripts/build-release.sh:46` 与 `scripts/build-release.ps1:55` 都固定 `CGO_ENABLED=0`，
六个目标（linux/darwin/windows × amd64/arm64）交叉编译出**单个静态二进制**。
因此依赖 cgo 的运行时（wasmtime-go 一类）**不可用**——这不是偏好问题，是与发布矩阵不相容。

### 已有的协议与沙箱

- subprocess 协议已定义输入方式（stdin / 文件路径 / `--config`）、输出（stdout 产物、stderr 日志）
  与退出码语义（引擎自己的退出码**不透传**）。
- ADR-012 建立了 Deno 沙箱，并留下一条**明确的未防护项**：没有内存上限（Deno 没有稳定的
  跨平台开关）。wasm 在这方面能补上——见决策 4。

### 实测前提（本 ADR 的全部论断都测过，不是查来的）

| 论断 | 实测结果 |
|------|---------|
| 纯 Go 运行时能进入发布矩阵 | wazero v1.12.0 在 `CGO_ENABLED=0` 下**六个目标全部编译通过** |
| 它真的能运行模块 | 手写一个 39 字节的 wasm 模块（`() -> i32` 返回 42），实例化并调用成功；WASI 预编译模块可实例化 |
| 依赖规模 | 共 **3 个模块**（`wazero` + `golang.org/x/sys` + 自身） |
| 体积代价 | 基线 2.23 MB → 含 wazero 7.37 MB；ngm 现值 11.07 MB → 预计 **16.21 MB（+47%）** |
| WASI 没有套接字 | 写一个导入 `wasi_snapshot_preview1.sock_open` 的模块 → 实例化被拒：`"sock_open" is not exported` |
| 能施加内存上限 | 声明 2 页内存的模块 + 1 页上限 → 实例化被拒：`min 2 pages (128 Ki) over limit of 1 pages (64 Ki)` |

## 决策

### 1. 运行时：wazero

纯 Go、无 cgo、依赖极少（实测 3 个模块）。任何依赖 cgo 的运行时与发布矩阵不相容，因此不在候选内。

### 2. ABI：WASI preview1 命令模块，且**沿用 subprocess 协议的语义**

- 选项按 argv 传入（与 subprocess 引擎相同的语义）；
- 产物写 stdout，日志写 stderr；
- 退出码 0 = 成功，非零 = 失败；运行时 trap 视同失败。

理由：让**同一个引擎能以两种形态提供而不改变契约**。为 wasm 另立一套输入输出协议，会产生
两套文档、两套测试，以及"我在 subprocess 下配的参数到了 wasm 下什么意思"这类问题。

**明确的边界**：期待 JS 宿主（`env.*` 一类导入）的 wasm 构建**不被支持**。那类模块需要一个 JS
运行时来提供服务，属 `subprocess` + node 的范畴。把这条写清楚，比让用户拿一个跑不起来的模块
去猜原因要诚实。

### 3. 能力：只映射 `read:`，其余**没有对应能力**

| ngm 权限 | wasm 下的形态 |
|---------|--------------|
| `read:<path>` | WASI 预开放目录（`--dir` 等价物） |
| `write:` | **不授予**：产物走 stdout，引擎没有写盘的需求 |
| `net:` | **不存在**：WASI preview1 没有套接字导入（已实测） |
| `run:` | **不存在**：wasm 模块无法派生进程 |
| `env:` | 默认不传入 |

因此 `wasm` adapter 在能力维度上**严格强于** subprocess 沙箱：后者靠 `--deny-run` 关掉派生，
前者**根本没有那条路**。这也意味着"需要网络的引擎不能用 wasm 形态"——那是能力的必然结果，
不是配置疏漏。

### 4. 资源：施加**内存上限**，超时沿用同一套

内存上限**要施加**（实测：超限的模块在实例化阶段就被拒绝，错误信息给出具体页数）。
这是对 ADR-012 留下的"没有内存上限"那项**部分补偿**——它只对 wasm 引擎成立，不改变 subprocess
沙箱的结论。

### 5. 默认不启用

内置清单里**不加** wasm 条目：一旦内置，它就会进入默认选择，而它需要用户自己提供模块。
用户在自己的 `ngm.engines.json` 里显式声明 `adapter: wasm` 时才生效——与 deno 引擎的处理一致。

### 6. 失败语义：不新增退出码

模块 trap / 非零退出即引擎失败，沿用现有的链式回退规则（`stub` 与不可用回退、其余不回退）。
wasm 不引入新的失败类别，因此不需要新的退出码。

## 理由

**支持点**

- 唯一"跑他人代码但不给任何进程能力"的形态：不是拒绝，而是不存在
- 内存可限（subprocess 沙箱做不到）
- **跨平台一致**：一份 wasm 模块在六个目标上行为相同，不需要为三平台各出一个产物
- 依赖规模小（3 个模块），新增信任面可控

**诚实的代价**

- **体积 +47%**（实测）。这是单二进制承诺的直接代价
- **生态小**：需要 WASI 兼容的模块；主流 JS 引擎的 wasm 构建多数不符合 ABI（决策 2 的边界）
- **"没有网络"是限制**：任何需要联网的引擎都无法以 wasm 形态出现
- **运行时成为新的信任对象**：wazero 自身若有缺陷，沙箱的性质就变了。它比大多数依赖树小，
  但"小"不等于"没有"
- 体积若日后成为障碍，退路是 build tag（只对需要的人编入），代价是**发布产物翻倍**——
  本 ADR 选择先接受体积，把这条件为**退路**而不是默认

---

## 后果

- 引擎清单新增 `adapter: wasm`，`ngm engines validate` 必须覆盖它（当前该 adapter 报"未实现"）
- 实现时 **ADR-012 的权限判定是唯一入口**：wasm adapter 不新造权限语言，只把 `read:` 映射成
  预开放目录
- `remote` adapter 不在本 ADR 范围内，它需要 **ADR-013**（信任边界：发给谁、如何证明未被替换、
  失败不静默降级）；**答不上来就不发布**
- 本 ADR 的论断都有实测支撑；实现阶段若要偏离（例如换运行时），必须先修订本 ADR
