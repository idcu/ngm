# ADR-014：依赖自述的签名检查

- **状态**：已定
- **日期**：2026-10-01
- **范围**：沙箱（ADR-012）中"依赖自述"的处理；身份与出处的信任边界

> **结论**：**不发布"自述文件签名检查"，也不发明签名格式**。
> 给一个 ngm 已明确声明**不解析、不采信**的自述加签名，只会把"未经验证的声明"
> 包装成"看起来经过验证的声明"——比不加更糟。而"这份代码出自谁手"这个问题，
> 在**更低、且已标准化**的层次上有答案：钉住 commit（[ADR-004](./adr-004-reftype.md)）
> 加 digest（[ADR-008](./adr-008-archive-digest.md)），身份则由 **Git 自己的签名机制**
> （signed commit / tag）回答——那需要用户自己的密钥信任配置，而不是 ngm 发明一套。
>
> **代价**：v0.3 计划里最后一个未打勾的框以"**决定不做**"结项。若用户确实需要
> "维护者身份"的可证明性，ngm 现在**没有任何原生答案**——只能用 Git 自己的工具
> （`git verify-commit` / `verify-tag`）手工做。这一点写清楚，不假装已经覆盖。

---

## 背景

v0.3 的 C 组把"依赖自带的脚本"放进沙箱执行，其中一类是**自述**：依赖根目录下的
`verify.js`，由**依赖作者**编写、随依赖进入 vendor，因此**不可信**
（[ADR-012](./adr-012-sandbox.md) 决策 2）。

[ADR-012](./adr-012-sandbox.md) 决策 4 已经定下它的处理方式，且相当克制：

- 脚本**只能否决**：退出码非 0 / 超时 / 崩溃 → verify 失败（`exit 2`）；
- 退出码 0 → 只记为"该依赖自证通过"，**不改变 ngm 自己的任何结论**；
- stdout / stderr 原样展示，带上"**来自依赖的自述，未经 ngm 验证**"的标注，
  **不解析、不采信**。

同一决策里留了一句"自述文件签名检查仍待实现"，并注明它还要**先定签名格式与密钥管理**。
v0.3 复盘把它列为唯一未结项，理由是"没有那两样就实现，只会做出一个看起来验过了的检查"。
本 ADR 把它结掉——结论是那道门不该开。

---

## 三个必须先回答的问题

### 1. 签什么 —— 答案决定了这件事有没有意义

候选有三个，逐个看：

| 签什么 | 它证明什么 | 有没有用 |
|--------|-----------|---------|
| **签脚本本身**（`verify.js` 的字节） | "这段脚本是某人写的" | **没有**。脚本随依赖进入 vendor，而 vendor 的字节已经由 commit + digest 钉住（ADR-004 / ADR-008）。签名是**冗余的**：能改脚本的攻击者，同样能改签名所处的那个 commit |
| **签脚本的输出** | "这句话是某人说的" | **没有，而且有害**。输出是运行时的、依赖本机环境的（见下） |
| **签一份关于外部事实的声明**（例如"某 URL 的内容 digest 是 X"） | "该维护者认可这个仓库之外的事实" | **这是唯一可能有用的形态**——但它属于另一个能力（引进并核验外部产物），不是本 ADR 要发明的格式 |

第二种值得展开，因为它是这个名字（"自述文件签名"）最自然的读法：

- 脚本输出**随运行环境变化**（时间、文件系统、已装工具）。同一个 commit 在两台机器上
  可以产出不同输出，因此"签输出"不能是一个稳定的格式——除非把输出定义成可复现的产物，
  而那要求先解决可复现构建（[ADR-013](./adr-013-remote-adapter.md) 已论证这件事在
  JS 生态里还不是既有能力）。
- 更根本的是：ngm **刻意不解析**这段输出（ADR-012 决策 4）。既然不采信，那么给它加签名
  就只是让它**看起来**更可信 ✗。一个加了签名的、仍不被采信的声明，与一个不加签名的、
  仍不被采信的声明，在 ngm 的结论里**完全相同**——唯一的差别是用户更容易误以为前者可信。
  这是把"看起来更安全"当成了"更安全"。

### 2. 密钥从哪来 —— 一整套要发明的东西

签名要可用，就得回答：公钥怎么分发、怎么更新、怎么吊销、过期了怎么办、用户怎么表达
"我信任这把钥匙"。

- **放在依赖仓库里**是循环论证：能改依赖的人就能换公钥。
- **放在 ngm 侧**意味着 ngm 要发明并运营一套密钥分发与轮换机制——这是一个**独立的
  大型主题**，而它解决的问题（"这份代码是否出自某个身份"）在更低层已经有标准答案。
- **交给用户配置**是唯一站得住的形态（信任是用户的决定，不是工具替用户做的），
  但那样一来，真正干活的是**用户已有的密钥信任配置**——即 Git 的签名机制，
  而不是 ngm 自定义的一套。

### 3. 验过了之后呢 —— 这是决定性的一问

即使前两问都被硬答上，还要问：**一次通过的签名检查，能让 ngm 的结论改变什么吗？**

不能。原因与 [ADR-013](./adr-013-remote-adapter.md) 第 2 问同构：**签名证明"谁说的"，
不证明"说的是真的"**。一把保管良好的钥匙照样能签出一个错误的、或恶意的自述。因此：

- 签名通过 **也不能**让 ngm 采信那段输出（决策 4 不变）；
- 签名失败 **能**让 verify 失败（这是唯一确定的效果）。

那么它实际提供的，是"要求这个依赖的自述由我所认可的身份签发"这一个门槛。而这个门槛
在**已经存在的一层**上更完整：要求 **signed commit / tag**。区别在于后者认证的是
**整份代码**，而不只是一段自述，且不需要 ngm 发明任何格式。

---

## 决策

1. **不实现"自述文件签名检查"**，也不定义任何自定义签名格式。
   `verify.js` 的处理维持 ADR-012 决策 4：只能否决、输出原样展示、明确标注未经验证。
2. **身份问题交回 Git**。用户若要"这份代码确实出自某个身份"，正解是要求
   signed commit / tag，用**用户自己的**信任配置（GPG keyring / `gpg.ssh.allowedSignersFile`）
   去验——那是标准、可互换、无需 ngm 发明任何东西的机制。
3. **ngm 侧只做"消费"，不做"发明"**：`ngm verify` 报告 Git 的签名状态
   （`--signatures` / `--require-signed`），判定交给**用户自己的**密钥配置。
   这属于"把已有控制点收束进同一条流程"，正是本项目声称要做的事
   （[README](../README.md) §"为什么不是又一个包管理器"）。

   **已实现（2026-10-01，v0.4）**，三条纪律写进了实现与文档：

   - **未签名默认不是失败**：绝大多数依赖没有签名，把它当错误会让 verify 对所有人变红——
     那是假警报，而假警报会让真的警报失效。要门槛的人自己开 `--require-signed`（exit 2）。
   - 判定用用户自己的配置；ngm 不管理、不分发密钥，也不发明格式。
   - 默认**不查**（每个依赖一到两次 git 子进程，而 verify 的主要成本就是 spawn）；
     与 `ngm tree --osv` 同一个先例：额外的成本必须由用户显式要求。

   覆盖范围是**锁定 commit 的签名**；commit 未签且声明是 tag 时，再看那个 tag 的签名
   ——多数项目只签 tag，不签每个 commit，只看 commit 会把它们一律误报成"没签名"。
   判定用 Git 的机器可读状态（commit 的 `%G?`）；tag 没有对应的状态码，
   因此"无效"与"无法确认"的分界依赖 git 的措辞——它只影响分类粒度，
   不影响"通过/不通过"（后者由退出码决定）。
4. **文档定位保持不变**：竞品对照表已写明 npm 的 signature / provenance 是它的标准答案、
   ngm 不重复造。本 ADR 与该定位一致，而不是绕开它。

## 什么条件下可以重新考虑

用可证伪的条件写，而不是"将来再看"：

1. **出现一个跨生态、有既定格式的"依赖自述"签名标准**（像 SBOM 的 SPDX / CycloneDX 那样
   有公认格式），且它能表达"对**仓库之外**的事实的认可"——那时 ngm 应当**实现该标准**，
   而不是发明自己的。注意条件里要求的是**标准**，不是"有签名的做法"。
2. **可复现构建成为既有能力**（同 [ADR-013](./adr-013-remote-adapter.md) 的翻案条件），
   使"自述的输出"成为一个可复现、可比对的对象——那时"签输出"才有稳定的格式可言。

任一条成立时，本 ADR 应被修订而非悄悄绕过。

---

## 后果

- **v0.3 计划里最后一个未打勾的框以"决定不做"结项**，而不是留一个永远不做的待办。
  这是本项目第二次这样做（第一次是 [ADR-013](./adr-013-remote-adapter.md) 的 remote adapter），
  而且两次的论证结构是同一个：**能证明"谁说的"，不等于能证明"说的是真的"**。
- **不新增任何密钥管理代码**：没有实现，就没有"半实现的密钥分发"这类东西可被误用。
- **用户的期望要写清**：ngm 不提供维护者身份的可证明性。需要的人用 Git 自己的工具，
  而这条限制写在这一页，不在别处含糊过去。
- **决策 3 已实现**：`ngm verify --signatures` / `--require-signed`。它不发明格式、
  不管理密钥，只是把 Git 已有的判定搬进 ngm 的结论里——**没有原生身份答案**这个缺口
  因此被补上，而补的方式是"消费标准"，不是"又造一套"。
