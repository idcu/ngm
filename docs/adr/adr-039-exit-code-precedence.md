# ADR-039：`verify` 退出码 2 压过 4（已确证的篡改 > 没查成）

## 结论

`ngm verify` 同时存在"完整性失败"（码 2）与"操作性失败"（码 4）时，**退 2**。
反过来（4 优先）在 v0.105 之前成立，现已推翻。

## 背景

`internal/core/verify/report.go` 的 `ExitCode()` 原来写的是：

```go
if d.Err != "" {
    hasOperational = true
    continue          // ← 这一句把该依赖的 DriftKind 整块丢掉了
}
switch d.DriftKind { ... }
```

配合"4 优先于 2"的判定顺序，产生两个后果：

1. **同一依赖**可以同时满足两件事：`checkLanding` 已确证 vendor 与内容库不一致
   （`DriftCritical`），而 `checkRef` 撞上网络失败（`Err` 非空）。这时 critical 被丢弃。
2. 即使分属不同依赖，"已证明被篡改"也会被"另有一个依赖没查完"覆盖。

## 为什么原来的理由不成立

原注释的理由是：**"不完整的校验不得被读作完整性结论"**。

这条理由排除的是 `0`（全部匹配）与 `1`（策略漂移），**不包括 `2`**。
而 `4` 的语义按 `observability.md` 是"Git/网络失败，含 `--offline` 资源缺失"——
那是**可重试**的信号。于是 CI 的真实行为是：

> 发现整棵树已被篡改 → 报"资源缺失" → 重试 → 再报 → 直到超时，
> 而**构建从未被阻断过**。

对一个以"可证明"为卖点的工具，这是最坏的一类错误：结论正确，处置相反。

## 后果

- `2` 现在是最高优先级；`4` 退居其次。两者都**不是**"通过"，所以原理由的意图
  仍然被满足。
- 判据：`TestV66ExitCodePrecedence` 增加一格"同一依赖既有 Err 又有 critical ⇒ 2"，
  并把跨依赖那一格的期望从 4 改成 2（改期望时写明了为什么——判据变红时
  要先分清"产品退步"与"说法变好"）。
- `--allow-drift` 对 `2` 依然无效（不变）。

## 代价

- 一个**真有网络故障**、同时又有一个依赖被篡改的项目，现在拿到 2 而不是 4。
  处置上的差别是"先看被篡改的那一个"——这是想要的顺序，因为它是唯一
  禁止构建的信号。
- 码 4 的"可重试"语义在多依赖场景下变窄：只有当**没有任何**已确证 critical 时，
  4 才代表"再来一次可能就好"。
