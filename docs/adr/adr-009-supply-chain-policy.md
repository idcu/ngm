# ADR-009：供应链策略的执行时机与失败语义

- **状态**：已定
- **日期**：2026-09-29
- **范围**：`supplyChain` 策略字段的校验、执行时机、作用域与失败语义

> **结论**：策略在**解析阶段**执行，对**传递依赖同样生效**；命中拒绝即 `exit 3`，
> 并输出从根到违规节点的**完整来源链**。v0.2 **不引入执行依赖脚本的入口**——
> `postInstallPolicy` 只被记录与报告，ngm 在执行层面始终不跑依赖脚本。
> **代价**：白名单需持续维护（漏配会直接阻断安装）；来源链要求依赖图携带节点身份（见「后果」）；
> `prompt` / `allow` 在 v0.2 属于"声明了但不会执行"，我们选择把它讲明白，而不是静默照做。

---

## 背景

v0.1 只**解析与校验** `supplyChain` 字段（`internal/config/validate.go` 里仅 `postInstallPolicy` 有取值校验），
这些字段不参与任何门禁。这带来一个真实的误读风险：用户写下 `minimumReleaseAge: "P30D"`，
会以为自己已经受保护——而我们**最不愿看到的就是这种误读**。

v0.2 要让字段真正生效，就必须先回答四个问题：

1. **何时执行**——解析阶段，还是安装完成之后？
2. **作用域**——只查根声明，还是也查传递依赖？
3. **失败长什么样**——什么退出码？能不能看出是谁把违规依赖引进来的？
4. **postinstall 到底做不做**——这是整个安全模型里最敏感的一块。

---

## 决策

1. **执行时机：解析阶段。** 白名单判定发生在 `resolve` 的图遍历中，且早于"解析 ref → commit"。
   理由：解析会访问远端；不该为了一个**必然被拒**的依赖去触碰网络。

   **唯一例外是 `minimumReleaseAge`**：它的时间源是 commit 的 committer date，
   只有拿到 commit 才判得出提交时间，因此必须在解析**之后**执行。
   它是唯一一个"先触网再判定"的门禁——这个代价要写清，
   免得后来的人以为"所有策略都不碰网络"，从而误判它在 `--offline` 下的语义。

2. **作用域：根声明与传递依赖一视同仁。** 传递依赖是投毒的主要入口——只看根声明等于没看。

3. **失败语义：`exit 3`（配置/策略错误）+ 完整来源链**（root → … → 违规节点）。
   只报"某依赖不被允许"而不说"谁把它引进来的"，使用者无法处置。

4. **匹配语义**：
   - `allowedGitHosts`：host **精确匹配、大小写不敏感**；非空即构成硬门禁。
   - `allowlistRepos`：对 `host/org/repo` 做 glob，`*` **不跨 `/`**（所以 `github.com/my-org/*` 表示该 org 下的仓库），
     跨层用 `**`；非空即构成硬门禁。
   - 两者同时非空时为 **AND**（都要通过）。

5. **`postInstallPolicy`：v0.2 收窄为"不执行"。**
   - `deny`（默认）= 当前实际行为；
   - `prompt` / `allow` **只记录判定结果**，并在 `ngm install` / `ngm audit` 输出中明确说明
     "该策略在 v0.2 不会导致依赖脚本被执行"。

   这是**对 v0.2 计划的一次主动收窄**（计划原写"在显式开启时提供受控执行入口"）。
   理由：执行依赖脚本是整个安全模型里唯一"运行他人代码"的能力，它需要沙箱作为前置
   （v0.3 的 Deno 权限模型 + `~/.ngm/config.json` 权限门禁）。在没有沙箱时先开一个执行入口，
   等于把最危险的能力放在最没有约束的时刻引入。

   6. **`verifyOnLock` 的失败语义**（2026-09-30 补录，实现时确立）：

    `ngm install` / `ngm update` 完成后，若该字段为真，自动跑一遍 `ngm verify`，
    **结论按 `verify` 自己的退出码返回**（`1` 漂移 / `2` 完整性 / `4` 网络），

    - **不折成 `0`**：把"装好了，但锁定的 ref 已指向别处"报成成功，这条策略就没有意义；
    - **也不套用本 ADR 决策 3 的 `exit 3`**：那条针对的是"配置或策略本身非法"（纯本地判定），
      而这里报告的是**内容与声明是否一致**，两者是不同的失败类别，混用会让 CI 无法区分
      "配置写错了"与"上游动了"；
    - **不撤回** install/update 已写下的内容：它是"之后"的独立复查，不是回滚。

    **无默认值**（未配置即不触发）：自动复查要重新解析每个 ref（100 依赖约 3 秒且需网络），
    默认替所有用户付这个代价不是好交易。

    > 本条为补录：ADR-009 的范围已包含"策略字段的…失败语义"，但起草时 `verifyOnLock`
    > 尚未实现，故其语义当时未写下。补录而非另立 ADR，是为了让"策略失败语义"只有一处定义。

---

## 理由

**支持点**

- 解析阶段执行让策略与网络解耦：策略拒绝是**纯本地判定**，不依赖远端可达
- 覆盖传递依赖，才真正覆盖投毒的常见路径（上游被投毒 → 你间接装上）
- 来源链把"策略失败"从一条错误变成一条**可处置的信息**
- 不在 v0.2 引入执行入口，使 v0.2 的信任面**保持不变**：v0.2 不新增任何"运行他人代码"的路径

**诚实的代价**

- **漏配即阻断**：白名单是硬门禁，配置不当会让正常依赖装不上——因此 Hint 必须给出可操作的修复建议
- **来源链要求图携带身份**：`resolve.Node.RequiredBy` 目前记录**依赖名**，而 monorepo 子路径下名字不唯一
  （节点身份是 `name#subPath`）。要输出无歧义的来源链，需让 frontier 记录 **Key**
- **`prompt` / `allow` 存在"名不副实"**：配置 `allow` 的人会期待脚本被执行，而 v0.2 不执行。
  我们选择在输出里明说，而不是静默照做——但这仍是一种语义落差，要等 v0.3 沙箱到位才消除
- **`minimumReleaseAge` 的时间源不可信**：committer date 由提交者控制，可被回填
  （见[供应链防护 · 时间源与局限](../architecture/supply-chain.md)）

---

## 后果

- 新增 `internal/supplychain/`：`policy.go`（加载与判定）、`allowlist.go`（host / repo 匹配）
- `internal/config/validate.go` 的 `SupplyChainConfig.Validate()` 由"仅 `postInstallPolicy`"扩展为
  **六个字段全校验**（含 ISO 8601 duration、host 形态、severity 取值）
- `resolve` 的 frontier 需携带节点 **Key**（而非仅 `Name`），否则来源链在 monorepo 场景会指错节点
- `ngm install` / `ngm update` 可能在解析阶段即以 `exit 3` + 来源链失败
- 将来若要为 `prompt` / `allow` 提供执行入口，**必须先有沙箱 ADR**（v0.3），并修订本 ADR
