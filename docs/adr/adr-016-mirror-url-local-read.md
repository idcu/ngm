# ADR-016：取 mirror 的远端地址——先读 config 文件，形状不认识才起 git

> **状态**：已定（v0.5 A4 组）。与 [ADR-015](./adr-015-commit-ref-resolution.md) 同一个轴：
> **不要为自己手里已有的东西付一次子进程**。ADR-015 处理"不需要问"的 ref，
> 本条处理"不需要问 git"的那个值。

---

## 背景

在线 verify 里，每个 tag / branch 型依赖都要先知道**去问哪个远端**。ngm 的答案是
"问 mirror 自己"——它的 `remote.origin.url` 就是当初 clone 时用的地址
（可能被改写、可能是本地路径、可能带凭证，因此**不能**从项目的 slug 推出来）。

取这个值的实现是：

```go
git -C <mirror> config --get remote.origin.url
```

**实测 30.6 ms/次**（本机，裸仓库）。在 100 依赖的在线 verify 里这是每个依赖一次，
按 ADR-015 的成本表约占**每依赖 spawn 成本的 17%**。

而这个值就明文写在 mirror 的 `config` 里：

```
[remote "origin"]
	url = https://github.com/org/repo.git
	fetch = +refs/*:refs/*
	mirror = true
```

那份文件是 **git 自己写的**——ngm 从不改写 origin（全仓没有 `remote set-url`）。

---

## 决策

`git.MirrorRemoteURL` 改为**先直接读 `<mirror>/config`**，只在"这份 config 的形状
不在我们敢解读的范围内"时回退到 `git config --get`。

**回退是这套设计的一部分，不是兜底**：函数签名是
`MirrorRemoteURLLocal(path) (url string, ok bool)`，`ok=false` 只意味着"这次没省下那 30ms"。
**返回 false 永远是安全的**；返回一个错的地址才是灾难——它会安静地对着另一个仓库解析 ref，
而结果看起来完全正常。

### 只接受这些形状（其余一律回退）

| 形状 | 处置 | 理由 |
|------|------|------|
| `[include]` / `[includeIf ...]` | 拒绝 | git 会展开它们，我们不会——两边的答案会不同 |
| `[extensions]` | 拒绝 | `extensions.worktreeConfig` 会让 git 再读 `config.worktree` |
| `[remote.origin]`（旧式点号） | 拒绝 | 与 `[remote "origin"]` 在 git 里等价，只认一种就可能与取值顺序不一致 |
| `[remote "Origin"]` | 拒绝 | 子段大小写语义交回 git |
| 同一段里多个 `url` | 拒绝 | `--get` 取最后一个，那条 tie-break 是 git 的 |
| 值带引号 | 拒绝 | 引号内是 git 的转义规则 |
| 值含 `#` / `;` | 拒绝 | 无法区分"注释开始"与"值的一部分" |
| 值里有 `\\` 之外的转义 | 拒绝 | 那是我们没复刻的规则 |

### 一处**只有实测才会知道**的细节

Windows 本地路径 URL：git 写进 config 的是

```
	url = C:\\Users\\me\\repo.git
```

**没有引号，但反斜杠成对**；而 `git config --get` 回来的是 `C:\Users\me\repo.git`。

第一版实现原样返回文件里的文本，于是与 git **不一致**——一个"看起来合理但相反"的地址。
它被 `TestMirrorRemoteURLLocal_NeverDisagreesWithGit` 当场抓住
（这正是那条断言存在的理由）。现在只实现 `\\` → `\` 一种还原，其余转义一律回退。

---

## 理由

**1. 读一个文件不需要"执行"任何东西。** 顺带说清一件与权限有关的事：
`CheckRunAccess`（`internal/git/remoteurl.go`）当初存在，
正是因为"判定去哪"要跑一次 git。走快路径时**没有任何进程被执行**，
因此不涉及 `run:git`；被 `deny run:git` 拒绝的配置不会因此得到别的结论——
verify 后续仍需要 git（`ls-remote` / `ls-tree`），那里照样会被拒。

**2. 保守回退把这个改动的风险压到"零收益"这一档。** 最坏情况是每次都回退（等于没做），
不存在"答错"的路径——**只要拒绝的条件比接受的条件宽松**。测试里刻意放了几类
"看起来能解析但必须拒绝"的形态（include / 多值 / 引号 / 旧式点号 / extensions）。

**3. 它可被两件仪器同时钉住**：
`git.SpawnCount()`（tag 型从 4.00 → **3.00** 次/依赖，与机器状态无关）
与 `TestV05RefResolutionSpawns`（tag 型**恰好 1 次** spawn——多了就说明配置又被拿去问 git 了）。

---

## 实测结果（2026-10-01，本机 Windows 10 / 8 逻辑核）

### 子进程次数（与机器状态无关的那一半）

| 形态 | 改动前 | 改动后 |
|------|--------|--------|
| commit 型（ADR-015） | 3.00 次/依赖 | **2.00** |
| tag / branch 型（本条） | 4.00 次/依赖 | **3.00** |

### 100 依赖在线 verify：**受控 A/B**（同一天、同一台机器、交替采样）

| | 5 次采样 | 中位 | 最大 |
|---|---------|------|------|
| 对照组（临时关闭快路径） | 2.355 / 2.364 / 2.416 / 2.427 / 2.433s | 2.416s | 2.433s |
| 实验组（快路径生效） | 1.752 / 1.910 / 1.969 / 2.065 / 2.078s | **1.969s** | **2.078s** |
| | | **−18%** | **−15%** |

### ⚠️ 一个必须写下来的观察：机器状态的影响**大于**这次优化

v0.5 复核里那三次采样是 2.201 / 2.556 / 3.068s（最大 **超过** 3s 目标）。
今天在**同一台机器**上，对照组（即"没做这次优化"的状态）最大只有 2.433s——
也就是说 3.068s 那次**没有**被这次改动解释掉，它是**另一件事**（当时的机器状态）。

因此结论要分开写：

1. **这次改动确实快了 15–18%**（受控对照，数字可信）。
2. **但"贴着 3s 线"这个问题不完全是取数策略造成的**——跨机器状态的方差比这次收益更大。
   今后比较性能，**次数优先于秒数**：`git.SpawnCount()` 不受机器状态影响，
   而秒数会（同一份代码在今天的两次采样相差 0.3s）。

---

## 后果

**正面**

- 每个 tag / branch 依赖少一次 spawn；`Mirror.Ensure` 那条路径同样受益（同一个函数）。
- `TestMirrorRemoteURLLocal_*` 三条断言覆盖面明确：**永不答错** / **常见形状确实走快路径**
  （防"回退总是被触发导致零收益"）/ **不敢承诺的一律回退**。

**负面 / 代价**

- 仓库里多了一份"git config 的极小子集解析器"。它必须**一直**保持"只接受能证明的形状"，
  否则就会从"快路径"变成"另一个答案"。新增接受条件时必须同时补一条等价性夹具。
- 判断条件比读文件本身更复杂——这是刻意的：**复杂度放在拒绝上，不放在解释上**。
