# ADR-012：沙箱与执行边界

- **状态**：已定
- **日期**：2026-10-01
- **范围**：`ngm verify --sandbox`、依赖自带校验脚本的执行、`postInstallPolicy` 的执行入口（ADR-009 决策 5 的前置）

> **结论**：需要运行**他人的代码**时，一律在 **Deno 子进程**里运行，并且权限**从 ngm 自己的权限词表一对一映射**过去、
> 默认全拒（无网络、无 `run`、无环境变量、只能读该依赖自己的 vendor 子树）。缺失 Deno 时 `exit 5`，**不降级**为
> 非沙箱执行。沙箱里跑出来的东西**只能否决、不能证明**：脚本失败会让 verify 失败，脚本成功不会让 ngm 改变任何
> 自己的判定。
>
> **代价**：Deno 成为一个可选但**硬性**的运行时依赖（用 `--sandbox` 就必须装，没装就报错而不是回退）；
> 依赖作者要写校验脚本才能享受自证；而"沙箱不是银弹"——它约束的是 Deno 进程，原生扩展之类的东西仍可能逃逸。

---

## 背景

### 为什么要这篇 ADR

[ADR-009](./adr-009-supply-chain-policy.md) 决策 5 定下一条前置约束：**先有"沙箱与执行边界"的 ADR，
才谈 `postInstallPolicy` 的执行入口**。理由是这条能力在项目里独一无二——它是**唯一"运行他人代码"**的地方：

- 其他所有能力都在"读别人的数据"：解析清单、校验 digest、查 OSV。读错了最坏是判断错——**不执行任何东西**。
- 沙箱要跑的是**依赖自带的脚本**：一段由**不受信任的第三方**写、并且**随依赖一起被拉进来**的代码。
  它的作者可能被投毒，而项目里没有任何机制能"证明"它无害。

v0.2 因此把 postinstall 的**执行入口**收窄到 v0.3（见 [P3](../modules/p3-supplychain.md)），
本 ADR 就是那道闸。

### 已有的约束与素材

- **权限模型（v0.3 D 组已实现）**：五个命名空间（`read:` / `write:` / `net:` / `run:` / `env:`）、
  三档默认（允许 / 需配置 / 默认禁止）、deny 优先、精确匹配。沙箱不需要新的权限语言——
  它需要的是把这些词表**翻译成 Deno 的 flag**。
- **不静默降级**是项目的一贯纪律：引擎缺失 `exit 5`、`--offline` 下取不到资源 `exit 4`——
  都不会"换个方式糊过去"。沙箱同理：安全语义不允许隐式降级（[安全模型](../architecture/security-model.md)）。
- **退出码即策略**：`2`（完整性失败）**必须**阻断构建，`--allow-drift` 对它无效。这一条决定了沙箱失败该用哪个码。

### 面临的问题

1. 沙箱里跑什么、谁决定跑不跑？
2. 脚本的输出算什么？如果它说"我检查过了，没问题"，ngm 能不能转述？
3. 权限怎么给？默认给什么？
4. 脚本卡住 / 吃满内存怎么办？
5. 没有 Deno 的机器上会发生什么？

---

## 决策

### 1. 执行体是 Deno 子进程，决策权留在 Go

core Go 做全部判定（哪些 ref 漂了、digest 是否匹配、哪些检查通过），Deno **只执行**被交给它的那一个脚本。
ngm 从不把沙箱的输出当成自己的结论来源。

### 2. 沙箱里跑什么：依赖自带的校验脚本

- 依赖根目录下的 `verify.js`（若提供）。它由**依赖作者**编写，随依赖进入 vendor，因此**不可信**。
- 同时保留安全模型里列的另外两种用途（自述文件签名检查、用户自定义 audit hook），它们**遵循同一套权限映射**。

**执行是 opt-in**：不带 `--sandbox` 时，`verify.js` 存在也不会被执行。是否需要为"执行依赖脚本"再加一层
`supplyChain` 开关，留到实现 postinstall 执行入口时一并决定——那时用户第一次有"我要跑它"的动机。

### 3. 权限映射：一对一，默认全拒

| ngm 权限 | Deno flag |
|---------|-----------|
| `read:<path>` | `--allow-read=<path>` |
| `net:<host>` | `--allow-net=<host>` |
| `run:<exe>` | `--allow-run=<exe>` |
| `env:<NAME>` | `--allow-env=<NAME>` |
| 未授权的一切 | 显式 `--deny-*` |

**默认授予的只有两样**：该依赖自己的 vendor 子树（只读）与脚本文件本身。
因此 `~/.ssh`、`~/.git-credentials`、网络、子进程**默认全部不可达**——不是靠 ngm 去黑名单它们，
而是靠"没有开过读权限"这件事本身。

显式写 `--deny-*` 而不是依赖 Deno 的 default-deny：真正的 flag 列表是可审计的，
而"它默认应该是拒绝的"是一句需要读者相信的话。

### 4. 脚本只能否决，不能证明

- 退出码非 0 / 超时 / 崩溃 → **verify 失败**，`exit 2`（完整性/信任类，`--allow-drift` 无效）。
- 退出码 0 → 记为"该依赖自证通过"，**不改变** ngm 自己的任何结论。
- stdout / stderr 原样展示（带上"来自依赖的自述，未经 ngm 验证"的标注），**不解析、不采信**。

如果一个脚本能通过输出让 ngm 认为"这个 digest 没问题"，那么投毒者只需要写一段脚本——
沙箱就成了一个更体面的 `curl | sh`。

### 5. 超时与资源

- **超时**：默认 30 秒，超时即失败（`exit 2`），并明确告知是超时而不是脚本报错。
- **内存 / CPU 上限**：**不施加**。Deno 没有稳定的跨平台资源限制开关，而用 `--max-old-space-size` 之类的
  近似手段会给人一种"已经限制住了"的错觉。这是本 ADR 明确记录的**未防护项**：`--sandbox` 不是
  "跑不可信代码也安全"的开关，它是"把爆炸半径限制在文件系统与网络两个维度"的开关。

### 6. 没有 Deno 的机器

`exit 5` + 安装提示，**不降级**。默认的 `ngm verify`（不带 `--sandbox`）不依赖 Deno，行为不变。

**限定条件（实现阶段补充）**：只有在**确有脚本要跑**时才要求 Deno。一个依赖都没提供 `verify.js` 时，
`--sandbox` 没有任何东西可执行——此时报"沙箱不可用"是一句与事实不符的话，因此改为明说
"没有依赖提供脚本"。这条细化只在减少误报，不改变"绝不非沙箱执行"的约束。

Deno 版本门槛**按能力判定，不按版本号**：需要目录级的 `--allow-read=<path>` 与一组 `--deny-*` flag。
启动时做一次能力探测，探测不到就 `exit 5` 并说明缺什么。

> **实测（Deno 1.45.2，Windows）**：`--allow-read=<dir>` 生效；读取允许目录之外的文件被
> `PermissionDenied` 拦下；网络默认不可达；`--deny-net --deny-run --deny-env --deny-write` 被接受。
> 写死一个版本号会在**能跑的版本上拒绝运行**（1.45 完全够用），也会在不能跑的版本上放行——
> 而"能不能跑"本来就该由探测回答。
>
> 探测**用真实的脚本文件**，不用内联表达式：`deno run` 并不接受 `-e`（那是 `deno eval` 的形式），
> 而沙箱真正要走的路径就是"跑一个脚本文件"。第一版探测正是写成了 `-e`，于是在完全够用的
> 1.45.2 上判定"不支持"，把整个功能挡在门外——探测用别的形式，等于探测了另一件事。

### 7. 与默认 verify 的关系

`--sandbox` **只追加**"依赖自检"这一层，不改变任何既有判定：同一份漂移结论、同一份 digest 结论。
验收里要明确钉住这一点（对象相同、权限不同）：同一个项目上两次 verify 的**判定对象**必须一致，
差异只应出现在"额外执行了什么"。

---

## 理由

- **为什么必须是子进程**：权限边界只能画在进程边界上。在同一进程里"限制"一段 JS，靠的是解释器没有漏洞——
  那是把安全押在别人的实现上。
- **为什么用 Deno 而不是 Node**：Deno 原生带 default-deny 的权限模型（ADR-007 也记录了这一点），
  Node 要走 `--experimental-permission` 且语义仍在变。这是**唯一**一个工具选型由安全语义决定的场合。
- **为什么权限从 ngm 词表映射而不是另起一套**：D 组的词表已经是用户要理解的那一套东西。
  沙箱再引入一套"沙箱专用"的权限名，等于让用户在两处配置同一件事，而它们迟早会不一致。
- **代价（诚实部分）**：
  1. Deno 变成硬依赖（仅对 `--sandbox`）；
  2. 依赖作者的校验脚本质量参差，而"自证通过"很容易被**误读**成"这个包是安全的"——文档必须反复说它不是；
  3. 资源上限缺位（见决策 5），恶意脚本仍能让一次 CI 变慢甚至 OOM；
  4. 沙箱约束不了 Deno 之外的逃逸路径（原生扩展、内核漏洞），这是"降低风险"而非"消除风险"。

---

## 后果

- `ngm verify --sandbox` 的实现必须**先**有 `internal/security` 的权限判定（已完成，D 组），
  沙箱**不新造**权限语言。
- 本 ADR 定稿即满足 ADR-009 决策 5 对**沙箱 ADR** 的前置要求；但 `postInstallPolicy` 的**执行入口**
  仍是独立的一步实现——届时需要**修订 ADR-009**（把"收窄到 v0.3"改成"已具备前置条件"并写明入口形态）。
- 退出码语义新增一条明确归属：**依赖自检失败 = `2`**，与 digest 不匹配同级——两者都是
  "这份代码没有通过它自己声称的检查"，而 `--allow-drift` 对它们都无效。
- `--sandbox` 不得改变默认 verify 的判定对象；这条要由测试固定，否则"沙箱只是多跑了一层"就会退化成一句口号。
