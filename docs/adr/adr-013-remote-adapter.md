# ADR-013：remote adapter 的信任边界

- **状态**：已定
- **日期**：2026-10-01
- **范围**：引擎 adapter 模型（`remote`）；供应链信任边界

> **结论**：**不发布** `remote` adapter。它要求把源码送出本机，而由此产生的核心问题——
> **产物无法由用户在本机证明**——不是工程问题，是立场问题。`adapter: remote` 在清单语法里
> 仍然合法并被识别，但**永远不会执行**：声明它的条目会被明确报为"本 build 不支持，且这是
> 一个决定"，并指向本 ADR。
>
> **代价**：v0.3 计划里承诺过的一项能力**不再交付**。需要共享 / 缓存构建的用户，ngm 没有
> 原生答案——他们得自己搭 CI，而"本地能证明"正是 ngm 的全部卖点。

---

## 背景

ngm 的立身之本是**第三方不进信任链**：

- 依赖直连 Git（[ADR-002](./adr-002-git-direct.md)），锁定到 commit（[ADR-004](./adr-004-reftype.md)）
- 纯 vendor 目录（[ADR-003](./adr-003-vendor.md)），内容可用 `archiveDigest` 核验（[ADR-008](./adr-008-archive-digest.md)）
- 供应链门禁在**本地**执行（[ADR-009](./adr-009-supply-chain-policy.md)）

这条链上每一步都能被用户自己检查：拿到的是哪个 commit、字节是不是那个 commit 的、
哪个依赖被哪条策略拦下。**remote adapter 把这个关系反转**：ngm 把源码交给一台
由**别人**控制的机器，取回一个产物，然后放进 vendor。

v0.3 计划对这个项目的措辞是"**默认禁用**，且**答不上来就不发布**"，并列出三个必须先答的问题。
本 ADR 逐个回答——两个答不上来，一个答得上来，但不足以改变结论。

---

## 三个问题

### 1. 发给谁 —— 答不上来

"自托管构建服务"听起来是可控的：配置里写的就是用户自己那台机器。但这个答案经不起追问：

- **谁运维它**？一个团队共享的构建机，对团队里的个人来说就是"别人控制的机器"。
- **它是不是它自称的那台**？ngm 无法认定一个远端端点的身份。今天指对了，明天 DNS、
  中间人、被改动的服务器都能让同一个 `url` 指向别的东西——而 ngm 没有任何依据能察觉。
- 更根本的是：**ngm 一旦承认"源码可以离开本机"，它的信任模型就必须新增一条 ngm 无法验证的假设**。
  这条假设没有任何本地证据可以支撑。

这一问本身不是致命的——"用户自己决定信任谁"是一种合理的立场。致命的是下一问。

### 2. 如何证明对方没替换字节 —— **答不上来，且这是个结构性问题**

本机构建时，用户能证明产物与源码的对应关系：源码来自哪个 commit、vendor 里的字节
是不是那个 commit 的（`archiveDigest`）、构建用了哪个引擎的哪个版本。

远端构建时，ngm 交出去的是源码，取回来的是**一个字节串**。要证明这个字节串就是
那份源码构建出来的，只有三条路，每条都不成立：

| 思路 | 为什么不成立 |
|------|-------------|
| **信任对方** | 这正是要避免的东西：把第三方放进信任链。而且信任是**全有或全无**的——一次被替换，所有产物都不可信 |
| **让服务签名** | 签名证明的是**谁**发的，不是**发了什么**。一台诚实的、密钥保管良好的服务器，照样能签出一个被植入后门的产物——攻击发生在签名之前 |
| **本地复现后比对** | 这是唯一真正成立的思路，但它要求**可复现构建**，而这恰恰意味着用户必须有能力、且真的在本机构建一遍。若如此，远端省下的只是算力，而"省算力"不需要 ngm 引入一个新的信任假设——用户完全可以自己搭 CI |

第三条值得多说一句，因为它是**唯一能让本决策翻案的路径**（见下方"什么条件下可以重新考虑"）。
但在当前的现实里它不成立：可复现构建在 JS 生态里远不是既有能力，把它作为依赖项，
等于把一个尚未解决的行业问题写进 ngm 的正确性前提。

**结论**：这不是"再多做点工程就能解决"的问题。它是"ngm 无法把这条信任假设变成可验证的"，
因此**不发布**是唯一与项目立场一致的选择。

### 3. 失败如何不静默降级 —— 答得上来

这一问有答案，而且是既有惯例：

- 服务不可达 / 超时 / 返回非零 → **`exit 5` + 明确说明**，绝不悄悄改走本地构建
- 绝不"取回了一个产物但没验过就用"——**没有验**这件事必须出现在输出里
- 远端返回的产物若与本地 `ngm.lock` 记录的 commit 对不上 → 失败，不是"以远端为准"

（静默降级是这个项目反复防的一类失败：看起来成功了，而实际做的事与用户以为的不同。）

但答得上这一问**不能**推翻第 2 问的结论：一个能在崩溃时诚实报错的功能，
依然可以在正常工作时替换你的字节。

---

## 决策

**不发布 `remote` adapter。** 并且：

1. `adapter: remote` 在清单里**保持合法**（语法不变，`IsValid` 为真），但任何使用它的条目
   都会被报为**按 ADR 排除**，指向本文件——而不是"v0.3 待实现"
2. 错误信息里不写"planned" / "coming soon" 一类措辞：那是**承诺**，而这里已经有结论了
3. 本 ADR 是决策快照。将来若要发布，**必须先修订本 ADR**（与 ADR 冲突的实现先改 ADR，再改代码）

---

## 什么条件下可以重新考虑

用**可证伪的条件**写，而不是"将来再看"：

1. **产物可复现，且用户能抽样本地复现**：同一份源码、同一引擎版本 → 相同字节。
   这时第 2 问的答案是"用户自己验"，服务仍然有价值（省算力，且可随时抽查）。
   这需要在实现前**先实测**某个真实引擎能做到——不是引用别人的说法
2. 或者：远端只接触**已经公开**的源码，且用户能独立核对它取回的产物与公开源的对应关系

任一条成立时，本 ADR 应被修订而非悄悄绕过。

### 第一条的实测进展（2026-10-01，v0.4 开工前复核）

"产物可复现"这一半**部分成立**，比本 ADR 写作时的假设更接近。用真实 esbuild 实测：

| 条件 | 结果 |
|------|------|
| 同一源码 + 同一版本（0.28.2）+ **不同目录**，`--minify` | 字节一致 ✓ |
| 同上，**三个平台**（linux / macOS / Windows）× 两个不同路径 | **六次构建字节全同**（`7f2c6fd5…`）✓ |
| 不 minify，同一路径、跨平台 | 字节一致 ✓ |
| 不 minify，且传入**绝对路径** | 字节**不同** ✗ —— 产物注释里嵌的是**传入的路径** |

最后一行是关键细节：路径是否泄漏进产物，取决于**调用方传的是绝对还是相对路径**。
ngm 传的是相对路径（`mappings` 里的 `to`），且把 CWD 固定为项目根——**它现在的调用方式
已经落在"路径无关"那一侧**。因此"用户本地复现远端产物"在机制上不是空想。

#### 第二批（2026-10-01）：其他引擎、多文件、sourcemap

把探针从"esbuild + 单文件"扩到**四种形态**，每种都在**三平台 × 两个不同路径**下构建
（`.github/workflows/repro-probe.yml`，结果见该工作流的头注释）：

| 形态 | 结果 |
|------|------|
| esbuild `--minify`（**多文件 + 一个依赖**） | 六次构建字节全同 ✓ |
| esbuild `--sourcemap`（`.map`） | 六次构建字节全同 ✓ |
| tsc `--emitDeclarationOnly`（声明树，目录聚合哈希） | 六次构建字节全同 ✓ |
| postcss（CSS，输入走 stdin） | 六次构建字节全同 ✓ |

调用方式**刻意模仿 ngm**：工作目录 = 项目目录、参数全用相对路径。这一点是前提——
"用户能本地复现远端产物"只有在**双方都用 ngm 的调用方式**时才谈得上，而 ngm 传的正是相对路径。

**一处与预期相反的结果**：我原以为 sourcemap 会把构建机的路径嵌进去（那样就无法逐字节比对），
实测 `.map` 里的 `sources` 是**相对**的，因此同样一致。这类"以为会失败、测出来通过"与反向的
结果一样值得写下来——两者都是"先猜后测"的产物。

**但结论仍是不发布**，因为已证的范围仍小于结论所需：

- 这些都是**小型合成项目**：多文件 ✓，但真实应用的插件 / loader / 压缩链**未测**
- 只测了引擎本身的确定性；**依赖是否只用了你送给它的源码**（例如会不会去读未送出的本地文件）
  仍是未答的问题，而它与字节是否一致无关
- 用户仍需**至少抽样构建一次**才能验证——那正是远端想省下的东西（抽样使其可行，但代价不为零）

因此本条记为"**条件正在收敛，但尚不成立**"。后续若要继续推进，应先在真实项目上重复这组
实测（不同引擎、多文件、带 sourcemap），而不是直接进入实现。

#### 第三批（同日）：规模放大 + 对照组

前两批都是单文件单依赖的合成用例，而且**缺少一个关键的对照**：两次构建字节相同，
也可能只是因为检查坏了（永远返回同一个值）。第三批补上它。

把项目放大到 **60 个源文件、两级嵌套目录、两个依赖**，仍在两个不同目录名下各构建一次：

| 形态 | 结果 |
|------|------|
| esbuild `--minify`（60 文件 + 两个依赖） | 两路径字节一致 ✓ |
| esbuild `--sourcemap`（`.map`，含 sources） | 两路径字节一致 ✓ |
| tsc `--emitDeclarationOnly`（声明树，聚合哈希） | 两路径字节一致 ✓ |
| postcss（CSS，输入走 stdin） | 两路径字节一致 ✓ |

**对照组**：改动一个源文件的一个字节后重新构建，产物哈希**必须**变化。

```
PROBE Windows esbuild=0.28.2 tsc=Version 5.6.3
      treeA=eef8b785e0e3f968  treeB=eef8b785e0e3f968  ctrl=cd7f300bc24498dd
      same_across_paths=yes   ctrl_sensitive=sensitive  verdict=REPRODUCIBLE  fails=
```

三个平台给出**相同**的 `treeA`（=`treeB`）与 `ctrl`。也就是说：**在 minify 与带
sourcemap 的常见生产形态下，产物字节既与构建路径无关，也与构建平台无关** ——
而这回这条结论有对照组托底 ✓：哈希确实对内容敏感（`ctrl` 不同），所以前面的"相同"
不是因为检查失灵 ✓。

**仍未证的范围不变**：这些仍是合成项目（60 文件，但没有真实应用的插件 / loader /
压缩链）；用户依然要**至少抽样构建一次**才能验证；"远端是否只用了你送出的源码"
这个问题与字节一致性无关，仍未答 ✓。因此**结论仍是不发布** ✓。

> 复核用的工具留在仓库里：`.github/workflows/repro-probe.yml`，手动触发，或**在改动
> 探针/工作流时随推送触发**（`push.paths` 限定在那三个文件）——"改仪器"与"看结果"
> 因此是同一个动作。它把结果发成 annotation，因为 Actions 日志匿名读不到。

#### 第四批（同日，v0.5）：插件链、loader 链与压缩链

第三批的形态都是"CLI 直调 + 简单入口"，而**真实项目走的不是这条路**：Vite / Astro 都经
esbuild 的 **JS API + 插件链**构建，还会打开 `metafile`（一份记录每个输入输出路径的清单）。
这正是"绝对路径泄漏进产物"最可能出现的地方，因此本轮补上它：

| 新增形态 | 结果 |
|----------|------|
| **loader 链**：`.png` → dataurl、`.txt` → text，再 `--minify` | 两路径字节一致 ✓ |
| **CSS 压缩链**：esbuild `--bundle src/app.css --minify` | 两路径字节一致 ✓ |
| **esbuild 插件（JS API）+ metafile**：自定义 `onResolve` 把 `github:` 裸导入解析到 vendor，`metafile` 写进产物目录并参与哈希 | 两路径字节一致 ✓ |

```
PROBE local-v05 esbuild=0.28.2 tsc=Version 5.6.3
      treeA=6e5cb4d34ce3af63  treeB=6e5cb4d34ce3af63  ctrl=c84e70e921e4acf5
      same_across_paths=yes   ctrl_sensitive=sensitive  verdict=REPRODUCIBLE  fails=
```

（本机两次独立运行给出**同一个** `treeA`，对照组敏感。）

插件那一步的纪律也写进了探针：**插件不得写入任何与机器或时间有关的东西**。若某个插件
非得写入绝对路径才能工作，"可复现"就不成立，而它应该在探针里失败，而不是在用户机器上。

##### 顺手取得的一个跨机器数据点

本机（Windows 10 / i3-10100）用**第三批的夹具**跑出 `treeA=eef8b785e0e3f968`——
与 CI 上 Ubuntu / macOS / Windows 三个 runner 记录的**完全相同**。也就是说，
"本机 ↔ CI 机器"这一维至少在旧夹具集上是一致的；它比之前只比"CI 的三个平台"多出一台机器。

##### 跨平台比对从"人读"改成机器判

此前"跨机器"靠读结果的人对照三行 annotation。那在结果相同时看不出问题，在结果不同时
又说不清是哪一层不同——而**最容易被漏掉的一条是引擎版本是否一致**：版本不同的两份字节
恰好相同纯属巧合，那样比出来的"可复现"没有意义。

现在由 `scripts/compare-probe-results.mjs` 判四层，任何一层不成立即失败：

1. 每个平台自身的结论成立（`verdict=REPRODUCIBLE`，且**对照组敏感**）
2. 没有任何构建步骤失败
3. **各平台的引擎版本一致**（否则第 4 条没有意义）
4. 各平台 `treeA` 完全一致，且各自 `treeA == treeB`

只收到一份结果同样失败——"没测出来"不得读成"通过"。

##### 这一批之后，仍未证的（以及为什么结论不变）

- **新形态的跨平台结果还没有**：跨平台比对需要一次 CI 运行，而本环境无法触发
  `workflow_dispatch`（探针会在推送这三个文件时自动跑，结果落在 artifact 里）。
  因此对**新**夹具集，"跨机器"这一维**仍未证**——本机两次一致只证明了同机可复现。
- **"合成项目"这顶帽子没有摘掉**：插件 / loader / 压缩链现在都有了，但它们仍是**我们自己写的**
  最小插件，不是真实项目的插件生态（Vite 插件、`postcss` 插件队列、资产指纹等）。
- 用户依然要**至少抽样构建一次**；"远端是否只用了你送出的源码"与字节一致性无关，仍未答。

因此**结论仍是不发布**：翻案条件的前半（产物可复现）在机制上继续收敛，后半（用户能抽样
本地复现）依旧要求用户自己构建一遍——那正是远端想省下的东西。

---

## 后果

- **v0.3 少一项能力**：计划里 `remote` adapter 的复选框按"已决定不发布"结项，而不是假装待办
- `internal/adapter` 不新增 `remote.go`：没有实现，就没有"半实现的信任边界"这类东西可被误用
- 引擎清单的 adapter 枚举保留 `remote`：删掉它会让"为什么没有 remote"这个问题无处可查。
  保留 + 指向本 ADR，是把决定放在用户会遇到它的地方
- **本 ADR 的论证方式**可以被复用：任何"把源码或产物送出本机再取回"的能力（包括将来的
  远端 verify、远端缓存），都要先回答同样第 2 问
