> 明确 N4 对 lock schema 的处理要先例可依、末尾加**验收看板**。

## 0. 完成定义（做到这三条就算完）

1. 四条缺口各有一条**带牙齿**的判据（夹具 + 反向对照），且都在 `go test ./...` 里跑；
2. 对外契约的改动都有决策记录（ADR 或标准页的例外小节），且**旧行为不被削弱**；
3. 文档与判据不打架：改完跑一遍活文档那几张网（V15 / V25 / V26 / V27 / V58 / V63）。

## 1. 优先级与估时（先做便宜的）

| 顺序 | 项 | 为什么这个顺序 | 估时 |
|------|----|----------------|------|
| 1 | **N3** 消费方静默少装 | 最便宜、收益最直接：它挡的是"装完了却少东西"，而症状离原因很远 | 0.5 天 |
| 2 | **N1** 行尾读数分索引/工作树 | 纯读数改动，不改任何判定语义；顺带让标准页那条边界有据 | 0.5–1 天 |
| 3 | **N2** 补"应用"角色 | 需要先决定角色模型（加角色 vs 加参数），影响标准页 | 0.5–1 天 |
| 4 | **N4** 许可读数进 lock/SBOM | 动的是**对外契约**（SBOM 形状 + lock 字段），最重，必须最后做 | 1–2 天 |

**N4 可以提前"测量"**：先把"上游 `package.json` 里有多少声明了 license"量出来，不改代码。

**不做会怎样**：

| 不做的项 | 最坏会发生什么 |
|---|---|
| N3 | 消费者装完少东西，失败点在构建期报"模块找不到"，与原因隔了一整层 |
| N1 | 每个在 Windows 上体检的人都拿到一份假缺陷清单——**判据会因此被忽视** |
| N2 | 应用形态永远红一条不该管的判据，看报告的人会去造一个不需要的入口 |
| N4 | 客户法务问"有没有 GPL"，答案只能是"不知道"——商业化交付少一件东西 |

**我们大概率会怎么搞砸**（这四条都有同族先例）：

1. **改断言而不是加字段**：为了让 N4 变绿，把 `NOASSERTION` 的测试删掉或放宽——那等于把"不猜"
   这条承诺拆了。正确做法是把它改成"两个字段口径"；
2. **把"不适用"写成静默跳过**：不适用必须被打印且不计入计数（v0.76 / v0.79 的先例）；
3. **只改 `.sh` 不改 `.ps1`**：两个入口的行为会漂移，而验收常常只在一边跑；
4. **把 N4 的 lock 字段当必填**：旧锁会读不进来——新增可选字段、`lockfileVersion` 不动。

**开工前置：先把在飞的工作处理掉**（2026-10-19 复核）

  （v0.100 / v0.101 在飞，其中包含 `docs/handover/` 这几份文档与评估文档本身）。
- 开始改判据之前先**提交或隔离**这批工作。否则 `go test ./...` 的红会被算到你头上。

| 测试 | 现象 | 成因 |
|------|------|------|

## 2. 四处缺口

### N1 · 行尾判据在 Windows 检出下会**误报**

- 现象：三个仓库的**索引里 CRLF 文件数为 0**，而工作树里 lytjs 有 1,709 个、qforge 有 102 个
  （`core.autocrlf=true` 的产物）。`lf-only` 把"检出设置"报成了"仓库缺陷"。
- 出处：`scripts/check-library-standard.sh`（唯一实现）；标准页
  [`docs/guides/js-git-library-standard.md`](../guides/js-git-library-standard.md) §必做 9 已写明这条边界。
- 建议：报 CRLF 时**同时报索引侧行尾**（`git ls-files --eol` 的 `i/` 与 `w/`），把"仓库事实"与
  "检出产物"分开说；结论里明确一句"请把 `core.autocrlf` 设为 false 或补 `.gitattributes`"。
- **先测量**：拿三个仓库各跑一次，确认"索引 0 / 工作树 N"这个形态能被稳定复现（已复现 ✔）。
- 判据（牙齿）：`core.autocrlf=true` 的临时仓库夹具 ⇒ 报告出现"索引为 LF，这是检出产物"；
  改成 false 重跑 ⇒ 该结论消失。
- 影响面：`.sh` 改动要同步 `.ps1` 转调；标准页那一节补一句指向新读数。

### N2 · 标准缺"**应用**（不是库）"这个角色

- 现象：qforge 是"双击即用的静态应用"，没有 JS 入口，于是**永远**红 `entry-resolvable`——
  这条判据问的是"库的入口在哪"，对应用不成立。与 v0.80 修掉的"用错理由红"同族。
- 建议（二选一，倾向后者）：(a) 加应用角色（入口判定改为 `index.html`）；
  (b) 让自检器接受一个角色参数，应用形态下 `entry-resolvable` / `entry-file-exists` /
  `dist-committed` 记**不适用**并打印原因。
- **先测量**：现在三种角色的判定在脚本里的位置与耦合（角色是从清单推出来的，还是外部传入的）。
- 判据（牙齿）：应用形态夹具 ⇒ 三条记"不适用"并打印原因；库形态夹具 ⇒ 三条照旧生效。
- 影响面：不适用是一种结论，必须**被打印**且不计入计数——先例已写在标准页 §5。

### N3 · 消费方会**静默少装**

- 现象（代码位置已核）：`checkUpstreamPackageJSON` **只在 `ngm.json` 不存在时**才被调用
  （`internal/resolve/graph.go` 第 483 行）；即使调用，也只对 `looksLikeGitSpec` 的写法报警
  （同文件第 562 行），而它的前缀表里**没有 `workspace:`**。
- 后果：像 lytjs 这样"两份清单都有、依赖写成 `workspace:*`"的上游，**两条路都走不到**——
  消费者以为装齐了，直到构建时报"模块找不到"。
- 建议：上游 `package.json` 的 `dependencies` / `devDependencies` 出现 `workspace:` 前缀时，
  **无论 `ngm.json` 是否存在**都给一条警告，点名这些依赖，并提示"请显式声明对应的 `#path=` 子路径"。
- **先测量**：当前行为（含它与"上游 package.json 损坏不影响判断"那条既有行为是否会冲突）。
- 判据（牙齿）：夹具 `package.json` 声明 `"@x/y": "workspace:*"` 且有 `ngm.json` ⇒ 一条警告点名
  `@x/y`；删掉该条目 ⇒ 警告消失。

### N4 · 商业交付要的"许可读数"：lock 与 SBOM **都不记**

- 现象（实测）：`internal/lock` 与 `internal/config` 里 `license` **0 命中**；
  `internal/sbom/spdx.go` 把 `licenseConcluded` / `licenseDeclared` / `copyrightText` 一律写死
  `NOASSERTION`，并有测试钉着这个口径。
- 为什么商业化后它会疼：客户法务的必问是"**这份依赖清单里有没有 GPL / AGPL**"，
  而现在的 SBOM 对每个组件都说"不知道"——**这不是缺陷**（v0.69 刻意不猜），但它让交付少了一件东西。
- 建议（**不违反"不猜"**，走 SPDX 的两个不同字段）：
  1. `licenseDeclared` ← 上游 `package.json` 的 `license` 字段**原文**（它是**声明**、有唯一来源；
     `checkUpstreamPackageJSON` 已在读那份文件，只是没取这个字段）；解析不出 SPDX 标识符时照抄原文
     或用 `LicenseRef-…` 形式；
  2. `licenseConcluded` **保持 `NOASSERTION`**——"声明"与"结论"必须分开；
  3. lock 里记录同一声明（例如 `declaredLicense`）——**新增可选字段，不改 `lockfileVersion`**
     （ADR-028 的先例：新增可选字段是既有契约，旧锁仍可读）；
  4. 可选（另立 ADR）：策略门禁 `licenses.deny`。
- 判据（牙齿）：夹具上游声明 `"license": "GPL-3.0"` ⇒ SBOM 里 `licenseDeclared` 照抄 `GPL-3.0`，
  而 `licenseConcluded` **仍是** `NOASSERTION`；上游没有声明 ⇒ 两者都 `NOASSERTION`。
  现有那条 NOASSERTION 断言要改成"两个字段口径"，**不是被削弱**。
- 影响面：v0.69 的 SBOM 契约表与 `docs/guides/cli.md` 的形状表都要跟着改——**先立判据 + 决策记录**。

## 3. 商业化场景里已经可用、值得确认并文档化的能力

| 能力 | 现状 | 要做的 |
|------|------|--------|
| **私有仓依赖**（企业版放私有仓） | 凭证纪律从 v0.1 起就是"不读不存 token、环境透传、输出脱敏" | 在 `docs/guides/dependency-management.md` 补一段"私有仓 + 环境凭证"的用法示例 |
| **合规交付物** | `ngm sbom` / `ngm attest` 能导出 CycloneDX / SPDX 与 SLSA 谓词，且导出是确定性的 | 与两个应用的发布流程接起来（每个版本存档一份） |
| **离线交付** | `install --frozen-lockfile --offline` + vendor 随仓库走 | 作为"内网、涉密"场景的推荐形态写进文档 |

## 4. 做这些改动时要遵守的本仓库纪律

- **先立判据**：四条都要有牙齿（夹具 + 反向对照），不能只改实现。
- **`.sh` 是唯一实现，`.ps1` 只转调**（v0.89 的约定），改一处必须改两处并跑入口对齐的判据。
- **改契约先立 ADR**：N1 / N2 / N4 动的都是"标准与机器接口"的读数口径，按 v0.59 的先例先写决策记录。
- **文档网会接管**：新增/修改的活文档会被 `TestV15`（示例命令成形）· `TestV25` / `TestV26`（形状表与字段）·
  `TestV27`（散文字段名）· `TestV58`（发布读数）· `TestV63`（逐版表）盯着——改完跑一遍。
- **不动 ngm core 的命令行为**：四条都在"标准与读数"这一侧，与
  [ADR-006](../adr/adr-006-lytd-merge.md)（lytjs 的能力不并入 ngm core）一致。

## 5. 不做的事

- 不为了让外部仓库的体检变绿而放宽判据（先例：v0.84 不放宽 `git://`，v0.94 不为子路径端到端放宽地址校验）。
- 不把"应用"角色的不适用写成静默跳过——不适用必须打印。
- **不为了让 SBOM 好看而"猜"许可证**：照抄上游的声明可以，推断 SPDX 标识符不行。
- 不在没有牙齿的情况下改 `lf-only` 的输出（否则只是换了一种说法）。
- **不为 N4 改 `lockfileVersion`**：新增可选字段即可（旧锁必须仍可读）。

## 7. 值得记录的一条读数教训

本次评估里最有价值的一步不是"发现问题"，而是**一次读数校准**：第一轮体检报告 qforge 与 lytjs
有 CRLF，看起来像两条待修缺陷。用 `git ls-files --eol` 与 `core.autocrlf` 对照之后，真相是
**索引里一个 CRLF 都没有**——要做的是一条 `.gitattributes`，而不是转换 1,709 个文件。
**"先量再改"在这里避免的是一整批错误工单**，这条经验值得写进标准页。
