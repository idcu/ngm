# 工程纪律方法论：把约定变成会变红的判据

> **这份文档是什么**：一套**可迁移**的做法——如何让"我们的约定"从口头承诺变成机器可跑的判据，
> 以及在什么规模、什么阶段值得这么做。它**不是** ngm 的能力声明（能力以
> [能力矩阵](../internals/capability-matrix.md) 与 [CLI 参考](../guides/cli.md) 为准），
> 也**不绑定**任何一个项目：文中所有案例都只是证据，不是方法本身。
> **读它的人**：打算给自己的仓库上一套"结构可控、变更可核"纪律的维护者；
> 判断某个项目是不是真的"有保证"的评估者。
> **怎么用**：先看 §1（什么值得写成判据）与 §4（成熟度分级）判断自己该做到哪一层，
> 再按 §6 的顺序动手；§5 是判据失效的四种形态，§8 是一份可以直接抄的自检清单。

---

## 0. 一句话，和它反对的那句话

**一句话**：任何"我们保证了 X"的说法，必须能指向**一条会变红的判据**；否则它只是一句愿望。

**它反对的那句话**："这条约定很重要，写进 `CONTRIBUTING.md`，评审时注意一下。"

反例不是修辞。一个真实项目曾有一条"命名必须经所有者批准"的口头约定，在没有判据的两天里
被执行成了一次未授权的全仓改名，事后需要一份事故记录来回退；另一个项目把依赖锁版本写进了
README，而下游照抄之后 CI 只能源码构建——**这两件事的共同点不是"人不小心"，而是"没有任何东西会红"**。

---

## 1. 判定标准：一条约定值得变成判据吗

不是所有约定都值得。三条门槛，全过才动手：

| 门槛 | 问法 | 不过关时 |
|---|---|---|
| **后果贵** | 违反了会怎样？静默错数据 > 构建失败 > 代码风格 | 只影响可读性的，交给格式化工具，别写判据 |
| **可判定** | 能不能用"读文件 / 跑一条命令 / 比两份数据"回答？ | 需要人判断的（"这个抽象合理吗"）不是判据，是评审 |
| **会被违反** | 过去 3 个月违反过吗？新增代码时容易漏吗？ | 一年没人碰的约定，先记着，别花判据的钱 |

再加一条**成本约束**：一条判据的维护成本 ≈ 它的代码量 × 它被改动的频率。
30 行能说清的事，不要写成 300 行；300 行能说清的事，不要写成框架。

> **结论**：优先选"最容易犯 + 后果最贵 + 一句话能说清"的那一条。
> 一条被阻断过一次的判据，价值高于七条从未红过的判据。

---

## 2. 约束条件：先判断自己在哪一格

方法论的**成本**随项目形态变化，而**收益**几乎不变。先定位：

| 维度 | 低 | 高 |
|---|---|---|
| **规模**（人） | 1–2 人 → 判据替代记忆 | 5+ 人 → 判据替代会议 |
| **变更频率** | 月级 → 文档足够 | 天级多轮 → 只有机器判据跟得上 |
| **数据持久性** | 无状态脚本 → 结构变更廉价 | 有真实数据 → 迁移必须可回滚、可重放 |
| **依赖面** | 零依赖 → 判据只能自己写 | 有生态 → 优先复用现成 lint/test/build |

**两条经验**：

1. **单人 + 快节奏**是最需要判据的组合，不是最不需要。人少意味着"人记着"的那条一定先失效。
2. **零第三方依赖**的项目不是不能有门禁，而是门禁必须"短、可跑、能说清为什么"——
   因为没有生态可以借，每条判据都得自己写，写长了就没人维护。

## 3. 九条可迁移做法

每条给四样东西：**做法**（做什么）、**判据形态**（怎么变红）、**最小落点**（今天就能做的第一步）、
**反例**（真发生过的那种）。案例只作证据。

### 3.1 契约先于代码：把"不许跨边界"写成机器可读的文件

**做法**：把跨模块的约束从文档搬进一个显式目录（`contracts/`），**一份文件管一件事**。
文件是 JSON/YAML 之类的数据，不是散文——因为它要被脚本读。

一份契约文件的典型内容：

```json
{
  "schemaVersion": 1,
  "tables": {
    "orders": {
      "allowed_writers": ["modules/orders/repo.js"],
      "baseline_writers": [],
      "why": "订单状态只有订单模块能改；其它模块通过服务调用"
    }
  },
  "ignore_files": ["test/fixtures/seed.js"]
}
```

**判据形态**：一个 `check-*` 脚本读契约 + 扫源码，把"契约说 A、代码在做 B"逐条打印出来。
**契约的价值不在文件本身，在于它被违反过一次并且当场变红**。

**最小落点**：挑**最容易犯、后果最贵**的那一条（多数项目是"谁能写这张表 / 谁可以 import 这个包"），
写成 30 行检查脚本挂进 CI。不要一次写七份。

**反例**：把约定写进 `CONTRIBUTING.md` 然后指望评审记得。同一类事故在不同项目里重复出现，
区别只在"改名""删表""谁批准发版"。

### 3.2 结构只有一个来源：spec → 生成物 → 校验生成物

**做法**：把手工维护的枚举/常量/表结构收敛成**一个源文件**，由生成器产出可执行形态，
再把生成结果**入库**并由判据比对。

```
schema-spec.json  ──生成器──▶  schema.generated.js  ──判据──▶  与 spec 重跑结果逐字一致
      ▲                              │
      └────── 唯一的编辑入口 ─────────┘
```

**为什么生成物要入库**：部署机不必跑生成器；而"入库 + 校验"同时得到两个好处——
读者能直接看到真实产物，篡改或忘记重跑会被判据抓住。
**代价**：每次改 spec 都要重跑生成器，否则 CI 红。这正是它起作用的方式。

**最小落点**：任何"手工维护的枚举表"都可以这么处理：一个 JSON 源、一个生成器、一个比对判据。
先做**一个**，跑上一个月，再决定要不要做第二个。

---

### 3.3 生成物策略：一条判据，而不是一条命令

这是最容易搞错的一条，也最值得写成决策表。判据只有一句：

> **删掉它，CI 能不能从源重建并得出结论？**
> 能 → 不入库并加进 `.gitignore`；不能 → 入库并由判据守住。

| 生成物 | 入库？ | 理由 |
|---|---|---|
| 结构 DDL（供校验比对） | ✅ | 它是"比对基准"，不入库就没得比 |
| 前端常量表（运行时依赖 + 被判据逐字读取） | ✅ | 同时是运行时依赖与校验基准 |
| 拼接出来的测试总文件（每次跑前必然重建） | ❌ | 入库只会产生无意义 diff |
| 二次分发副本（浏览器可加载的 vendor 副本） | ❌（通常） | 可由生成脚本重建；要入库就必须有判据守它 |
| 打包产物（`dist/`、单文件发行包） | ❌ | 有 SHA256 与发布记录，不需要进版本库 |

**要点**：不要统一 `ignore`，也不要统一提交——**逐个回答上面那句话**。
同一份依赖的两个形态（随仓库分发的 vendor、浏览器用的副本）按这条判据会得到相反的结论，
那不是不一致，是**判据在起作用**。

### 3.4 门禁分层：单项 → 总闸门 → CI 多 job

**做法**：

```
check-*.{js,mjs,sh}      单项：每个只回答一个问题，可单独跑，输出一行读数
        ↓
verify（或 make check）   总闸门：语法 + 导入解析 + 全部单项 + 全量测试；只做聚合
        ↓
CI 多 job                 每个 job 只回答一个问题，且"跑不了"与"通过"在输出里长得不一样
```

**三个关键点**：

1. **单项必须能在本地一条命令复现**，否则它就只是 CI 的属性，而 CI 的属性无法在提交前使用。
2. **总闸门不塞新逻辑**。它一旦有独立判断，本地通过就推不出 CI 通过。
3. **跳过要说出来**。`::notice::` / `skipped: no binary` / `COULD NOT CHECK`——
   "静默成功"是这类系统里最贵的一种谎：它让缺失读起来像保证。

**反例**：一个仓库的本地 `npm test` 只跑 3 项，CI 跑 5 项，其中一项是性能阈值。
本地全绿、CI 红，而人学会的第一件事是"CI 有时会抽风"——**门禁的可信度是这样丢掉的**。

**最小落点**：先把本地能跑的那几条串成一个 `verify`，再让 CI 调它；
不要在 CI 里写本地跑不了的步骤。

### 3.5 破坏性结构变更：物理拆分 + 只读兼容视图 + 单一写入口

**做法**：当一张表/一个模块承担了两个职责，把它**物理拆开**，而不是靠命名约定区分：

```
旧：employees（人员 + 账号身份）
新：people_employees（人员） + identity_accounts（账号身份）
    employees  →  保留为 LEFT JOIN 只读视图（旧查询与历史快照仍能解析）
写入：只经 people / identity 仓储；跨两者的组合写必须在同一个事务里（unit-of-work）
```

**三条配套判据**（缺一条都会退化成"看运气"）：
禁止直写旧表、读路径白名单、事务边界检查。

**最小落点**：任何"表拆分/改名"都保留一个只读兼容层，并把写入收口到一处；
否则旧代码会以"读不到数据"或"写了一半"的方式**静默失败**——这两种都不会抛异常。

### 3.6 基线重置 + 历史归档，而不是无限叠加迁移

**做法**：当迁移数量超过约 20 个、且早期版本已无人能验证时，**重置一次基线**：

1. 旧迁移的逐版 STEP 归档到 `legacy/`（不参与运行，只作历史证据）；
2. 结构基线重置到新版本号；低于该版本号的库**启动即拒绝**，并给出重建步骤；
3. 重建动作必须是"备份 → 按基线重建 → 逐表复制旧数据"这样**可重放**的；
4. 一条**等价性判据**：升级库与新建库必须逐表、逐列、逐索引、逐外键一致。

**前提**：没有第 4 条就不要做第 1–3 条——否则"重置"只是把风险藏起来。

### 3.7 文档分层与去重：入口 / 权威 / 过程

**做法**：文档只允许三层，每层有明确规则：

| 层 | 位置 | 规则 |
|---|---|---|
| **入口** | `README.md` | 只放定位、快速启动、目录用途、文档索引；建议 200 行封顶 |
| **权威** | `docs/*.md` | 每份一个主题，细节只在这里维护；入口里与它重复的段落改为链接 |
| **过程** | `analysis/`、临时评估、交接方案 | **本地留存、不入库**；`.gitignore` 里显式写入 |

**三条配套动作**（少一条就会留下死链或双份事实源）：

1. 入口里与权威层重复的章节**删掉并改成链接**；
2. 指向过程文档的引用**清理掉**（否则新克隆者看到死链）；
3. 过程文档出库时，**同时**修三处：`.gitignore`、引用它的文档、以及因此暴露的脚本假设。

**判据**（可自检，也可机器化）：

- README 里出现的每条命令，是否能在仓库根目录直接执行？
- README 与 docs 里出现的每条相对路径，是否真实存在？
- 每份权威文档是否被入口索引到？（"写了但没人找得到"与"没写"等价）

**反例**：一个项目 README 写着"`src/` 已清空"，而该目录已被**删除**，连带 `verify` 脚本里
无条件的 `readdirSync('src')` 直接崩溃。**文档失真会以"门禁崩溃"的形式收账**——
而且是在别人克隆之后。

### 3.8 变更治理：命名、删除、出库都要有授权与记录

**做法**：三类动作必须有闸门或记录：

| 动作 | 闸门 | 记录 |
|---|---|---|
| **命名**（品牌名、模块 id、包名） | 命名策略文件 + 检查脚本；变更须所有者批准 | 谁批准、影响哪些文件 |
| **删除**（结构性删除：目录、公共 API、兼容层） | 删除前列出"谁还在读它"；账本本身由判据校验（见下） | 删了什么、为什么、哪条判据的假设因此被打破 |
| **出库**（把生成物/过程文档移出版本库） | `.gitignore` + 引用清理 + 脚本假设复查 | 出库后仍要跑一遍全量门禁，证明没有东西依赖它 |

**为什么"出库"单列一条**：它是最容易只做一半的动作。实测常见形态是——
文件移走了，`.gitignore` 忘了写（下次又提交回来），或者某个脚本一直在读它（CI 从此红）。

**最小落点**：为每一次结构性删除写一行记录（删了什么、为什么、谁批准、哪条判据要改）。
写在变更日志或 ADR 里都行，**关键是有地方可查**。

**记录本身也要有判据**（否则它是第二份会腐坏的文档）：

| 查什么 | 为什么 |
|---|---|
| 六个字段齐全（删除 / 日期 / 批准 / 为什么 / 影响 / 验证） | 缺"影响"与"验证"的记录，等于只写了"我删了" |
| 日期不晚于今天 | 记录不是计划；写未来日期通常是事后编的 |
| 记录的路径**不在** `git ls-files` 里 | **假删除**：账上删了、库里还在（目录要按前缀整查，`tracked.has('old/')` 永远为假） |

最后一条最值得写：它把"账本"从叙述变成了**可核对的事实**。四个仓库里有两个仓库的账本
建立时就是空的——空账本不失败，但文件必须存在，否则下次删东西时没人会想起要登记。

### 3.9 模块化装配：manifest + 装配清单 + 可撤销的启停

**做法**：把"模块"从一句口号变成**可枚举、可校验的装配动作**。五个要素，缺一个就不是模块化，
只是"把文件放进了不同目录"：

| 要素 | 写在哪 | 没有它会怎样 |
|---|---|---|
| **manifest**（id / 版本 / 依赖 / 入口 / 占用资源） | 每个模块目录一份 `module.json` | 只能靠目录名猜它是谁、依赖谁 |
| **装配清单**（启用哪些、按什么顺序） | 一个 `config/*.json`，**唯一事实来源** | "扫描目录就等于装了"——停不掉的模块没人认领 |
| **依赖拓扑**（缺依赖拒绝装配、环报错） | 装配器 | 半装状态：路由在、权限没在 |
| **占用冲突要失败**（路由前缀 / 表 / 权限 / UI 插槽） | 装配器 | 后来者静默覆盖前者，线上难查 |
| **启停只反注册，不删数据** | 装配器 + 生命周期约定 | 一次"先禁用试试"就丢了业务数据 |

**为什么这几条必须一起**：只做 manifest 不做清单，模块无法停用；只做清单不做冲突检测，
冲突表现为"某个接口 404 或返回别人的数据"；只做启停不做数据分离，运维不敢碰开关。

**违反时的表现**（都是"看起来正常"的那种）：路由挂了但权限没挂；两个模块注册同一个 `/api/xxx`
后者生效；禁用模块后权限目录里留着孤儿权限；启用顺序靠文件夹字母序，`require` 顺序随机。

**三档适配**——不要一开始就上全套：

| 档位 | 需要什么 | 判据形态 | 典型规模 |
|---|---|---|---|
| **L2 装配清单** | manifest + 清单 + 静态双向比对（声明↔注册） | `check-modules`：清单里的必须存在，代码里注册的必须登记 | 单页应用、单体前端（插件/扩展点） |
| **L3 加载顺序** | 上面的 + **层顺序**约束（目录级，而非逐文件依赖图） | 判据校验"哪些层必须排在哪些层之前" | 几十个 `<script>` 顺序加载的单体前端 |
| **L4 运行期装配** | 上面的 + 拓扑排序、冲突失败、启停 API、失败回滚 | 装配器 + `GET/POST /api/<platform>/modules` | 服务端多模块、有真实数据与运维窗口 |

**最小落点**：一份清单 + 一个双向比对的脚本。它挡不住"业务逻辑写错"，但能挡住
"注册了但没人登记"与"登记了但没注册"——这两类在生产里表现为"功能时有时无"，最难复现。

**不要做的事**：给每个模块加沙箱。同进程运行的扩展没有沙箱，**评审与签名**才是它的边界；
把"我们打算做沙箱"写成保证，比不做更危险。

## 4. 成熟度分级：你该做到哪一层

| 级别 | 名字 | 最小交付物 | 适合 |
|---|---|---|---|
| **L0** | 无纪律 | 无 | 一次性脚本、试验代码 |
| **L1** | 一条判据 | 一个 `check-*` 挂在 CI，且你**亲眼见它红过一次** | 任何有第二个人用到的项目 |
| **L2** | 两份文档 + 生成物策略 | 入口/权威两分；所有生成物逐个回答 §3.3 那句话 | 小工具、单页应用 |
| **L3** | 契约 + 总闸门 | 至少一份契约文件 + `verify` 聚合 + CI 多 job | 有跨模块边界的产品 |
| **L4** | 变更治理 | 命名闸门、删除记录、兼容层到期日期（过期即红） | 多人协作、有真实数据、需要长期维护 |

**升级的唯一理由**：某一类事故**真实发生过第二次**。没有第二次，就停在这一层——
多出来的判据会腐坏，而腐坏的判据比没有更坏（它制造"查过了"的错觉）。

## 5. 判据的四种失效形态（先认出来，再谈建设）

| 形态 | 表现 | 怎么发现 |
|---|---|---|
| **恒绿** | 判据跑得通、永远通过 | 故意改坏一次，看它红不红（"牙齿测试"） |
| **空跑** | 扫到 0 个文件，于是"全部通过" | 判据必须打印**读数**（扫了几个、比了几项）；读数为 0 视为失败 |
| **平台相关** | 同一份仓库在 Windows 绿、Linux 红 | 大小写、路径分隔符、换行；判据要跑在目标平台上 |
| **假跳过** | 缺工具时静默成功 | 跳过必须打印并带原因；"跑不了"与"通过"要长得不一样 |

这四种的共同点：**它们都不会自己暴露**。所以每条判据落地时至少配一个**牙齿用例**——
用临时目录构造一份"应当失败"的输入，断言它确实失败。

---

## 6. 接入顺序

按这个顺序做，**前一步没成立就不要做后一步**：

1. **先有一条判据**：挑最贵的那条约定，写成脚本，挂进 CI，并确认你亲手看到它红过一次。
2. **把最贵的跨边界约定变成契约文件**：表所有权 / 包所有权 / 字段单一源 / 品牌闸门，任选其一。
3. **确定生成物策略**：把所有 `*.generated.*` / `dist/` / 拼接产物列成表，逐个回答 §3.3 那句话。
4. **引入依赖层的证明（如需要）**：锁文件入库、`install --frozen-lockfile --offline` 可复现、
   `verify` 能重放 digest；部署形态决定 vendor 是否随仓库分发。
5. **CI 两段式**：先安装（离线可复现），再校验（机器可读报告）；跑不了就明说跳过。
6. **文档分层**：先做"入口/权威"两分，过程文档不入库。
7. **每次结构性删除写一行记录**，并回头检查哪条判据的假设被打破了。

**不要做的事**：先写框架、先做仪表盘、先把所有约定都列出来。
顺序反了就会出现"九条判据、零次变红"——那是最坏的状态，因为它看起来像有纪律。

---

## 7. 失效边界（这套方法论什么时候不该用）

- **判据不是免费的**：每条都是要维护的代码。没人跑、或跑起来恒绿的判据，
  比没有更坏——它制造"查过了"的错觉。
- **契约文件会腐坏**：写进 JSON 的约束如果不再对应代码，就变成第二份真相。
  至少要有一条"过期即红"的机制（兼容层写到 `due_date`，到期判据变红）。
- **小项目不该背全套**：三个脚本、无持久数据、单人维护的项目，只需要 §6 的第 1 步与第 6 步。
- **拿不出读数就别声称**：任何"我们保证了 X"必须能指向一条会变红的判据。
  **结论写得比实现强时，没有任何判据会变红**——这是本方法论里最贵的一课。
- **判据不能替代判断**：它能挡住"已知的错"，挡不住"没人想到的错"。
  判据覆盖的是**重复性错误**，边界之外仍然需要评审。

## 8. 自检清单（可直接抄进仓库）

按顺序问，每个"否"都是一个待办：

```text
[ ] 有没有一条判据，我亲眼见它红过？
[ ] 每条判据都打印读数（扫了多少、比了多少）？读数为 0 会失败吗？
[ ] 本地一条命令 == CI 的结论？不一致的地方是否明说？
[ ] 跑不了的步骤，输出里能看出来吗（而不是静默通过）？
[ ] 每个生成物都能回答："删掉它，CI 还能重建并得出结论吗"？
[ ] 有没有一份契约文件，违反它会让构建失败？
[ ] 契约里的每条约束，都对应现存代码吗（还是已经腐坏）？
[ ] 入口文档里的每条命令、每个相对路径，都能在仓库根目录成立吗？
[ ] 有没有死链？最后一条结构性删除，有记录吗？
[ ] 目标平台上跑过吗（大小写、路径分隔符、换行）？
```

机器化建议（成本从低到高）：

| 检查 | 实现成本 | 建议 |
|---|---|---|
| 相对链接存在性 + 本机绝对路径告警 | ~60 行 shell/JS | **先做**，几乎零维护 |
| 版本号多处一致（清单/包/入口常量） | ~20 行 | 先做，最容易漂 |
| 契约 ↔ 代码（所有权、白名单） | 30–100 行 | L3 再做 |
| 生成物 ↔ 源一致 | 生成器 + 20 行 | 有生成器就做 |
| 跨平台一致性 | 换 CI 矩阵 | 有 CI 就做 |

### 8.1 把清单本身脚本化：十问看板

清单写在文档里，没人每周对着它自检。**把十问做成一个脚本**，输出就是成熟度看板：

```text
discipline: 9/10 项具备 → L3
  ✅  1. 有一条会变红的判据 —— 24 个 check-* + 160 个 Go 判据文件
  ✅  2. 判据在 CI 上跑 —— workflow 里调用了判据/总闸
  ❌  4. 最贵的约定写成了契约文件 —— 0 份契约
  ...
  缺口：第 4 问
```

**它不替代判据，只回答"缺哪一条"**。价值在于把"纪律不均衡"从感觉变成清单：
五个真实仓库跑下来，四个 10/10、一个 9/10——而其中三个在第 4 问（契约）上
是**真缺**，两个在第 5/6 问上是**结构上不适用**。没有看板时，这两种情况都表现为"CI 是绿的"。

**关键设计：允许声明不适用**（`docs/discipline-exemptions.json`）：

```json
{ "exemptions": { "5": "纯静态单页：源码即产物，没有构建步骤，不存在生成物归宿问题。" } }
```

三个约束，缺一个它就变成刷分工具：

1. **理由必须 ≥10 字且写清"为什么结构上不成立"**——"暂时没做"不是理由；
2. **不适用项从分母里剔除**，而不是从分子里加分（比例算档，不算绝对条数）；
3. **不得用来掩盖"该做没做"**：契约缺失是没做，不是不适用；包仓库没有构建产物才是不适用。

**成本**：一个脚本、五份复制、一份 JSON。收益是每次评审都能直接看到
"这个仓库现在几档、缺哪一条"，而不是靠回忆。

### 8.2 第 11 问：文档规模（拆分只做一次不算数）

单向的文档拆分**一定会回潮**：拆完 118KB 的入口，三个月后又长回 90KB，而没有任何东西会红。
所以把规模也做成一条判据：

| 项 | 口径 |
|---|---|
| 阈值 | 单文件 ≤60KB 且 ≤600 行（**拦截器，不是排版标准**） |
| 范围 | 活文档（README + `docs/**`） |
| 排除 | **快照**：复盘、评估、竞品对照、ADR —— 它们按纪律不重写，体积是历史事实 |
| 失败时 | 报最大文件的行数与体积，并指出超限个数 |

三个必须记住的取舍：

1. **阈值要能过**。30KB 会让 `cli.md`、`observability.md`、方法论本身全部挂红；
   一挂红就是十几条，人会去调阈值。60KB 只拦真正的膨胀（80KB 以上）。
2. **快照必须排除**。把 `EVALUATION-*.md`（80KB/861L）算进来，等于逼人删历史。
   快照与活文档的区别就是"会不会被未来修改"。
3. **账本是已知例外，而且是真的债务**。逐版账本 80–130KB，因为判据要求
   "同一本账里每版恰好一行、顺序正确"；要降体积必须把判据改成**跨卷合并校验**
   （先改判据、再分卷，顺序不能反——先分卷会让判据静默失效）。
   实测中 ngm 就是唯一挂在这一问上的仓库：10/11 → L3。**这条红是诚实的**，
   它记录的是"我们知道账本还很大，且知道怎么拆但还没做"。

> 一个反例值得记：把阈值设成 30KB 时，qforge 一次红 9 个文件——其中 8 个是过程快照。
> 一个"永远红 8 条"的判据，唯一的结局是被 `|| true` 掉。
