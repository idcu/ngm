# 案例：枢衡 Pivoise 的工程方法论，以及它如何反向要求 ngm

> **这份文档是什么**：一个真实项目（枢衡 Pivoise，企业运营平台，私有仓库）在 10 个月内形成的工程纪律的**外部复盘**，
> 以及这些纪律对 ngm 的反向要求。它**不是** ngm 的能力声明——ngm 的能力以
> [能力矩阵](../internals/capability-matrix.md) 与 [CLI 参考](../guides/cli.md) 为准。
> **读它的人**：想给自己的项目上一套"结构可控、变更可核"纪律的维护者；评估 ngm 是否值得引入的决策者。

---

## 0. 为什么值得记下来

枢衡不是 ngm 的演示项目：它的依赖只有 9 个 Git 模块，ngm 在其中占的篇幅不到 1%。
但它在另一件事上走得比多数项目远——**把"约定"逐条变成"可执行的判据"**，
并且在过程中被自己的判据抓到过多次（命名事故、文档失真、生成物腐坏、目录残留导致门禁崩溃）。

把这套做法写下来的价值不在工具，而在**顺序**：先立哪个、后立哪个、哪些看似必要其实可以不做。
下面的每条都带"枢衡里的证据"和"迁移到你的项目时的最小落点"。

---

## 1. 约束条件（方法论成立的前提）

| 约束 | 枢衡的实际情况 | 对方法的影响 |
|---|---|---|
| 无第三方依赖 | 后端只用 Node 内置模块 + `node:sqlite`，前端原生 ESM，无打包器 | 不能用生态里的 lint/test/build 全家桶，判据只能自己写——于是每条判据都要求"短、可跑、能说清为什么" |
| 单进程 + 单库起步 | SQLite (WAL) → 预留 Postgres 驱动 | 结构变更可以在启动时强制、失败即拒绝启动 |
| 数据敏感 | 工资、身份证、账号 | 真实库永不入库；测试只用 `.tmp-*` 隔离库；备份先于重建 |
| 结构持续演变 | 9 域从 `src/` 物理搬迁到 `core/` + `modules/`，基线重置到 v100 | 迁移必须可回滚、可重放、历史可归档 |
| 迭代节奏快、单人主笔 | 一天内多轮结构性提交很常见 | **判据必须机器可跑**，否则"人记着"的那条一定先失效 |

> 适用边界：如果你的项目是脚本集合、无持久数据、或改动频率极低，
> 第 3/4/7 条的成本会大于收益。第 1/2 条则几乎总是划算的。

## 2. 八条可迁移做法

### 2.1 契约先于代码：把"不许跨边界"写成机器可读的文件

**做法**：把跨模块的约束从文档搬进 `contracts/`，一份文件管一件事：

| 文件 | 管什么 | 违反时的处置 |
|---|---|---|
| `tables.json` | 表级写所有权（哪个模块可写哪张表） | `check-ownership` 阻断 |
| `teams.json` | 域边界与 `shared_points` 登记 | `check-teams` 阻断 |
| `relations.json` | FK / 逻辑关联 / 多库策略分层 | `check-orphans` + DDL 校验 |
| `payroll-fields.json` | 工资字段单一来源（前端列由它生成） | `check-payroll-fields` 阻断 |
| `query-budgets.json` | 接口查询次数预算 | `check-query-budget` 阻断 |
| `branding-policy.json` | 品牌名/文案闸门 | `check-branding` 阻断 |
| `compat-plan.json` | 旧路径兼容层删除批次与到期 | `check-compat` 阻断 |

**证据**：7 份契约 + 9 份契约文件（含读写白名单）对应 24 个 `check-*` 脚本；
`npm run verify` 一次跑完全部。**没有一条约束只写在 markdown 里。**

**迁移落点**：先挑**最容易犯、后果最贵**的那一条（多数项目是"谁能写这张表"），写成一个 30 行的检查脚本挂进 CI。
不要一次写七份——契约的价值在"被阻断过一次"，不在数量。

**反例**：把约定写进 `CONTRIBUTING.md` 然后指望评审记得。枢衡曾有一条"命名必须经所有者批准"的口头约定，
在没有判据的两天里被执行成了一次未授权的全仓改名，事后需要一份事故记录来回退。

---

### 2.2 结构只有一个来源：spec → 生成物 → 校验生成物

**做法**：`core/db/schema-spec.json` 是唯一结构来源；`ddl.js` 由它生成 SQLite 与 Postgres 两套 DDL；
生成结果落成 `schema.generated.js` / `schema.generated.postgres.js` 并**入库**；
`scripts/check-schema-generated.js` 每次 CI 比对"spec 生成的"与"仓库里存的"是否一致（30 表 / 43 索引）。

**为什么生成物要入库**：部署机不需要跑生成器；而"入库 + 校验"同时得到两个好处——
读者能直接看到真实 DDL，篡改或忘记重跑会被判据抓住。

**迁移落点**：任何"手工维护的枚举/常量表"都可以这么处理：一个 JSON 源、一个生成器、一个比对判据。

---

### 2.3 生成物不入库，除非它本身是校验基准

这是 2.2 的反面，也是最容易搞错的一条。枢衡里同时存在两类 `*.generated.*`：

| 生成物 | 是否入库 | 理由 |
|---|---|---|
| `core/db/schema.generated.js` | **入库** | 它是 `check-schema-generated` 的比对基准，不入库就没得比 |
| `public/js/payroll-columns.generated.js` | **入库** | 被 `check-payroll-fields` 逐字读取；同时是前端运行时依赖 |
| `test/smoke.js` | **不入库**（2026-11 移出） | 由 `scripts/build-smoke.js` 从 39 个域片段拼接，`npm test` / `verify` 前必然重建；入库只会产生无意义的 diff |

**判据**：问一句"删掉它，CI 还能不能从源重建并得出结论？"
能 → 不入库并加进 `.gitignore`；不能 → 入库并由判据守住。

**迁移落点**：把所有 `*.generated.*` / `*_pb2.py` / `dist/` 列成表，逐个回答上面那句，而不是统一 `ignore` 或统一提交。

---

### 2.4 门禁分层：单项 → 总闸门 → CI 多 job

**做法**：

```
scripts/check-*.js        单项，每个只回答一个问题（可单独跑，输出一行读数）
        ↓
npm run verify            总闸门：语法 + 导入解析 + 全部单项 + 全量冒烟
        ↓
CI（.github/workflows/ci.yml）
  job test          : npm test（装依赖无关：零依赖，但有 vendor 自检）
  job vendor-check  : scripts/check-ngm.mjs（vendor ↔ ngm.json ↔ ngm.lock 三角）
  job ngm-preflight : 没有二进制就明说跳过，不假装通过
  job ngm-verify    : 仅当仓库变量配好时才跑 ngm verify --deep
```

**关键点不是"有 CI"，是每个 job 都能**单独**回答一个问题**，且"跑不了"与"通过"在输出里长得不一样
（`ngm-preflight` 用 `::notice::` 明说跳过，而不是静默成功）。

**迁移落点**：单项检查必须能不依赖 CI 在本地跑一条命令复现；总闸门只做聚合，不塞新逻辑。

---

### 2.5 破坏性结构变更：物理拆分 + 只读兼容视图 + 单一写入口

**做法**：把 `employees` 一张宽表物理拆成 `people_employees`（人员）与 `identity_accounts`（账号身份），
原 `employees` 保留为 **LEFT JOIN 只读视图**，供旧查询与历史快照解析；写入只经 people / identity 仓储，
跨两者的组合写必须走 `unit-of-work` 的同一事务。

**三条配套判据**：`check-employees-writes`（禁止直写）、`check-employees-reads`（读路径白名单）、`check-uow`（事务边界）。

**迁移落点**：任何"表拆分/改名"都应保留一个只读兼容层，并把写入收口到一处；
否则旧代码会以"读不到数据"或"写了一半"的方式静默失败。

---

### 2.6 基线重置 + 历史归档，而不是无限叠加迁移

**做法**：迁移版本 1–23 的逐版 STEP 归档到 `legacy/`（不参与运行），
结构基线重置为 v100：`user_version < 100` 的库**启动即拒绝**，要求执行 `--rebuild-db`（备份 → 按基线重建 → 逐表复制旧数据）。
`check-baseline-equivalence` 判据要求"升级库"与"新建库"逐表逐列逐索引逐 FK 一致。

**迁移落点**：当迁移数超过约 20 个、且早期版本已无人能验证时，重置一次基线比继续叠加便宜；
重置的前提是**有一条等价性判据**，否则"重置"只是把风险藏起来。

---

### 2.7 文档分层与去重：入口 / 权威 / 过程

**做法**（2026-11 定型）：

| 层 | 位置 | 规则 |
|---|---|---|
| 入口 | `README.md` | 只放定位、快速启动、目录用途、文档索引；约 200 行封顶 |
| 权威 | `docs/*.md`（10 份） | 每份一个主题，细节只在这里维护 |
| 过程 | `analysis/`、`.trae/` | 逐轮评估报告与设计草案，**本地留存、不入库** |

配套动作：README 里与 `docs/` 重复的章节被删掉并改为链接；
指向过程文档的引用被清理（否则新克隆者看到死链）；
`.gitignore` 里显式写入这两个目录。

**判据**（可自检）：README 里出现的每条命令，是否能在仓库根目录直接执行？每条路径是否真实存在？
—— 枢衡在这上面栽过：README 曾写着 `src/ 已清空`，而该目录已被删除，连带 `verify.js`
因为无条件的 `readdirSync('src')` 直接崩溃。**文档失真会以"门禁崩溃"的形式收账。**

**迁移落点**：先做"入口/权威"两分，过程文档一律不入库；再定期跑一次"文档里的路径/命令是否还有效"。

---

### 2.8 变更治理：命名、删除、出库都要有授权与记录

**做法**：

- **命名**：品牌名与模块 id 的变更必须由所有者拍板；`branding-policy.json` 是闸门。
  一次未经授权的全仓改名被完整回退，并留下事故记录（哪些文件、为什么、如何防止）。
- **出库**：把生成物/过程文档移出版本库时，**同时**修三处——`.gitignore`、引用它们的文档、以及因此暴露的脚本假设。
  枢衡出库 `test/smoke.js` 后仍跑 `npm test` 验证；出库 `.trae`/`analysis` 后修掉 3 处文档引用。
- **清理**：删本地残留前先确认它是否被别的脚本当作输入（空目录 `src/` 被删后，
  两个脚本的 `readdirSync` 才暴露出来）。

**迁移落点**：为每一次"结构性删除"写一行记录（删了什么、为什么、谁批准、哪条判据因此需要改）。

## 3. ngm 在这套方法论里的位置

枢衡的方法论解决"**代码与结构**的可核对"，ngm 解决"**依赖字节**的可核对"——
两者是同一件事在不同层的实例化：

| 方法论条目 | 枢衡的做法 | ngm 的对应能力 |
|---|---|---|
| 2.1 契约先行 | `contracts/*.json` + `check-*` | `ngm.json` 声明 `(name, ref, refType)`，非法即 exit 3 |
| 2.2 单一来源 | `schema-spec.json` 唯一源 | `ngm.lock` 是唯一事实源，必须提交 |
| 2.2 生成物可校验 | `check-schema-generated` 比对 | `ngm verify` 重放 digest；`--content` 逐字节比对 |
| 2.4 门禁分层 | 单项 → verify → CI job | `verify --json` / `--format=github|sarif` 供 CI 消费 |
| 2.6 可回滚 | 备份 → 重建 → 等价性判据 | `install --frozen-lockfile --offline` 只重放已钉住的内容 |
| 2.8 留痕 | 事故记录 + 兼容计划到期 | `ngm sbom` / `ngm attest` 从 lock 导出可审计产物 |
| 2.3 出库判据 | 生成物是基准才入库 | `vendor.mode=local` 时 `ngm.vendor/` 随仓库分发，由 Git 侧决定是否提交 |

### 枢衡实际怎么用 ngm（可复现的细节）

| 项 | 取值 | 说明 |
|---|---|---|
| 依赖 | 9 个模块，全部按 tag 锁定（`gitee:idcu/ngm-repo`） | `packages/core/{rbac,sqlite,util,validate}` + `packages/format/{dsv,xlsx-read,xlsx-write,xml-lite,zip}` |
| vendor | `mode: local`、`linkMode: copy` | 需要在部署机上直接分发，硬链接跨卷不可用 |
| CLI 版本 | `.ngm-version` = `0.102.0-dev.1` | CI 校验二进制版本；没有匹配产物时按源码构建 |
| 自检 | `scripts/check-ngm.mjs` | 校验 vendor 目录 ↔ `ngm.json` ↔ `ngm.lock` 三角一致 |
| 二次分发 | `scripts/vendor-public.js` 生成 `public/vendor/` | 浏览器 ESM 需要另一份可加载的副本，**这份不入库** |
| CI | `vendor-check` job | 只跑三角自检；`ngm-verify` 在未配置二进制时明说跳过 |

一个值得注意的取舍：枢衡**提交了** `ngm.vendor/`（部署机不装 npm、不联网），
但**没有提交** `public/vendor/`（可由 `vendor-public.js` 重建）。
——同一份依赖的两个形态，按 2.3 的判据分别处理，而不是统一策略。

## 4. 反向优化：枢衡的实践对 ngm 提出的要求

以下每条都先写"现有能力到哪一步"，再写缺口。**没有一条要求 ngm 接管 Git 或 npm。**

### P1 — 下游 pin 住的那个版本，必须存在可下载产物

**现状**：下游仓库 `ngm-repo` 的 `.ngm-version` 固定在 `0.102.0-dev.1`；
README「已知问题」已承认该版本没有可下载产物，下游 CI 只能源码构建。
**代价**：每个下游都要复制一段"如何构建正确的 ngm"的知识，而这段知识没有判据守着。
**建议**：把"下游 README 宣称的 pin 版本 ⇔ 存在对应 release/tag"做成发布前的机械对账
（与 `scripts/check-release-status.sh` 同族，但方向相反：不是"每个版本都有复盘"，而是"每个被下游引用的版本都有产物"）。
落点：`docs/development/README.md` 的发布清单 + 一条读数脚本。

### P2 — "vendor 是否被 Git 忽略"应该是可见读数，而不是失败判定

**现状**：ngm 的立场明确——`ngm.vendor/` 是否提交由 Git 侧决定，ngm 不执行 `git add`（见
[configuration](../guides/configuration.md) 与 ADR 相关裁决）。这个边界是对的。
**缺口**：当项目**打算**随仓库分发 vendor（枢衡就是），却因为 `.gitignore` 或
`git add` 遗漏而没提交时，冷克隆的 CI 会在 `install --frozen-lockfile --offline` 处以 exit 4 失败，
错误信息指向"缺内容"，指向不了"你的 Git 忽略了整棵 vendor 树"。这是**配置意图与 Git 状态的错配**，
不是网络问题。
**建议**：在 `ngm doctor` 中增加一条**只读**读数（不改变任何退出码语义）：
`vendor: present / ignored-by-git / absent`，并在 ignored 时提示"若打算随仓库分发，请检查 .gitignore 与 git add"。
落点：`internal/doctor` + `observability.md` 的 doctor 小节。仍然不执行任何 Git 写操作。

### P2 — `ngm.mappings.json` 是否必须提交，应在一处写死

**现状**：文档说它"由 install 生成"，`ngm mappings validate` 能校验它与 lock/vendor 一致；
但是否入库没有明确结论。枢衡选择了入库，并额外写了 `check-ngm.mjs` 做三角对账。
**缺口**：下游要自己决定，且不同决定会让 `install` 后的工作树呈现不同的 diff 噪音。
**建议**：在 `guides/configuration.md` 的配置文件表里给这一行加"是否必须提交 + 理由"
（按 lock 同级的确定性要求，倾向"必须提交"），并在 `mappings validate` 的失败提示中复述。

### P3 — 二次分发（vendor → 浏览器/构建产物）的证明边界值得一节

**现状**：ngm 的证明链止于 `ngm.vendor/`。枢衡在此之上还有一步：
`vendor-public.js` 把模块再导出到 `public/vendor/` 供浏览器加载，这一步**不在任何 digest 覆盖内**
（文件是复制 + 改名，但复制过程本身没有判据）。
**缺口**：文档没有说明"当依赖被再次分发/转换后，哪些保证仍然成立"。
**建议**：在 `architecture/vendor-layers.md` 增一节"层的下游"：
明确列出仍成立（`verify` 对 vendor 的结论）、已失效（对二次产物的字节保证）、以及补偿手段
（把二次产物也做一次内容摘要，或在 CI 里对生成脚本做确定性检查）。

### P3 — 文档里的本机路径应进检查网

**现状**：`check-docs-links.sh` 已覆盖仓库内链接的存在性与大小写（v0.93 / v0.96）。
**缺口**：绝对路径（如 `d:\repos\mine\...`）不违反链接判据，但它对任何其它机器都不可复现。
本仓库根 README 曾在「已知问题」处出现一条这类路径（本次已修）。
**建议**：给文档检查加一条低成本规则：`.md` 中出现盘符路径或 `/home/<user>/` 即告警
（不阻断，因为引用外部环境有时是必要的——但要让它可见）。

## 5. 给其它项目的接入顺序

按这个顺序做，前一步没成立就不要做后一步：

1. **先有一条判据**（任何一个 `check-*`），挂进 CI，并确认你亲手看到它红过一次。
2. **把最贵的约定变成契约文件**（表所有权 / 字段单一源 / 品牌闸门，任选其一）。
3. **确定生成物策略**：列出所有生成物，逐个回答 2.3 的判据。
4. **引入 ngm 的证明层**：`ngm init` → `ngm add`（tag 优先）→ `install` → 提交 lock；
   部署形态决定 `linkMode`（跨卷或需分发用 `copy`）。
5. **CI 两段式**：`install --frozen-lockfile --offline` + `verify --json`；跑不了就明说跳过。
6. **文档分层**：先做"入口/权威"两分，过程文档不入库。
7. **每次结构性删除都写一行记录**，并回头检查哪条判据的假设被打破了。

## 6. 这套方法论的失效边界

- **判据不是免费的**：枢衡的 24 个 `check-*` 脚本本身就是需要维护的代码；一条没人跑、或跑起来恒绿的判据，
  比没有更坏（它制造"查过了"的错觉）。ngm 自己的复盘反复踩过这个坑，结论相同：**判据存在不等于会红**。
- **契约文件会腐坏**：写进 JSON 的约束如果不再对应代码，就变成第二份真相。
  枢衡用 `compat-plan.json` 的到期日（`due_date`）来强制回收，其它项目至少要有一条"过期即红"的机制。
- **小项目不该背这套**：三个脚本、无持久数据、单人维护的项目，只需要第 1 条（一条判据）与第 6 条（两份文档）。
- **拿不出读数就别声称**：任何"我们保证了 X"的说法，必须能指向一条会变红的判据；
  否则它只是一句愿望——这是枢衡这次复盘里最贵的一课，也是 ngm 逐版复盘里反复出现的那句
  「结论写得比实现强时，没有任何判据会变红」。
