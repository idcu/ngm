## 0. 结论：下一阶段是“证据与读数”，不是“功能补齐”

两份评估已经把问题分清楚了：

- **指令面无缺口**：28 个命令、14 个 `--json` 命令、删除线/退出码/机器接口已由判据守住；
  逐行审计 35 项、竞品 followup 10 项均已落地。
- **真实落后只剩外部性**：签名溯源链（不自签，配方已有但未集成到消费方）、
  发布覆盖与采用度、外部安全审计；其余是 ADR-044 的明确边界或正交轴。
- **最大的可立即消除风险不是代码，而是读数说谎**：`COMPETITIVE-ANALYSIS.md` 的“诚实结论”
  仍写“refType 必填 / 内容摘要 / ref 漂移三态三项在主流工具里仍无对应物”，
  与同日差距评估 §5.2 的纠偏结论冲突；SLSA 段也缺 provenance 实测覆盖率的补充证据。

因此下一步按 **P0 读数纠偏 → P1 闭环证据 → P2 采用门槛 → P3 观察项** 推进。
**本轮不改产品代码、不新增命令、不翻转 ADR-014/018/044。**

## 1. 准入规则（ADR-044）

一件事情只有满足下面任一条才进任务表：

1. 它让“内容身份可被独立复核”这一主轴更容易被第三方验证；
2. 它消除一条已经存在的、会误导读者/脚本的读数；
3. 它有独立的工程或安全理由，而不是“npm/pnpm 有所以 ngm 也要有”。

不满足的一律进 §4“明确不做/观察”，不进任务表。

## 2. 批次与顺序

### P0 · 读数纠偏（低风险，无产品代码）

目标：让对外文档与同日差距评估说同一句话。

1. **N1 三项“无对应物”措辞纠偏**：把“三项仍无对应物”改为“唯一把这些控制点收束为
   默认、可离线重放的同一状态机”，并加 2026-11 时间限定；保留 refType 与三态的有限成立判断，
   明确“内容摘要”单项不再独有。
2. **N2 SLSA 段补证据**：补 provenance 实际覆盖率读数（top50 约 12% / 另一口径 38.8%），
   保留“告警而非拒绝”的结论；不改动“ngm 在 SLSA 轴上是 L2 的一半”的判断。

### P1 · 闭环可复核证据（低风险，文档 + 判据）

目标：把 ngm 真正独有的东西做成可复现演示，而不是停留在自述。

3. **N3 真实消费方端到端案例**：产出一份从 `init` → `add` →
   `install --frozen-lockfile --offline` → `verify --content` → `sbom` / `attest` →
   现场 cosign 签名验证的完整案例，并列明每一步证明什么、不证明什么。
   案例必须包含一个**注入演示**：改动 `ngm.vendor/` 的字节后 `verify --content` 退 2，
   证明“篡改会被抓到”而不是只展示通过路径。边界：延续 C1 决定，**不提供 ngm 自签命令、
   不固化第二份 cosign smoke 脚本**，签名步骤只引用 [signing.md](../../guides/signing.md)。

### P2 · 采用门槛（非代码，需人或外部条件）

目标：降低“能被找到、能被补发”的门槛，但不把阻塞项伪装成可自动完成的任务。

4. **N4 仓库元数据**：填写 GitHub 仓库 description 与 topics（网页操作，需要仓库所有者）。
   验收以网页可见为准，agent 不代做。
5. **N5 发布回填**：**保持暂缓**。当前可做的只有 Gitee 侧 3+1 个发行版（需 `GITEE_TOKEN`）；
   38 个缺口是 release-pipeline.md 明确**不回填**的区间，GitHub 维持 63。
   恢复信号见 [project-state.md §3.2](../../internals/project-state.md#32-阻塞需要人)。本轮不排期、不执行。

### P3 · 观察项（不承诺）

6. **N6 OSV commit + 版本双查**：当前不在轴上；触发条件是 OSV 对 Git commit 的覆盖显著改善，
   或出现真实漏报案例。
7. **N7 Git 非默认端口支持**：需要给 `Canonical` 加字段，是 schema 级变更；
   触发条件是真实项目提出需求，而不是“别的工具支持”。
8. **N8 全局可达性 GC**：ADR-018 明确拒绝自动全局删除；触发条件是出现项目注册表之类的
   新增事实源，而不是磁盘占用数字变大。
9. **N9 季度端到端复核**：project-state.md #7 的季度重跑；如果用户希望自动化，
   再单独创建定时自动化，本 spec 不擅自建。

## 3. 契约决定（本轮先拍板，未授权不改）

- **D1**：本轮不写产品代码。N1–N3 只改文档与新增判据；N4/N5 是人工/外部条件项。
- **D2**：发布保持暂缓，不把“38 个缺口”复活为待办；只承认 Gitee 3+1 的 token 阻塞。
- **D3**：纠偏采用“加时间限定与当前状态”的方式，不重写历史快照（延续 11-21 两轮评估的做法）。

## 4. 明确不做（不是差距）

registry 包管理、semver/peer deps、workspace 共享 lock、接管 `node_modules`、
自研 bundler/transformer/HMR/test runner/LSP/dev server、自造签名体系、自动全局 GC、
“更像 npm”的生命周期脚本兼容。理由见 [ADR-044](../../adr/adr-044-independent-ecosystem.md)
与[能力矩阵 §47](../../internals/capability-matrix.md#明确不做的能力)。

## 5. 完成定义

每项必须同时满足：文件已改/案例已产出 + 会红的判据 + 变异检验结果；只写“文档更新”不算完成。
批次顺序：P0 → P1 → P2（人工项只记录状态）→ P3（只记录触发条件，不执行）。
全部完成后同步 docs/README 的入口与本 spec 的实施补记，跑 docs-links / discipline / diff-check，
再提交推送。
