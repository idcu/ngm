基线：`b6cfad8`（审计报告已合入并推送；工作树干净，CI 24/24）。
本 spec 定义**计划与任务**，逐项清单见 [tasks.md](./tasks.md)。

## 0. 结论：按 A → B → C → D → E 五批推进，前一批合入才开下一批

审计报告确认 35 条发现（P1 9 / P2 24 / P3 2），无 P0。排序原则不是"严重级别从高到低"，
而是**先让绿灯重新可信，再改产品代码**——审计中 12 条发现本身就是判据空转，
在这些网修好之前改代码，回归可能悄悄溜过。

1. **A 判据复健（12 项，无产品代码变更）**：修 T-01~T-08、C-04、I-01~I-03 的恒真/恒假断言、
   过宽映射、永不匹配的 glob 与注释蒙混。只**强化现有判据**，不新建网、不删网。
2. **B 错误通道与 JSON 契约（5 项）**：A-01/A-02/A-05/A-06/A-03——`--json` 错误信封的 writer 绑定、
   早期失败绕过信封、`config validate` 假通过。必须先定 §3.1/§3.2。
3. **C 安全边界与校验一致性（8 项）**：A-04/C-01/C-02/C-03/P-01/V-01/V-02/C-05——
   vendor 逃逸校验跳过、批量模块路径漏路径校验、`LSRemote` 无 URL 形状校验、含逗号权限放大、
   git 输出无界。必须先定 §3.3/§3.4。
4. **D 退出码与语义分类（5 项）**：K-01/K-02/K-03/P-02/P-03——SARIF 级别与退出码不一致、
   伪造清单被归 operational、JSON 解析失败吞成空值、tree/why 自环分歧、配置浅拷贝。必须先定 §3.5。
5. **E 确定性与信任根（5 项）**：K-04/K-05/V-03/I-04/I-05——digest 排序键、lock 尾部垃圾、
   首次 clone 非原子落地、adopt 的 `git:` 前缀残留、版本号整数溢出。必须先定 §3.6。

**风险最低的 A 批先做**不是因为它最不重要，而是因为它是后面四批的回归安全网。

## 1. 不变量（任何批次都不得破坏）

- **定位不变量（ADR-044）**：不新增 registry 能力、不解析 semver/peer deps、不接管 `node_modules`、
  不做 publish。35 条发现全部在既有边界内，不需要也不允许借机扩边界。
- **签名不变量（ADR-014/027）**：本轮不碰签名格式、密钥、信任根；K-01 只改 SARIF/注释级别映射，
  不改 `attest` 语句或 cosign 配方。
- **JSON 契约（ADR-045）**：`--json` 的 stdout 恰好一份 JSON；"接受 `--json` 的命令早期失败给信封"
  与"不接受 `--json` 的命令 stdout 为空（v0.16 规则④）"两条同时成立。B 批不得用"多写一份报告"
  来绕过单文档约束。
- **退出码语义（ADR-039）**：完整性失败(2) 不被资源缺失(4)/工具缺失(5) 覆盖；
  `run` 透传族不变。D 批改分类时必须让报告级别与进程码同源。
- **确定性**：lock / SBOM / attest / 模块清单"同输入同字节"；E 批改排序键与 lock 解析时，
  `TestV69` / `TestV70` / lock 字节复现判据保持绿。
- **权限闸门独立（ADR-012）**：`run:git` / `net:<host>` / `run:<engine>` / `run:script` 各自独立；
  判定主机必须等于实际访问主机。C 批修逗号放大时不得放宽其他维度。
- **判据纪律（ADR-049）**：新增源码扫描/AST 判据必须指向审计报告里**已发生**的缺陷条目；
  不为假想问题造网；**不删存量网**（除非满足 ADR-049 的 3 版本自红门槛，本轮不触发）。
- **默认决定不重开**：ADR-050（默认 P1D）、ADR-051（action verify 默认 content）不在本轮范围内；
  审计没有产生推翻它们的证据。
- **文档同源**：README 现为 599 行（discipline 第 11 问硬上限 600）——任何 README 追加前先看 `wc -l`；
  ADR 数当前 51，若新增 ADR 必须同步 `docs/adr/README.md` 索引、README 的"N 个决策记录"、
  `docs/README.md` 的 "ADR-001 ~ ADR-NNN"（V71/V142 守）。**优先用既有 ADR 补记，避免新增 ADR**。

## 3. 必须先拍板的契约决定

### 3.1 `--json` 中途失败的 stdout 内容（B 批 A-01）
现状：`install --json` 失败时错误信封因 writer 绑定错误进了 stderr，stdout 仍由 `emitWriteReport`
写一份成功形状的 `writeReport`（`install.go:801-815`）。选项：
- (a) **保留报告，同时把错误信封写回真正的 stdout** → stdout 两份 JSON，违反单文档契约；
- (b) **失败时只写错误信封，不写 `writeReport`** → 单一机器可读结论，但与当前"报告是附加通道、
  不参与判定"的注释（`install.go:798-800`）表述冲突，需要把注释和 ADR-045 一起补记；
- (c) 保持现状，只修文档 → 不修复契约违背，不可接受。

建议 **(b)**：报告只在成功路径写；失败路径 stdout 恰好一份错误信封，stderr 保留人读文本。
先确认 `TestV51` / `TestV136` 是否有用例依赖"失败时也写报告"，有则按新契约改写并记理由。

### 3.2 "JSON-aware = 所有早期失败都给信封"是否写成统一规则（B 批 A-02/A-05）
现状：`c.rejectExtraArgs`（`cmd_context.go:122-128`）已是统一出口，但 `modules` 7 处、
`integrations` 1 处仍手写 usage + `return 3`。选项：
- (a) 逐处改成 `rejectExtraArgs`，不写总规则；
- (b) 把"接受 `--json` 的命令，任何参数级失败都给信封"写成 ADR-045 补记 + 一条覆盖所有 JSON-aware
  命令的判据（按命令表枚举，而非源码扫描）。

建议 **(b)**：(a) 会重演 P1-4 只迁移 5 个命令、遗漏其余的失效模式；
(b) 的判据是行为级枚举，不属于 ADR-049 禁止的源码扫描网。

### 3.3 URL 形状校验的构造点（C 批 C-02/C-03）
`ValidateRemoteURL` 只在 `clone.go:34,99` 调用；`LSRemote` 的两个调用方只做 `CheckNetAccess`。
选项：
- (a) 在 `LSRemote` 入口校验（与 clone 同一构造点语义：任何交给 git 的 URL 都要过形状检查）；
- (b) 在两个调用方分别校验（易漏第三个调用方）；
- (c) 只校验非本地 mirror 路径的 URL。

建议 **(a)**。同时 C-03 的解析改为"接受 40/64-hex、畸形行 fail-closed 返回 error"；
实施前跑全量 `cmd/ngm`，确认没有 fixture 依赖"静默丢弃畸形行"的旧行为。

### 3.4 含逗号权限 target 的处理（C 批 P-01）
`ReadDirs` 已对含逗号路径 fail-closed，`NetHosts`/`EnvVars` 没有，而 `DenoArgs` 用逗号拼接。
选项：
- (a) 复用 `ReadDirs` 逻辑，对 net/env target 含逗号直接拒绝（破坏性：现有配置若依赖逗号形式会失败）；
- (b) 在 `DenoArgs` 里转义/改用重复 flag（Deno 语义需实测，且会改变 argv 形状）；
- (c) 只加 warning 不拒绝（仍可能放大权限）。

建议 **(a)**，按 ADR-012 补记 + CHANGELOG 破坏性变更说明，因为这是安全边界漏洞而非新特性。

### 3.5 完整性失败与操作性失败的边界（D 批 K-01/K-02/K-03）
选项：
- (a) `digest.ValidateRecord` 失败 → critical(2)；文件读取/JSON 语法失败 → operational(4)；
  SARIF / GitHub 注释 level 由**最终退出码**派生（含 `--strict` / `--allow-drift` 调整）；
- (b) 全部归 critical（会把"文件没下载全"说成"被篡改"，误报更糟）；
- (c) 只改 SARIF 文案，不改 level（CI 与进程码仍相反）。

建议 **(a)**。这是 ADR-039/045 的语义精确化，写补记，不新开 ADR。

### 3.6 lock 尾部内容与模块清单排序（E 批 K-04/K-05）
- **K-05**：lock 是信任根，`Parse` 只 `Decode` 第一个值。建议"再 Decode 一次要求 `io.EOF`"，
  对象内未知字段的前向兼容不变。
- **K-04**：模块清单来自可改写 store 文件，`ValidateRecord` 不查路径唯一性、`sort.Slice` 不稳定。
  建议先加唯一性校验（重复 Path 直接拒绝），再按 `(Path, Mode, BlobSHA256)` 复合键排序；
  不要只改成 `sort.SliceStable`（输入顺序仍影响字节）。

两者都会改变边界输入的行为，实施前用既有 lock / 模块 fixture 做回归语料。

## 4. ADR-049 合规说明

- A 批只**强化**已存在的判据，不新建网、不删除网；每条变异验证用审计报告的具体发现作为证据。
- B–E 批若需新判据，证据必须是审计报告里对应 ID 的已确认发现（例如 A-02 → 7 处信封遗漏），
  提交说明写清"指着的缺陷条目 + 会红的变异"。
- 不为"以后可能出问题"新增源码扫描；T-08 的 AST 解析是**替换**现有过宽子串判据，不是新增一张网。

## 5. 明确不做（定位边界，授权也不解除）

- 不做 registry / semver / peer deps / `node_modules` / publish，不碰 ADR-044 边界。
- 不自造签名格式、不管理密钥，不碰 ADR-014/027。
- 不重开 ADR-050 / ADR-051 的默认决定。
- 不拆 `cmd/ngm` 包（ADR-047 触发条件未达成）、不做 usage 单源重构（ADR-048 同）。
- 不按"数量多"删除存量契约网（ADR-049）。
- 不追 P3 之外的新功能；审计报告不存在 P0，不要把 P1 包装成 P0 做破坏性重构。
- 不做发布资产回填（凭据阻塞：`GITHUB_TOKEN` / `GITEE_TOKEN`）。

## 6. 校验闸门（每批都必须过）

- `go build ./...`、`go vet ./...`、`gofmt`、`git diff --check`。
- **定向 + 全量**：`go test ./...` 全量跑，不能只跑改到的包；上一轮 P1 经验是"定向绿、全量现形"。
  Windows 本机 ExecutionPolicy 环境组用**进程级** `$env:PSExecutionPolicyPreference='Bypass'`
  隔离，不改注册表；已知环境组失败（V79/V86/V87/V88/V90/V91/V95/V102*）单独说明，
  不把环境失败当回归。
- `bash scripts/check-docs-links.sh docs README.md`、`node scripts/check-discipline.mjs --strict`（13/13 L4）。
- 每个新判据必须给出**变异结果**：撤掉修复即红、装上即绿；不能只给"测试通过"。
- CI 24/24 合入前确认；README 追加前 `wc -l` 确认仍在 600 行内。
